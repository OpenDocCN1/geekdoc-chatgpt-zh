[PRE2]

先看 LangChain 框架里的 Agent 设计，内部被拆成三大核心：Agent、Message、Toolkits。一个 Agent 通常由大语言模型+提示词+输出解析器构成，形成 Chain 来处理用户输入。Agent 能接收的输入来自三方面：Input 是用户的原始提问，Model Response 是模型对子任务的中间输出，Context 则携带上下文信息。Agent 的输出会连接到真实的工具库，具体调用哪些工具，由 Agent 拆分后的子任务决定。大模型调用外部函数分为两步：识别工具和真正执行。Messages→AI Agent→Toolkits 这条路径负责把复杂任务拆解，在工具库里匹配对应工具并提取名称与参数，可视为一种“静态”执行流程。而把决策落地为行动的重任则交给 AgentExecutor。

总结来看，在 LangChain 的 AI Agent 架构里，Agent 只负责接收输入并判断该做什么，自己并不执行，执行动作由 AgentExecutor 完成。只有把作为决策中心的 Agent 与负责运行的 AgentExecutor 结合，才能构成完整智能体。AgentExecutor 调用 Agent 并执行其指定的工具，从而实现整体功能。

LangChain 仍是构建大模型应用的前沿框架之一。最新 v0.3 基本完成了从传统类到 LCEL 的过渡，让定义和执行分步操作序列变得更简洁高效。专业上说，LangChain 本质是在构建有向无环图 DAG。随着 AI 应用尤其是 AI Agent 的演进，大模型的使用正从单纯的工具执行转向更复杂的推理引擎，这正是 LangGraph 诞生的根本原因。这一转变对循环结构和复杂条件交互提出了更多需求，而基于 LCEL 的线性序列在构建更高级、更智能系统时逐渐暴露局限。

#### 8.1.10 LangGraph 构建 AI Agent 的底层逻辑

##### 1. LangGraph

从名称看 LangGraph 与 LangChain 关系紧密。实际上它是以 LangChain 表达式语言为基础构建的框架，用来开发 AI Agent。因此在模型能力接入和 Agent 构建上的优势，能自然继承自 LangChain。从技术发展看，大模型本身无法采取行动，只能输出文本，即接收输入并给出响应。

##### 2. 图结构：节点与边的组合

在图式框架里，任何可执行逻辑都能作为对话、Agent 或程序的起点。该起点可以是模型 API、基于模型构建的 AI Agent，或通过 LangChain 等实现的线性序列，如图 8.13 中“Start”圆圈所示。无论形式如何，它首先处理用户输入并决定下一步操作。图 8.13 展示了一个基于 LangGraph 概念的基础 Agent 模型。

LangGraph 中，凡是包含可执行逻辑的组件都被视作节点 Node，包括模型调用、搜索操作及条件判断。流程入口的“Start”节点接收用户输入，并根据需求进行：

- （1）调用 Action 节点进行外部信息查询，例如 Web 搜索、数据库查询或 RAG 检索。
- （2）把获取的信息传给语言模型节点，用于生成自然语言响应。
- （3）最终把响应传递到 End 节点，完成链路。

如图 8.13 所示，每个圆圈是一个节点，每条连线是一条边 Edge，用来控制流程方向；状态通过消息沿边更新。

因此，无论 Agent 设计多复杂，最终都是节点和边以特定方式组合成的图结构。工作流核心在于：节点完成任务后，会经由边通知下一个节点继续。简言之，LangGraph 底层的消息传递算法定义了通用程序模式：节点完成操作后沿一条或多条边向其他节点发送消息，接收方执行功能并把结果传给下一节点，如此循环往复。

##### 3. 条件边与 Router 路由决策

在更贴近实际的场景里，Agent 不会沿固定路径执行，需要判断是否调用工具、调用哪个工具、是否直接给出答案等。看一个更复杂的例子。

我们把 AI Agent 定义为应用起点。构建 AI Agent 通常需要配置一个或多个工具，否则功能有限，因为即使问题很复杂，仅靠提示词引导大模型如 OpenAI 的 o1 推理模型也能自行完成推理。当 Agent 配备工具后，它通过函数调用机制使用工具，而非直接执行。当用户原始问题被处理时，一般出现两种情况。

- （1）不需要调用工具时，Agent 直接给出自然语言响应。例如：

用户：你好，请你介绍一下你自己。

AI Agent：你好，我是一个人工智能助手，可以帮助你解决问题。

- （2）需要调用工具时，输出为特定格式的 JSON，用于指示要调用的函数及其参数。例如：

如图 8.14 所示，经过第一个节点 Agent 后，若认为需要调用函数，会选哪个工具、传哪些参数？在多工具可选时，Action 节点呈现多条路径。如何选择？LangGraph 引入了条件边组件。条件边根据是否满足特定条件决定走向，例如 Agent 可能要决定使用搜索工具还是直接生成最终答案。为管理这些决策，使用了类似 if-else 的结构，称为 Router。基于 Router 的判断，Agent 可能导向网络搜索节点执行搜索并返回原始文本，或直接前往 End 节点获取格式化后的自然语言响应。若选择搜索路径，获取的文本还需经另一个大语言模型处理以生成用户可读的回答；若直接回答，则可用专门工具格式化输出。

在 LangGraph 中，Router 以 if-else 形式决定路径，主要通过三种方式实现。

- 提示工程：指示大模型以特定格式回应。
- 输出解析器：用后处理从模型响应中提取结构化数据。
- 工具调用：利用大模型的内置工具调用功能生成结构化输出。

##### 4. 共享状态 State 机制

我们已知道 LangGraph 通过组合节点和边创建复杂的循环工作流，通过消息传递串联节点形成通路。维持消息及时更新并准确投递则依赖 State 概念。在 LangGraph 流程中，每次执行都会启动一个状态，节点在处理时会传递和修改该状态。这个状态不是静态数据，而是由各节点输出动态更新，进而影响循环内的后续操作，如图 8.15 所示。

共享状态指图执行过程中节点之间传递的数据或信息。LangGraph 允许节点在执行时通过共享和更新公共状态进行交互。这种机制使节点能基于共同维护的数据通信、交换信息并相互影响行为。借助共享状态，LangGraph 能实现节点操作的协调与同步，支持动态交互和复杂工作流构建，使节点可依据已有共享信息协同工作并做出决策。

##### 5. 官方定义与核心优势

从官方定义看，LangGraph 是一个用于用大模型构建有状态、多参与者应用的库，可创建 Agent 和多 Agent 工作流。官方总结的优势如下。

- 循环和分支：在应用中实现循环和条件。
- 持久性：图每步执行后自动保存状态。可随时暂停和恢复执行，以支持错误恢复、人机交互工作流、时间旅行等。
- 人机交互：中断图形执行以批准或编辑 Agent 计划的下一步操作。
- 流支持：每个节点生成的输出流，包括令牌流。
- 与 LangChain 集成：与 LangChain 和 LangSmith 无缝集成。
