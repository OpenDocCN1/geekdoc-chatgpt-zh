怎么挑最合适的交互方式
把 DeepSeek R1 部署到本地后，和它打交道的途径并不唯一。不同方式各有取舍，适合的场景也不同。比如开发者更爱直接在终端敲命令，团队协作则更偏好有界面的网页方案。选对交互形式，才能在不同用途下把模型价值发挥到最大。

表 8-1 对比三种交互方式

| 交互方式 | 安装复杂度 | 使用难度 | 是否支持历史记录 | 适合场景 |
| :--- | :--- | :--- | :--- | :--- |
| 终端模式 | 低 | 高（需要命令行） | 否 | 开发者、技术人员 |
| Open WebUI | 低（图形界面） | 低 | 是 | 团队协作、长期使用 |
| Chatbox AI | 低（图形界面） | 低 | 是 | 个人快速使用 |

从表 8-1 可见，交互方式的选择要看需求侧重点。

- 追求长期使用和更丰富的功能，比如保存聊天记录、支持多人协作，Open WebUI 更合适。
- 只想快速对话、不想装 Docker，Chatbox AI 是更省心的选择。
- 习惯命令行、在轻量环境下运行，终端模式也够用了。

8.1.3 适合本地部署的用户和未来发展趋势
本地部署并非人人适用。若只是偶尔提几个问题，云端 API 更省事；若对隐私要求高、需要长时间高频使用，或想对模型做个性化定制，本地部署的优势才明显。

比较适合本地部署的对象有：
- 对数据隐私要求严格的机构和企业，例如政府部门、医疗机构、金融机构等。
- AI 使用频率很高的个人或团队，例如客服、开发者、研究人员等。
- 需要让 AI 访问私密数据源，例如企业内部文档、科研论文等。

随着计算优化技术不断进步，未来本地 AI 部署的门槛会持续降低，越来越多的人能拥有真正属于自己的 AI 助手。

8.2 调用 DeepSeek API 实现自动化工作
上一节讲了本地部署和配置 DeepSeek 模型，也提到本地模型在隐私保护和离线使用上的好处。但一个现实限制是，受电脑配置约束，绝大多数人没法跑满血的 671B 参数版 DeepSeek R1，体验会打折扣。

因此本节聊另一种不打折、更偏自动化的用法——API。API 能够让 AI 无缝嵌入工作流、应用和产品里。

如果你希望 AI 不仅是聊天窗口，而是能后台处理任务、接入业务系统，甚至成为你产品的核心能力，那学会调用 API 就是必备技能。

8.2.1 什么是 API? 它如何工作
1. API 的基本概念
API 即应用程序接口，本质上是不同软件或系统之间沟通的“桥梁”。常见例子：
- 天气 App 查看天气时，是通过 API 从气象服务商取数。
- 在网站用微信、支付宝付款，是网站通过 API 连接支付服务商。
- AI 绘画网站生成图片，是站点调用了 AI 的 API 让服务器上的模型产出结果。
API 是一套标准化的规则，让你向某个系统发送请求并拿到想要的数据或结果。

2. API 调用的基本流程
用 API 与 AI 交互，大致经历以下几步。
（1）获取 API Key：调用需要身份验证，先申请一个唯一的 API Key 作为凭证。
（2）发送请求：用代码如 Python、JavaScript，向 DeepSeek R1 服务器发起 HTTP 请求并携带 API Key。
（3）服务器处理请求：云端模型接收请求、执行计算并生成回答。
（4）返回结果：服务器把生成的文本返回，应用可直接展示或做后续处理。

8.2.2 API 使用场景：让 AI 融入你的工作流
API 最大的价值是自动化，能在后台完成任务，无需人工逐条对话。典型场景包括：
- 智能客服系统：企业用 API 让 AI 自动回复常见咨询，并生成工单。
- 自动写作与内容创作：批量生成文章、广告文案、社媒内容。
- 代码生成与编程助手：自动写代码、修复 bug、优化算法。
- 语言翻译与文本处理：快速翻译长文本、摘要、关键词提取。

8.2.4 如何优化 API 调用，降低成本
API 通常按 token 数量计费，频繁调用费用会累积。可从以下角度优化：
- 控制 token 消耗，提升调用效率。
  - 限制 max_tokens 参数，避免生成过长的输出。
  - 提问时精简表述，去掉冗余信息。
- 缓存高频问题：如果业务存在大量重复问答，如 FAQ，可缓存模型生成的结果，避免重复请求。

8.2.5 API 的未来与发展趋势
随着 AI 技术演进，API 会变得更强：
- AI API 会更便宜、更快，成本下降普及度提升；
- 越来越多企业和个人开发者把 AI API 嵌入产品，形成更智能的应用；
- 本地 AI API 部署会更普及，让企业和个人拥有自己的 AI，减少对云端的依赖。
