面对海量文档资料时，能不能让用户迅速抓住关键信息，直接决定了文档助手的实用价值。过去常用的关键词匹配很难读懂用户的真实意图，搜索回来的结果往往鱼龙混杂、信息冗余。近两年，随着预训练大模型和向量数据库的快速发展，基于语义的检索已经成为文档查找的主流方向。

LangChain 在这方面提供了相当完整的组件库，把 LLM 和向量索引串起来就能搭建高效的语义检索流程。可以按需选择嵌入模型，比如 OpenAI 的 Ada 或 Instructor Embedding，也能接入 Chroma、Pinecone 等向量库，实现从文本处理到检索的端到端搭建。

[PRE0]
实践上通常先用 TextLoader 把原始素材读入，再借助 RecursiveCharacterTextSplitter 把长文本切成长度合适的知识块。随后通过 OpenAIEmbeddings 将这些块转为向量并写入 Chroma 库中。用户发起提问时，系统会按向量相似度从库里挑出 Top-K 最相关的片段作为候选，供下一步使用。候选片段确定后，还能调用 LLM 的阅读理解能力，把多块信息整合成语义连贯、信息精炼的最终答案。

[PRE1]
VectorDBQAWithSourcesChain 就是一套封装好的检索-阅读-生成方案。它先基于向量库召回 K 个相关片段，再把问题和片段一起交给 LLM 做机器阅读理解，生成简洁自然的回答，同时附上原文出处方便核查和追溯。这种先检索后生成的组合，既发挥了语义检索的效率，也利用了大模型的推理能力，是大规模问答的常用路径。

除了被动回答提问，文档助手更应该主动推送用户可能感兴趣的内容。个性化推荐可以帮助用户发现“不知道自己不知道”的知识，拓宽视野，同时提升留存和使用时长。传统的协同过滤难以刻画文档本身的语义，而基于 LLM 的语义推荐则更擅长理解内容与兴趣的匹配关系。

用 LangChain 搭建一个基于内容的推荐流程并不复杂：先根据用户的浏览、点击、收藏等行为构建一个用户画像向量，再与候选文档的嵌入向量做相似度匹配，选出 Top-N 最贴合的文档作为推荐。

[PRE2]
具体做法是先加载候选文档集合 doc_db，并收集用户近期浏览过的文档列表 user_history_docs。用 OpenAIEmbeddings 把浏览历史综合编码成一个用户画像向量 user_embedding，最后调用 doc_db.similarity_search_by_vector 方法，找出与画像最相似的 Top-5 文档作为个性化推荐输出。

这只是一个最简化版本，工程化落地时还要兼顾文档的新鲜度、多样性、用户的显式反馈等维度，设计更复杂的排序策略，并定期刷新用户画像以捕捉兴趣变化。

更进一步，还能利用 LLM 的 few-shot 能力定制推荐风格。比如给用户 A 生成专业性强、信息新颖的推荐，给用户 B 生成通俗易懂、偏实操的推荐，只需通过 Prompt 让模型学会不同的偏好即可。一个典型的 Prompt 如下。

整体来看，智能检索与推荐大幅提升了知识获取的效率与精准度，大模型的语义理解与推理为文档助手注入了更多智能，未来将在各类知识产品中扮演核心角色。当然，算法的公平性、推荐的透明度也需要持续关注，以保证知识获取的包容与可解释。

#### 6.6.2 文档智能分类与聚类：从规则到自适应
企业和个人每天都要处理巨大规模的文档，如何从多个维度对它们进行归类，是提升检索利用效率的关键。传统分类主要分为基于规则和基于机器学习两类。前者需要专家手工提炼显式规则，成本高且泛化差；后者依赖大量标注数据，类别通常预先固定，灵活性不足。

随着预训练模型尤其是指令微调 Instruction Tuning 范式的普及，利用 LLM 做少样本学习的分类方式逐渐成为主流。核心思路是设计一个分类任务的 Prompt 模板，并在其中嵌入少量带标签的示例，让模型快速掌握任务规则，对新文本做出判断。
