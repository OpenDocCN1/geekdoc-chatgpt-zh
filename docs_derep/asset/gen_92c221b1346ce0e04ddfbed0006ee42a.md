先搭起底座。execute_sql 用来统一整个系统的查询层，负责执行 SQL、采用参数化传参、捕获异常、格式化结果，确保数据访问既安全又规范。在此之上，把高频查询需求打包成三个核心方法：query_scenic_spots 能对景区做多条件组合检索，例如按所在城市、景区等级、当月游客量筛选；query_city_info 提供城市信息的灵活查询，支持排序；cross_table_query 则封装了景区信息表与城市信息表的关联查询逻辑。这三个方法就是基于业务逻辑预先定义好的 SQL-Data-Function。

[PRE1]
这批方法在安全上做了双重加固。全部使用参数化查询来阻断 SQL 注入，同时通过枚举类型对参数取值做严格限定，比如景区等级只能选 AAAA 或 AAAAA。返回体统一用 QueryResult 对象封装，固定包含执行状态 success、数据 data 和提示 message，并伴随详细的执行日志输出。异常处理也做了统一归口，保留原始错误信息，让查询过程更透明、调试也更方便。

随后借助大模型的 Tool Calls 功能做工具路由，每个工具都对应一套预定义的 SQL-Data-Function 模板。工具调用完成后，结果会自动写入对话上下文，便于后续追问跟进。

define_tools 函数声明了三个结构化的查询工具：query_scenic_spots 用来查询景区信息，支持按所在城市、景区等级和当月游客量筛选；query_city_info 用来查询城市信息，支持按年度文旅收入或特色美食排序；cross_table_query 用来做跨表查询，能够关联景区与城市信息。

process_query 函数实现了一个双轮对话的查询流程。

第一轮：先把用户问题和数据库结构信息一起发给 GPT 模型，由它挑选合适的查询工具；然后依据模型的选择执行对应的数据库查询。

##### 第二轮：将查询结果再发回给 GPT 模型，生成自然语言形式的回答。
