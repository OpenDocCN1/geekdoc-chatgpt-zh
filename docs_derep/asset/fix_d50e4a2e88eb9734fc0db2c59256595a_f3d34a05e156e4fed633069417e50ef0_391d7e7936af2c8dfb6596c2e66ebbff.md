图0-17 展示的工作流包含输入处理、分类、检索和生成等环节。下面简要说明各模块的作用。

- START 模块接收用户的查询和上下文记忆，定义工作流的初始输入参数。
- QUESTION CLASSIFIER 模块借助 GPT-3.5-turbo 对问题进行分类，分为售后相关问题、产品定位与规划问题，以及其他问题三类。
- 对于知识库无法回答的问题，即第 3 类，在 DIRECT ANSWER 模块直接返回“Sorry, I cannot answer this question.”
- 对于可回答的问题，则进入 KNOWLEDGE RETRIEVAL 模块，根据分类结果选择对应的检索路径，从产品文档中检索相关信息，随后调用大模型 API 进行文本生成。
- LLM 模块根据检索到的文档生成回答，不同类型的问题可选用不同的大模型。

这一类低代码工具的优势在于流程可视、模块独立、功能明确，支持条件分支与分类，适合复杂的检索-生成任务。RAG 或 AI 应用发布后，大多数平台也会提供 API，方便开发者调用。

低代码工具让 RAG 系统和 AI 应用的开发更便捷，但通常不涉及嵌入、索引、检索、生成等组件的算法级优化。若要打造高质量的 RAG，仍需对每个环节进行更细化的探索。本书重点不在于工具使用，而在于如何借助代码以及 LangChain、LlamaIndex 等框架来优化 RAG 的各个环节和组件。

## 三个关键问题：RAG 系统该从哪里优化

RAG 系统该从何处优化，这更贴近实践，也更考验经验。优化的第一步是明确目标与瓶颈。由于流程较长、环节众多，需要像侦探一样定位出拖累整体性能的关键组件。

下面咖哥用两张图来说明如何逐步排查故障组件。

第一张图来自 ABACUS.AI（见图0-18）。它不仅展示了 RAG 的结构流程，也标注了各环节可能的优化点。图0-18 RAG 系统的结构流程

[PRE5]

依据图0-19，首先可从分块策略入手。分块策略决定检索的粒度与上下文的完整度，直接影响检索和生成的效果。可以尝试调整分块大小和重叠比例。例如提高重叠度能增强上下文连贯性，但会带来存储冗余；缩小分块能减少无关信息，但可能导致语义断裂。

其次是嵌入策略的优化。选对嵌入模型至关重要，目前既有大量开源模型也有商业模型，性能和语义捕捉能力差异明显。若使用 Transformer 架构的开源模型，适度微调常能提升语义相关性。此外，领域专属的嵌入模型往往在特定场景下表现更好。优化时还需权衡向量维度与计算效率。

接下来是检索器的优化，涉及向量数据库的选择、索引结构和检索算法的调整。例如可从简单的扁平索引过渡到 IVF 或 HNSW 等更高效的索引。调整 Top K 和相似度阈值有助于提高相关性并减少噪音。动态检索策略，如根据用户问题动态调整检索参数，以及各类索引优化技巧，也能提升结果质量。

然后是上下文生成策略的优化。检索到多个片段后，如何组合并传入大模型会影响最终答案。可以按语义相关性重排结果，压缩或扩充检索内容，或在片段间加入解释性连接词。上下文长度需结合所用大模型的最大 token 限制来控制，避免过载。

大模型的选择与提示词设计同样关键。要挑选更适合任务的模型，并调整生成参数如温度、Top-p、最大 token 数。提示词应给出明确指令或补充上下文，引导模型产出更符合需求的回答。

优化的最后一步是对响应的评估。生成后可使用 BLEU、ROUGE、BERT 等自动化指标，结合人工评估，对比不同优化组合的表现。通过实验迭代，逐步找到最优配置，提升整体效率和准确性。

企业环境中文件类型多样，既有 PDF、.doc/.docx 等常见格式，也可能出现冷门或专用格式。需要为每种类型制定解析策略并挑选合适工具（见图1-2）。优先考虑能覆盖常见格式的通用解析库或工具，例如 Unstructured 可统一处理同一目录下多种格式的文件。图1-2 为每种文件类型选择合适工具

[PRE9]

对于常见且重要的文件类型如 PDF，可选用专用工具如 PyPDF2、PyMuPDF、Marker、MinerU 和 PDFPlumber 等，具体取决于应用场景，例如结构化数据提取、文本搜索、OCR 或图像提取。

OCR 即光学字符识别，是一种把印刷或手写文本图像转为可编辑文本的技术，常用于扫描文档、图片文字识别、身份证车牌等场景。

对于较少见的文件类型，需先弄清生成工具、数据结构及用途。例如目录中出现 product_sales.jsonl 文件，文件名暗示它是产品销售日志，采用 JSON Lines 格式，每行是一个独立的 JSON 对象，行间无逗号分隔，解析时需注意。

针对复杂文档，可先转为更易解析的中间格式。例如 PPT 可先转成 PDF 再提取，因 PDF 提取工具更丰富。又如 PDF 可先统一转为 Markdown 再处理，因 Markdown 更规范，便于提取标题、段落、列表，且大模型基于网页资源训练，对 Markdown 有天然亲和力，更利于理解。

此外，大模型也能辅助解析结构化、半结构化和非结构化数据，在多模态等复杂场景下效果很好。

在 LangChain 中，Document 是一种核心数据结构，表示从外部文件或其他数据源加载的文本内容。主要包含两类属性。

- Metadata：存储与文档相关的元信息，如来源路径、作者、日期等。
- page_content：保存实际文本内容，是文档的主要数据部分。

小冰：为什么要用 Document 对象？

咖哥：Document 中记录的元数据很重要。它们虽非正文，却包含丰富信息，在 RAG 中作用显著。文档可能来自 TXT、PDF、HTML 或数据库记录，仅靠原始字符串无法追溯来源或获取额外信息如日期、类别等。许多 NLP 或信息检索任务中，结合元数据进行过滤、排序或分析是必不可少的。在高级索引技术中，也可利用元数据存放摘要、父文档 ID 等。

此外，不同数据源特性各异，如分块策略、段落间隔等，需要统一的数据结构进行抽象与标准化。Document 对象能把多样数据源抽象为统一结构化形式，便于在 LangChain 中无缝处理，顺利传递到嵌入模型、分类器或问答系统。
