当集成遵循同一套规范，组件的复用与流通会变得格外高效。现在，随着 MCP 服务端被持续构建并在社区间共享，新生的 AI 应用能够迅速对接各类外部数据与工具，重复开发与资源浪费被大幅压缩。由此形成一种全新的 AI 应用生态，整体效能明显提升，也为 AI 应用的繁荣提供了土壤。

生成式 AI 领域里，也存在一个类似的思路，那就是大模型 API 网关，典型代表是 OpenRouter 以及开源的 One-API。这类服务把不同厂商的大模型接入协议都统一成 OpenAI 兼容形态，让上层应用接入更省心，开发效率与灵活性都有提升。只是各家开放 API 本身差异有限、数量也不多，所以难以复制 MCP 那种规模效应。

基于 MCP 的集成架构如图 1-8 所示。

**1.MCP 服务端**

MCP 服务端是整个架构的枢纽，以独立进程的方式运行。它通过统一协议对外暴露特定功能接口，让智能体可以连接并使用外部数据源与工具。接口范围涵盖本地文件系统与软件模块访问、数据库查询、以及企业内部应用和互联网开放 API 的调用等。

它更像一个面向智能体的服务网关，以一致且安全的方式提供通往外部世界的能力。服务端采用标准化的消息格式与传输协议来收发请求与响应，就像外部设备严格遵循 USB 标准，因而具备很强的通用性与可共享性。

关于服务端，值得先了解以下要点。

1）服务端在何处运行

服务端主要有两种部署方式，通过不同的通信协议与客户端交互。

（1）本地模式，部署在客户端本机，通过 IPC 进程间通信 与客户端交互。
（2）远程模式，部署在远端服务器，通过 HTTP 超文本传输协议 与客户端交互。

第二章会详细说明这两种通信协议的工作原理。

2）服务端能公开哪些服务类型

在当前规范中，服务端可按需暴露三类常见服务。

（1）工具 Tool。供应用调用的工具服务，例如谷歌搜索。
（2）资源 Resource。供应用访问的各类数据，例如一张截图。
（3）提示 Prompt。供应用使用的模型提示词模板，例如反思类提示词。

3）服务端从何而来

开发者可以使用 MCP 官方提供的 SDK 自行开发服务端，供个人或企业内部使用。也能够从社区共享的海量服务端中挑选直接下载使用，或将自研服务端贡献出去。图 1-9 展示了一个优质的 MCP 服务端共享社区。 ^(¹)

4）服务端用什么语言开发

理论上只要理解 MCP 规范，就能用任何语言开发符合标准的服务端。实践中建议基于官方 SDK 减少工作量。目前已开放的 SDK 版本包括 Python、TypeScript、C#、Java 等。

5）服务端如何启动

不同语言的服务端启动命令不同，例如 TypeScript 编写的服务端可能用 npx 启动，Python 编写的服务端可能用 uvx 启动。使用第三方服务端时请阅读其说明文档。另外，若选择本地模式，客户端会自动拉起服务端。

这种启动方式目前仍显繁琐，相信未来会有更简洁的体验。

**2.MCP 客户端**

这里的客户端并非独立可运行的程序，而是一个负责与 MCP 服务端建立连接并通信的模块，用来简化智能体对服务端的访问，并保证请求与响应遵循标准格式与协议。运行时可把它视作智能体维护的一个会话连接，类似使用 MySQL 客户端组件发起 SQL 请求。借助它可以向服务端发起请求并拿到响应。

MCP 中定义了少量客户端可向服务端提供的功能。

**3.宿主**

宿主是指需要访问外部资源的智能体或各类 AI 应用，也可看作一种特殊的“用户”。它借助 MCP 客户端，按标准协议与 MCP 服务端交互，调用其公开的接口以访问外部数据与工具，从而完成任务。

总体来看，MCP 定义了一套标准化的 AI 应用集成方式，规定了客户端、服务端及外部资源如何组合连接，以实现高效、可扩展、安全的集成。简要概括如下。

（1）MCP 服务端。独立运行的应用，向客户端开放可用的工具等。
（2）MCP 客户端。嵌入在宿主中的模块，与服务端保持一对一连接。
（3）宿主。完整的客户端应用，例如一个智能体，通过服务端使用其开放功能。

为避免混淆，后文提及的“客户端”，除非特别说明，均指包含 MCP 客户端模块的完整客户端应用。

# 拆解 MCP 规范与底层原理

MCP 提出了一种将智能体与外部资源标准化的集成方式。目标是降低集成时的强耦合与复杂性，提升互操作性与扩展能力。MCP 的本质是面向 AI 应用集成的开放标准。需要从两个层面去理解与学习，如图 2-1 所示。

[PRE19]

图 2-1

（1）MCP Specification，即 MCP 规范。对基于 MCP 的集成架构及其关键模块的功能、通信协议、消息格式、安全机制等制定的标准。遵循该规范实现的模块可实现互操作。
（2）MCP SDK。基于规范实现的多种语言开发框架与工具，帮助开发者快速构建符合规范的模块并完成集成。

本章首先深入探讨 MCP 的底层规范与设计动机。我们不只是罗列条款，而是力求理解其背后的原因。值得注意的是，尽管许多内容在日常开发中无需直接处理，但对底层原理的掌握将极大帮助调试、优化与排障，甚至在必要时对 SDK 进行改造与扩展。

下面将按消息与通信、MCP 服务端、客户端的顺序解析规范与原理。

## 2.1 消息规范：互操作的基础

MCP 作为简化集成与实现互操作的标准，最基础的就是消息协议。就像国际会议需要共同语言，效率才会提升。在 MCP 规范中，唯一的消息协议是 JSON-RPC 2.0。

### 2.1.1 JSON-RPC 2.0 是什么

JSON-RPC 2.0 是一种轻量级的远程过程调用消息协议，使用 JSON 作为数据格式。注意，它不是底层传输协议，而是一种应用层消息格式标准。形象地说，它规定了包裹如何打包、如何分区、如何贴标签，但不规定如何运输。
