这次定义的资源和前面版本最大的差别，是引入了 URI 模板 users：//｛user_id｝/profile。这里的 ｛user_id｝ 就是一个可被替换的占位符。FastMCP 能够自动识别客户端传来的 URI 里对应的占位部分，并把它解析成参数传给目标函数。比如客户端发起 user：//user1/profile 的请求，MCP 服务端就会去调用 get_user_profile（user_id＝"user1"） 这样的函数。在函数内部，你可以根据收到的参数自行设计处理逻辑，例如拿这个 user_id 去数据库查用户信息。

有了资源机制，开发者可以按需声明资源和参数，客户端直接访问，相当于给大模型持续补充丰富的上下文。

### **3.2.5 服务端启动方式**

我们已经搭好了一个功能有限的 MCP 服务端，现在需要把它跑起来让客户端调用。查文档时你会看到调试模式启动、命令行启动、集成到第三方工具启动等多种写法，表面不同，本质来自同一套启动代码。下面从两种基础传输模式的启动原理说起。

**1.两种传输模式的启动原理**

在 MCP 集成架构里，客户端和服务端有两种传输方式，即 stdio 传输和 SSE 传输。服务端的启动方式也由此分为两种，如图 3-4 所示。

[PRE4]

图 3-4

（1）基于 stdio 的本地传输启动。这种模式下服务端和客户端通常在同一台机器。两者通过标准输入输出 stdin/stdout 做进程间通信。服务端的启动一般由客户端程序通过命令行自动触发，启动后服务端成为客户端的子进程，通信依赖启动时建立的 stdin/stdout 通道。

因此用 stdio 时，服务端的启动命令通常写在客户端的配置里，虽然也可以手动执行命令启动，但这样无法与客户端建立传输。

（2）基于 SSE 传输启动。这种模式下服务端不能由客户端拉起，需要单独执行命令启动。启动后服务端会在配置的端口上监听连接和请求。

因此用 SSE 时，需要在客户端配置服务端的地址、端口和连接端点，例如 /sse。然后手动执行命令启动服务端。可以用 python 或 uv run 启动，在 TypeScript 环境下常用 node 或 npx，也可以直接用 SDK 提供的 mcp cli 工具。
