本地数据问答实战：从Text2SQL到Agent工具链

想让大模型直接和本地SQLite对话，最快的方式是先搭一个可复现的最小实验床。用一个库建两张表，一张记录景区信息，一张记录城市信息，放入少量山西地区的示例记录，就能作为后续验证的沙盒。

###### 连接SQLite数据库

import sqlite3

conn = sqlite3.connect('data/tourism.db')

cursor = conn.cursor()

###### 创建景区信息表

cursor.execute("""CREATE TABLE IF NOT EXISTS scenic_spots (

    scenic_id INTEGER PRIMARY KEY,

    scenic_name VARCHAR(100) NOT NULL,

    city VARCHAR(50) NOT NULL,

    level VARCHAR(20),

    monthly_visitors INTEGER

)""")

###### 创建城市信息表

cursor.execute("""CREATE TABLE IF NOT EXISTS city_info (

    city_id INTEGER PRIMARY KEY,

    city_name VARCHAR(50) NOT NULL,

    annual_tourism_income INTEGER,

    famous_dish VARCHAR(100)

)""")

schema_description = """你正在访问一个包含两张表的数据库：

1. scenic_spots（景区信息表）

    - scenic_id (INT): 主键，景区唯一标识

    - scenic_name (VARCHAR): 景区名称

    - city (VARCHAR): 所在城市

    - level (VARCHAR): 景区等级

    - monthly_visitors (INT): 当月游客量

2. city_info（城市信息表）

    - city_id (INT): 主键，城市唯一标识

    - city_name (VARCHAR): 城市名称

    - annual_tourism_income (INT): 年度文旅收入（单位：元）

    - famous_dish (VARCHAR): 当地名菜/特色小吃"""

###### 初始化OpenAI客户端

from openai import OpenAI

import os

client = OpenAI(

    base_url="https://api.deepseek.com",

    api_key=os.getenv("DEEPSEEK_API_KEY")

)

###### 设置查询

user_query = "查询太原市的AAAAA级景区及其当月游客量"

###### 准备生成SQL的提示词

prompt = f"""

以下是数据库的结构描述：

{schema_description}

用户的自然语言问题如下：

"{user_query}"

请注意：

1. scenic_spots表中的city字段存储的是城市名称，对应city_info表中的city_name

2. 两张表之间的关联应该使用city_name和city进行匹配

3. 请只返回SQL查询语句，不要包含任何解释、注释或格式标记（如sql）

"""

###### 调用大模型生成SQL语句

response = client.chat.completions.create(

    model="deepseek-chat",

    messages=[

        {"role": "system", "content": "请只返回SQL语句，不要包含任何Markdown格式或其他说明。"},

        {"role": "user", "content": prompt}

    ],

    temperature=0

)

###### 清理SQL语句，移除可能的Markdown标记

sql = response.choices[0].message.content.strip()

sql = sql.replace('sql', '').replace('```', '')

把清洗后的语句在本地库里执行，得到的结果再交给模型做自然语言复述。

##### 4. 结合Agent、SQL-Data-Function和Tool Calls的方案

小雪：咖哥，前面讲的Text2SQL在轻量查询上挺好用，但一旦涉及多步推理或业务约束，生成的语句容易偏离，可靠性也难以保证。落地时有没有更稳妥的思路？

咖哥：我和业界朋友交流过类似痛点，这正是直译类方案的短板。经过多次迭代，我们摸索出一种兼顾效率与可控性的中间做法。

> 这个思路受咖哥朋友卢向东2024年6月在掘金大会分享的启发，其公众号“土猛的员外”持续分享RAG落地的实践。

核心是让Agent的Tool Calls负责调度，配合事先封装好的数据函数模板，模板内部预置可复用的查询逻辑，再加上人工补全的元数据，形成从口语提问到结构化操作的安全过渡。

小雪：元数据提取具体指什么？

咖哥：就是把表结构、字段说明、视图描述等信息整理出来，并人工补充业务关联和使用场景。处理后的元数据才能做向量嵌入。

小雪：数据函数又是什么概念？

咖哥：它是一套函数模板体系，用来覆盖常见查询模式。为特定业务开发数据函数，和开发MyBatis、Hibernate这类ORM模板的思路类似，把复杂的SQL封装起来，提升复用与可控性。

整体是智能调度：工具调用负责分发与执行，大模型负责意图理解、检索匹配的元数据与数据函数，完成单步或多步的查询组装。

下面示例展示了如何用模块化工具定义注册描述并实现具体逻辑。系统提示里会注入表的业务含义及关联关系，帮助模型更安全地完成查询。
