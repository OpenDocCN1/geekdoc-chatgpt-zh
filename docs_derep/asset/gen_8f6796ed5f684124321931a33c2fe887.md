## 9.2 Plugin 的物理结构

一个 Plugin 本质上就是按约定好的目录规范组织的版本库，通常托管在 Git 上，它的身份凭证是放在 .claude-plugin/ 子目录下的 plugin.json 清单文件。

下面以 react-workflow 为例，看一个典型的目录样貌。

[PRE0]

这里有个必须牢记的物理限制：只有 plugin.json 必须落进 .claude-plugin/ 这个固定子目录，其它所有功能目录比如 commands、agents、skills、hooks，以及配置文件 .mcp.json 都要直接放在 Plugin 根目录下。

正是这种安排，让 Plugin 的根目录本身就是一个合规的 Claude Code 项目目录。开发者可以直接在根目录里写代码、跑测试，无需切到特殊的开发模式。

| 字段 | 必需 | 说明 |

| :--- | :--- | :--- |

| name | 是 | Plugin 的唯一标识符，用于安装命令及内部引用 |

| version | 是 | 语义化版本号（SemVer） |

| description | 是 | 简短描述，将显示在 Plugin 列表中 |

| author | 否 | 作者个人或团队名称 |

| repository | 否 | 源代码仓库地址 |

| license | 否 | 开源许可证协议 |

| keywords | 否 | 用于检索的搜索关键词 |

需要特别强调 name 字段。它不只是展示用的名字，更决定了命名空间。安装后，Plugin 里的所有组件都会自动以该名称做前缀，避免和其他插件冲突。所以名称要选得清楚、简短、不易撞车。推荐示例：react-workflow、pr-reviewer、db-tools。不推荐示例：my-plugin 过于宽泛、tools 太容易冲突、v2 包含版本号没有意义。

在企业环境中，管理员可把该路径指向共享网络存储，实现 Plugin 的统一部署、集中管理与分发。

## 9.4 命名空间：多 Plugin 共存

多个 Plugin 同时存在且包含同名 Skill 或 Command 时会怎样？系统通过命名空间机制自动化解冲突。

所有经 Plugin 安装的组件都会自动获得 plugin-name:component-name 的全限定名，确保全局唯一。以安装 react-workflow 为例：

- 原 review Command 变为 /react-workflow:review。
- 原 code-reviewer Skill 变为 react-workflow:code-reviewer。
- 原 security-scanner Agent 变为 react-workflow:security-scanner。

冲突不存在时，直接用简短命令名如 /review 即可，Claude Code 会自动解析成唯一组件。只有检测到同名冲突时，系统才要求使用完整命名空间限定符如 /plugin-a:review 来明确指定。

这一机制的工程价值在于：团队可以放心安装组合多个 Plugin，无需提前协调命名；开发者也不用刻意避让，降低了维护成本。

#!/bin/bash

# Bash 命令安全拦截脚本

# 用于在 Claude Code 执行危险命令前进行阻断

INPUT=$(cat)

COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')

DANGEROUS_PATTERNS=("rm -rf /" "rm -rf ~" "sudo rm" "> /dev/" "chmod 777")

for pattern in "${DANGEROUS_PATTERNS[@]}"; do

    if echo "$COMMAND" | grep -qF "$pattern"; then

        cat << EOF

{"decision": "deny", "reason": "Blocked dangerous pattern: $pattern"}

EOF

        exit 1

    fi

done

exit 0
