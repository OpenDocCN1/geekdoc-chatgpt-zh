Claude Code 记忆体系：从公司红线到个人便签

最底层落在每个人工位上的私人便条，是完全私有的知识沉淀，只对自己可见，用来记临时的调试诀窍或个人的操作偏好。从顶层往下，覆盖面逐步收窄，信息颗粒越来越细，可调整的灵活性也越高。图 2-2 把 Claude Code 的五层记忆架构完整呈现了出来。

下面按层拆解定位与典型用法。

**企业级** 坐镇整个架构的顶端，普通开发者基本触碰不到。该层由公司 IT 管理员通过系统级配置文件，Linux 环境下常见于 `/etc/claude-code/CLAUDE.md`，或通过 Anthropic 企业管理后台统一推送。常见管控例如禁止把源码发往外部 API、所有数据库操作必须走 ORM、代码里严禁硬编码密钥。它划定全公司的合规底线，下方四层的任何设定都无法绕过这层强制约束。对独立开发者或小团队而言，这层通常是空的，无需特别关注。

**用户级** 相当于是个人工作习惯的档案。文件放在用户主目录下的 `~/.claude/CLAUDE.md`，在这台机器上打开的所有工程都会生效。这里适合放一些与具体业务无关、但能体现个人风格的通用设定，比如沟通语言选中文还是英文、Git 提交信息格式、把常用的快捷指令映射成具体执行命令。这类偏好很稳定，不会因为换项目而变动。

[PRE1]

**项目级** 是日常开发里使用频率最高的，也是本章的重点。它就是项目根目录下的 `CLAUDE.md`，必须进 Git 仓库成为代码资产。

新同事 clone 项目后，Claude Code 能自动读取该文件，不需要额外配置就能拿到完整的项目上下文。好比入职第一天收到一本专属的《项目开发手册》，技术选型、目录结构、编码规范与常用命令一目了然。怎么把这份关键文件写好，会在 2.3 节展开。

**规则级** 用来解决单一 CLAUDE.md 难以承载复杂规则的问题。可以在 `.claude/rules/` 目录下放置多个独立的 Markdown 文件，每个文件聚焦一个主题，例如数据库规范、API 设计风格或测试策略。关键在于该层支持条件触发，规则文件只有在操作特定文件或进入特定情境时才被动态加载，避免无关信息占用会话窗口。

**本地级** 是开发者的私人便签，对应 `CLAUDE.local.md`。该文件不会进 Git 仓库，Claude Code 会自动把它加入 `.gitignore`。它专门收纳对个人很有价值但不宜公开的内容，如测试服务器地址与端口、私人调试积累的心得、临时工作备忘等。

举例来说，开发环境数据库在某时段要做维护，这种信息只记在本地层就够了，避免制造团队信息噪声。

[PRE2]

小冰立刻追问了一个关键问题：“五层内容冲突时怎么算？比如用户级写了‘4 空格缩进’，项目级却要求‘2 空格缩进’。”

“问得好。”咖哥评价道，“这些文件的关系是叠加而非覆盖。Claude Code 会把所有层级的内容合并成一份完整上下文。遇到矛盾时，模型会基于具体性来判断。缩进的例子里，项目级的‘2 空格’针对当前项目，具体性高于用户级的通用‘4 空格’，因此会被优先采纳。唯一例外是企业级，它拥有绝对强制力，任何下层设置都无法违背，就像法务与安全红线，无人可以逾越。”

另外，CLAUDE.md 还支持文件引用机制。任意层级的记忆文件都可以用 `@path/to/file` 语法把其它文件拉进来，实现配置模块化。

比如在项目层的 CLAUDE.md 中写 `@docs/api-conventions.md`，Claude 就会自动加载 API 规范文档的内容。该机制允许最多五层嵌套递归，足以覆盖复杂项目的组织需求。

这让大型项目的文档治理更优雅：CLAUDE.md 不必堆砌细节，而是充当索引总纲，灵活指向专题文档，避免单一文件信息过载，结构更清晰、可维护。

## 2.3 CLAUDE.md 写作范式

弄清记忆文件的存放位置与职责后，更关键的问题是怎么写。

咖哥在白板上强调核心原则：克制优先。

“CLAUDE.md 具备全局持久性，”他解释，“它会在每一次对话初始化时完整注入会话窗口。每一行文字都在消耗 Token。”

他用办公桌作比：“会话窗口像面积固定的桌面。启动工作前就把厚厚的参考资料堆满，留给代码、文件和临时草稿的空间就会被挤占。一旦桌面被占满，Claude Code 就得丢弃早期关键信息，导致重要指令被遗忘。”

这一直觉有数据支撑。据 Anthropic 工程实践，Claude Code 的 System Prompt 已内置约 50 条核心指令，构成‘操作系统级’基石。当用户自定义的 CLAUDE.md 使总指令数突破约 150 条临界值，模型对指令的遵循质量会明显衰减。指令密度越高，每条规则被深度关注并严格执行的概率越低。

这与管理学的信息过载原理一致：员工手册厚到无人可读，还不如一张提炼精髓的 A4 摘要。在 AI 协作中，精简既是省 Token 的手段，也是保证指令落地的关键。

筛选内容可以用三问框架。

**第一问：WHY 为什么这样做**

核心价值是赋予模型举一反三的推理能力。揭示决策背后的底层逻辑，帮助 Claude 理解项目的核心关切。掌握了为什么，即使遇到未明示的边缘场景也能正确推导。

示例：‘选用 Fastify 而非 Express，是因为 Fastify 的 schema-based validation 与本项目类型安全优先的战略一致。’

效果：理解类型安全是最高优先级后，Claude 会主动偏向类型定义更完善的方案，而非机械匹配关键词。

**第二问：WHAT 做什么、不做什么**

核心价值是划定行为边界。最直接、最刚性的行为指令，明确允许与禁止范围，通常不需要解释原因，要求绝对服从。

示例：“必须使用 pnpm 作为包管理器；禁止使用 npm 或 yarn。”

效果：建立清晰红线，消除工具选型上的不确定性，保证技术栈统一。

**第三问：HOW 如何一步步做**

核心价值是固化标准作业流程。适用于常用命令、固定流程或特定操作范式，模型只需准确执行步骤。

示例：“执行数据库迁移运行 pnpm db:migrate；填充测试数据运行 pnpm db:seed。”

效果：把团队最佳实践变成模型的肌肉记忆，减少拼写错误或参数遗漏。

并非每条规则都需要三种问题。大多数规则一句 WHAT 就够。只有容易被误解或模型容易好心办坏事的关键决策，才值得补充 WHY 层面的解释。

如果你发现 CLAUDE.md 里每条规则后都跟一大段背景说明或感性描述，那基本就是过载了。精简才是高效协作的王道。

下面用反面与正面案例对比。

先看反面：模糊的正确的废话。

## 项目说明

这是一个电商平台后端服务，团队 5 人，项目从 2024 年 3 月启动。用 Node.js 写成 RESTful API 服务。代码要写得好一些，注意性能。测试要全面。请遵循最佳实践。

这类描述充满社交客套和模糊指令，对 AI 基本无效。

“写得好一些”：好到什么程度？是 Prettier 格式还是设计模式？
“全面”：单元、集成还是 E2E？覆盖率 80% 还是 100%？
“最佳实践”：谁的最佳实践？

Claude 读完可操作信息几乎为零。尤其“遵循最佳实践”看似正确实则空洞。Claude 默认会遵循它认知中的最佳实践，而通用实践与团队约定常有偏差。

“团队 5 人”“2024 年 3 月启动”这类元数据对代码生成无指导意义，却占用宝贵上下文。

除手工编写外，Claude Code 提供两个辅助工具。

第一个是 /init 命令。在项目根目录执行后，Claude Code 会扫描目录结构、依赖配置如 package.json、pyproject.toml、Cargo.toml 等，自动生成 CLAUDE.md 初稿。通常包含技术栈识别、目录概览和常用脚本，是很好的起点。

仍需人工补充 /init 无法推断的内容，如分层架构约束、API 响应统一约定、团队命名规范等。这些隐性知识只存在于团队脑中，必须显性化才能让 AI 完全贴合预期。

第二个是 /memory 命令，用于对话中动态更新记忆。执行后会弹出文件选择器，列出当前可用记忆文件供编辑，覆盖范围如表 2-1。

表 2-1 项目记忆的作用范围

| 文件类型 | 路径 | 作用范围 |

| :--- | :--- | :--- |

| 项目记忆 | ./CLAUDE.md 或 ./.claude/CLAUDE.md | 团队共享：可纳入版本控制，适用于统一团队规范 |

| 用户记忆 | ~/.claude/CLAUDE.md | 个人全局：个人偏好配置，对当前用户的所有项目均生效 |

| 项目本地记忆 | ./CLAUDE.local.md | 个人局部：仅针对当前项目的个人偏好，通常会被 .gitignore 排除，避免提交至代码仓库 |

选中文件后可在编辑器直接修改。

例如交互中发现 Claude 反复误用 moment.js，而规范要求使用 date-fns。无需退出对话，只需 /memory → 选择项目级 CLAUDE.md → 追加“日期处理统一使用 date-fns，禁止使用 moment.js” → 保存。下次对话即刻生效。若只是个人偏好，可写入 CLAUDE.local.md，该文件默认被排除，不会进仓库。

这形成“犯错→纠正→写入记忆→避免再犯”的闭环，记忆越用越精准，Claude 在项目中的表现持续进化。

## 2.4 条件化规则系统

项目演进后，单一 CLAUDE.md 必然触及容量瓶颈。当规则涵盖前端组件规范、后端 API 设计、数据库迁移、测试策略与基础设施等所有方面时，堆砌在一个文件会带来两大问题：维护困难，查找更新耗时；注意力分散，前端组件编写时仍被迫加载数据库迁移和 CI 配置等无关信息，导致噪声稀释注意力，甚至产生幻觉或忽略关键约束。

.claude/rules/ 目录正是为此而生。它把记忆系统从“一本厚重手册”变为“按需取用的模块化知识库”。优势有二：

领域拆分：将庞大规则拆成多个主题文件，各自专注，提高可维护性。
智能激活：文件头部用 YAML Frontmatter 的 paths 字段声明 Glob 模式，只有操作路径匹配时规则才被注入上下文，不匹配时安静存储，不消耗 Token。
