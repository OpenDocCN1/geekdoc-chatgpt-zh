### 9.3.5 协调过程是怎样的

首次渲染时，React 会先把元素树搭好，随后 Fiber 机制会从 HostRoot 这个特殊节点出发，逐层遍历整棵树，为每个节点生成对应的 FiberNode。

## 第9章 生命周期与虚拟 DOM

当组件内部的 state 或 context 发生变化时，React 会进入渲染阶段。该阶段是异步进行的，Fiber 机制会启动 workLoop，从 Fiber 树的根节点开始遍历，对已处理过的节点快速略过；对于有变动的节点，会为 Current 节点克隆一个 WorkInProgress 节点，两者通过 alternate 属性互相引用，并把本次的更新全部记录在 WorkInProgress 节点上。如图 9-4 所示。

[PRE4]

可以理解为两棵 Fiber 树在同时工作：**Current 树代表已经渲染到页面上的内容；WorkInProgress 树则负责把将要发生的改动记录下来。**

函数组件的 Hooks 同样在渲染阶段运行。除了 useContext，其他 Hook 在挂载后会以 Hook.next 把它们串成一条单向链表，随后挂到 fiberNode.memoizedState 上。

在此基础上，像 useEffect 这类可能产生副作用的 Hook，还会为每个 Hook 实例创建对应的 Effect 对象，写入 Hook.memoizedState；同时在 FiberNode.updateQueue 上维护一条由 Effect.next 连接的单向链表，把该 Effect 追加到链表末尾。

先暂停一下，回想 Hooks API 的两条重要规则：第一，只能在 React 函数组件内部调用 Hook，第二，只能在组件函数最外层调用 Hook。这是因为函数组件重新渲染时，每个 Hook 会按顺序再次执行，并沿着上述链表找回上一次的状态，据此决定复用或更新自身在链表中的状态。这也解释了为何同一个 useState 在每次渲染时返回的 state 更新函数引用保持不变，以及 useEffect 如何通过对比 Hook 状态来判断依赖数组是否变化，从而决定是否重新执行副作用。

结合原理再看这两条规则。

- 若在函数组件之外调用 Hook，Fiber 机制就不会为其创建记录状态的单向链表。

- 若在循环、条件分支等不稳定的位置调用 Hook，重新渲染时执行的 Hook 数量、类型和参数可能与上一次的链表不匹配，从而破坏 Hook 的内部逻辑。

回到协调流程。当整棵 Fiber 树的工作全部完成后，WorkInProgress 节点会被重命名为 FinishedWork 节点，WorkInProgress 树也随之变为 FinishedWork 树。此时 React 进入提交阶段，该阶段是同步执行的。引擎会按特定顺序把 FinishedWork 节点上记录的所有变更应用到页面。

提交阶段可以拆分为三个依次同步执行的子阶段。

- **变更前（Before Mutation）子阶段**。会调用类组件的 getSnapshotBeforeUpdate 方法。

- **变更（Mutation）子阶段**。会更新真实 DOM 树。

  - 递归提交与删除相关的副作用，包括移除 ref、移除真实 DOM、执行类组件的 `componentWillUnmount`。

  - 递归提交添加、重新排序真实 DOM 等副作用。

  - 依次执行 FiberNode 上 `useLayoutEffect` 的清理函数。

  - 用 FinishedWork 树替换 Current 树，供下一次渲染使用。

- **布局（Layout）子阶段**。此时真实 DOM 已变更但浏览器尚未绘制，会同步调用 `useLayoutEffect` 的副作用回调和类组件的 `componentDidMount` 方法。

在提交阶段中，引擎还会多次异步或同步调用 `flushPassiveEffects()`。该函数会分两轮深度优先遍历 Fiber 树上的每个节点。

- 如果节点的 `updateQueue` 链表中有由 `useEffect` 定义的待执行副作用，则按序执行它们的清理函数。

- 如果节点的 `updateQueue` 链表中有由 `useEffect` 定义的待执行副作用，则按序执行它们的副作用回调，并保存清理函数供下一轮提交阶段使用。

`flushPassiveEffects()` 的实际执行时机是在上述三个同步子阶段之后、下一次渲染之前，引擎会确保在下一次渲染发生之前，所有待执行的副作用都已完成。

你可能好奇 Diffing 算法在哪个环节。实际上从渲染阶段到提交阶段，整个过程都在用 `memoizedProps` 和 `memoizedState` 与新的 `props`、`state` 做比较，以减少不必要的工作，提升性能。

最后补充一点，workLoop 能灵活暂停与恢复，除了自身设计外，还得益于调度器 Scheduler 的支持。它负责按优先级分批执行任务，并允许执行队列暂停与恢复。想深入了解，建议阅读相关 React 源码。

## 9.4 小结

本章先梳理了 React 的生命周期，包括跨组件的渲染阶段与提交阶段、单个组件的挂载、更新、卸载与错误处理阶段，以及副作用的生命周期。随后引出虚拟 DOM 的概念，说明 React 中的虚拟 DOM 是真实 DOM 的轻量抽象，是开发者 API 与内部实现之间的桥梁。接着解释了当 props、state 或 context 变化时，React 如何触发协调过程，对比新旧元素树以确定真实 DOM 的变更，并简要介绍了负责协调的 Fiber 调度机制。上述概念共同构成了 React 组件的渲染机制。

用 props、state、context 来保存和传递数据的方式足以应对小型乃至中型的 React 应用。但随着项目规模扩大和复杂度提升，开发者会遇到新的难题。

- 处理对象或数组类型的 state 时，必须格外注意保持不可变性。

第一个挑战的核心是不可变数据，后两个挑战则直接关联应用状态管理。这些概念与 React 密不可分。

- React 的状态更新依赖不可变数据。

- React 可以配合独立的状态管理框架来管理应用状态。

- 大多数应用状态管理框架都是基于不可变数据构建的。

本章首先介绍应用状态管理的基本概念，然后重点阐述不可变数据的重要性，接着探讨在 React 中管理应用状态的不同方案，并讨论何时使用 React 自带的 state、何时采用状态管理框架。最后以 oh-my-chat 的实践为例，介绍主流的状态管理框架 Zustand。

## 10.1 什么是应用状态管理

先来厘清应用状态（Application State）的含义。理论上，应用运行时内存中所有相关联的数据都可以算作应用状态，但实际开发中我们只关注其中一小部分。

可以拿后端服务来类比：有状态服务和无状态服务常被一起讨论。比如一个购物车 HTTP 服务，服务器端会临时保存当前登录用户的 session 信息，后续请求都会读写该 session，属于有状态服务；而商品列表 HTTP 服务则只依赖请求参数返回结果，不关心用户是否登录，属于无状态服务。由此可判断，服务器端临时保存的登录用户 session 信息才是需要关注的应用状态。

越是“富 JS” 的浏览器端应用，越倾向于把服务器端的应用状态迁移到浏览器端，于是出现了以“浏览器端临时存储的登录用户 session 信息”为代表的前端专用的应用状态。

如果不这么做会怎样？以一个极端反例说明：一个对话框是否显示取决于一个布尔值，若把该状态放在服务器端，每次打开关闭都要调用后端服务，不仅用户体验因等待响应而下降，前端开发也将被迫把原本同步的本地逻辑转为异步请求，复杂度大幅上升。你可能会问，真的有框架这么做吗？答案是肯定的，比如当年的 JSF。

React 作为数据驱动的前端框架，高度依赖浏览器本地的应用状态。随着本地状态复杂度提升，甚至需要专门的抽象层时，应用状态管理框架应运而生，用来统一管理这些状态。需要注意的是，应用状态管理并不等同于状态管理框架，利用 React 内部机制同样可以实现应用状态管理，本章后半部分会讨论何时需要引入独立框架。

## 10.2 不可变数据

在深入应用状态管理之前，先了解不可变数据的概念，它是应用状态管理的重要基石。在 React 开发中，对数据变更方式不当往往是 Bug 的主要来源之一。以 oh-my-chat 项目的 MessagesPane 组件为例，更新 messages 状态时使用了 [...currentMessages, newMessage] 返回新数组。你可能会问，为什么不能直接 messages.push(newMessage)。掌握不可变数据的原理后，就能更深刻理解 React 渲染机制与数据流的关系。
