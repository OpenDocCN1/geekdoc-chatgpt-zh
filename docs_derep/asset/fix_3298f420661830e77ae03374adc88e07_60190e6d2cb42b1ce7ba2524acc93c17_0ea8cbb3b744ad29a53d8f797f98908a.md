schema_description = """你正在访问一个包含两张表的数据库：

1. scenic_spots（景区信息表）

    - scenic_id (INT): 主键，景区唯一标识

    - scenic_name (VARCHAR): 景区名称

    - city (VARCHAR): 所在城市

    - level (VARCHAR): 景区等级

    - monthly_visitors (INT): 当月游客量

2. city_info（城市信息表）

    - city_id (INT): 主键，城市唯一标识

    - city_name (VARCHAR): 城市名称

    - annual_tourism_income (INT): 年度文旅收入（单位：元）

    - famous_dish (VARCHAR): 当地名菜/特色小吃"""

###### 初始化OpenAI客户端

from openai import OpenAI

import os

client = OpenAI(

    base_url="https://api.deepseek.com",

    api_key=os.getenv("DEEPSEEK_API_KEY")

)

###### 设置查询

user_query = "查询太原市的AAAAA级景区及其当月游客量"

###### 准备生成SQL的提示词

prompt = f"""

以下是数据库的结构描述：

{schema_description}

用户的自然语言问题如下：

"{user_query}"

请注意：

1. scenic_spots表中的city字段存储的是城市名称，对应city_info表中的city_name

2. 两张表之间的关联应该使用city_name和city进行匹配

3. 请只返回SQL查询语句，不要包含任何解释、注释或格式标记（如sql）

"""

###### 调用大模型生成SQL语句

response = client.chat.completions.create(

    model="deepseek-chat",

    messages=[

        {"role": "system", "content": "请只返回SQL语句，不要包含任何Markdown格式或其他说明。"},

        {"role": "user", "content": prompt}

    ],

    temperature=0

)

###### 清理SQL语句，移除可能的Markdown标记

sql = response.choices[0].message.content.strip()

sql = sql.replace('sql', '').replace('```', '')

##### 4. Agent 工具调用与数据函数的稳健组合

小雪：咖哥，Text2SQL 在简单问答上确实好用，但一旦涉及多步推理或业务约束，生成的 SQL 很容易出错，可靠性也难以保证。落地时有没有更稳的做法？

咖哥：我和业界朋友交流过很多案例，这正是直译 SQL 的痛点。经过多次实践，大家形成了一条兼顾效率与可靠的中间路线。

> 这套思路源自咖哥的朋友卢向东在 2024 年 6 月掘金大会的分享。他运营的公众号“土猛的员外”常写 RAG 落地的实战笔记。

核心做法是让 Agent 的工具调用参见人民邮电出版社出版的《大模型应用开发 动手做AI Agent》。承担调度，结合提前封装好的数据函数模板，模板内部预置了可复用的 SQL，再配合人工补全的元数据，构建从自然语言到结构化数据库操作的安全通道。

小雪：元数据的抽取到底指什么？

咖哥：就是把数据库的表结构、字段含义、视图说明等信息整理出来，再人工补充业务关联和使用场景。这样处理后的元数据才适合做向量化检索。

小雪：数据函数又该怎么理解？

咖哥：可以看成一套函数模板体系，用来覆盖常见的查询模式。给特定业务开发数据函数，和开发 MyBatis、Hibernate 这类 ORM 模板的思路类似，把复杂的 SQL 逻辑封装起来，提升复用性与可控性。

整体是智能化调度：工具调用负责分发与执行，大模型负责理解意图、检索匹配的元数据和数据函数，完成单步或多步的 SQL 拼装与查询。

下面示例展示了如何用模块化工具定义注册描述并实现具体逻辑。系统提示里会注入表的业务含义及关联关系，帮助模型更安全地完成查询。
