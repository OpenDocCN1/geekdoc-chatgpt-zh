多智能体协作新范式：从单打独斗到分工共建

本章收尾我们要搭一个更复杂的 AI 形态——多智能体体系。比起让单个智能体包打天下，多智能体的协作会更灵活、扩张更方便，也更贴合未来智能体的演进方向。它的优势可以概括为三点。

分工明确。各类智能体各自承担擅长的子任务，研发、调试、评估都可以独立完成。
扩展便捷。需求变化时可动态接入新智能体，直接并入现有团队。
协作灵活。多个智能体能以不同方式配合，共同攻克复杂目标。

多智能体体系的根基仍是单体智能。借助社区里大量可复用的共享 MCP 服务端，就不必从零造工具箱，能快速获得通用能力的智能体基础，从而迅速拼装出多智能体体系。下面以开放社区的 MCP 服务端为例，演示一条可快速落地的搭建路径。

③浏览器智能体 Browser Agent：用于自动浏览、抓取网页数据、模拟用户交互，一般结合 Playwright 自动化框架与 Chromium 内核实现。
④文件系统智能体 FS Agent：在限定安全目录内完成目录查询、创建、文件增删、读写等操作。
可选流程节点。为让任务规划更合理，可在规划阶段引入专门的规划与反思智能体 Planner/Reflection Agent。例如使用深度思考模型预生成执行计划，并在每一步或多步完成后依据实际执行情况对计划进行修正与完善。
共享 MCP 服务端。为各功能专一的工作智能体提供标准化的工具集合。本项目尽量复用现成的共享 MCP 服务端，以发挥 MCP 的效率优势。

这就是典型的任务主管式协作：一个主管带多个执行者协同完成任务。接下来将按后端到前端、基础到上层的顺序完成实现。

### **6.5.4 工作流组装**

在具体执行智能体之上，我们再构建更高层的智能体工作流 Workflow。在 LangGraph 中，工作流的定义和组装通过 Graph 基础类型完成。本项目的实施步骤如下。

设计状态管理及必需的输出对象类型。
实现 Supervisor 节点，负责动态推理步骤并分配任务。
实现 Graph 中调用智能体的节点，明确各节点职责。
构建 Graph，连接各节点、定义路径，实现多节点协同。

**1.状态 State 与类型定义**

在 LangGraph 里，State 是核心概念。它是一个用 TypedDict 定义的字典结构，用于保存工作流运行期间的关键信息，并在节点间传递。节点接收 State、处理后返回更新后的 State。例如为保持上下文，可设置 messages 字段保存本次运行的历史消息。

为便于理解，这里直接使用 TypedDict。State 的定义如下，源码路径为“app_manus/graph/types.py”：

[PRE11]

该 State 包含以下字段：
messages。保存历史消息，包含人类消息、AI 消息、工具调用消息、系统消息等，可按需裁剪以控制成本。
next。表示下一步要执行的智能体，用于控制流程走向。
current_task。描述下一步具体任务，帮助对应智能体理解待办内容。
curretn_step。记录当前执行步数，仅作参考，无实际操作意义。

基于此定义，每个节点都能依据最新状态执行，并保证历史和上下文完整。
