### 1.2.3 多智能体协作：告别单体天花板

1.2.2 里讲的都是单体方案，一个代理独自扛下用户全部需求。工具挂载不多时体验尚可，一旦工具膨胀到上百上千，单纯的使用说明就能把大模型的上下文挤爆；选择面过大也会让决策变得迟钝。正是在这种瓶颈下，多智能体系统应运而生。

通俗点说，多智能体就是一套分工明确、相互配合的代理集合。思路很直接：把一个复杂的总任务拆成若干个可处理的子任务，再分派给不同专长的代理去执行。这样既能把单个代理的工具负担压下来，也能避免工具描述本身就占据大量记忆。

目前业界流行的架构主要分两类。一类是流程固定的工作流 Workflow，扣子与 Dify 都在用；另一类是让大模型自行决定执行顺序的主从架构，2025 年火起来的 A2A 协议就是为此服务的，近来热度很高的 SubAgent 也是这一路线的延伸。下面简要拆开讲。

#### 1. 工作流

工作流很像公司的请假审批链，发起后要逐级签字落地。技术上它是由开发者提前编排好的任务序列，规定了先后顺序、触发条件和环节间的数据流向，擅长处理流程确定、步骤清晰的场景。

如图1-4所示，把工作流的每个处理节点替换成智能体，就能拼出一个多智能体系统。工作流形态很灵活，可串行也可并行。

假设要做一份符合小红书等平台爆款调性的标准化旅游攻略，要求贴近用户习惯、丢掉教科书式的章节划分，强调好懂好用有亮点，具体要做：

- 本地美食清单，要带品类、热门小店和避坑提示。
- 必去景点推荐，分核心景点与小众打卡，并标明停留时长。
- 交通攻略，涵盖落地出行和景点间往返技巧。
- 基于以上三部分，整合成小红书图文笔记。

这时候撰写与图文生成的先后顺序已经确定，代理不需要自行调整先后，也无需多模块同时开工，关键是严丝合缝地把既定流程走完。可以排成如图1-5所示的工作流。

- 工作流会同时启动美食代理、景点代理、交通代理，分别产出三类初稿。
- 初稿汇总后交给图文生成代理，完成最终笔记。

链路环环相扣，能保证结构规范不遗漏。

#### 2. 主从智能体架构

主从架构如图1-6所示，典型角色有两类。

- 主控代理 MasterAgent：负责理解总任务、拆解任务并调度。
- 子代理 SubAgent：只负责执行某个具体的子任务。

用户提问先到达主控代理，由它做任务解析和拆分，再决定交由哪个子代理执行。视规划而定，可以单次只挑一个子代理，也可以让多个子代理并行。主控最后把各子代理的结果归并，返回给用户。

它的适用面与工作流相反，适合步骤不确定、需要主控自行规划的情形。

以如图1-7所示的AI医疗问诊为例，构建思路是：主控接收请求后先判断科室归属。如果用户说“最近感冒了，嗓子疼”，就调度呼吸内科子代理处理；如果用户说“最近胃疼，想要中西医结合治疗”，主控就会让中西医结合科子代理和中医科子代理并行诊断。每个子代理拥有独立模型与执行环境，互不干扰；主控只在最后做汇总交付。

## 1.3 Skills概述

Skills 是把智能体从通用助手推向领域专家的关键抓手，它正在改写普通人做 AI 应用的方式：不用写大量代码，仅靠自然语言加结构化文档，就能为代理注入可复用、可组合、可进化的专业能力。

### 1.3.1 Skills是专家经验的沉淀与复用

工作中很常见这样的场景。

你作为项目首任负责人，从零把一个难题啃下来。结束时领导会要求：“按公司模板把资料、操作步骤、关键判断和注意事项整理成文档，给后面同事快速复现。”

本质上是把个人经验变成团队可复用的知识资产。Skills 的设计正是这一管理逻辑的延伸。它提供一套标准结构，让用户把解决问题的思路、操作流程、依赖工具、参考资料和输出规范等，以 Markdown 等形式打包成一个专家经验包。

之后代理就像接手的同事，能读懂经验包的格式与内容。再次遇到类似任务时，代理参照包内定义的逻辑就能自主完成，不需要人工反复介入。

从这个角度看，Skills 本质仍是提示词工程。与只堆人设、抠措辞的传统做法不同，Skills 有了明确的格式规范，能把过去散落在多轮对话里的提示词、参考文件、代码等集中起来，让代理一次拿到完整方案，一次性解决问题。

### 1.3.2 Skills的格式与工作机制

既然 Skills 提供标准化格式，下面系统介绍其规范与运行方式，帮助理解 Skills 长什么样、怎么被代理使用。

#### 1. Skills的格式规范

物理上一个 Skills 就是一个文件夹，文件夹名即技能名。内部通常包含：

- SKILLS.md 文件必选。这是核心，也是唯一必选项。它相当于技能的标签与说明书，用 Markdown 清晰描述功能、输入输出规范、调用条件、执行步骤、使用示例等。代理正是通过阅读它来判断是否调用及如何使用。
- scripts 文件夹可选。放可执行代码脚本，如 Python。第4章会演示如何搭建抓取短线封板股的 Skills，其中就包含由扣子编程自动生成的爬虫脚本。在 AI 编程时代，只要用自然语言准确描述需求，AI 就能自动生成代码，无需编程基础，后续章节会手把手教学。
- references 文件夹可选。放支撑 Skills 运行的参考资料。例如做每日营养餐推荐 Skills，可放入权威食谱、营养成分表或饮食指南等，为代理提供领域依据，提升专业性与准确度。
- assets 文件夹可选。存放静态资源与模板，如图片、音频、配置模板、输出格式样例等。这些不参与逻辑计算，但在执行时可作为辅助素材。

#### 2. Skills的工作机制

工作机制源于上下文工程里的上下文污染现象。

主流大模型的上下文已扩展到 128K Token 甚至更高，但仍是有限资源。若把所有可能用到的信息一次性塞入，不仅浪费容量，还会干扰模型对当前任务的理解，这就是上下文污染。

直观类比来自《哆啦A梦》的记忆面包：大雄想记住书本需要吃印有文字的记忆面包，但先吃了大量甜点，肚子饱了，再也吃不下记忆面包，结果什么也没记住。这里大雄相当于大模型，甜点是无关信息，记忆面包是真正有用知识。无关内容会挤占关键信息的空间。

为避免此问题，Skills 采用渐进式按需加载机制，如图1-8右侧所示，整体内容按加载级别分为 L1、L2、L3 三层。左侧展示的是代理加载的顺序。

- 加载 Skills：代理加载一个 Skills 时，仅把 L1 级别的内容，即 SKILLS.md 中的标签部分放入大模型记忆。此时代理只知道“有这么一个技能可用”，但不会加载全部细节。
- 读取说明：当用户提出具体任务，代理判断某个 Skills 可能适用时，才会加载 L2 级别，即 SKILLS.md 的全部内容，以此指导后续操作。
- 按需加载资源：实际执行时，若任务需要调用代码、参考文档或模板，代理会按需加载 L3 级别，即 scripts、references 或 assets 中的相关文件。未使用的资源始终保留在外部，不进入大模型记忆。

这种按需加载有效防止上下文污染，同时保障复杂 Skills 的可扩展性与运行稳定性。

“旧时王谢堂前燕，飞入寻常百姓家”，用来形容 Skills 普及历程，恰到好处。

这不仅是用户体验的升级，更是 AI 应用开发范式从人适配工具走向工具理解人的根本转变。
