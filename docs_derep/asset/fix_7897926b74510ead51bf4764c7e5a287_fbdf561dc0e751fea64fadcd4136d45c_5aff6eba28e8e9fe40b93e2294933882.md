第二步：厘清何时触发
采用 Use when user... 的表达方式，尽可能罗列会激活该 Skill 的用户说法、口语短语与关键词，提升语义匹配的覆盖率。

第三步：划定不适用边界
属于可选但强烈建议的操作。若 Skill 容易被误启动，务必补充 Not for...，明确列出不触发的情境，以提升决策的准确性。

> 你撰写的 description 读者是 Claude，不是人类。人类浏览文档时依赖标题与结构快速抓取要点；Claude 解析 description 时在做深层语义匹配，需要捕捉意图的细微差别。为提高命中率，必须在 description 里穷尽用户可能使用的各种表述。例如“生成 API 文档”这一需求，用户可能说“生成 API 文档”“编写接口文档”“输出 OpenAPI 规范”“帮我写个 Swagger”。这些不同说法都应显式收录。同义词库越丰富，语义覆盖越广，触发越精准。

### 3.4.3 欠触发与过触发的防范

实践中 Skill 的触发常出现两种失效模式，理解并修复它们是优化表现的关键。

#### 1. 欠触发
表现：本应激活却未激活。
数据提示：Vercel 的评估显示，若缺乏明确指引，Agent 有 56% 的概率完全忽略现有 Skills。
根源：description 过于技术化、学术化，与用户自然的口语之间存在语义鸿沟。
补救思路：用用户的语言“翻译”一遍。在 description 中大量植入用户常用的表达，涵盖术语同义、口语化说法，甚至常见误用，比如很多人混淆 “Swagger” 与 “OpenAPI”，两者都要写进。

#### 2. 过触发
表现：Skill 在不该启动的场景下被错误激活。
根源：description 定义过宽，包含大量高频通用词，导致匹配阈值过低。
补救思路：引入负向约束。明确划定边界，使用 Not for... 句式排除干扰项。

> 示例：“Not for general code questions or debugging. Only for structured documentation generation.”（不适用于通用代码提问或调试，仅用于结构化文档生成。）

为验证触发是否准确，可构建 10～20 个测试用例，兼顾应触发与不应触发。

应触发示例：
- “帮我生成 src/api/ 的接口文档” → 期望触发
- “写一份 OpenAPI 规范” → 期望触发
- “document the REST endpoints” → 期望触发
- “帮我写 Swagger” → 期望触发

不应触发示例：
- “帮我 debug 这个 API 调用” → 不应触发
- “这个接口为什么返回 500 ？” → 不应触发
- “优化一下这个 API 的性能” → 不应触发

验收标准：相关任务触发率需 ≥90%，无关任务误触发率需 ≤5%。

### 3.4.4 参考型 Skill 与任务型 Skill：两种设计哲学

disable-model-invocation 字段定义了两种截然不同的交互模式。

#### 1. 参考型 Skill
配置：默认。
核心逻辑：按需加载的知识库。Claude 会依据上下文自动判断是否需要，description 作为触发条件并注入上下文。
适用场景：提供知识、规范、框架或标准。用户无需感知 Skill 存在，Claude 会在合适时机自动“查阅手册”。
示例：API 设计规范、代码审查清单、行业标准文档。

#### 2. 任务型 Skill
配置：显式设置 disable-model-invocation: true。
核心逻辑：受控执行工具。Claude 无法自动触发，必须由用户通过 /skill-name 命令手动调用。description 仅作为命令行选择时的说明，不注入上下文。
适用场景：存在副作用的操作，需要明确授权。
示例：/commit、/deploy、/notify。

表 3-4 参考型 Skill 与任务型 Skill 的对比

| 维度 | 参考型 Skill | 任务型 Skill |
| :--- | :--- | :--- |
| Claude 自动触发 | 能（基于语义匹配） | 不能（必须手动） |
| 用户/触发 | 能 | 能 |
| description 作用 | 触发条件（注入 Claude 上下文） | 仅供用户识别（不注入 Claude 上下文） |
| 消耗 Token 预算 | 是（自动加载即消耗） | 否（仅手动调用时消耗） |
| 典型场景 | 知识提供、规范查询 | 动作执行、副作用操作 |
| 经典案例 | API 规范、审查清单 | /commit、/deploy |

> 咖哥发言：这里的副作用指操作不仅返回结果，还会改变系统外部状态。比如提交代码会改写 Git 历史，部署应用会改变线上状态，发通知会真的发消息。一旦执行就影响真实世界且多不可逆，所以这类 Skill 要用户显式触发，不能让模型自行决定。

小冰问：“一个任务该做成参考型还是任务型？”
咖哥答：
“用‘最坏情况测试’来决定：如果 Claude 自动执行，最坏会怎样？
若结果令人不安，例如自动提交未测试代码、自动部署带 bug 版本、自动删除生产数据、自动发送错误通知，必须选任务型，设置 disable-model-invocation: true，把控制权牢牢握在用户手中，只有输入 /skill-name 时才执行。
若结果影响不大，例如多展示一段参考文档、多给一条建议、稍增 Token 消耗，可选参考型，让 Claude 按需智能加载。
> 核心原则：副作用越大，控制越要收紧。任何可能改写状态、造成不可逆后果的操作，都不要交给自动判断。”

## 3.6 allowed-tools：用知识框定权限
allowed-tools 是 Skills 安全架构的核心。它体现的设计原则是：知识应当约束行动。
权限配置要基于 Skill 对业务逻辑的“认知”。

代码审查 Skills：只读代码，严禁修改，故只授予只读工具。
文档生成 Skills：可创建新文件，但绝不篡改已有文件，故只给写入权限，禁止编辑权限。
测试运行 Skills：仅执行特定测试命令，故精确限制可执行的 Bash 命令，防止任意注入。
