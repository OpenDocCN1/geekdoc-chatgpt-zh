子智能体分工与安全机制

让多个子智能体协同工作，关键在于自动匹配、最小权限和精准选型。下面拆解一套可落地的组合方式。

自动分派任务的底层逻辑
当用户给出具体指令，比如“帮我审查一下这个 PR”，主智能体不会硬编码路由，而是先盘点已注册的子智能体。盘点依据是每个子智能体在描述文件里写的 description 字段。随后主智能体把用户意图和这些描述做语义上的相似度比对，判断当前需求是否落在某个子智能体的能力范围内。一旦匹配程度很高，例如 code-reviewer 的描述覆盖“代码审查”“安全审计”等关键词，主智能体就会把完整的任务上下文打包，直接转交给该子智能体执行，全程无需用户手动指定名字。

安全基石是工具白名单
tools 配置是子智能体机制里最值钱的安全设计，它在系统层贯彻最小权限原则。以前面提到的 code-reviewer 为例，其可用的工具只有三个只读操作：Read 读取文件内容、Grep 在文件中按模式查找、Glob 匹配文件路径。白名单之外的能力，比如 Edit、Write、Bash，对该子智能体来说完全不可见、也不可调用，从根源上避免越权操作。

模型选择是隐形成本杠杆
model 字段常被忽视，实际是成本与质量的平衡点。处理格式校验、日志过滤这类简单且模式化的工作，选用 Haiku 这类轻量快速的模型就够了；面对架构设计、安全审计等需要深度理解与复杂推理的场景，则更适合 Sonnet 或 Opus 这类高性能模型。合理搭配既能压住开销，又能保证交付质量。

权限模式提供第二层保障
permissionMode 用于调节权限边界。设为 plan 时，子智能体进入系统级只读保障状态，这比单纯的工具白名单更严格，是全局性的安全兜底；默认值 default 则沿用常规的权限控制流程。

执行型子智能体的不同取舍
再看一个偏执行的例子——测试运行器。和代码审查专家不同，它必须调用 Bash 来执行测试命令，所以工具权限相对更宽，但对输出规范的要求更严。

[PRE0]
你是一名测试执行专家。你的核心价值是从海量测试输出中提炼关键信息，为主对话提供精准的测试摘要

## 执行流程

1. 确认项目的测试命令（查阅 package.json 或 CLAUDE.md）

2. 运行测试套件

3. 分析输出结果，区分通过和失败的测试用例

4. 针对失败的测试，定位具体失败原因

## 输出格式（严格遵守）

### 测试摘要

- 总计：x个测试

- 通过：x个

- 失败：x 个

- 跳过：x 个

### 失败详情（仅列出失败的测试）
[PRE1]
### 建议

> [ 如果存在明显的失败模式，请给出修复方向 ]

注：输出中严禁包含完整的测试日志，仅需要输出上述格式的摘要信息
