#### 8.1.9 LangChain到LangGraph的平滑过渡

LangChain 在 2023 年就聚集了活跃的社区来定义大模型应用规范，至今已发布三个大版本，其构建体系里最核心的两块是 RAG 与 AI Agent。构建 AI Agent 的底层结构见图8.12。

[PRE7]

在 LangChain 框架中，AI Agent 的内部被拆成 Agent、Message、Toolkits 三大要素。每个 Agent 通常由大模型 + 提示词 + 输出解析器组成，形成一个 Chain 来处理用户输入。Agent 可接收的输入有三类：原始用户输入 Input、子任务的模型响应 Model Response、以及携带上下文的 Context。输出端则接入工具库，具体调用哪些工具由 Agent 拆分后的子任务决定。大模型调用外部函数分为识别工具和实际执行两步。Messages → AI Agent → Toolkits 的流程负责拆解子任务、定位工具、提取名称与参数，可视为静态执行流程。把决策落地的执行工作则交给 AgentExecutor。

总体来看，LangChain 的 AI Agent 架构里，Agent 负责接收输入并决定做什么，但并不亲自执行，执行由 AgentExecutor 完成。只有 Agent 作为决策核心与 AgentExecutor 作为运行时结合，才能构成完整 Agent。AgentExecutor 调用 Agent 并执行其指定的工具，从而实现整体功能。

LangChain 至今仍是搭建大模型应用的前沿框架。v0.3 版基本完成从传统类到 LCEL 的过渡，让分步操作序列即“链”的定义与执行更简洁高效。专业角度看，LangChain 构建的是一个有向无环图 DAG。随着 AI 应用尤其是 AI Agent 的发展，对大模型的使用正从单纯工具调用转向更复杂的推理引擎，这正是 LangGraph 诞生的根本原因。更多循环与复杂条件交互的需求，使得基于 LCEL 的线性序列在构建更高级系统时逐渐受限。

#### 8.1.10 LangGraph构建AI Agent的底层原理

##### 1. LangGraph

从名字看，LangGraph 与 LangChain 关系紧密。实际上 LangGraph 是基于 LangChain 表达式语言构建的框架，专门用来开发 AI Agent。因此在大模型接入与 Agent 构建上的优势，可自然迁移自 LangChain。从技术本质看，大模型本身无法采取行动，只能输出文本，接收输入并给出响应。

##### 2. LangGraph的基础图结构模型

在图式框架里，任何可执行逻辑都能作为对话、Agent 或程序的启动点。启动点可以是大模型 API、基于大模型的 AI Agent，或通过 LangChain 等实现的线性序列，如图8.13 中的“Start”圆圈。无论形式如何，它首先处理用户输入并决定后续操作。图8.13 展示了一个基于 LangGraph 概念的基础 Agent 模型。

LangGraph 中所有带执行逻辑的组件都被视为节点 Node，包含模型调用、搜索操作、条件判断等。图中“Start”节点作为入口，接收用户输入并按需执行：

- (1) 调用工具 Action 节点做外部信息查询，如 Web 搜索、数据库查询或 RAG 检索。
- (2) 将获取的信息传给语言模型 LLMs 节点，生成自然语言响应。
- (3) 最终把响应送至终点 End 节点，完成链路。

如图8.13 所示，每个圆圈是一个节点，每条连线是一条边 Edge，用于控制流程方向；状态通过消息沿边更新。

因此无论 Agent 设计多复杂，最终都是节点与边特定组合的图结构。工作流核心在于节点完成任务后经由边通知下一个节点继续。简言之，LangGraph 底层的消息传递算法定义了一个通用模式：节点完成操作后沿一条或多条边向其他节点发送消息，接收方执行相应功能并把结果传给下一节点，如此循环往复。

##### 3. 条件边与Router决策机制

实际场景中 Agent 不会走固定路径，需要智能判断是否调用工具、调用哪个工具、是否直接生成答案。下面看一个更贴近现实的示例。

把 AI Agent 设为应用起点。通常 Agent 需配置一个或多个可用工具，否则功能有限，因为仅靠提示词引导大模型推理即可应付复杂问答。当 Agent 配备工具后，通过函数调用机制使用工具而非直接执行。用户问题进入 Agent 后大致有两种走向：

- (1) 不需调用工具时，Agent 直接给出针对问题的自然语言响应。例如：

    用户：你好，请你介绍一下你自己。

    AI Agent：你好，我是一个人工智能助手，可以帮助你解决问题。

如图8.14 所示，经过首个 Agent 节点后，若需调用函数，该用哪个工具、传哪些参数？多工具情况下 Action 节点会出现多条路径。LangGraph 引入了条件边组件，根据是否满足特定条件决定走向，如决定是使用搜索工具还是直接给出最终答案。为管理这些决策，使用了类似 if-else 的 Router。基于 Router 的判断，Agent 可能导向网络搜索 Web Search 节点执行搜索并返回原文，或直接前往终点 End 节点获取格式化自然语言响应。若走搜索路径，答案文本还需经另一个大模型处理以生成可读响应；若直接回答，则可用专门工具格式化输出。

LangGraph 中 Router 以 if-else 形式决定路径，主要依赖三种方式：

- 提示工程：指示大模型以特定格式回应。
- 输出解析器：通过后处理从模型响应中提取结构化数据。
- 工具调用：利用大模型的内置工具调用功能生成结构化输出。
