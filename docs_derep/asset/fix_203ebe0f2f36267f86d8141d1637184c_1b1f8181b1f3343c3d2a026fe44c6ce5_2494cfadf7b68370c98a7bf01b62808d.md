LangGraph 依托 LangChain 生态构建，强调以图状态机为核心的可控编排，偏向工程落地。企业级验证典型是 Klarna 的客服机器人，基于该方案支撑超 8500 万活跃用户，问题解决耗时被压缩约八成。借助 LangSmith 可实现全链路观测与故障定位，检查点机制则让长周期工作流具备状态快照与恢复能力。

CrewAI 秉持角色扮演理念，为每个智能体划定明确角色与职责以达成分工。该方案不绑定 LangChain，整体实现更轻巧。GitHub 累计星标超过 32000，月度下载量接近百万，已形成活跃社区。主要场景集中在客服自动化与内容生产流程。

MetaGPT 将传统软件研发组织的分工映射到智能体体系，从产品经理到研发工程师实现完整角色闭环。框架可把需求分析到代码实现的端到端流程自动化，体现了多智能体在复杂知识工作中的潜力。

MCP 由 Anthropic 于 2024 年底发布，定位为 AI 应用与外部工具及数据源之间的标准接口。可类比为“AI 领域的 USB-C”，它解决了 AI 模型接入多类工具时面临的 M×N 集成难题。MCP 采用客户端-服务器架构，基于 JSON-RPC 2.0，支持资源访问、工具调用、提示模板与采样指令四类核心原语。目前国内主流模型已广泛支持，通义千问 Qwen3 原生支持 MCP 协议，豆包经火山引擎提供 MCP 服务，阿里云百炼首批上线高德、Notion 等 50 余款 MCP 服务，魔搭社区亦设立 MCP 广场供开发者使用。

A2A 由 Google 于 2025 年 4 月发布，专注智能体间的通信与配合。与 MCP 聚焦智能体-工具连通不同，A2A 关注智能体-智能体互操作。核心设计包括 Agent Card、任务管理、消息传递与能力发现等。Agent Card 是一个置于 .well-known/agent.json 的标准化元数据文件，描述智能体的能力、端点与认证要求，便于其他智能体发现与评估配合可行性。A2A 已获 Salesforce、Accenture 等 50 多家技术伙伴支持，并以开源项目形式加入 Linux 基金会。

MCP 与 A2A 是互补关系。MCP 解决智能体与工具的垂直连接，A2A 解决智能体间的水平配合。构建多智能体系统时二者可组合使用，形成完整互操作能力。跟踪两大协议的标准化进展，对把握技术方向具有重要意义。

# 第2章 Agent的协同通信机制

传统多智能体系统的通信依赖严格定义的协议与消息格式。大模型时代彻底改变了这一范式。基于 LLM 的智能体能够像人类一样用自然语言交流，不仅降低了系统构建复杂度，更赋予了前所未有的灵活与适应性。本章将深入剖析协同通信的核心机制。

## 2.1 基于自然语言的Agent协同

【学习目标】

- 1) 理解自然语言协同与传统协议通信的本质区别
- 2) 掌握Prompt链的设计原则和实现方法
- 3) 学会上下文窗口的管理策略
- 4) 能够通过System Prompt定义Agent角色

自然语言协同是 LLM-based Agent 相较传统 Agent 的核心差异，使交互从刚性协议转向柔性对话。

### 2.1.1 从协议到对话：协同范式的转变

传统多智能体系统的通信建立在严格的协议规范之上。以 FIPA-ACL 为代表的通信语言，要求智能体遵循预定义的消息类型、语义规则与交互协议交换信息。该方式虽保证了确定性与可验证性，却限制了扩展性与表达力，新增场景需扩展协议规范。

LLM-based Agent 的出现从根本上改变了局面。LLM 具备自然语言理解与生成能力，智能体可直接使用人类语言交流。这不仅是格式变化，更是协同范式的革新。在自然语言协同模式下，智能体无需预先约定结构，可随上下文动态调整表达；能理解隐含意图，而非仅解析显式指令；面对未预见情况，可通过对话协商求解。

图2-1 清晰对比了传统协议通信与自然语言通信两种模式。

从图2-1可见，传统协议通信要求严格遵循预定义消息格式，如 FIPA-ACL 的 performative 结构，机器解析方便但限制表达。自然语言通信则允许使用人类可读语句交流，降低开发门槛，同时使智能体能表达复杂意图与上下文信息。

自然语言协同并非没有挑战。缺乏形式化约束可能导致理解偏差，语言模糊性或带来执行不确定性。因此实际设计中常通过精细的 Prompt 模板与对话协议规范交互，在保持灵活性的同时确保通信可靠性。

### 2.1.2 Prompt链：Agent间的对话设计

Prompt 链是实现多智能体协同的核心模式。与单次 Prompt 调用不同，Prompt 链将复杂任务拆解为多个关联步骤，步骤输出成为下一步输入，形成完整处理流程。在多智能体场景下，Prompt 链既连接同一智能体的多次调用，也串联不同智能体间的配合。

Prompt 链设计遵循若干原则：单一职责原则要求每个节点只负责明确子任务，避免过度复杂；接口清晰原则要求明确输入输出格式，确保数据传递准确；容错设计原则要求在链路中设置验证点与回退机制，节点失败时可优雅处理。
