图驱动的Agent：LangGraph节点、边与状态解构

最简形态下，Agent 运行可拆成三段。首段由动作单元向外取数，比如 Web 查询、数据库读取或 RAG 召回。其次把取回的材料交给大模型单元，将原始信息转成自然语言回复。末段把该回复送至 End 单元完成一次调用。

见图8.13，这是用 LangGraph 概念搭建的最小样例。图中圆点即处理单元，连线即控制走向的边；状态沿边流动，通过消息不断刷新。换句话说，无论设计多复杂，本质都是若干单元按特定方式组合，再由边编排顺序。工作流的核心在于单元完成后经由边通知下一环节继续推进。概括起来，LangGraph 底层消息传递定义了通用程序的运行范式：单元完成操作后沿一条或多条边投递消息，接收方执行相应功能再把结果传给下一个单元，如此循环往复。

##### 3. 条件边与Router决策机制

真实场景里 Agent 不会走死板的直线，需判断是否调用工具、调用哪项、或直接给出答案。下面看一个更贴近实用的例子。

这里把 AI Agent 当成应用入口。组建可用 Agent 通常需配置一到多个工具，否则能力受限，因为即便问题再复杂，仅靠提示词让大模型如 o1 自行推理也能应付部分。当工具就位后，Agent 通过函数调用去使用它们，而不是直接执行。用户原始问题进入 Agent 后，大致分两种走向。

（1）不需要工具时，Agent 直接给出自然语言的回答。例如：
用户：你好，请你介绍一下你自己。
AI Agent：你好，我是你的 AI 助手，可以帮你解决各种问题。

（2）需要工具时，输出会变成特定格式的 JSON，用来指明要调用的函数名和参数。例如：

见图8.14，在 Agent 单元之后，若模型判断需要调用函数，下一步该走哪条路、带什么参数？当可选工具不止一个时，动作单元会呈现多条备选路径。如何抉择？LangGraph 提供了条件边这一组件。条件边依据是否满足特定条件来决定分支，例如决定是用搜索工具还是直接产出最终答案。为了统一管理这类判断，会使用类似 if-else 的结构，即 Router。依 Router 的决策，Agent 可能被导向网络搜索单元执行检索并返回原始文本，也可能直达最终答案单元得到格式化后的自然语言。若走搜索分支，拿到的文本还需经另一轮大模型处理才能变成用户可读的回复；若走直接回答分支，则可调用专门的格式化工具。

在 LangGraph 里，Router 以 if-else 形式判定路径，主要有三种实现手段。
- 提示工程：要求大模型按固定格式给出判断结果。
- 输出解析器：对大模型回复做后处理，抽取出结构化数据。
- 工具调用：借助大模型内置的工具调用能力直接产生结构化输出。

##### 4. 共享状态机制

我们已经知道 LangGraph 靠单元和边组合出复杂的循环流程，靠消息传递把各单元串成通路。而让消息及时更新并送到正确位置，则依赖 LangGraph 的状态概念。每次执行启动一个状态图，单元在处理时会读取、修改这一状态。该状态并非静态数据集合，而是随各单元输出动态演进，进而影响循环中的后续行为，如图8.15所示。

共享状态指的是图运行期间单元间传递的数据与信息。LangGraph 允许单元在执行时通过读写同一个公共状态来交互。这种机制让单元可以基于共同维护的数据通信、交换信息并相互影响行为。借助共享状态，LangGraph 能协调单元间的操作、实现同步，支撑动态交互与复杂工作流的搭建，使各单元可依据已有信息协同工作并做出决策。

##### 5. 官方对LangGraph的定位与优势总结

按官方定义，LangGraph 是一个用于构建有状态、多角色参与应用的库，可用来创建 Agent 与多 Agent 工作流。官方归纳的核心优势如下。
- 循环与分支：在应用中实现循环和条件判断。
- 持久化：每一步执行后自动保存状态，可随时暂停恢复，支持错误恢复、人机协作、时间回溯等。
- 人机交互：可在图形执行中中断以审批或编辑 Agent 下一步计划。
- 流式输出：每个单元均可产生流式输出，包括 token 流。
- 与 LangChain 集成：与 LangChain 和 LangSmith 无缝衔接。

（1）用户输入问题，对应图中的①。
（2）进入检索单元做信息检索，对应②③④。
