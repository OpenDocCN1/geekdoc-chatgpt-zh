**OpenClaw 稳定运行与省钱进阶指南**

**建议一：先看状态，再开日志**
遇到问题别急着翻日志，先跑一次 status 命令确认网关是否在线、通道是否已连通。这样几秒钟就能判断是服务层还是渠道层的问题，避免盲目排查。

**建议二：开一个窗口一直跟日志**
写代码或测试时，单独开一个终端执行 openclaw logs --follow，让日志实时滚动。异常一出现就能立刻抓住报错点，省去反复刷新。

**建议三：每周主动体检一次**
养成每周运行一次 doctor 的习惯，提前揪出配置漂移、依赖缺失等潜在风险。等故障发生了再检查，成本更高。

**建议四：改动前先记变更**
每次调整配置前，用笔记或提交记录写下改了什么。回溯时可以快速判断是不是这次改动引发的异常。

**建议五：单点修改，单点验证**
不要一次性改多处配置再统一测试。一次只改一个参数，改完就验证，确认正常再进行下一步，出问题也能马上定位源头。

**建议六：把报错丢给搜索和 AI**
看不懂的错误信息，直接复制完整日志去社区或搜索引擎检索。OpenClaw 社区活跃度高，多数常见问题都有现成解法。实在拿不准时问 AI 也不错，大部分“突然不行了”的情况就集中在几类：配置被改动、认证过期、网络不通、权限变更、端口冲突。按这套路径过一遍，九成问题能自己解决，剩下的疑难杂症再去 GitHub 或社区求助。

### 6.6 本地模型与云端模型混搭更省钱

用 OpenClaw 久了，API 账单会慢慢变重。月费几百元还好，重度使用、定时任务或批量处理时，费用很容易飙到上千。这时候就会考虑本地模型。

本地模型完全免费，电脑配置够就能跑 Qwen、DeepSeek、GLM 等开源模型。但质量不及顶级云模型，对硬件要求高、启动慢、占内存。

最划算的做法不是全云也不是全本地，而是混着用。

## 第六章 用熟之后玩得更溜

混用云模型和本地模型不是炫技，而是实实在在的省钱策略。Fallback 链设置好，强模型该用时用，能省时省，既保质量又控成本，这才是会养虾。

### 6.7 API 费用失控？省钱实操指南

刚开始月费几十元还能接受，用几个月后费用明显上涨。更糟的是定时任务进入循环推理，一晚上就能把余额烧光。社区里这类“恐怖故事”不少，省钱是必修课。

#### 6.7.1 看清成本构成
很多人只盯模型单价，换便宜模型就以为省了。实际成本是：
总成本 = 调用次数 × 每次 token 数 × 模型单价
三个变量失控都会导致账单爆炸。降单价只是其一，次数和上下文长度同样关键。

#### 6.7.2 第一招：自动降级省开销
官方最核心的省钱策略是主模型 + 备选链。

[PRE7]

机制：
- 正常用主模型 Claude Sonnet
- 主模型限流或任务简单时自动降到 Haiku
- 仍不行继续降到 DeepSeek
每级更便宜，质量相应递减。复杂任务保质量，简单任务自动省钱，无需人工判断。

注意不要盲目追求最便宜，降级链是自适应选择，不是全切最低价。

#### 6.7.3 第二招：精简上下文
上下文越长，单次 token 消耗越大。

[PRE8]

精简 Bootstrap 文件

官方限制：单个文件最多 20 000 字符，总注入上限 150 000 字符。优化方式是删除赘述、重复示例和过时信息，只留核心规则。

定时任务如心跳、提醒、自动爬虫，24 小时不停跑，绝对不能用强模型。

检查 HEARTBEAT.md 或任务配置，换成 DeepSeek、通义千问或本地 Ollama。重复性检查、抓取、提醒用普通模型足够。

#### 6.7.8 第七招：子 Agent 降配
主 Agent 用强模型做规划与整合，子 Agent 用普通模型做并行检索与提取。复杂推理保质量，重复劳动控成本。

**省钱小结**
建议一：先设预算上限，是最后安全网。
建议二：每周复盘用量，找异常峰值。
建议三：测试功能时用本地模型，验证通过后再切云端。
建议四：杜绝循环调用，仔细检查定时任务与 Skill 逻辑。
建议五：80% 日常任务用普通模型，创意写作与复杂推理才上顶级模型。
建议六：关注价值成本比，不是越省越好，而是每一分钱花在刀刃上。
