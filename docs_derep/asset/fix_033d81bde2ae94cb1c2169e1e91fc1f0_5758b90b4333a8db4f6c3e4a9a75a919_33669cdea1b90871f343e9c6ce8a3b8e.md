当检索增强的提升空间被压缩到极限时，业界常会把目光投向模型微调。提示工程与 RAG 本质上是对外层的修补，而微调则是直接触及模型内部参数，让它在特定任务、特定行业或特定使用场景里具备更强的契合度。

微调所依托的是与 RAG、智能体开发完全不同的技术体系，核心在于深度学习与训练调优。本书不会对这部分展开细谈。在实践层面，绝大多数停留在应用层的模型工作，也基本在微调处止步。

微调与检索增强并非水火不容。借助合适的微调策略，可以把大模型嵌入具体业务语境，从而带动整个 RAG 流程的效能提升。

## Agent 与 RAG 合流：双引擎驱动
智能体与检索增强正在成为大模型落地的两条主线并加速交汇。智能体的主动属性体现在它能自主执行、调用工具并与外界交互；检索增强则持续为其补给动态的外源知识。两者叠加后可孕育更强的智能体：既能办事，也能在决策前主动查证。以客服场景为例，基于检索增强的智能体会实时调取最新产品资料或用户历史，输出更精准、更贴合上下文的回复。

## MCP 与 A2A：正在加速的未来
这种融合在 MCP 与 A2A 协议的标准化接口加持下被进一步放大。MCP 为智能体与检索系统提供统一的外部数据与工具接入口，打破模型与企业内部数据库、API、知识库之间的壁垒，实现无缝对接。A2A 则定义了智能体间的通信规范，解决了多智能体协作的沟通难题，让来自不同生态的智能体可以用同一种“语言”协作，完成复杂任务。

例如，一个基于 AutoGen 的财务分析智能体可以通过 A2A 与 LangGraph 驱动的市场预测智能体协作，实时共享任务状态，并结合检索增强获取的实时市场数据，共同生成综合报告。这种多智能体协作与知识增强的叠加，正在把单一的 AI 应用推向分布式、模块化的智能生态，重塑应用边界，从单体智能迈向协同智能网络。

MCP 与 A2A 的出现，让检索增强与智能体的应用像细流汇成江河，为大模型应用开发注入新动能。未来的系统不再是孤立的模型或产品，而是由众多智能体和知识模块构成的动态网络。开发者可以以前所未有的便捷，把智能体、检索增强、MCP、A2A 整合成业务可用的、高效灵活且易扩展的方案。

智能体既能通过检索增强获取知识，也能通过 A2A 与其他智能体协同，并借助 MCP 接入全球化的数据与工具资源。在这一生态里，创新会以指数级速度涌现，企业与个人都将共同见证 AI 潜力的全面释放。

从简到繁、从通用到专业的演进路线，正是当下大模型应用浪潮的底层内核。作为开发者，需要在这条路上持续学习、实践与创新。既要夯实经得起时间考验的基础，也要敏锐捕捉新技术带来的机遇与挑战，真正释放大模型的价值，做出对个人有用、对企业实用、甚至能改变世界的应用。

检索增强是这条路径的核心技术，潜力巨大且入门坡度相对平缓，但技术栈覆盖面极广，实现过程也藏着不少难点。数据导入要处理多源异构、清洗与标准化要高效；查询预处理中的 Text2SQL 要把自然语言准确转为结构化查询，以应对复杂模式与动态需求；索引的构建与优化则要在语义准确性、查询速度与动态更新之间找平衡。这些难题构成了检索增强开发的核心攻关点。

在大模型时代，下定决心深挖某项技术内核是有风险的，未经充分验证的技术可能很快过时。时间有限而知识海量，选择学习内容与方法必须更审慎。感谢你的信任，接下来让我们一起打开检索增强的大门，探索它带来的无限可能。

### 一问 从实际项目展示到底何谓RAG
## 何谓RAG? 图0-2 RAG的工作流程
检索增强生成是一种提升大模型回答质量与准确性的技术思路。简单说，它把语言模型如 GPT 类模型与检索系统如向量数据库结合，让模型在生成时能直接调用与用户问题相关的外部知识或文档。检索增强的工作流程如图0-2所示。

[PRE5]
检索增强的大致流程如下。

（1）嵌入与索引：在准备阶段，先对一批文档如新闻报道、博客文章、分析报告等做分块处理，并把文本块转为嵌入向量。这些向量存入向量数据库中以便后续检索，也称索引。

（2）用户输入：用户提出问题或查询。例如：“《黑神话：悟空》是什么类型的游戏？”

（3）检索：提交查询时，系统把问题转为查询向量，在向量库中检索最相关的文本块。这是检索增强的核心，先找信息再回答。

（4）生成并输出：把原始问题与检索到的文本块一起传给大模型。模型在上下文支持下融合用户问题与检索信息，生成更准确的回答。此时回答既依赖模型参数与训练记忆，也结合了更新、更权威的外部资料。

检索增强把信息检索与文本生成结合，让回答更有依据、更贴上下文，从而提升质量、可靠性和时效性。

检索增强系统到底长什么样、怎么设计？用 LangChain、LlamaIndex、Dify 或 Ragflow 等框架 30 分钟就能搭一个，但会掩盖大量底层细节，不利于深入探究。

实际上咖哥手工构建了一个简易且自主的检索增强框架

关于检索增强框架完整代码示例，请访问咖哥的 GitHub 仓库 https://github.com/huangjia2019/rag-project01-framework。

该框架不依赖 LangChain 或 LlamaIndex 等开源框架，有利于在项目中调试不同配置，对比文档导入、分块、向量库、嵌入模型与生成模型，选择更合适的方案，也有助于理解系统设计细节。

## 文档的导入和解析
此阶段需把原始数据如 PDF、纯文本、HTML 甚至图片中的文字加载到系统，以便后续分块处理。就像图0-3展示的界面一样，这个简易系统支持从本地上传 PDF，并按不同解析方式加载文档。目前支持 PyMuPDF、PyPDF、Unstructured 等解析工具，当然也可以扩充更多。

图0-3 文档的导入和解析

[PRE6]
不同解析工具各有特点。实际项目中文档格式、结构与排版差异，会导致文本提取质量不同。下面列举三款工具的特点。

- PyMuPDF：基于 MuPDF 引擎，对 PDF 解析准确高效，但在复杂排版下可能出现字符错位或换行混乱。
- PyPDF：更基础的 Python PDF 解析工具，对简单 PDF 处理良好，但在扫描版 PDF 或复杂格式文件上解析质量可能不如 MuPDF。
- Unstructured：不仅能解析 PDF，还支持 HTML、Word、邮件等多种格式，并提供更细致的结构化输出。对非 PDF 文档或需要控制标题、段落、列表等结构时优势明显。

在《黑神话：悟空》问答系统中，会把游戏官方设定文档、媒体采访稿、预告片文案及相关背景资料通过这些工具载入。各类文件的载入方式、解析工具使用，包括表格、图片等细节，后续内容会详细讲解。

## 文档的分块
文档导入并解析为纯文本后，下一步是对文本做合理切分（见图0-4）。检索增强生成时，大模型需要从外部存储迅速找到与查询最相关的片段。常用做法是把长文档切成较小的文本块，每个块可能含几百字符或几句话。图0-4 文档的分块

[PRE7]
## 为何要进行分块？
长文档无法一次性全部塞入大模型上下文，即便能塞也极耗资源。切块后可对每个块独立做嵌入与向量索引。检索时只需计算用户查询向量与块向量的相似度，就能快速定位最相关段落。

此外存在多种分块策略，如图0-5所示。例如 PDF 可按页码分块，保留版面与分页逻辑；也可按固定字符或 Token 数切分，均衡控制块大小，便于嵌入计算。但这种方式可能破坏句子或段落的语义完整性。更符合语义的做法是按自然结构如段落、句子切分，使检索内容更连贯，更易被大模型理解。图0-5 分块策略

[PRE8]
选择分块策略时，需在语义完整性与检索粒度间求平衡。具体细节后续会详细讨论。

## 向量数据库的选择
文本块转向量后存于何处？向量数据库登场。此阶段咖哥会把文本块向量及其元数据如所属文档 ID、段落位置、主题标签等写入向量数据库。

向量数据库可选方案如图0-7所示。

- Faiss：Meta 开源的轻量级向量检索库，适合本地快速搭建。
- Pinecone、Weaviate、Qdrant：云端或本地先进方案，提供丰富 API 与可扩展性。
- Milvus：国产开源向量数据库，提供大规模相似度检索优化。

图0-7 向量数据库的选择

做原型时可先用 Faiss 或 Chroma 这类简单易用的库快速迭代调试；准备生产部署时再切换到 Milvus 及其托管版 Zilliz Cloud 等更强大的方案。

索引是向量数据库用于高效存储与检索嵌入向量的底层数据结构。它通过组织向量数据，让大规模数据中查找相似向量既快又省资源。大多数向量数据库支持多种索引结构。
