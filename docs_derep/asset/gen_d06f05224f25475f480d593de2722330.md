#### 2.2.3 在线大模型API关键参数说明

主流平台的对话接口大多沿用OpenAI ChatCompletion的设计思路，参数结构基本一致。下面对这些常用参数做梳理，帮助更好地把控输出效果。

##### 1. model：模型选择与指定

同一家族往往包含多个版本，model参数用于明确具体使用哪一个，是必填项。各平台支持的命名各异，常见例子见表2.1。

表2.1 不同平台支持的模型名称

| :--- | :--- |

| OpenAI | gpt-3.5-turbo、gpt-4、gpt-4-turbo、gpt-4o |

| DeepSeek | deepseek-chat、deepseek-coder |

| 阿里 DashScope | qwen-turbo、qwen-plus、qwen-max |

| 智谱 BigModel | glm-4、glm-4v |

##### 2. messages：对话上下文

messages为必填项，是构成对话上下文的主体，格式为字典列表，包含三种角色。

1. system：用于定义AI的身份或行为边界。
2. user：用户输入内容。
3. assistant：AI过往回复，用于维持多轮上下文。

##### 3. temperature：生成多样性

temperature控制输出的随机程度。OpenAI系模型标称范围0.0～2.0，而国内DeepSeek、Qwen、GLM的标称范围多为0.0～1.0。

在问答、代码编写等任务里通常取接近0的值，让结果更确定保守；在故事创作类任务里倾向取较高值，让文本更灵活生动。一般不会取到极值，高温下容易跑偏出现怪句。

##### 4. max_tokens：回复最大长度限制

max_tokens限制单次响应的最大生成token数，即输出上限。

> **注意**
需要区分token与字符，一个中文字符可能对应多个token。此外max_tokens指单次响应的长度，而非整段对话的总量。

不同模型的上下文窗口不同，支持的max_tokens范围也有差异。max_tokens与messages历史总token数之和不能超过窗口限制，否则调用失败。主流模型普遍支持128K上下文，但实际中大部分token被历史消息占用。

设得过高会浪费配额，设得过低会导致截断。简单问答或检索约100～300，摘要或翻译约200～512，内容创作约800～2000，代码生成或分析约500～1500。可结合上下文长度、目标和成本多次调试。

##### 5. top_p：核采样策略

top_p取值0.0～1.0，是控制多样性的另一方式。与temperature调整概率分布不同，top_p采用累积概率采样，即按候选token概率从高到低累加，选择总概率不超过阈值的前若干token，再在此集合中采样。

top_p=1.0不做剪枝，采样范围最大，创意强但不稳定；top_p=0.9只从累计前90%的token中采样；top_p=0.1接近贪心采样，输出稳定重复性高。

> **注意**
通常不建议同时大幅调整temperature与top_p，避免过度控制导致输出异常。

### 2.3 本地大模型部署及使用

本节围绕本地部署的核心流程，介绍算力资源与环境依赖，涵盖模型下载、推理测试等关键环节，并与主流第三方部署工具做对比，为后续Agent开发提供运行基础。

#### 2.3.1 本地大模型部署需求概览

因数据安全、访问稳定性、成本控制、模型可控性等需求，越来越多的开发者和企业选择将大模型部署在本地或私有云。本地部署能掌控推理过程、降低隐私泄露风险、减少长期接口费用，并提升响应速度与离线可用性。同时部署门槛更高，需在动手前对以下关键需求做评估。

##### 1. 算力资源

在所有部署条件中，算力尤其是GPU是运行大语言模型的决定因素。轻量场景可尝试CPU模拟推理，但速度远逊GPU，对中大型模型基本不可行。

> **说明**
>
> 为什么不能只用CPU？
>
> 大语言模型推理涉及十亿级参数的矩阵计算，多层Transformer中包含大量矩阵乘法、归一化、注意力计算等高强度并行任务。GPU在并行数值计算上优势明显，CPU更擅长逻辑控制与串行任务。同等条件下CPU推理速度可能仅为GPU的1/100至1/10。

推理场景下不同参数规模的显存需求如表2.2所示。

**表2.2 不同模型参数规模对应的显存需求**

| 模型规模 | 推理时显存需求（FP16） | 支持的典型GPU（单卡） |

| :--- | :--- | :--- |

| 7B | 14GB～16GB | RTX 3090 / 4090 / A500 |

| 13B | 26GB～30GB | RTX 4090（24GB）基本可运行 |

| 33B | 60GB～80GB | 多卡 A100 或 2×4090 并行 |

采用量化如INT4、INT8、GPTQ等技术，可把显存需求减少约1/4～1/2。以7B为例，FP16需14GB～16GB，INT4量化后约4GB～6GB，可在RTX3060/4060甚至笔记本GPU上运行。

当前训练或推理多基于NVIDIA GPU，因其CUDA+cuDNN+PyTorch生态成熟。主流型号如表2.3所示。

| 类型 | 常见型号 | 适用说明 |

| :--- | :--- | :--- |

| 数据中心级 | A100, H100, A800, L40S | 高稳定性、高带宽，适合集群部署 |

| 消费级高端 | RTX 3090, 4090, 4080 | 适合个人开发与小模型推理 |

| 云租用平台 GPU | Tesla V100, T4 | 支持量化模型，成本可控 |

若本地无GPU，可租用AutoDL、阿里云PAI、百度飞桨Studio、Google Colab等在线GPU资源。

##### 2. 操作系统与环境依赖

硬件到位后，还需配置操作系统与软件依赖栈。

1) 操作系统

建议优先使用Ubuntu，其作为稳定兼容CUDA的Linux发行版，对NVIDIA工具链支持全面。CentOS和Windows+WSL2也能运行部分模型，但不推荐用于生产环境。

2) 软件依赖环境（PyTorch栈）

系统运行所需依赖及安装说明如表2.4所示。

| 组件 | 推荐版本 | 安装说明 |

| :--- | :--- | :--- |

| Python | ≥ 3.9 | 建议使用 Conda 虚拟环境隔离 |

| PyTorch | ≥ 2.0 | 需安装 GPU 版本（pip/conda 安装） |

| CUDA | 11.8 / 12.1 | 与 PyTorch 安装包版本匹配 |

| cuDNN | 对应 CUDA 版本 | NVIDIA 官网下载安装或驱动自带 |

| Transformers | ≥ 4.35 | Hugging Face 的核心推理库 |

##### 3. 模型格式支持

部署前需确认目标模型是否提供开放权重、支持格式及是否有量化版本。主流格式如表2.5所示。

**表2.5 主流模型格式**

| 格式类型 | 常见后缀 | 说明 | 适用部署框架 |

| :--- | :--- | :--- | :--- |

| 原始 PyTorch 格式 | .bin | Transformers 默认格式，文件较大，占用显存高 | Transformers/vLLM/TGI |

| 安全张量格式 | .safetensors | 安全、加载更快、支持并发加载的张量格式 | Transformers/vLLM/TGI |

| 量化格式-INT4 | .bin, .pt (压缩) | 通常通过 GPTQ/AWQ 等量化工具压缩后发布 | AutoAWQ/GPTQ-for-LLaMA/vLLM |

| 量化格式-GGUF | .gguf | llama.cpp/Ollama 使用的统一格式，支持 CPU/GPU 部署 | llama.cpp/Ollama/KoboldCpp |

选定模型后，需确认是否开源、是否有Hugging Face或GitHub地址、是否提供INT4/INT8/GGUF版本，以及是否有官方或社区推荐的部署脚本或Docker镜像。
