这项设计的工程收益非常可观。`!command` 是否启用会直接改变交互效率，对比情况整理在表 3-7 中。

表 3-7 `!command` 特性未使用与使用的对比

| 维度 | 未使用 `!command` | 使用 `!command` |
| :--- | :--- | :--- |
| Claude 启动时的上下文 | 初始为空，需要多轮对话来摸清意图 | 关键信息已预先注入 |
| 首次响应的工具调用次数 | 3~5 次，主要用于信息收集 | 0~1 次，可直接进入执行 |
| Token 消耗 | 偏高 | 偏低 |
| 响应速度 | 偏慢 | 偏快 |
| 结果一致性 | 偏低，存在信息遗漏风险 | 偏高，注入内容固定可复现 |

> 咖哥提醒：执行边界必须卡死。Claude 处理 `!command` 时的时序是先把 $ARGUMENTS 变量替换掉，再去跑 Shell 命令。也就是说用户输入会原样拼进 Shell，如果不做管控很容易被注入。因此任何基于 `!command` 的 Skills，都要用 allowed-tools 精确限定可运行的命令范围，形成必要的安全围栏。

## 3.8 作用域与优先级

Skill 可以放在不同层级，不同层级决定了生效范围和适用场景，具体见表 3-8。

表 3-8 Skills 的作用范围与适用场景

| 存放位置 | 生效范围 | 典型用途 |
| :--- | :--- | :--- |
| 企业配置中心 | 全员生效 | 强制执行的企业级开发规范与安全策略 |
| ~/.claude/skills/<name>/ | 个人所有项目 | 个人编码习惯、通用工具集及跨项目辅助脚本 |
| <project>/.claude/skills/<name>/ | 仅限当前项目 | 项目特有的工作流、业务逻辑定制及团队协同规范 |
| Plugin 内置资源 | Plugin 启用时 | 社区共享的能力包、特定框架的专用指令集 |

当多个来源出现同名 Skill 时，系统按从高到低的顺序解析加载。

企业策略 > 个人配置（~/.claude/）> 项目配置（.claude/）> Plugin 内置

这个顺序呼应企业治理思路，从不可违背的底线过渡到个性化偏好。

- 企业策略即不可逾越的底线：企业级配置权限最高，用于强制安全与合规。例如安全审计类 Skill 必须强制检查 OWASP Top 10，关键规则不能被项目或个人覆盖，保证组织安全红线。
- 个人配置是效率个性化：放在个人目录的配置服务开发者习惯。比如自定义 /commit 命令按 conventional commit 生成提交信息，只影响本用户。
- 项目配置是业务场景定制：放在项目根目录的配置服务特定代码库。比如前端项目定制组件文档生成 Skill，适配自身技术栈和文档结构。

把 Skill 目录 .claude/skills/ 纳入项目 Git 版本控制，是团队知识低成本共享的好做法。

- 即插即用：新人克隆仓库后 Skill 自动生效，无需手动安装。
- 同步演进：Skill 随代码迭代更新，团队始终使用最新工作流规范。

## 代码审查流程

你是一名资深代码审查员。执行审查时，请严格按以下优先级顺序进行

### 第一优先级：安全检查

发现以下问题应立即上报：

- SQL 注入风险：直接拼接 SQL 字符串、未使用参数化查询
- XSS 漏洞：未转义的用户输入直接输出到 HTML
- 敏感信息硬编码：密码、密钥、Token、数据库连接字符串等
- 权限验证缺陷：缺少认证中间件、存在越权访问逻辑

### 第二优先级：性能问题

- N+1 查询：循环内频繁访问数据库
- 索引缺失：高频查询字段未建索引
- 重复计算：循环内可提到循环外的不变量计算
- 内存泄漏风险：未关闭的连接、持续增长的缓存等

### 第三优先级：代码质量

- 函数过长：超过 50 行且无合理理由
- 命名不规范：变量或函数命名含义不清
- 错误处理缺失：空的 catch 块、异常被静默吞掉
- 代码重复：违反 DRY 原则

### 输出格式规范

每个发现的问题必须包含 4 项要素：

- 严重等级：Critical/ Major/ Minor
- 问题描述：具体说明问题所在
- 文件位置：file_path:line_number
- 修改建议：给出具体的代码修正方案或解决策略

若未发现问题，请明确回复“通过审查”，并简要说明已检查的主要方面。

审查过程中的风险点。

- 优先级排序策略：严格遵循“安全 > 性能 > 质量”的审查顺序，确保关键隐患优先被发现，避免遗漏。
- 结构化输出规范：统一采用“严重等级 + 问题描述 + 文件位置 + 修改建议”的格式，保证结果一致且可追溯。
