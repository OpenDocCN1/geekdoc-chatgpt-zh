#### 8.1.9 从 LangChain 到 LangGraph 的迁移路径

LangChain 在2023年就聚拢起活跃的社区来定义大模型应用规范。至今已发布三个大版本，体系里最关键的两块是RAG和AI Agent。LangChain中构建AI Agent的底层结构如图8.12所示。

[PRE2]

先看LangChain框架里的Agent设计，内部拆成三大核心要素：Agent、Message 和 Toolkits。单个Agent通常由大语言模型加提示词再加输出解析器组成，形成一条Chain来处理用户输入。Agent可处理的输入来自三路：Input是用户原始提问，Model Response是模型对子任务的中间输出，Context则携带上下文信息。Agent的输出端会连到实际工具库，具体调用哪些工具由Agent拆解的子任务决定。大模型调用外部函数分两步走：先识别工具，再执行。Messages→AI Agent→Toolkits这条路径负责把任务拆解，然后在工具库里匹配对应工具并提取名称与参数，可视为一种“静态”执行流程。把决策落地为行动的工作交给AgentExecutor。

总体来看，LangChain的AI Agent架构里，Agent只负责接收输入并决定做什么动作，自身并不执行；执行由AgentExecutor承担。唯有把作为决策中枢的Agent和负责运行的AgentExecutor结合起来，才能形成完整Agent。

LangChain依然是构建大模型应用的前沿框架之一。最新v0.3版本基本完成从传统类到LCEL的关键过渡，让定义和执行分步操作序列变得更简洁高效。专业角度讲，LangChain构建的是有向无环图DAG。随着AI应用尤其是AI Agent的发展，大模型的使用正从单纯的工具执行转向更复杂的推理引擎，这正是LangGraph诞生的根本原因。新的需求带来了对循环结构和复杂条件交互的强烈诉求，而基于LCEL的线性编排在构建更高级智能系统时逐渐暴露局限。

#### 8.1.10 LangGraph 构建 AI Agent 的底层原理

##### 1. LangGraph

从名称就能看出与LangChain关系紧密。LangGraph正是基于LangChain表达式语言搭建的框架，专门用于开发AI Agent。因此在大模型接入与Agent构建上的优势可以自然迁移过来。从技术本质看，大模型本身无法行动，只能输出文本，即接收输入并给出响应。

##### 2. LangGraph 的基础图结构模型

在图式框架下，任何可执行逻辑都能作为对话、Agent或程序的启动点。该入口可以是大模型API、基于大模型构建的AI Agent，或通过LangChain等实现的线性序列，如图8.13中“Start”圆圈所示。无论形式如何，它首先处理用户输入并决定下一步操作。图8.13展示了基于LangGraph概念的基础Agent模型。

在LangGraph中，具备可执行逻辑的组件都视为节点Node，涵盖模型调用、搜索操作、条件判断等。“Start”节点作为入口，接收用户输入后可做如下处理。

- (1) 调用工具Action节点做外部信息查询，如Web搜索、数据库查询或RAG检索。
- (2) 将获取信息送入语言模型LLMs节点，生成自然语言回复。
- (3) 最终把回复传递给终点End节点，完成整条链路。

如图8.13所示，这是一个基于LangGraph概念的基本Agent示例。每个圆圈为一个节点，每条连线为边Edge，用来控制流程方向；状态通过消息沿边更新。

因此无论Agent设计多复杂，最终都是节点和边以特定方式组合的图结构。这种工作流的核心在于：节点完成任务后会经由边通知下一个节点继续执行。简言之，LangGraph底层采用的消息传递算法定义了通用程序的工作模式：节点完成操作后沿一条或多条边向其他节点发送消息，接收方执行相应功能并把结果传给下一节点，如此循环往复。

##### 3. 条件边与Router决策机制

在真实应用里，Agent不会沿固定路径执行，需要判断是否调用工具、调用哪个工具、是否直接给出答案等。看一个更贴近实际的例子。

此例把AI Agent定义为应用起点。构建AI Agent通常要配置一个或多个可用工具，否则能力有限，因为即便问题复杂，也可通过提示词引导大模型如OpenAI的o1自行推理完成。配备工具后，Agent通过函数调用使用工具而非直接执行。用户原始问题进入AI Agent后一般有两种情况。

（1）无需调用工具，Agent直接给出自然语言响应。例如：

用户：你好，请你介绍一下你自己。

AI Agent：你好，我是一个人工智能助手，可以帮助你解决问题。

如图8.14所示，经过首个节点Agent后，若认为需要调用函数，会选哪个工具、传哪些参数？在多工具可选时，Action节点会出现多条可能路径。如何选择？LangGraph引入了条件边组件。条件边根据是否满足特定条件决定走向，例如Agent可能需决定使用搜索工具还是直接生成最终答案。为管理这些决策，使用了类似if-else的结构即Router。基于Router的判断，Agent可能导向网络搜索Web Search节点执行搜索并返回原文，或直接前往最终答案End节点获取格式化自然语言响应。若走搜索路径，获取的文本还需经另一大语言模型处理以生成用户可理解的回复；若直接回答，则可用专门工具格式化输出。

在LangGraph中，Router以if-else形式决定路径，主要通过三种方式实现。

- 提示工程：指示大模型以特定格式作出回应。
- 输出解析器：用后处理从模型响应中提取结构化数据。
- 工具调用：利用大模型的内置工具调用能力生成结构化输出。

##### 4. 共享状态（State）机制

我们已知道LangGraph通过组合节点Node和边Edge创建复杂的循环工作流，消息传递串联所有节点形成通路。而保持消息及时更新并传向正确位置，则依赖LangGraph的State概念。在LangGraph流程中，每次执行都会启动一个状态，图中节点在处理时会传递和修改该状态。该状态不是一组静态数据，而是由各节点输出动态更新，进而影响循环内的后续操作，如图8.15所示。

共享状态指图执行过程中节点间传递的数据或信息。LangGraph允许节点在执行时通过共享和更新公共状态交互。这种机制使节点能基于共同维护的数据通信、交换信息并相互影响行为。借助共享状态，LangGraph可实现节点间操作协调与同步，支持动态交互和复杂工作流构建，使节点能根据已有共享信息协同工作并做出决策。

##### 5. 官方对 LangGraph 的定位与优势总结

从官方定义看，该框架是使用大模型构建有状态、多参与者应用程序的库，可创建Agent和多Agent工作流。其官方总结的优势如下。

- 循环和分支：在应用中实现循环与条件。
- 持久性：图每一步后自动保存状态，随时暂停恢复图形执行，支持错误恢复、人机交互流程、时间旅行等。
- 人机交互：中断图形执行以批准或编辑Agent计划的下一个操作。
- 流支持：流输出由每个节点生成，包括令牌流。
- 与LangChain集成：LangGraph与LangChain和LangSmith无缝集成。
