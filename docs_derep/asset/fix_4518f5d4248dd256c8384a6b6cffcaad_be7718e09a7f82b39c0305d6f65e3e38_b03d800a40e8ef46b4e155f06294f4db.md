简言之，RAG 是一种借助外部知识库来扩充 LLM 推理能力的增强范式。宏观来看，LLM 在理解与推理上具备很强能力，却受限于训练截止时间，只能基于既有公开语料作答，这种信息孤岛特性削弱了它在细分领域与时效性场景下的实用价值。若想让系统能即时调阅私有资料、按需注入背景，就必须搭建一条把高质量外部信息送进推理链路的通道，这正是 RAG 诞生的缘由。整体思路参考图 8.6。

[PRE0]

图 8.6 把 RAG 提炼为三步走。

- 索引（Index）：离线预处理环节。先对原始素材做清洗抽取，把 PDF、HTML、Word 等格式统一转成纯文本；再按上下文长度切成小块，即分块；随后用 embedding 模型映射为向量表示；最后以键值对形式保存文本块与向量，便于高效可扩展的检索。

- 检索（Retrieval）：用户提问先经编码模型生成语义向量，再在向量库中做相似度匹配，取出最相关的前 k 条数据对象作为上下文。

- 生成（Generation）：把原始提问与检索到的补充信息填入提示模板，形成增强提示，再送入 LLM 生成最终回复。

手工实现这套链路成本较高，LangChain 已将其封装为简洁接口。但照搬基础三步在复杂任务里往往不够理想，优化是刚需。图 8.7 展示了 LangChain 已封装的高阶 RAG 实现方案。

##### 1. 翻译查询
自然语言提问常表达不规范、语义复杂，直接检索召回率偏低。LangChain 在入口层提供改写机制，支持多查询生成等价表述以提升召回、RAG 融合把多版本检索结果聚合、分解把复合问题拆成子问题等策略，核心是提升查询与知识库的语义对齐，让下游检索更精准。

##### 2. 路由
路由模块依据问题类型或语义特征挑选合适的检索路径与提示模板，主要包括：

- 逻辑路由：基于问题结构决定调用哪类数据库或哪种查询方式。
- 语义路由：将问题映射到向量空间，按语义相似度匹配最合适的 Prompt 结构。

##### 3. 数据库的支持
在 LangChain 的高级构建流程中，底层可同时接入图数据库、关系型数据库和向量数据库。

[PRE1]

##### 4. 构建查询
面对自然语言输入，系统会先按目标库类型生成结构化指令。

- 关系型数据库：通过 Text-to-SQL 把自然语言转为 SQL 查询，并结合向量检索做增强。
- 图数据库：采用 Text-to-Cypher 生成如 Cypher 的图查询语言，从知识图谱中抽取语义关联。
- 向量数据库：使用 Self-query retriever 自动从问题中抽取意图与元数据过滤条件，生成向量检索请求。

##### 5. 索引
检索质量取决于索引质量。LangChain 在索引构建中引入了以下机制。

- 块优化：按字符、段落、语义断点切分原始文档，提升 embedding 效果。
- 多表示索引：如 Parent + Summary + Dense 向量结构，使召回更全面。
- 专业嵌入：结合微调或 ColBERT 等模型，生成更精准的领域向量。
- 层级索引：如 RAPTOR，构建跨层级、多抽象层的文档树，实现摘要层级的高效索引。

##### 6. 检索
路由确定后进入实际信息检索阶段，具体包括：

- 排名：对候选文档做语义打分排序，方法包括 Re-Rank、RankGPT、RAG-Fusion 等。
- 细化：首轮结果不理想时可执行再检索或检索压缩。
- 主动检索：依据首轮回答质量自动判断是否重写问题并重新检索。

##### 7. 生成
检索到文档后，LLM 将结合用户原始问题与增强上下文生成最终回答。LangChain 在生成阶段引入 Self-RAG / RRR 优化，让模型主动校验问题理解是否正确、信息是否充分，不足时触发再检索与反馈闭环。
