`security: "full"` 代表最高放开级别，Agent 可调用任意命令无需审批，仅建议在完全可信的私人环境中使用。

#### apply_patch 代码编辑替代方案
`apply_patch` 为 `exec` 提供更安全的替代路径，专用于文件修改。它基于统一 diff 格式操作文件，本身不具备执行任意命令的能力，安全边界比 `exec` 更清晰。默认关闭，需通过 `tools.exec.applyPatch.enabled: true` 手动开启；未开启时 Agent 仅能使用 `write` 与 `edit` 工具改写文件。

#### 工具调用审计留痕
OpenClaw 会为每次工具调用生成完整审计记录，保存在会话转录的 `.jsonl` 文件中，包含工具名称、入参、执行结果与时间戳。对 `exec` 工具还会记录完整命令行（含参数）、退出码及输出内容，输出长度受配置上限截断。管理员查阅 `.jsonl` 即可完整回溯 Agent 执行了哪些命令以及结果。

### 16.11 配置热重载与管理
#### openclaw.json 顶层结构说明
`openclaw.json` 统一收敛 OpenClaw 各组件配置，顶层键包含：`agent`/`agents`、`models`、`secrets`、`skills`、`plugins`、`gateway`、`channels`、`tools`、`sandbox`。其中 `sandbox` 的细化设置在 `agents` 内部配置。

#### 无需重启的热更新机制
Gateway 支持在进程不断开的情况下动态刷新配置，对生产环境意义重大，例如切换 API Key、调整工具策略、更新 Skills 等均可不中断会话完成。触发方式有三种：命令行 `openclaw gateway reload`、向 Gateway 发起 `config.reload` RPC 调用、开启 `gateway.watchConfig: true` 后文件保存自动生效。

热重载强调原子切换：新配置先在内存中完整解析并校验所有 SecretRef，全部通过才一次性生效；校验失败则保留旧配置继续服务，避免出现新旧混杂的状态。

#### 不同项的生效时机差异
- 立即生效：模型配置如新增 Provider 或 API Key、工具策略与安全策略、Secrets 提供方变更。
- 新会话生效：Skills 配置变更、Agent 人格与工作区引导文件变更。引导文件在会话创建时注入，已有会话不受影响。
- 必须重启：`gateway.bind` 绑定地址变更、监听端口变更、部分渠道连接参数变更，例如更换 WhatsApp 账号认证。

热重载期间 Gateway 会记录每项配置的生效时间点，并在需要完整重启时给出提示，避免盲目猜测。

### 16.12 纵深防御安全体系与实践
#### 六层纵深防御架构
OpenClaw 采用 Defense in Depth 策略，每层独立防护，单层被突破仍有后续层兜底，自上而下为：

第一层，提示词安全护栏，属于建议性约束。系统提示内置反提示注入、反能力请求等引导，仅能影响模型行为，无法强制执行，不宜作为公开部署的主要防线。

第二层，工具策略 `tools.allow/deny`。硬逻辑控制，Agent 只要不在 allow 列表中就无法调用，与提示词无关。

第三层，`exec` 审批机制。Shell 执行可加入人工把关，allowlist 模式可建立长期可信命令白名单，高风险操作须经人工审批。

第四层，沙盒隔离。Docker/SSH/OpenShell 提供系统级隔离，工具运行被限制在容器内，文件系统与进程访问受物理限制，影响范围被框定在容器边界。

第五层，渠道接入管控。通过 `mentionPatterns`、`allowedSenders` 等限制可触发 Agent 的外部用户，从源头减少恶意输入。

第六层，SecretRefs 机密管理。架构层面消除配置文件明文凭据，敏感信息交由环境变量、加密文件或外部密钥管理服务存储，切断凭据泄露常见路径。

#### 三种信任场景的配置建议
##### 场景一：个人私用 高信任
- 沙盒：`off` 或 `non-main`，有群组接入时建议 `non-main`。
- 工具策略：不设白名单，允许全部内置工具。
- exec 审批：`security: "full"`，完全信任自用。
- SecretRefs：至少使用 env 来源，避免明文 API Key 写进配置。
- Gateway 认证：本地直连可不设；需远程访问时必须配置 token。

##### 场景二：家庭/团队共享 中等信任
- 沙盒：`non-main`，主 Agent 不受限，群组/渠道会话强制沙盒。
- 工具策略：群组/渠道 Agent 采用最小权限，建议拒绝 `exec` 或仅 allowlist。
- SecretRefs：强制启用，推荐 file 或 exec 来源。
- 多 Agent 隔离：不同用户/群组使用独立 Agent，不共享认证 profile。
- 定期执行 `openclaw secrets audit --check`排查明文凭据残留。

##### 场景三：公开服务 低信任
- 沙盒：`all`，`scope: session`，`backend: docker`，`workspaceAccess: none`。
- 工具策略：严格白名单，`exec` 默认拒绝或仅极窄 allowlist。
- 网络隔离：`sandbox.docker.network: none`，禁止沙盒容器对外联通。
- SecretRefs：必须启用，推荐 exec 来源对接外部密钥管理器。
- Gateway 认证：必须开启 token 认证，推荐 Tailscale serve 模式保护访问。
- 渠道白名单：通过 `allowedSenders` 限制可触发 Agent 的用户范围。

#### 日常安全运营清单
- 定期运行 `openclaw secrets audit --check` 检查明文凭据。
- 所有 API Key 与 Token 均使用 SecretRef，至少使用 env 来源。
- 面向外部用户的 Agent 必须开启沙盒 `mode: all`。
- 不同信任等级用户/渠道使用独立 Agent，不共享认证 profile。
- 工作空间纳入私有 Git 仓库，禁止提交明文密钥。
- 配置 `gateway.auth.token`，阻止未授权连接。
- 远程访问优先 Tailscale serve，避免直接暴露 Gateway 端口。
- 定期轮换 API Key，通过 `openclaw secrets reload` 无重启刷新。
- 监控 `SECRETS_RELOADER_DEGRADED` 事件，及时发现凭据失效。
- 定期执行 `openclaw doctor` 进行健康自检。

#### 安全演进方向
依据官方路线图，安全能力持续演进：工具输出处理链上增强提示注入检测；审计日志支持按 Agent、渠道、时间范围精细查询；`exec` 提供商模式引入 SecretRef Attestation 加密证明；沙盒容器出网控制从全开/全关细化为域名/IP 白名单。随着生态成熟，安全模型将覆盖更广的部署规模与信任等级，建议持续关注官方文档与 Releases。

### 17.2 Git 与 GitHub 必要工作流
Git 是常用的分布式版本控制系统，GitHub 是代码托管与协作平台，掌握其工作流是贡献基础。Git 分布式特性让每个开发者本地拥有完整仓库，可离线修改后同步，降低单点故障风险。核心概念包括仓库、分支、提交、拉取、推送、合并。

仓库分为本地与远程。OpenClaw 远程仓库托管于 GitHub，开发者先 `git clone` 到本地，再本地修改后同步回远程。

分支支撑并行开发。主分支保存稳定可发布版本，开发分支承载进行中功能。贡献时应基于开发分支创建功能分支，命名如 `feature/xxx`、`bugfix/xxx`、`doc/xxx`，在功能分支上完成修改，避免直接改动主干。

标准工作流六步：仓库克隆、分支切换与创建、代码修改与提交、本地与远程同步、提交拉取请求与审核、合并代码。
先通过 `git clone 仓库URL` 克隆远程仓库；切换至 `develop` 分支，创建个人功能分支并切换；本地修改后提交；与远程同步；通过 Pull Request 提交审核，最终合并。
