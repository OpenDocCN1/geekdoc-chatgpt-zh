## 12.1 在 CoreML 的魔法背后

粗略来看，`CoreML` 就是把在 `CreateML` 或 `TensorFlow` 之类工具里训练好的模型文件读进来，执行一遍，然后按给定的输入返回预测结果。

第 11.1 节里我们曾泛泛聊过 `CoreML` 的内部运行，当时有意避开了模型格式本身，因为只要明白流程即可。要弄清它在做什么，至少要先对模型格式有个基本认识。`CoreML` 的模型格式建立在 `protobuf` 序列化格式之上，并用一套定制化模式来定义模型的类型、特征、标签、输入输出、属性、元数据等所有描述模型所需的要素。

格式的核心作用就是把模型描述得足够精确，让别的程序能读懂并完整复原。

[PRE0]有关`CoreML`模型格式的更多细节，请参阅 2.3.1 节。

也就是说，`CoreML` 必须先把模型文件读入，解析成神经网络、广义线性模型、树分类器等具体形态再执行。从开发者手里拿到的模型本质上是一个 `.mlmodel` 文件，也就是模型的通用描述。

为了适配实际硬件，`CoreML` 会在运行前把它转成设备专属的版本，这个转换过程的思路和本章要做的事情很像，只是为了在目标设备上更高效，并不会改变模型行为。

转成设备专属格式后会编译并保存为 `.mlmodelc`，运行时真正用到的就是它。

`CoreML` 平时并不直接执行 `.mlmodel`，而是先编译再执行。

[PRE1]如果要动态更新或加载模型，可以在`MLModel`类上使用`compileModel(at:)`方法，该方法将接受一个`.mlmodel`并从中创建一个`.mlmodelc`。

这套流程是本书主线，也是日常该用的方式，但要真正理解 `CoreML`，光看这套是不够的。本章我们就退一步，借助苹果 `Accelerate` 框架下的基础神经网络子程序 `Basic Neural Network Subroutines, BNNS` 库自己手写一个神经网络，该框架在 2.3.4 节中提及过。

这里只讲神经网络， `CoreML` 实际支持的类型远不止于此，不过神经网络是目前最主流的形式，也是最值得手写来学习的部分。

[PRE2]`Accelerate`框架不仅包含`BNNS`，还有各种不同的库来实现 CPU 的快速加速。

除了 `BNNS`，`Accelerate` 还提供向量与四元数运算、信号处理、稀疏矩阵线性代数求解等代码。虽然自己写也行，但苹果提供的高度优化硬件加速版本更值得使用。

`BNNS` 是 `CoreML` 依赖的底层库之一，只跑在 CPU 上。你日常不一定会直接写 `BNNS` 代码，但几乎所有经 `CoreML` 运行的模型都可能用到它。借助 `BNNS` 可以搭建任意规模和复杂度的网络，支持三种层：

• 卷积层

• 池化层

• 稠密层

[PRE3]`BNNS`通常被戏称为香蕉(`bananas`)。你明白了吗？

只要网络结构能用这三种层表达，就可以用 `BNNS` 造出来。`BNNS` 用 `C` 语言实现，`Swift` 通过桥接调用，表面像原生 `Swift` 代码，但底层仍有不少细节需要注意，后面遇到时会指出。

[PRE4]`BNNS`只是苹果在`CoreML`中使用的众多技术之一。

`CoreML` 还有另一套技术叫 `Metal Performance Shaders`，更准确说是其中用于搭建神经网络的部分，API 设计思路相近但表现不同。

两者关键区别在于 `BNNS` 仅限 CPU，`Metal Performance Shaders` 仅限 GPU。我们选 `BNNS` 的原因很简单：它同时能在 `macOS` 和 `iOS` 上运行，而 `Metal Performance Shaders` 主要面向 `iOS`。

尽管部分 `macOS` 设备支持 `Metal Performance Shaders`，但几乎所有苹果设备都支持 `BNNS`。因此代码既可以在 `macOS` 的 `Playground` 里跑，也能搬到 `iOS` 上。

总之 `XOR` 足够简单，可以从零搭出可用的网络，也挺有趣。
