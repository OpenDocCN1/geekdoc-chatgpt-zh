在逻辑已经固化的、体系比较成熟的场景里，比如风控模型、量化交易系统，AI 代理未必能体现出明显优势。它的长处更多体现在自然语言理解、多源信息融合以及非结构化数据处理上，反而要避免把难以获取或根本不存在的外部依赖，比如未公开的内部交易记录，作为核心前提。

### 11.1.2 步骤 2：为代理制定标准作业流程
为 AI 代理编写一份详尽的标准作业规程，内容要涵盖人工分析师完成任务的每一步操作指引。

这一步能让开发者明确任务边界是否合理、代理需要调用哪些工具，为后续构建奠定基础。

以金融投资分析类代理为例，典型的工作流可以描述为：

（1）抓取并解析财经新闻、财报数据、行业报告等多来源信息。
（2）提炼关键事件与核心财务指标，完成情感分析与影响度评估。
（3）结合历史数据和市场走势，形成投资观点或风险提示。
（4）生成初稿报告，经由分析师等安全审核节点确认后再对外发布。

### 11.1.3 步骤 3：用提示词快速做出可用原型
起点选得是否恰当很关键。先依据作业规程完成代理的架构设计，明确运行路径、决策点和推理环节。

随后聚焦最核心的大规模模型推理任务，例如分类、判断等，通过设计提示词来搭建 MVP，最小可用产品。大多数代理失败的根因是模型推理不通，先手工喂数据让提示词跑通，有助于在完整系统成型前建立信心。LangSmith 这类工程化工具可以在提示词版本管理、跨场景测试、迭代性能追踪等方面提供支持。

MVP 的落地动作包括：

（1）先手工输入提示词所需的数据或上下文，暂不考虑自动化。
（2）参照 11.1.1 节列出的任务样例进行验证，检查常见用例的表现。

此时要先锁定一项高价值的推理任务。对金融投资分析代理来说，可以先集中在财报关键信息抽取与分类上，因为这是后续功能运转的基础。

例如输入财报段落，检验抽取的指标与情绪判断是否可靠。

**·** 输入：本季度营收同比增长 15%，净利润下降 8%。
**·** 输出：关键指标 = {"营收增长率": "15%", "净利润变动": "−8%"}，情绪 = "中性偏负"。

通过手工测试确认模型推理是否稳定可靠，再进入下一步开发。

### 11.1.4 步骤 4：把提示词接入真实数据与用户输入
有了可用的提示词后，需要将其与真实数据源和用户交互联通。

首先构建系统消息框架。撰写定义代理角色、元规则和操作边界的基础系统提示，是确保预期执行并抵御提示注入等风险的首要安全措施。

然后明确每个提示词所需的上下文或数据，如内部外部数据、工作文档等，并规划通过 API、数据库或文件系统等方式的程序化获取路径。

接着编写具体工作流的运行逻辑，把正确的数据送入提示词。简单场景可直接传入，复杂流程则需要业务逻辑层来决定查询哪些数据源、何时调用、如何组合结果后再喂给模型。

以金融投资分析代理为例，本步可能通过 API 接入财经数据平台如 Bloomberg、Wind，联动内部数据库获取历史交易记录，并用网络爬虫获取实时新闻。

运行逻辑可设计为：

（1）定时触发或事件驱动，如财报发布即启动代理。
（2）从多个源头获取结构化与非结构化数据。
（3）调用大规模模型进行信息抽取与情感分析。
（4）生成初步分析报告。
（5）经人工安全审核后推送至投资决策系统。

### 11.1.5 步骤 5：测试与持续迭代
首先用 11.1.1 节的任务样例手工测试 MVP，目标是验证核心用例是否能输出合理准确的结果。若涉及多轮模型调用，可用 LangSmith 等工具追踪流程，直观调试各阶段决策。

手工稳定后，转向自动化测试以保证一致性并捕捉边界情况。团队通常会把用例扩充到几十条，以更清晰认识代理的优劣，并在提升复杂度前量化性能。具体做法：

**·** 以编程方式批量跑通代理，覆盖原始及新增用例。
**·** 设定自动化成功指标，明确预期行为。
**·** 选择性人工复核，挖掘指标难以发现的问题。

以金融投资分析代理为例，可用指标包括：

**·** 准确性：财务数据抽取是否无误。
**·** 及时性：能否在限定时间内完成分析。
**·** 合规性：输出是否符合金融监管要求。

随后扩展自动化测试，设定成功门槛如抽取准确率>95%，并借助 LangSmith 跟踪多步推理过程。

### 11.1.6 步骤 6：部署、扩容与持续完善
MVP 运行稳定后即可开始扩展范围，新增功能、覆盖更广场景，甚至构建多代理协作流。每新增一项功能都要重复 11.1.5 节的测试流程，确保不破坏已有能力。

准备就绪后将代理部署到生产环境供用户使用。可选用外部云平台，例如 LangGraph 平台支持一键部署，便于发布、管理和扩容。

观察真实使用情况。LangSmith 等工具可实时跟踪代理操作，帮助发现成本飙升、准确率下滑等问题。实际使用往往与预期有差异，这些洞察能揭示不足、发现隐性需求，并指导下一步迭代优先级。

关键在于把上线视作迭代的起点而非终点。

以金融投资分析代理为例，上线后通过监控流量与高频用例，可能发现未覆盖场景如特定行业的分析需求，需逐步扩展：

**·** 增加新兴市场分析模块；
**·** 支持多语言财报处理；
**·** 引入多代理流程，如风险预警代理+投资建议代理。

这些新需求意味着可以扩大功能边界。开发者可逐步新增能力、更新提示词与运行逻辑，并在进一步扩展前始终通过测试与用户反馈验证。这不仅保证系统可用，更能打造贴合真实工作方式、可靠好用的代理。

扩展过程中要始终关注数据隐私、输出合规与潜在偏见，通过持续的人机协同设计和反馈机制，把安全与信任作为核心特质。

## 11.2 企业级 AI 代理的项目概览

### 11.2.1 DACA 设计模式与相关项目
DACA（Dapr Agentic Cloud Ascent）设计模式为用代理打造大规模系统提供了可行解法。

该模式融合 OpenAI Agents SDK 的代理引擎与 Dapr 的分布式能力如状态管理、服务调用，支持 Kubernetes 动态扩缩容与千万级并发，适用于高并发企业级应用，例如实时金融交易分析、自动化财报解析。凭借巧妙的架构与灵活组合，它成为开发部署大型多代理系统的首选。无状态、容器化部署策略也大幅提升了可扩展性。

DACA 的创新在于用 OpenAI Agents SDK 承担核心代理逻辑，结合 MCP 与 A2A 协议，实现工具标准化和代理间无缝通信。

越来越多行业需要在创新与成本效益间取得平衡，DACA 为开发者和架构师提供了一套稳健灵活的框架，助力构建复杂云原生代理。

作为云原生代理设计模式，DACA 整合并用：

**·** OpenAI Agents SDK，提供核心代理逻辑；
**·** MCP，标准化工具调用接口；
**·** A2A 协议，实现代理间无缝协作；
**·** Dapr 分布式框架，提供底层支撑。

该模式强调“AI 优先”和“云优先”原则，采用无状态容器化部署，可从本地开发平滑扩展到全球规模。

核心设计理念：

（1）**开发环境无关**。通过容器化技术 Docker/OCI 实现跨平台一致性，提供隔离的开发环境如 VS Code Dev Containers，采用开源技术栈如 Python、Dapr、Kubernetes。
（2）**云环境可移植**。基于 Kubernetes 的标准化部署实现多云/混合云兼容，Dapr 简化分布式系统开发，Helm/Argo CD 实现自动化交付。
（3）**开放核心与托管边缘**。核心系统采用开源技术如 Kubernetes、Dapr；边缘服务采用托管数据库/AI API；兼顾成本、掌控力和性能。

DACA 为构建大型并发代理系统提供了完整技术框架。通过云原生与代理范式的深度融合，解决了可扩展性、可靠性与成本效益问题，有望成为下一代代理系统的标准范式。
