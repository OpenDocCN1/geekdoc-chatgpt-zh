零运行时的一种常见做法是让编译器在构建阶段借助抽象语法树把 JavaScript 代码里声明的样式抽离出来生成独立的静态文件，随后在页面中按需引用。

开源界里常见的 CSS in JS 实现基本都是上述一种或多种手法的组合。oh-my-chat 中落地的具体细节会在 8.4 节展开，这里暂不展开。

### 8.2.4 原子化 CSS

面对组件化带来的样式冲突与污染，有一种反向思路是把选择器的粒度压到最小来规避风险，这就是原子化 CSS。其主旨是让每一个类只负责一种视觉表现，并通过语义化的命名表明用途，开发者在标签上叠加多个类来拼装最终效果。下面是不借助任何库的简易演示：

原子化 CSS 也常被称作函数式 CSS，可把这些单职责类看作函数，在 HTML 中通过 class 属性调用并自由组合。因为原子类是 CSS 的最小单元，其作用域与副作用都极易掌控，基本杜绝了不同区块间的相互影响。无论如何组合类名，都不会波及其它标签，从而实现隔离。

该思想最早在 2013 年提出，随后出现多套落地实现。2017 年发布的 Tailwind CSS 以工具优先为定位，内置了海量原子类，并配合现代构建工具与 IDE 插件，为样式开发提供了高效体验，很快成为风向标。Tailwind 同样支持 React，例如：

## 8.4 项目实现：为 oh-my-chat 实现 CSS 组件化

前七章里 oh-my-chat 仍使用最基础的写法，所有样式集中在 App.css。随着功能增长，该文件会变得臃肿难维护，且容易因类名重复引发冲突，这类问题在大型项目中排查成本很高。因此需要选定合适的样式方案并重构现有代码。

### 8.4.1 技术选型：Linaria 方案

基于我在多个 React 项目的统计，按代码量计使用率最高的三类是 CSS Modules、emotion 与 Linaria，后两者都属于 CSS in JS。实践表明 CSS in JS 能明显提升 React 的开发体验。Linaria 作为零运行时 CSS in JS 的代表，在保持与传统方案相似 API 的同时，运行时开销更小，因而被选为 oh-my-chat 的样式方案。使用感受上，Linaria 功能完备，API 与 styled-components、emotion 高度兼容，且比起偏向 JS/TS 语法写样式的方案，更贴近原生 CSS 的书写习惯。

接下来用 Linaria 重写组件样式，过程中会掌握 css 基础用法、嵌套选择器、样式组合复用、伪类以及把组件数据融入样式等核心能力，基本覆盖 CSS in JS 的典型场景。
