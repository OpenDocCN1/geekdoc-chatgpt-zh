## 8.11 Agent SDK 与 Headless CLI：如何选型

Agent SDK 和 Headless CLI 都能让 Claude 在无人值守环境下运行，但适用边界很清晰，见表 8-4。用错工具容易让架构变复杂或能力受限。

表 8-4 Agent SDK 与 Headless CLI 的场景选择对照

| 场景 | 推荐方式 | 原因 |

| :--- | :--- | :--- |

| CI/CD 流水线中的单步任务 | Headless CLI | 部署零依赖，可直接写入 YAML 配置，无需 Python/Node 运行时 |

| Shell 脚本自动化 | Headless CLI | 与管道组合天然契合，操作简单直接 |

| 构建 Web/ 桌面 AI 应用 | Agent SDK | 支持流式输出、精细状态管理，利于前端交互 |

| 需要自定义工具 | Agent SDK | 支持 @tool 装饰器注册本地函数，完成复杂业务闭环 |

| 多轮对话 / 持续会话 | Agent SDK | 内置 session 管理，自动维护上下文历史，无需手动拼接消息 |

| 需要精细控制消息流 | Agent SDK | 基于异步生成器，可逐块拦截、修改或路由消息 |

| 并发管理多个实例 | Agent SDK | 支持编程化并发控制如 asyncio.gather，轻松应对高并发请求 |

一个实用的判断原则：逻辑能用一行 Shell 描述就选 CLI；一旦需要 if/else 或循环，就用 Agent SDK。

## 本章小结

Agent SDK 让 Claude Code 从单一终端工具转型为可嵌入任意应用的 AI 组件，这一转变建立在两大核心 API 上——`query` 函数和 `ClaudeAgentOptions`。

`query` 函数是 Agent SDK 的入口，对标 Headless 模式的 `claude -p` 命令，但以异步生成器形式返回消息流，支持实时处理 Claude 的每一步输出。消息流包含 5 种类型：`system/init` 为初始化信号、`assistant` 为 Claude 的回复可能含文本及工具调用请求、`user` 为工具执行后的反馈结果、`result` 为任务终止信号，携带成本、轮数、耗时等元数据。

`ClaudeAgentOptions` 提供了与 Headless CLI 参数等价的编程接口，覆盖模型选择、工具权限、权限模式、Prompt 定制、会话管理及结构化输出。相比命令行，编程接口的核心优势是动态配置：可按用户角色动态调整权限模式，按任务类型灵活切换模型，或基于上一轮结果实时优化下一轮 Prompt。

自定义工具通过 `@tool` 装饰器与进程内 MCP 服务器实现，让 Claude 能调用任意自定义函数，如查询数据库、调用内部 API 或发送通知。同时 4 道安全防线——权限模式、工具白名单、`canUseTool` 回调、PreToolUse Hooks——确保 Claude 在应用中只做该做的事。

从 CLAUDE.md 配置、Skills 定义，到 Hooks 拦截、MCP 集成，再到 Headless 模式与 Agent SDK 的全面掌控，每深入一层，就更接近构建成熟的产品而非单一工具。第 9 章将探讨如何把这些能力打包分发，并深入解析 Plugins 插件生态。

# 第 9 章 集腋成裘：Plugins 生态

独行快，众行远。

小雪最近在开源社区看到一个名为“React 全栈团队的 Claude Code 最佳实践”的 GitHub 仓库，标题很有吸引力。点开后发现里面有一套设计得很精细的 Skills，覆盖代码审查、组件文档生成、测试用例编写等；还附带了用于自动格式化和 PR 规范的 Hooks 脚本，以及一份完整的 `.mcp.json`，已预集成 GitHub API 与 Linear 项目管理工具。

“要是能直接用就好了。”小雪感叹。

现实却很折腾。Skills 放在一个目录，Hooks 脚本在另一个目录，`.mcp.json` 是独立文件，自定义命令的定义文件又散落在各处。想用这套配置，就得手动复制到指定位置，理清安装顺序，还要担心漏掉依赖。最后她只花了半天搞清楚安装顺序就放弃了。

“这正是 Plugins 要解决的问题，”咖哥说，“它把一套完整的 Claude Code 能力打包成可一键安装的单元。就像 npm 之于 JavaScript、pip 之于 Python，Plugins 是 Claude Code 能力的标准化分发机制。”

## 9.1 Plugins 的定位：能力的封装与分发

在理解 Plugins 之前，有必要回顾已有的工具栈。目前我们已有 6 种独立的扩展机制：用 CLAUDE.md 管理项目记忆、用子智能体实现任务委派、用 Skills 封装领域工作流、用 Hooks 提供事件驱动控制、用 MCP 连接外部服务、用 Headless 模式 / Agent SDK 实现编程调用。虽然各有专长，但共同短板是彼此割裂，难以整体分发。

当你花数周为团队打磨出一套开发工作流，想分享给另一团队时就会很头疼：Skills 要复制到 .claude/skills/，Hooks 配置要合并到 settings.json，MCP 服务器要单独配置，自定义命令要放到 .claude/commands/，子智能体定义又在别处。接收方不仅要逐一理清安装步骤，还要处理命名冲突，这已不是经验分享，而是繁琐的迁移作业。

Plugins 本身不创造新功能，而是提供统一的打包格式和安装机制。一个 Plugin 能同时包含 Skills、Hooks、Commands、Agents 及 MCP 配置，一行命令即可让所有组件就位。
