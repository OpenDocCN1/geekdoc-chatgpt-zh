### 6.1.3 动态团队组建与解散机制

固定编队的智能体组合难以应对真实业务中任务类型和规模的快速波动。动态组队思路让系统能够依据当前作业要求临时拉起专项小组，完成后自动遣散并归还算力资源。这种弹性编组既提升了资源利用效率，也增强了对复杂多变场景的适应力。

一个动态小组的运转可以拆解为四个连贯环节。需求评估环节先对待办作业的类型、复杂度与时效进行判断，明确所需的能力集合。组建环节从智能体池中挑选适配成员，并设定协作规则与通信方式。执行环节是团队活跃期，各成员协同推进直至交付。解散环节把成员释放回池，保留必要的运行记录以供后续复盘优化。

智能体重要性评分是实现智能编队的核心手段。该方法借由历史任务中的贡献度分析，为每个智能体构建动态的能力画像。新作业到来时，系统依据作业特征与智能体能力的契合度打分排序，优先召集高分者组队。相较于静态规则，数据驱动的选择更贴合任务多样性。

团队规模并不总是越大越好，成员过多会因通信开销拖慢整体效率。引入早停策略可缓解此问题，当成员对同一结果达成高度一致时提前终止后续讨论轮次，在保障质量的前提下节约计算开销。

### 6.1.4 跨团队协作与资源共享

单一团队的内部协同难以覆盖跨领域的复杂作业。跨团队协作机制允许不同团队的智能体在需要时交换信息、协同处置；资源共享机制则确保知识库、工具服务等公共资产被多团队高效复用。

典型情境包括：研发团队的代码生成智能体需要调阅测试团队沉淀的用例；运维团队发现生产异常可能关联近期代码变更，需与研发联合排查。协作的前提是保持团队边界清晰，同时打通有效的跨团队通信通道。

共享资源的访问控制涉及三大要点。向量数据库中的知识片段、API调用配额、计算资源时片等均属公共资产，需解决资源发现、访问授权与并发控制。

### 6.2.1 LLM API的并发调用优化

当智能体数量增至数十上百时，API调用的并发管理成为稳定性的关键。主流LLM厂商均设有速率限制，包含每分钟请求数RPM与每分钟Token数TPM两个维度，超限请求会被拒或延迟。

优化需从三层入手：请求队列统一收集并按优先级排序，避免洪峰直击API；限流算法在客户端主动控速，保证调用频率合规；错误重试机制针对限流或服务端错误采用指数退避，避免重试风暴。

令牌桶与漏桶是两种经典方案。令牌桶以固定速率补充令牌，每个请求消耗令牌，允许一定突发，适合偶发高峰。漏桶以固定速率泄漏处理请求，多余请求排队等待，保证流出速率平稳，适用于对调用频率要求严格的场景。

async def acquire(self, token_count: int) -> bool:
    self._refill()
    if self.request_tokens >= 1 and self.token_tokens >= token_count:
        self.request_tokens -= 1
