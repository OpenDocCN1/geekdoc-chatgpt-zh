可见，SQL 联动能让模型检索能力大幅提升。和 RAG 类似，它也是通过引入外部信息来增强模型，但 SQL 联动更像一把双刃剑：查询更灵活的同时，也带来了更高的幻觉风险，比如：

· SQL 注入：模型生成的 SQL 多为字符串拼接，可能被恶意利用篡改数据库。
· 越权查询：模型可能生成访问敏感表或字段的语句，造成数据泄露。
· 性能拖垮：若生成的查询负载过高，会拖慢数据库甚至导致服务阻塞。

因此在使用 SQL 联动时必须做好安全与信息保护，建议做法有：

（1）限定查询范围：对敏感表或字段禁止开放查询权限。
（2）解析校验：借助社区 AST 解析库对生成的 SQL 做语法和语义校验，确认无安全与性能风险后再执行。
（3）只读权限：仅允许执行 Select 语句，避免模型幻觉导致的数据修改或删除，后果难以挽回且排查成本高。

**5.3 langgraph 模块**

在 LangChain 体系里，langgraph 模块负责高效搭建和运行状态图。借助它，开发者可以把各种处理流程编排起来，构建更稳定、可维护的 Agent 系统。主要能力包括：

· 编排能力：用状态图控制复杂流程的节点跳转与条件分支。
· 记忆：支持把状态和历史数据存到内存或持久化存储，用于上下文记忆或中断恢复。
· 人类在环流程：允许人工或外部系统动态介入 Agent 执行路径。
· 路径回放：可重建和复盘历史执行路径，便于调试和审计。
· 工具调用：原生支持 LangChain 工具的调用与链式组合。
· 子图嵌套：一个状态图可以嵌套进另一个图，提升模块化与复用。

这些特性共同构成了 langgraph 在构建可控、可追溯、模块化 Agent 中的核心价值。

**5.3.1 编排能力**

langgraph 的核心竞争力在于状态图的编排。通过简洁的 API，即便流程图结构很复杂也能快速搭建和管理，从而提升复杂 Agent 任务的开发效率。

本节从常规编排和条件编排两个角度，解析节点定义、边控制、状态更新与数据流转的设计方式。

**1．常规编排**

langgraph 编排体系的核心概念是边 Edge 和点 Node。点即节点，是一个可执行的操作单元；边是节点间的关系，决定状态在图中的流转路径。概念比较抽象，下面用示例说明。

图 5-24 常规编排示例状态图

示例里有 4 个关键点：

（1）定义状态结构：Annotation.Root({...}) 用来描述整个图的状态模型。其中 reducer 定义节点返回值的合并策略。例如下面对 route 字段做拼接：

    const StateAnnotation = Annotation.Root({
      route: Annotation<string>({
        reducer: (x, y) => (x ? `${x} -> ${y}` : y),
      }),
    });

（2）节点处理函数：创建节点时传入回调，该回调返回一个高阶函数并在执行时调用。回调的返回值会交给 reducer 合并。例如返回的 route 会作用于上一步定义的 route 字段。

    const nodeFactory = (route: string) => {
      return (state) => {
        console.log(`Executing node ${route}, current route state:`, state.route);
        return { route };
      };
    };

（3）图构建方式：状态图由节点和边组成。langgraph 内置 START 和 END，分别代表入口和出口。自定义节点和边分别用 addNode 和 addEdge 添加，添加边前节点必须已通过 addNode 创建。

    const builder = new StateGraph(StateAnnotation)
      .addNode("a", nodeFactory("A"))
      .addEdge(START, "a")
      ...

（4）执行图：图实例实现了 Runnable 接口，可用 invoke、stream 等方法消费。

    const finalRoute = await graph.invoke({ route: "root" });
    console.log("Final route: ", finalRoute);

**2．条件编排**

常规编排中 A→B/C 会无条件并行触发。但实际场景里往往需要根据上下文或用户意图在多个分支中择一执行，这就是意图驱动的决策分支。

示例先定义了包含 route 和 intent 的状态结构，route 记录轨迹，intent 控制分支。除了常规的节点和边，还使用了 addConditionalEdges API，实现动态流程控制，定义如下：

    .addConditionalEdges(fromNode: string, conditionFn: (state) => string[],
candidateNodes: string[])

三个参数含义：

· fromNode：条件跳转的起点节点，如示例中的 "a"。
· conditionFn：接收全局状态，返回将要跳转的节点列表。
· candidateNodes：候选节点白名单，确保跳转目标合法。

回到代码，节点 A 执行完后会根据 intent 字段判断下一步：intent 为 "do_b" 时走 B，为 "do_c" 时走 C，最终都到 D。完整状态图如图 5-26 所示。
