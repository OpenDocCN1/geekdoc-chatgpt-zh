## 使用 coze、Dify、RAGFlow、FastGPT 等工具

大模型普及后，低代码和可视化方案成为快速搭建检索增强生成的热门手段。常见的产品有 coze、Dify、RAGFlow、FastGPT、LangFlow 与 FlowiseAI 等（见图0-16）。这些平台提供图形化界面和预设模块，降低门槛，让非技术人员也能参与设计。图0-16 低代码和可视化工具

> 这类工具层出不穷，多为开源并附带文档，故不再逐一展开。

以 Dify 为例，可用模块化和可视化方式构建并运行检索增强工作流，便于快速把握流程。工作流设计界面如图0-17。图0-17 RAG 工作流设计界面（图片来源：dify.ai）

[PRE4]

图0-17 所示的工作流包含输入处理、分类、检索与生成等环节，各模块作用简述如下。

- START 模块接收用户查询和上下文记忆，定义工作流的初始参数。
- QUESTION CLASSIFIER 模块用 GPT-3.5-turbo 对问题分类，分为售后相关、产品定位与规划、其他三类。
- 对知识库无法回答的第三类问题，DIRECT ANSWER 模块直接返回“Sorry, I cannot answer this question.”
- 可回答的问题进入 KNOWLEDGE RETRIEVAL 模块，按分类选择检索路径，从产品文档中找出相关信息，随后调用大模型 API 生成文本。
- LLM 模块依据检索到的文档生成最终回答，不同类型问题可选用不同大模型。

这类低代码工具流程清晰、模块独立、功能明确，支持条件分支和分类，适合复杂的检索生成任务。发布后多数平台也会提供 API，方便开发者调用。

低代码方案让系统开发更便捷，但通常不涉及嵌入、索引、检索、生成等组件的算法级优化。若要打造高质量方案，仍需对每个环节细化探索。本书重点不在于工具使用，而在于如何借助代码及 LangChain、LlamaIndex 等框架优化各环节和组件。

## 三问 从何处入手优化 RAG 系统

优化检索增强生成系统该从何处着手，这更贴近实战，也更考验经验。首要步骤是明确目标与瓶颈，因流程环节众多，需要像侦探一样定位拖累整体性能的关键组件。

下面用两张图说明排查思路。

第一张图来自 ABACUS.AI（见图0-18）。该图不仅呈现检索增强生成的结构流程，还标注了各环节的优化空间。图0-18 RAG 系统结构流程

[PRE5]

按照图0-19，先可从分块策略入手。分块策略决定检索粒度与上下文完整度，直接影响检索和生成效果。可尝试调节块大小与重叠比例。例如提高重叠能提升上下文连贯性，但会增加存储冗余；缩小块可减少无关信息，却可能导致语义碎片化。

其次优化嵌入策略。嵌入模型的选择至关重要，当前既有开源也有商业模型，性能和语义捕捉差异明显。若使用 Transformer 架构的开源模型，适度微调往往能提升语义相关性。此外，领域专属嵌入模型在特定场景表现更佳。优化时需权衡向量维度与计算效率。

接下来是检索器优化，涉及向量库选择、索引结构与检索算法调整。例如可从扁平索引过渡到 IVF 或 HNSW 等高效索引。调整 Top K 与相似度阈值有助于提升相关性并减少噪声。动态检索策略，如依据用户问题动态调整参数，以及各类索引技巧，也能改善结果质量。

然后是上下文组装策略优化。检索到多条片段后，如何组合并传入大模型会影响最终答案。可按语义相关性重排，压缩或扩充内容，或在片段间加入解释性连接词。上下文长度需结合所用大模型的最大 token 限制，避免过载。

大模型挑选与提示词设计同样关键。要挑选更适配任务的模型，并调整温度、Top-p、最大 token 等生成参数。提示词应给出明确指令或补充上下文，引导模型产出更符合需求的回答。

优化的最后一步是响应评估。生成后可用 BLEU、ROUGE、BERT 等自动化指标，结合人工评估，对比不同优化组合的表现。通过实验迭代，逐步找到最优配置，提升整体效率与准确性。

第二张图是基于 LangChain 的 RAG 流程图补充重设计而成（见图0-19），旨在细化每个可优化的技术环节。鉴于检索增强生成持续演进，整体流程被重构为十大核心组件，以实现更全面的技术覆盖。

图0-19 清晰呈现各环节可优化点，从数据导入、文本分块到查询构建，直至响应生成与系统评估，每一步均可借助新技术与设计思路改进，模块化设计也为后续迭代和功能扩展提供灵活性。

对常见且重要的文件类型如 PDF，可选用专用工具如 PyPDF2、PyMuPDF、Marker、MinerU、PDFPlumber 等，具体取决于应用场景，如结构化数据提取、文本搜索、OCR 或图像提取。

OCR 即光学字符识别，能将印刷或手写文本图像转为可编辑文本，常用于扫描文档、图片文字识别、身份证车牌等。

对较少见的文件类型，需先弄清生成工具、数据结构及用途。例如目录中出现 product_sales.jsonl 文件，文件名暗示它是产品销售日志，采用 JSON Lines 格式，每行是一个独立 JSON 对象，行间无逗号分隔，解析时需注意。

针对复杂文档，可先转成更易解析的中间格式。例如 PPT 可先转 PDF 再提取，因 PDF 提取工具更丰富。又如 PDF 可先统一转 Markdown 再处理，因 Markdown 更规范，便于提取标题、段落、列表，且大模型基于网页资源训练，对 Markdown 有天然亲和力，更利于理解。

此外，大模型也可辅助解析结构化、半结构化和非结构化数据，在多模态等复杂场景下效果很好。

在 LangChain 中，Document 是一种核心数据结构，表示从外部文件或其他数据源加载的文本内容。主要包含两类属性。

- Metadata：存储与文档相关的元信息，如来源路径、作者、日期等。
- page_content：保存实际文本内容，是文档的主要数据部分。

小冰：为什么要使用 Document 对象？

咖哥：Document 中记录的元数据很重要。它们虽非正文，却包含丰富信息，在检索增强生成中作用显著。文档可能来自 TXT、PDF、HTML 或数据库记录，仅靠原始字符串无法追溯来源或获取额外信息如日期、类别等。许多自然语言处理或信息检索任务中，结合元数据进行过滤、排序或分析是必不可少的。在高级索引技术中，也可利用元数据存放摘要、父文档 ID 等。

此外，不同数据源特性各异，如分块策略、段落间隔等，需要统一的数据结构进行抽象与标准化。Document 对象能把多样数据源抽象为统一结构化形式，便于在 LangChain 中无缝处理，顺利传递到嵌入模型、分类器或问答系统。
