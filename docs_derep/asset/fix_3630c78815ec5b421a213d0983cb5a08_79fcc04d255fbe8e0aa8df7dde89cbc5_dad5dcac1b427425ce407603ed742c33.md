外观模式把多个子系统的调用收敛到一个入口时，容易出现三个风险。第一，外观层会累积大量转发逻辑，类体膨胀，职责边界不清，违背单一职责。第二，后续对底层子系统的增删改通常需要回头修改外观的实现，与开闭原则冲突。第三，外观可能让调用方间接感知底层细节，提升耦合度，降低系统的灵活性和可维护性。

综合来看，外观模式在需要简化复杂交互、隔离底层变动、提供统一高层入口的场景下有价值。落地时应权衡利弊，结合具体业务决定是否引入。

# 5.13 享元模式

享元模式归属结构型范式，核心理念是通过对象复用来支撑海量轻量级实例。

# 5.13.1 应用场景

可考虑的情形主要有：

+   (1) 系统中出现大量形态相近且构造成本不低的对象时，借助共享机制压缩内存占用。
+   (2) 需要对实例做缓存并循环复用时，享元机制能够改善运行效率。
+   (3) 对象状态能拆分为可复用的固有部分与每次调用不同的外部部分时，可抽取固有部分共享以减少实例总数。

# 5.13.2 结构

该模式包含以下参与者。

+   • Flyweight（享元）：给出享元对象的交互规范，包含设置外部状态的方法。
+   • ConcreteFlyweight（具体享元）：落实规范，为内部状态与外部状态提供存储。
+   • FlyweightFactory（享元工厂）：负责享元的创建与管理，并对外提供获取入口。
+   • Client（客户端）：使用方，通过工厂获取并操作享元。

图5-11 描绘了享元模式的构成，其中“Flyweight”为享元接口，“ConcreteFlyweight”为具体类，“Flyweight Factory”为工厂类，“Client”为客户端类。

+   • 客户端依赖工厂来获得享元对象。
+   • 工厂承担享元对象的创建与维护职责。
+   • 接口规定了享元对象可进行的操作。
+   • 具体享元类实现接口契约。

架构进阶手册 / AI辅助设计思路

采用该模式后，相似实体的固有状态得以集中复用，从而减少实例创建量与内存开销。

# 5.13.3 优缺点

优势体现在：

+   (1) 资源复用：同类对象可被共享，避免重复构造带来的浪费。(2) 内存占用收敛：共享固有状态后实例数下降，内存压力随之降低。(3) 效率提升：减少频繁创建销毁的开销，系统响应更快。

短板在于：

+   (1) 管理复杂度上升：需要引入共享对象的管理机制，设计难度增加。(2) 状态可共享的限制：享元内部状态必须能安全共享，这对模型设计与扩展形成约束。(3) 并发安全隐患：多线程同时访问时需做同步，增加实现负担。

选用前应结合实际场景权衡利弊，确保模式能真正带来资源与性能改善。

# 5.14 代理模式

代理模式属于结构型方案，核心是通过代理层调控对真实对象的访问。代理充当替身，可在请求转发前后加入额外控制。

# 5.14.1 应用场景

常见用途包括：

+   (1) 远程代理：处理对远程对象的调用。
(2) 虚拟代理：对象创建成本高时延迟实例化，待真正需要时才生成。
(3) 安全代理：限定对真实对象的访问权限。
(4) 智能代理：在访问真实对象时加入日志、缓存等增强行为。

# 5.14.2 结构

代理模式包含以下角色。

+   - 抽象主题( Subject )：为真实对象与代理对象提供统一接口，可为接口或抽象类。
- 真实主题( Real Subject )：真实业务逻辑的具体实现，被代理所指向。
- 代理( Proxy )：持有对真实主题的引用并实现同一接口，可在调用前后执行权限校验、缓存等额外处理。

架构进阶手册 / AI辅助设计思路

图5-12 展示了代理模式的构成，其中“Subject”是代理和真实主题实现的共同接口，“RealSubject”表示真实对象，它实现了“Subject”接口的功能。“Proxy”充当客户端和真实主题之间的中介，它实现了与“Subject”相同的接口，并持有对真实主题的引用。“Proxy”可以在将请求委托给真实主题之前或之后执行其他任务。

# 5.14.3 优缺点

优点有：

+   (1) 代理模式可以实现客户端和真实对象的解耦，客户端只需与代理进行交互，无须直接与真实对象进行通信。
(2) 代理模式提供对真实对象的控制和管理，可以在代理中添加额外的逻辑，例如，权限验证、缓存等。
(3) 代理模式可以增强真实对象的功能，通过代理对象可以在不修改真实对象的情况下，对其进行扩展或增强。

不足有：

+   (1) 引入代理对象会增加系统的复杂性，需要额外的代码来处理代理和真实对象之间的交互。
(2) 在一些情况下，引入代理对象会增加请求的处理时间和资源消耗。

整体上代理模式在解耦、控制与功能增强方面有价值，但需权衡复杂度与性能成本。

# 5.15 策略模式

策略模式归属行为型范式，允许在运行期灵活挑选算法。把算法封装到独立策略类中，调用方无需关心具体实现。

# 5.15.1 应用场景

适用情境包括：

+   (1) 系统中存在多个相似算法，且实现可能随时间演进时。
+   (2) 需要在运行时动态切换算法时。
+   (3) 需要把一组相关算法打包成整体，在使用时进行切换时。

# 5.15.2 结构

策略模式由三个核心组件构成。

+   * 策略接口( Strategy Interface ): 规定算法的统一契约，具体策略需实现该接口。
+   * 具体策略类( Concrete Strategies ): 实现策略接口，封装各自算法。
+   * 环境类( Context ): 持有策略接口引用，负责在需要时调用对应策略。

图5-13展示了策略模式的结构，其中，“Strategy”是策略接口，定义了策略类需要实现的方法。“ConcreteStrategyA”“ConcreteStrategyB”和“ConcreteStrategyC”是具体的策略类，分别实现了不同的策略。“Context”是环境类，持有策略接口的引用，并提供设置策略和执行策略的方法。

[PRE41]

# 5.15.3 优缺点

好处有：

+   (1)可以在运行时动态地改变对象的行为，即使在程序运行时也可以根据需要选择不同的策略。
+   (2)可以通过定义不同的策略类避免使用大量的条件语句，使代码更加清晰、简洁。
+   (3)提供一种松耦合的设计，策略类之间相互独立，易于单独修改、扩展和维护。

劣势有：

+   (1)会增加系统中的类和对象数量，每个具体策略类都需要一个对应的类。
+   (2)客户端必须知道所有的策略类，并自行选择合适的策略，这会增加客户端的复杂性。

总体而言，策略模式适合在不同情境下选用不同算法的场合，能提升灵活性与可扩展性，但使用时需权衡类数量膨胀与客户端选择复杂度。
