## 15.4 异步状态管理利器 React Query

15.3.1 节的做法是每次进入聊天视图都向服务器请求最新的对话列表，这样会不会造成资源浪费？对话列表并非每次都会变化，反复出现加载态也会干扰操作流程。浏览器端缓存是一个更理想的方案。不过从 15.2 节可以看出，fetch 或 Axios 这类基础网络库并没有内置请求缓存，缓存策略往往需要结合业务自行设计。与底层 API 相比，我们更需要一层贴近业务、符合 React 特性的解决方案。

在 React 社区里，React Query 已成为主流的异步状态管理库。它不仅提供缓存能力，还为 React 应用的服务端通信提供了全套方案。

### 15.4.1 异步状态到底是什么

React Query 的全称是 TanStack React-Query。除 React 外，TanStack Query 还提供了面向 Vue、Svelte 等框架的版本。名字容易让人误以为它只是发起请求的工具，实际上覆盖范围远大于此。库内部并不会直接提供发起 GET 或 POST 的接口，这部分仍需配合 15.2 节的 fetch 或 Axios。正如官方定义，它是一款专为 React 设计的异步状态管理库。

异步状态和 10.1 节讨论的应用状态是同一类问题吗？异步状态可以理解为来自服务器的状态，与 React 的 state 及其他状态库有三点不同：
- 数据源头是远程服务器；
- 必须通过异步 API 获取或更新；
- 服务器端数据可能在客户端不知情的情况下发生变化，导致本地状态过期。

浏览器资源有限，出于性能和网络考虑只能下载服务器的必要数据，这就不是简单的远程数据同步。相比传统应用状态管理，异步状态管理要解决的挑战包括如何用缓存减少请求、怎样在合适时机更新过期的本地数据、分页处理等。React Query 正是为应对这些挑战而生。也可以继续使用 React state 或 Zustand 管理异步状态，但需要自行设计上述方案。特定需求下可以尝试整合 React Query 与 Zustand，但必须遵循单一事实来源原则，避免同一应用出现重复状态。

这就是 React Query 的缓存机制：useQuery 会根据 queryKey 尝试从缓存读取数据，命中则直接展示。默认缓存会被视为已过期，React Query 会在后台再次请求以更新数据。开发者可通过 staleTime 参数延长缓存有效期，降低请求频率。除主动再次调用 useQuery 外，浏览器窗口重新获得焦点或网络中断后恢复时，React Query 也会后台刷新过期缓存。失败请求会默认自动重试 3 次，可通过 retry 参数自定义。整体 API 设计声明式，与 React 范式高度一致。
