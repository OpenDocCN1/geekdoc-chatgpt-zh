# OpenClaw 安全凭据管理与 Agent 沙盒实操

官方把这套思路描述为增量叠加，而不是强制替换。明文配置仍然可用，你可以挑选需要保护的字段单独升级为 SecretRef，分批完成迁移，无需一次性把所有配置都改动。这种分步方式把从明文向安全过渡的难度压到最低。

这种做法的最大收益是主配置文件可以完整进入版本控制系统，即便仓库为私有，文件内部也不会出现真实密钥。真正的敏感信息被抽离到环境变量、本地存储或 1Password、HashiCorp Vault 等外部密钥服务中，与配置完全解耦。更换运行环境时只需重新提供凭据，不必再搬运密钥文件。

#### SecretRef 三种取值来源拆解

无论采用哪种来源，描述结构都是统一的 `{ source: "env" | "file" | "exec", provider: "...", id: "..." }`。不同之处在于读取位置和校验规则。

**source: "env" —— 环境变量读取**

最简方式。示例：`{ "source": "env", "provider": "default", "id": "OPENAI_API_KEY" }`。id 对应环境变量名称，需符合 `^[A-Z][A-Z0-9_]{0,127}$`，必须以大写字母开头。若变量不存在或为空，解析会报错。

**source: "file" —— 本地文件读取**

示例：`{ "source": "file", "provider": "filemain", "id": "/providers/openai/apiKey" }`。从本地 JSON 或单值文件取值。id 采用 RFC6901 JSON Pointer 定位目标字段。mode 为 "json" 时按指针解析对象；mode 为 "singleValue" 时 id 只能写 "value"，直接返回文件内容。路径需通过权限检查，Windows 下若 ACL 验证不可用则 fail-closed。

**source: "exec" —— 外部程序读取**

示例：`{ "source": "exec", "provider": "vault", "id": "providers/openai/apiKey" }`。OpenClaw 会启动外部可执行程序，通过 stdin 传入请求、从 stdout 读取结果，全程不经 Shell，降低命令注入风险。常用于对接 1Password CLI、HashiCorp Vault CLI、sops 等。默认要求 command 为普通文件，若需兼容 Homebrew 等生成的软链接，可开启 `allowSymlinkCommand: true`，并用 `trustedDirs` 限定可信目录。

#### Secrets 解析的四项设计承诺

OpenClaw 的解析机制围绕四条原则构建：

第一，解析是急切的而非懒加载。Gateway 启动或重载时即尝试解析所有活跃的 SecretRef，而不是等到首次使用时才处理。故障因此出现在启动重载的冷路径，而非请求处理的热路径。

第二，重载过程采用原子交换。先完整构建新的 secrets 快照，全部成功后再一次性替换旧快照。失败时保留上一个可用快照，避免部分更新导致的不一致。

第三，活跃面过滤。只有真正启用了的 Channel、已选用的工具等活跃配置面的 SecretRef 才会被强制解析。未激活面解析失败仅会发出 `SECRETS_REF_IGNORED_INACTIVE_SURFACE` 诊断，不阻断启动。

第四，降级与恢复可观测。重载失败后 Gateway 进入降级状态，发出 `SECRETS_RELOADER_DEGRADED` 事件并继续使用旧快照；下次重载成功后发出 `SECRETS_RELOADER_RECOVERED` 事件，运维可据此监控凭据健康。

### 16.4 沙盒安全机制——为 Agent 限定执行范围

#### 沙盒的定位与边界

即便自托管 Agent 也面临两类风险：模型被精心构造的输入诱导执行不当操作，即提示注入；模型在无恶意输入时仍可能误操作，误删文件或生成破坏性脚本。沙盒是系统层面的应对手段。

官方表述务实：“This is not a perfect security boundary, but it materially limits filesystem and process access when the model does something dumb”。并非绝对安全，但在模型失误时能实质限制文件系统与进程访问范围。

边界说明：沙盒仅覆盖工具执行，如 exec、read、write、edit、apply_patch 等，Gateway 进程本身始终在宿主机运行，不受沙盒约束。这样保证 Gateway 稳定，同时把隔离聚焦在工具调用层。

#### 三种运行模式

可通过 `agents.defaults.sandbox.mode` 全局设定，也可在 `agents.list[].sandbox.mode` 为单个 Agent 指定：

- **off**：关闭沙盒，所有工具直接在宿主机运行。默认值，适合开发测试或完全可信的单用户本地部署。
- **non-main**：仅对非主会话启用沙盒。`session.mainKey` 为 "main" 的会话不受限，群组聊天、消息渠道等会话会被沙盒化。判断依据是 `session.mainKey`，而非 agent id。
- **all**：所有会话均在沙盒中运行，提供最强隔离，适合面向不可信用户或高安全企业场景。

#### 容器作用域

作用域决定容器创建粒度与存活时间：

- **session** 默认：每个会话一个独立容器，会话结束即销毁。隔离最彻底，但新会话需创建容器。
- **agent**：同一 Agent 的所有沙盒会话共享一个容器，容器随 Agent 生命周期存在，可在多次对话间保留中间产物。
- **shared**：所有沙盒会话共享同一容器，创建成本最低，但隔离最弱，不同会话操作互相可见，不适合多用户场景。

#### Docker 后端

Docker 是默认后端，提供基于 Linux 的文件系统与网络隔离。主要配置：

- **image**：镜像名，默认 `openclaw-sandbox:bookworm-slim`，通过 `scripts/sandbox-setup.sh` 构建。需要 Node.js 时可构建 `openclaw-sandbox-common`。
- **network**：容器网络，默认 `none` 完全禁止外网。需要网络时可改为 `bridge` 或自定义网络。
- **setupCommand**：容器创建后执行一次，常用于安装 Skills 依赖的 CLI 工具。
- **binds**：额外挂载，格式 `{ hostPath, containerPath, mode: "ro"|"rw" }`。全局与 per-agent 挂载会合并。
- **workspaceAccess**：容器对真实工作区的访问等级，见下节。

#### SSH 后端与 OpenShell 后端

SSH 后端将 exec、文件工具和媒体读取卸载到远程主机，适合把计算密集型调用从轻量 Gateway 如树莓派转移到更强服务器。采用远程规范模型：首次使用时将本地工作区同步到远程，之后远程成为权威状态，本地改动不会自动同步。SSH 认证材料 identityData、certificateData、knownHostsData 支持 SecretRef，激活时解析后写入临时文件。

OpenShell 后端是 OpenClaw 托管的远程沙盒，复用 SSH 传输并增加生命周期管理。支持两种同步模式：mirror 模式下本地始终权威，每次 exec 前把本地增量同步到远程、执行后再同步回本地；remote 模式初次 seed 后远程权威，后续不自动回传，开销更低。

#### 工作空间访问三级控制

`workspaceAccess` 控制容器可见范围：

- **none** 默认：完全隔离。容器仅能看到 `~/.openclaw/sandboxes` 下的独立沙盒工作区。OpenClaw 会自动镜像符合条件的 Skills 目录，确保 SKILL.md 可加载。
- **ro** 只读：将真实工作区以只读方式挂载到 `/agent`。写操作被禁用，适合仅需读取上下文的场景。
- **rw** 读写：将真实工作区以读写方式挂载到 `/workspace`。修改直接作用于真实工作区，行为与非沙盒一致，安全性稍弱但最便利。

#### 工具策略与沙盒的分工

`tools.allow/deny` 与沙盒是两层独立防护。工具策略先于沙盒生效，决定工具是否可用；沙盒决定可用工具在何种环境运行。二者互不替代。

`tools.elevated` 是高权限逃生舱：授权发件人可让特定 exec 调用绕过沙盒直接在宿主机运行，适用于 Docker 管理、系统配置等宿主机专属操作，应谨慎授予。

### 16.5 Cron 任务调度——让 Agent 主动执行

#### 从被动响应到主动自动化

多数 AI 助手被动等待消息。OpenClaw 的 Cron 打破这一模式，可定义“每天 9 点整理待办”、“每小时检查指标”、“周五提醒提交报告”等任务，无需人工触发，Gateway 按计划自动执行并推送结果。

官方将 Cron 定位为 proactive automation 的核心机制，由 Gateway 管理，独立于用户主会话，可后台静默运行，也可推送到指定消息渠道。

#### 任务结构

一个 Cron 任务由六个字段定义：

- **name** 可选：任务名称，便于 `cron list` 与日志识别。
- **schedule** 必需：触发时间规则，决定何时执行。
- **payload** 必需：执行内容，决定执行什么。
