**8.1 框架设计**

在复合型 Agent 开发中，框架选择直接影响推理、任务分解、工具调用与上下文管理的表现。合适的架构能让 Agent 更好地应对复杂任务，也能提升可控性与稳定性。以下依次介绍 ReAct、Supervisor、Hierarchical 三种典型思路，分别对应轻量化探索、集中调度与层级化组织。

**8.1.1 ReAct**

ReAct 是普林斯顿大学与谷歌研究团队提出的框架，把推理链与工具调用融合，形成“思考→行动→观察→再思考”的闭环。模型在推理时可显式生成思考步骤，并在合适时机触发工具调用，使任务逐步分解推进，整体流程如图 8-1 所示。

[PRE3]

图 8-1 ReAct 架构流程

相较于依赖数据流向和业务定制驱动的工作流，ReAct 更适合应对多变灵活的 Agent 场景。逻辑清晰、可解释性强，开发者能直观看见模型的推理链路。推理与行动交替进行，使 Agent 自然处理动态环境中的复杂任务，尤其适合需要频繁调用外部工具的场景。

例如，用户输入“我下周去北京出差，帮我规划一天的日程，包含天气、路线和餐厅推荐”时，ReAct 会按以下流程运行：

（1）Agent 先推理出需要天气信息，随后调用天气 API。

（2）接着推理出交通方式推荐需求，调用地图 API。

（3）随后思考餐厅建议，调用美食插件。

（4）最终整合输出：“早上 9 点出发，天气晴，建议地铁 x 号线前往会场，午餐可选择 XXX 餐厅。”

这一思想在前几章已有体现，无论是 Function Calling、MCP 还是 A2A，本质都是为模型提供更多行动维度。ReAct 的核心优势在于，工具调用不再依赖额外定制开发，只需统一工具协议，模型即可直接触发。这极大推动了 Agent 生态的发展。

**8.1.2 Supervisor**

ReAct 在复合型 Agent 中应用广泛，其“模型自主决策+工具调用”的核心思想被众多生态延续，并提供了丰富的工具链。

但 ReAct 也有明显短板，即过度依赖单一模型实例完成推理、工具选择到结果整合的全流程。任务链路变长或需要更强全局把控时，错误会不断累积，导致结果不稳定。好比一个简单任务一个人加工具就能完成，若让一个人独自负责整条生产线，仅靠工具很难不出问题。

为此出现了 Supervisor 架构。它引入一个中心调度者 Supervisor Agent 统一管理执行。Supervisor 本身不直接处理任务，而是负责全局规划：拆解目标、分配子任务、调用合适的子 Agent 或工具，最后整合结果。它像项目经理，根据整体目标把任务派给合适的员工，保证协作效率与结果稳定。流程如图 8-2 所示。

[PRE4]

图 8-2 Supervisor 架构流程

在图 8-2 的流程中，Supervisor 调度的对象不再是工具本身，而是各类 Agent。这些子 Agent 又可采用 ReAct 架构，进一步调用不同工具完成具体任务。因此 Supervisor 具备很强的灵活性，能跨领域调用不同 Agent 或工具，胜任多环节跨模块的复杂任务。同时可控性更高，开发者可在调度逻辑中加入规则与约束，确保执行链路符合预期。

例如，用户输入“请帮我生成一份 8 月的市场运营报告”时，流程如下：

（1）Supervisor 识别任务并拆解为“数据收集→数据分析→报告写作”。

（2）调度数据收集 Agent，抓取销售额、转化率、市场投放等核心数据。

（3）调度分析 Agent，进行同比环比分析，生成趋势图与关键结论。

（4）调度写作 Agent，基于数据和图表撰写报告正文。

（5）Supervisor 汇总整合，产出完整的 PDF 报告。

需要注意，Supervisor 作为中心调度者，其设计质量决定整体效果。调度策略不合理会造成资源浪费或执行延迟；任务过多时也可能出现单点瓶颈。因此 Supervisor 适合中高复杂度场景，面对超大规模、全局强耦合且周期长的系统，则需要进一步演进到 Hierarchical 架构。

**8.1.3 Hierarchical**

对于复杂度更高、任务周期更长的场景，通常会引入 Hierarchical 架构。该框架采用层级化组织，构建类似树状结构的 Agent 系统。顶层 Agent 负责接收整体任务并做宏观拆解，中层 Agent 进一步细分子任务，底层 Agent 专注执行具体操作。运行模式与企业组织类似：高层做战略规划，中层做任务分工，基层做具体落实。流程如图 8-3 所示。

[PRE5]

图 8-3 Hierarchical 架构流程

相较于 Supervisor，Hierarchical 结构层次更清晰，任务分解更明确，且具备高度可扩展性：每一层 Agent 都可独立优化或替换，不影响整体架构。这使其在具有天然固定层级逻辑的任务中尤为适用。

例如，用户输入“请帮我完成一个电商网站的自动化测试”时，流程如下：

（1）顶层 Agent 将任务拆分为注册登录、商品搜索、购物车下单、支付订单等模块。

（2）中层 Agent 把“购物车下单”细分为添加商品、修改数量、提交订单、校验信息等子任务。

（3）底层 Agent 调用自动化脚本完成点击、输入、断言等具体操作。

（4）各层逐步衔接，最终汇总生成完整测试报告。

缺点是层级较深，信息传递与上下文保持成本较高，执行效率可能受影响。灵活性也低于 Supervisor，对需要快速调整任务链路的场景适应性较差。方案选择需结合业务复杂度与稳定性权衡。

**8.2 通信设计**

在多智能体系统中，通信设计相当于神经网络。无论是单个模型的流式输出，还是多个 Agent 的复杂协作，都依赖高效稳定的通信机制完成信息传递。

不同协议会直接影响实时性、扩展性与实现复杂度。本节聚焦 Agent 场景下两种常见客户端-服务端协议：SSE 与 WebSocket，对比优劣并结合示例说明实现方式。

**8.2.1 SSE：轻量式流式推送**

SSE 在 LLM 场景中很常见，既可作模型 API 的流式输出，也可作复合型 Agent 系统的通信协议。它基于 HTTP，服务端维持一个单向长连接，通过 text/event-stream 格式持续向客户端推送消息，客户端只需一次 HTTP 请求即可持续接收流式数据，无需轮询。其工作机制如图 8-4 所示。

从示例可见，SSE 最大优势是实现简洁且浏览器原生支持，无需额外库即可实现服务端到客户端的单向流式传输，适合大模型逐字生成、长任务进度推送、实时日志流等场景。其局限也很明显——通信单向，客户端无法主动向服务端发送消息，这在复合型 Agent 交互中常成瓶颈。

在需要 Human-in-the-Loop 或更灵活交互的场景下，SSE 无法胜任，只能额外发起连接模拟请求，因此更适合作单向数据通道而非双向交互通道。

顺带一提，4.3 节提到的 HTTP SSE 替代方案 Streamable HTTP，它基于 HTTP/1.1 的分块传输编码实现流式输出，响应可边生成边返回，在 MCP Server 这类一次请求一段输出的任务型场景表现不错。但它本质仍是一次性请求-响应模型的延伸，不维持长连接，也无天然双向能力。在需要持续上下文与多轮对话状态保持的场景，每次交互都需重建连接，增加开销并削弱实时性与连续性。

相比之下，WebSocket 更适合高交互需求，单一长连接即可实现低延迟全双工通信，支持多轮会话与状态保持，下文将详细介绍。

**8.2.2 WebSocket：全双工实时通信**

WebSocket 也是 LLM 应用和复合型 Agent 系统的核心通信协议。最大区别在于支持全双工：一旦连接建立，客户端与服务端均可主动发送消息，适合高频交互、实时响应的场景，如人机协同、多人协作 Agent、实时推理反馈等。

工作机制比 SSE 复杂。初始阶段仍基于 HTTP/HTTPS 发起握手，握手完成后协议升级为 WebSocket，后续数据传输脱离 HTTP 语义，基于 TCP 的持久化双向连接。客户端与服务端无需频繁发起请求或轮询，低延迟与带宽利用上有明显优势。其工作机制如图 8-6 所示。
