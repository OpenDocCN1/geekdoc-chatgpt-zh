**零库存一句话清理**

> 把 products 表里库存为 0 的商品全部删掉。

发出这类口语化指令后，SOLO 会把你的意图转写为合规的 SQL，再经由安全通道在 Supabase 上执行，最后用通俗的语言把执行结果反馈给你。

把 SOLO 与 Supabase 串联起来，后端数据操作的体验被重写了。没有技术背景的人也能像资深数据库管理员那样，轻松驾驭一个强大的数据库系统。

#### 4.1.4 十分钟产出技术方案与数据模型

PRD 告诉我们要做什么，技术设计文档 TDD 则回答如何做。它像一份施工图，把系统的内部结构和实现路径讲清楚，在后端尤为关键，因为后端是整个系统的地基。

##### 1. 技术设计文档的价值

很多团队拿到需求就直接开写，相当于没有图纸就施工，很容易出现结构性问题，白费时间和成本。

一份合格的 TDD 体现的价值有：

- **形成共同认知** ——让团队对架构选型、接口约定、数据流动有同一套精确理解；
- **提前发现隐患** ——在设计阶段就挑出技术难点、性能瓶颈、安全漏洞，比上线后修复省力得多；
- **提供落地方案** ——为开发者给出清晰的行动清单，明确模块怎样实现、怎样交互；
- **支持后续维护** ——作为项目档案，帮助新人或未来的维护者快速上手，避免改动时引入严重错误。

写好 TDD 需要深厚的架构能力，SOLO 充当一位称职的智能架构助手。

##### 2. 让 SOLO 产出设计文档

SOLO 遵循“先规划后执行”的文档驱动思路。PRD 确定后，可以直接让它继续生成 TDD。

参考提示如下：

> 基于前面确定的写作平台 PRD，产出一份后端技术设计文档。技术栈用 Node.js 和 Express，数据库使用已连接的 Supabase。文档要包含架构图、完整的接口定义和数据模型设计。

几分钟后就会得到结构完整、表述专业的 TDD，通常包含：

- **系统概览**：项目目标、范围与核心技术选型；
- **架构设计**：用图文展示整体分层和各层交互方式；
- **接口定义**：列出所有接口的路径、方法、参数和响应格式，是前后端协作的契约；
- **数据模型设计**：TDD 里最核心的部分，下面展开。

##### 3. 数据模型规划与落地

数据模型定义了要存储哪些信息、信息之间如何关联。以创作平台为例，需要用户表、文章表、评论表、标签表，并明确关系。

- **单用户多文章**：一个用户可以发布多篇文章，这是最常见的情形；
- **多标签共享**：一篇文章可关联多个标签，一个标签可用于多篇文章，这类关系通常借助中间关联表实现。

SOLO 会依据业务需求自动设计模型，清晰列出表名、字段名、类型与约束。表4-1 是 SOLO 为示例创作平台设计的结构。

**表4-1 示例创作平台数据结构**

| 表名 (Table) | 字段名 (Column) | 数据类型 (Type) | 约束/描述 (Constraint/Description) |

|---|---|---|---|

| users | id | uuid | PRIMARY KEY (主键)/用户唯一标识 |

| | email | text | UNIQUE, NOT NULL/用户邮箱 |

| | password_hash | text | NOT NULL/加密后的密码 |

| | username | text | UNIQUE/用户名 |

| | created_at | timestamptz | DEFAULT now()/注册时间 |

| posts | id | uuid | PRIMARY KEY/文章唯一标识 |

| | author_id | uuid | FOREIGN KEY (外键)关联users.id/ON DELETE CASCADE |

| | title | text | NOT NULL/标题 |

| | content | text | NOT NULL/内容 |

| | published_at | timestamptz | 发布时间 |

| comments | id | uuid | PRIMARY KEY/评论唯一标识 |

| | post_id | uuid | FOREIGN KEY关联posts.id/ON DELETE CASCADE |

| | author_id | uuid | FOREIGN KEY关联users.id/ON DELETE CASCADE |

| | comment_text | text | NOT NULL/评论内容 |

| tags | id | uuid | PRIMARY KEY/标签唯一标识 |

| | name | text | UNIQUE, NOT NULL/标签名 |

| post_tags (连接表) | post_id | uuid | PRIMARY KEY/FOREIGN KEY关联posts.id/ON DELETE CASCADE |

| | tag_id | uuid | PRIMARY KEY/FOREIGN KEY关联tags.id/ON DELETE CASCADE |

其中 ON DELETE CASCADE 很重要，被引用的记录删除时，关联的文章、评论等会跟着自动清理，保证数据完整。

这份模型结构清晰，符合设计规范。无需手写建表，只要下指令：

> 按这个数据模型执行，连接 Supabase 创建这 5 张表，并配置好主键、外键及级联删除。

SOLO 会解析文档，生成对应 SQL 并在 Supabase 中建好表。

##### 4. 文档随需求演进

开发是持续演进的。需求变更比如新增点赞，代码和设计文档必须同步更新，否则文档会脱节变成技术债。

SOLO 的优势是把文档和代码视作整体。提出新需求时，它先更新 TDD 里的数据模型和接口定义，再据此改动代码。文档驱动的流程确保蓝图和最终产品始终一致，为长期维护打基础。它把撰写文档、预先设计等工程实践融入自动化，让项目结构更优、更易维护。

#### 4.1.5 十分钟搭建认证与业务逻辑

有了数据库基础和清晰设计，就可以构建后端核心功能：用户认证和业务逻辑。

##### 1. 用户认证

主流方案有三种：

- **Session 会话**：登录后服务端记录状态并返回 Session ID，后续请求携带该 ID 校验。是有状态方案，在分布式环境下扩展困难。
- **JWT**：登录成功后服务端签发加密令牌，客户端保存并在请求中带上。服务端无需保存会话，是无状态方案，适合前后端分离和微服务。
- **OAuth 开放授权**：让用户用微信、抖音等第三方账号登录，认证过程委托给第三方，适合社交登录和授权访问。

表4-2 认证方式对比

| 认证方式 | 状态 | “凭证”存储位置 | 适用场景 |

| :--- | :--- | :--- | :--- |

| Session | 有状态 | 服务器端 | 简单的网站应用 |

| JWT | 无状态 | 客户端 | 现代前后端分离的应用、API、微服务 |

| OAuth | 无状态 | 第三方服务 | 第三方社交账户登录、授权访问 |

对非技术人员选型有难度，借助 SOLO 只需描述需求：

> 为写作平台做完整用户认证，支持邮箱密码注册登录，使用 JWT，信息存在 Supabase users 表，密码存储前用 bcrypt 做加盐哈希。

SOLO 会自动完成：

- 生成注册登录接口；
- 注册时校验邮箱格式和唯一性，用 bcrypt 加盐哈希不可逆加密后写入 Supabase；
- 登录时比对哈希；
- 登录成功签发 JWT，后续请求通过中间件校验令牌，确认身份和权限。

几分钟即可得到专业可用的认证系统。

##### 2. 业务逻辑

认证完成后，需要通过 API 端点暴露核心业务，类似餐厅菜单。

- GET /api/v1/posts 获取文章列表
- POST /api/v1/posts 创建文章
- PUT /api/v1/posts/{id} 修改文章
- DELETE /api/v1/posts/{id} 删除文章

不用记术语，用用户故事格式描述即可：作为一个<角色>，我想要<行为>，以便<收益>。例如：

> 实现文章管理核心功能。
> 1. 已登录用户希望能发布包含标题和正文的新文章，以便分享观点。
> 2. 访客希望能获取已发布的文章列表，以便浏览内容。
> 3. 文章作者希望能删除自己的文章，以便管理内容。

SOLO 能理解这种指令并生成对应端点和代码。删除文章时，代码会自动加入权限检查：先用 JWT 确认身份，再查数据库确认是否为作者，两者都通过才执行删除。

##### 3. 安全性与最佳实践

AI 生成的代码安全吗？SOLO 把安全作为设计核心：

- **依托成熟框架**：基于 Node.js、Express 等经过验证的开源框架，遵循安全编码规范，自动过滤用户输入防注入，密码单向加密；
- **优先集成专业服务**：认证、数据交互等高风险环节优先接入 Supabase 等 BaaS，由专业厂商保障传输加密和存储安全；
- **透明可审查**：所有代码完全开放，可随时请专家复核。AI 执行，你保留最终监督权和所有权。

这样既大幅提升效率，也为应用筑起安全防线。

#### 4.1.6 十五分钟完成完整项目

前几节分别掌握了连接数据库、生成设计文档、实现核心功能。现在把流程串起来，15 分钟内从想法到上线一个带前后端的个人写作平台。

##### 1. 项目需求分析

基础完备的平台需要：

- **用户模块**：邮箱密码注册登录退出，区分普通用户和管理员；
- **文章模块**：登录用户可创建编辑删除自己的文章，任何人可查看列表和详情；
- **评论模块**：登录用户可评论，作者或管理员可删评论，任何人可查看；
- **技术架构**：后端 Node.js + Express 提供 RESTful API，数据库 Supabase， 前端简约 SPA，与后端交互，部署到 Vercel。

##### 2. 用 SOLO 完成全流程开发

新建项目，下第一个指令：

> 从零构建完整的个人写作平台，按以下步骤自主完成。
> 1. 规划：生成 PRD 和后端 TDD。TDD 必须包含基于 Supabase PostgreSQL 的完整数据模型 users、posts、comments、tags、post_tags，明确字段关系约束，并定义所有 RESTful API。
> 2. 后端与数据库：技术栈 Node.js 和 Express，连接已授权 Supabase，按 TDD 自动建表。
> 3. 核心功能：搭建 JWT + bcrypt 认证；实现文章发布、评论管理、标签关联的完整 API，含全部 CRUD 和基于角色的权限控制。
> 4. 前端：生成简洁美观响应式界面，含文章首页、详情页、登录注册页、登录后可访问的创建编辑页，确保能正确调用后端 API。
> 5. 部署：在本地测试无误后部署到 Vercel，给出公开访问地址。

执行后，SOLO 的集成视图会同步展示诞生过程：文档面板先出 PRD 和 TDD，终端面板自动装依赖、配环境、跑迁移并启动服务，代码编辑器实时生成前后端文件，浏览器面板逐步呈现可用界面并可交互，流程视图把复杂任务拆成小步骤并逐项打勾。几乎无需干预，只在关键节点做决策。

##### 3. 项目优化与迭代

软件生命力在于迭代。上线 1.0 后新增“点赞”，直接下指令：

> 为平台增加点赞功能。
> 1. Supabase 新建 likes 表，记录 user_id 和 post_id。
> 2. 创建 POST /api/v1/posts/{id}/like，允许登录用户点赞。
> 3. 创建 DELETE /api/v1/posts/{id}/like，允许取消点赞。
> 4. 更新获取文章 API，返回每篇文章的总点赞数。
> 5. 前端文章详情和列表页添加点赞按钮与计数展示。

SOLO 保留完整上下文，知道如何安全改动文件、数据库结构和前后端交互，高效安全地新增功能。

#### 4.1.7 小结

一次从 0 到 1 的演练不仅做出可运行的平台，更掌握了与 AI 工程师协作的新范式。

- **指令的艺术**：协作效率取决于需求描述质量。清晰结构、无歧义的指令让 AI 事半功倍。工作从写代码转向设计指令和定义规则，需要更强的系统思维和表达力。
- **角色的转变**：几乎不写代码就主导产品诞生，角色从实现者变为定义者、架构师、决策者。技术不再是瓶颈，瓶颈是对产品的想象力和需求定义能力。这种转变孕育出能独立构思并闭环落地的超级个体。
