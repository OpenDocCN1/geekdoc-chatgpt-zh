### 3.3.5 十分钟实战：RLS 锁住数据

目前所有登录用户都能浏览和修改 projects 文件柜里的全部内容。本节目标是打造一套精细的安保规则，确保员工只能触碰自己创建的项目。

RLS 即行级安全，是一种把权限规则下放到数据行层的强力模型。它不是在档案室门口站岗，而是为每一行数据贴上隐形权限标签。用户发起访问时，系统会比对 ID 卡与标签是否匹配，校验全程在数据库内部完成，更加牢固。

下面按步骤配置 RLS，让数字总部拥有细粒度的访问控制。

1. 为项目文件指定归属。在 Table Editor 中打开 projects 表，点击表头最右侧 + 新建列，列名设为 user_id，类型选 uuid，因为 Supabase 用户 ID 即为该格式。点开 Foreign Key 旁的 Add foreign key，在弹框里设置 Schema 为 auth、Table 为 users、Column 为 id。保存关联关系后再保存整张表的修改。

2. 进入策略中心。左侧主导航找到盾牌图标 Authentication，点击后在左侧子菜单进入 Policies 策略。

3. 为 projects 开启 RLS。在策略管理页找到 projects，点击右侧 Enable RLS。若初始显示 Disable RLS，说明 RLS 已默认开启。注意，开启 RLS 的瞬间默认规则为拒绝全部，此时任何 API 都无法读取 projects 数据。这是安全最佳实践：先全部关闭，再择优开放。

4. 新建第一条策略。在 projects 右上方点击 Create policy。

5. 选择策略模板。右侧 Templates 列表中滚动到最下方，选取 Enable users to view their own data only，点击选中，如图3-20 所示。

[PRE1]

图3-20 创建 RLS 策略

6. 设定读取规则。在配置界面填写 Policy Name，例如“用户仅可查看自己的项目”；Policy Command for clause 选 SELECT；将 using expression 改为 (select auth.uid()) = user_id，核心逻辑可参考图3-20 左侧示例。

该表达式含义是，只有当前登录用户的唯一 ID auth.uid() 与行数据的 user_id 完全一致时，才允许读取。

7. 保存策略。点击 Save policy 完成保存。

8. 补充其它操作。按相同思路配置 INSERT、UPDATE、DELETE。

- 插入策略：操作选 INSERT，with check expression 设为 (select auth.uid()) = user_id。
- 修改与删除策略：操作分别选 UPDATE 和 DELETE，using expression 设为 (select auth.uid()) = user_id。

至此完成一次企业级安全配置。RLS 将安全逻辑与数据绑定，规则一旦生效便持续管控。Supabase 的可视化界面让复杂的安全设置变得直观。

### 3.3.6 十分钟实战：搭建文件存储与 CDN 加速

项目管理工具还需要承载需求文档、设计稿、演示视频等附件，需要为总部启用中央仓库 Supabase Storage。

Storage 专为非结构化数据设计，可看作一个大型仓库。通过划分不同存储桶来分类管理文件。创建桶时可指定公开或私有：公开桶的文件只要链接即可访问，私有桶则需权限校验。此外 Storage 自带 CDN，上传后会自动将副本分发到全球边缘节点，大幅提升加载速度。

配置流程如下。

1. 进入存储入口。仪表盘左侧主导航点击桶形图标 Storage，进入管理区。

2. 新建存储区域。点击 New bucket，Bucket name 填 project-files，勾选 Public bucket。生产环境对敏感文件应设为私有并配置策略。点击 Create 完成。

3. 上传文件。进入 project-files 桶，点击 Upload file，从本地选择任意文件上传。

4. 获取公开链接。悬停文件，在右侧三点菜单选择 Get URL，链接即复制到剪贴板。

5. 验证全球加速。另开浏览器标签页粘贴链接回车，文件立即加载。该链接指向 Supabase CDN，全球访问均可获得高速体验。

你已为数字总部部署世界级仓储与物流能力。得到的不只是存储地址，更是自带全球加速的 CDN 链接。传统方案需额外配置与费用，Supabase 已将其无缝集成。

#### 4.1.2 从需求到 API：全流程自主开发

前端自动化流程在后端场景下侧重点不同。以架构师视角重新审视 SOLO 的后端能力。

##### 1. 需求分析与文档生成

每个项目始于蓝图。后端蓝图是严谨的 PRD，明确系统结构与功能规格。

与重视觉的前端 PRD 不同，后端 PRD 核心是“能做什么”与“数据如何流转”，需清晰定义：

- 功能模块：如用户管理、文章发布、评论系统等。
- 用户角色与权限：访客、注册用户、管理员各自可执行的操作。
- 数据实体与关系：用户、文章、评论等实体及关联。
- 业务规则：如每日发文上限、评论字数限制等。

非技术人员撰写结构化文档困难。SOLO 只需自然语言描述即可自动产出符合后端需求的严谨 PRD。例如：

> 为我规划个人博客后端。支持访客、注册用户、管理员三类角色。注册用户可发布管理自己的文章并评论他人文章，管理员拥有全部权限。文章包含标题、内容、发布日期，最终提供 API 供前端调用。

SOLO 启动文档工具，将描述转化为结构清晰、逻辑严谨的后端 PRD，成为开发蓝图。

##### 2. 环境配置与依赖管理

蓝图完成后需搭建环境并选定技术栈。

技术栈包括编程语言、框架、数据库、Web 服务器等。对于新手，版本冲突、依赖缺失、系统差异常导致阻塞。

SOLO 会根据 PRD 自动选型。例如需要大量实时消息时，可能优先选择擅长高并发 I/O 的 Node.js。

确定后，SOLO 在 Terminal 面板自动执行安装语言环境、下载框架、配置数据库连接等命令，短时间内完成专业稳定开发环境。

##### 3. 编码与错误修复

环境就绪后进入编码，将需求转化为可执行指令。

SOLO 逐条阅读 PRD 与技术设计文档，把“创建注册接口”“实现权限校验”等需求转化为高质量后端代码。

同时具备自检修复闭环：编写后即在终端运行，如启动服务或单元测试。若出现 ECONNREFUSED、SyntaxError 等错误，会自动分析日志并修改，直至解决。也可把外部报错粘贴给它定位修复。

##### 4. 本地测试与预览

后端测试不如前端直观，输出多为终端 JSON 或数据库变更。

SOLO 的集成工作区内置浏览器工具，测试更直观。后端逻辑构建时，浏览器可同步渲染可交互前端界面调用接口，无需专业 API 测试工具即可实时验收。

例如用户登录 API 完成后，浏览器立即出现登录页，可尝试正确或错误密码，观察响应与日志验证逻辑。

##### 5. 部署与上线

功能验收稳定后需发布到互联网，即部署。

传统部署需配置服务器、域名、证书、防火墙与 CI/CD，多由 DevOps 负责。

SOLO 深度集成 Vercel 等云平台。确认完功能后输入如“功能测试完成，请部署博客后端到 Vercel”，即可自动打包、配置环境变量、发布上线，数分钟后获得公开 API 地址，完整生命周期结束。
