客户端要摸清服务器能提供哪些资源，唯一入口就是资源清单接口。向服务器发出 resources/list 请求，就能拿到一份可用的资源目录。接口本身支持分页查询，通过传入可选的游标参数，可以把成千上万的资源分批拉取回来。

[PRE0]

返回的每条资源记录都包含几个关键字段：唯一标识 uri、资源名称 name、可选的展示用标题 title、可选的说明描述 description、可选的 MIME 类型 mimeType，以及可选的字节大小 size。

##### 2. 资源读取（resources/read）

需要内容时，客户端用 resources/read 请求指定目标资源的 URI，服务器随后把对应的资源内容以列表形式返回。

[PRE1]

[PRE2]

资源本身可能是文本也可能是二进制。文本类走 text 字段，二进制类则使用 Base64 编码的 blob 字段。有个细节值得注意，一次 resources/read 调用可以返回不止一个资源，例如读取目录时，服务器可以直接把目录下的文件集合一并返回。

##### 3. 资源更新通知（notifications/resource/updated）

MCP 给资源实时变化提供了两套方案。

（1）列表变更通知：当资源清单发生变化时，只要服务器声明了 listChanged 能力，就会主动推送变更提醒。

[PRE3]

（2）资源订阅机制 resources/subscribe：客户端可以对某个具体资源进行订阅。

[PRE4]

[PRE5]

一旦被订阅的资源有更新，客户端会先收到通知，再通过 resources/read 拿取最新内容。取消关注则调用 resources/unsubscribe 即可。

错误处理上，服务器应遵循标准 JSON-RPC 规范，常见错误有资源不存在 -32002 和内部错误 -32603。

[PRE6]

[PRE7]

在搭建 MCP Server 并落地资源 API 时，安全必须放在首位。服务器要把模型暴露到本地文件、数据库乃至外部 API，任何疏漏都可能带来严重风险。可靠的 Server 需要构建纵深防御。

第一道防线是严格校验资源 URI。所有进来的 URI 都应视作不可信输入。校验不只是看格式对不对，更要确认它落在预期授权范围内，防止路径穿越攻击，比如被构造出 ../../etc/passwd 之类非法路径去读取敏感文件。URI 校验就是守住资源的第一道门。

确认 URI 合法后，第二道防线是细粒度的访问控制。不同资源敏感度不同，含个人隐私、系统配置或商业机密的资源必须做严格权限管控。判断不只是能不能访问，还要结合操作类型读取、写入或执行来决定是否允许。权限校验最好在真正执行操作前一刻完成，保证授权状态实时有效，贯彻最小权限原则，让客户端只能触碰完成任务所必需的最小范围。

第三道防线是数据完整性。处理二进制资源如图片、音频或可执行文件时，必须先做正确编码，MCP 里通常是转成 Base64。因为传输层基于文本的 JSON-RPC，裸流二进制极易导致解析错误或损坏。编码之后，客户端收到的内容才能与源文件完全一致，保障整条链路的保真度。总的来说，严谨的 URI 校验、最小权限的访问控制和审慎的二进制编码，是构建安全可用的 MCP Server 的关键。

#### 2.3.2 工具集成

MCP 让服务器可以向大模型暴露可调用的工具，从而实现查询数据库、调用外部 API、做计算、获取实时数据或执行自动化等能力。每个工具以唯一名称标识，并附带使用方式的元数据说明。

在 MCP 中，工具大致可归为 6 类，如表2-4 所示。
