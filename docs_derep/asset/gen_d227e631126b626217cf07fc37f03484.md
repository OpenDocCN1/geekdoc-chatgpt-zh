在 Agent 架构里，Serverless 函数扮演着“休眠技能包”的角色。架构师可以把成千上万的工具以 Serverless 形式部署到云端，它们静静躺着，构成 Agent 庞大而灵活的外挂能力池。Agent 本身不用扛着笨重的本地代码库，等到产生明确意图的瞬间，通过 API 把对应的函数叫醒就行。

### 4. 从接口调用到函数调用的跃迁

OpenAI 在 2023 年推出的 Function Calling，本质上是 Serverless 思想在 AI 领域的投射。

Serverless 的核心范式是 Handler(Event) → Result。Function Calling 则把函数的元信息结构化为 {name, description, parameters}。两者配合天衣无缝。于是架构师可以批量开发 Serverless 函数，并把其定义注册给 Agent。从此 Agent 化身超级路由器，不必关心函数跑在哪台机器，只需判断何时触发。图2-8 描绘了 Agent 的唤醒链路。

### 5. 终局形态：液态化软件

Serverless 把分布式解耦推向了极致。

空间解耦：代码在哪运行已不重要。时间解耦：运行完全由事件驱动，无需预先排程。

这为未来的多 Agent 协作奠定了基础：成千上万的微型 Agent 与工具像液体一样在网络中自由流动、动态组合与即时拆解。软件不再是以“大教堂”形态存在的固态结构，而是演变为流动不息的“海洋”。

至此，单体被微服务拆解，Kubernetes 实现了声明式编排，Serverless 提供了极致的原子化算力。表面看，灵活、弹性、按需分配的理想架构似乎已到手。

[PRE0]

然而，打开运行在 Serverless 容器里的代码，会发现现实并未真正改变。架构已焕然一新，写法却仍停留在几十年前。我们依然用 C++、Java 或 Python 一行行堆砌僵化的 if-else 逻辑，试图以有限规则穷尽无限复杂的现实。肉身已是高度分布、弹性伸缩的现代架构，大脑却仍是靠发条齿轮驱动的旧式程序逻辑。

这种割裂感在 2017 年达到临界点。要迎接 Agent 的诞生，我们不仅要重构服务器，更要重新定义“编程”本身。

## 2.3 软件2.0：概率与代码的交汇

2017 年，时任特斯拉 AI 总监的安德烈·卡帕西 Andrej Karpathy 发表文章《Software 2.0》，这不仅是新名词的提出，更是对计算机科学根基的深刻反思。

在此之前，软件工程致力于消除不确定性；此后，软件工程开始学会利用不确定性。

### 2.3.1 规则时代的终结：告别 if-else 编程

在软件1.0 时代，开发者如同拥有绝对权力的建筑师，对每一行逻辑进行“独裁式”控制。只要能把问题转化为极其精确的指令序列，计算机就能实现，确定性是基石。

进入以神经网络为代表的软件2.0 时代后，这种确定性被打破。开发者的角色从“建筑师”转向“园丁”或“引导者”——我们提供“土壤”即训练数据，并设立“栅栏”即损失函数与约束，而具体的决策逻辑与能力则由模型在海量数据中自行涌现。

### 1. 软件1.0：人扮演编译器

在软件1.0 框架中，开发者的任务是将问题空间转换为代码空间。

场景：写程序判断图片是否包含“猫”。做法：先在脑中把“猫”解构为线条、颜色、纹理、耳朵形状等基本元素，再用 C++ 编写条件语句实现边缘检测，判断特征是否存在。

每一行代码都是人类认知的直接固化。开发者不仅要精通编程，还要深入理解“猫”的特征，甚至要把握现实中千变万化的类猫形态。

然而现实复杂度远超人类显式编码极限。你永远写不完所有“像猫但不是猫”的情况，也写不出覆盖全部例外的 else 分支。因此在视觉识别、自然语言处理、复杂决策等充满模糊与不确定性的任务上，软件1.0 显得笨拙又脆弱。

### 2. 软件2.0：数据成为源代码

## 2.3.2 MLOps 给 AgentOps 的启示

当代代码演变为数据时，传统 DevOps 工具链如 Git、Jenkins 便力不从心。你无法对 100GB 二进制模型文件执行 git diff 查看逻辑改动，也无法通过 assert 断言模型在所有情况都正确。

在软件2.0 时代，我们无法像调试传统代码那样在 IDE 中“调试”神经网络权重。那如何保障质量？

为驯服软件2.0 的“黑盒”特性，MLOps 应运而生。它并非单一工具，而是一套管理概率性软件生命周期的方法论，为 Agent 架构师提供三大启示。

### 启示一：数据即代码

软件1.0 时代源代码是真理唯一来源，代码不变行为不变。而软件2.0 时代数据取代源代码的核心地位：即使模型架构与代码不变，只要训练数据改变，如混入10%脏数据，模型行为可能剧变。

对 Agent 开发者，我们通常不直接训练基座模型，而是聚焦提示工程。Prompt 并非代码中的字符串常量，而是需版本控制的关键资产。System Prompt 从 v1.0 升级到 v1.1 的微小改动，可能导致 Agent 行为风格甚至“性格”根本变化。

同时出错时需追溯：当时使用哪个版本的知识库？是否混入过期文档？这种追溯机制被称为上下文谱系，因为知识库变更可能迫使下游 Prompt 重构。

MLOps 告诉我们要像管理代码一样严谨管理数据和 Prompt，这推动了 LangSmith、LangFuse 等 AgentOps 平台的发展。

### 启示二：测试从确定走向概率

传统单元测试是二元的：通过或失败。但在 MLOps 中我们面对的是概率分布，无法要求模型识别猫达到100%准确率，只能追求超过95%。

这是 Agent 开发最深刻的教训：Agent 行为本质难以测试，除非构建专门的评估数据集 Evals。

面对 LLM 输出，无法简单写 assert response == "巴黎"，模型可能答“法国的首都巴黎”。此时需引入 LLM-as-a-Judge，用另一个模型判断“这句话是否等同于‘巴黎’”。

Agent 质量不由传统测试通过率决定，而取决于“在100个真实场景中，新版 Agent 战胜旧版的次数”。

MLOps 告诉我们要放下对确定性的执念，转而构建基于统计的质量护栏。

### 启示三：可观测性要语义化

DevOps 时代监控 CPU 使用率、内存、延迟和错误率。但在 MLOps 时代，模型可能 CPU 占用很低、延迟极短且无报错，却已“疯了”——输出有害内容或开始胡言乱语。这就是数据漂移或概念漂移。

对 Agent 的监控必须深入语义层面：不再依赖传统的 INFO/ERROR 日志，因为在 LLM 场景下它们往往无意义；而要关注追踪轨迹，可视化 Agent 的完整推理链路——用户输入→检索→思考→工具调用→响应。

我们还需要实时检测 Agent 输出是否变得“有毒”，或陷入无意义的“复读”。

MLOps 告诉我们不仅要监控软件跑得快不快，更要监控它想得对不对。

MLOps 是一场软件2.0 时代的工业革命，将炼金术式的模型训练转变为可复现、可管理的工程流程。对 Agent 而言，我们继承 MLOps 理念并发展为 AgentOps。不再直接训练模型权重，而是专注精调 Prompt；不再仅仅监控损失函数，而是更注重追踪思维链。

图2-12 展示了运维范式从代码到思维的演进。

然而无论工具多么先进，概率模型的核心特征——不确定性——始终存在。在概率地基上如何建造坚固的“房子”？这是每位 Agent 架构师必须直面的终极命题。

### 2.3.3 驯服不确定性：在概率之上建可靠系统

我们承认软件2.0 具有概率本质，但不意味着必须接受不可靠系统。恰恰相反，Agent 架构师的核心竞争力，正是通过确定性工程框架驾驭并约束概率智能核心，构建高可靠性系统。

软件1.0 时代可靠性源于“证明”——通过逻辑推导和单元测试确保输入 A 必然输出 B。而软件2.0 时代可靠性源于“统计”与“约束”。

这构成根本矛盾：用户要求 100% 确定的结构化数据如 JSON，而 LLM 本质倾向生成充满可能性、富有创造性的文本如诗歌。

为解决这一矛盾，“三明治架构”是一种有效策略，如图2-13。核心理念是通过两层确定性逻辑包围中间概率模型。

### 1. 输入侧防御：提示工程加固

在不确定性发生前先收敛。这已不只是写更好 Prompt，而是引入类似类型系统的强制性约束机制，即结构化强制。

当前模型如 GPT-4、DeepSeek 已支持 JSON 模式或 Function Calling，关键在于推理阶段采用受限解码技术。

例如要求模型生成 JSON 键时下一字符必须是冒号，生成值时严格符合 JSON Schema 定义的数据类型。这种约束在数学上消除“语法错误”可能，将不确定性有效限制在“语义”层面。

### 2. 输出侧校验：验证器机制

生成可以概率性，但验证必须是确定性。这是应对幻觉最有效手段之一——为 Agent 构建具备“怀疑”能力的反馈回路。

以代码为裁判：Agent 生成计算斐波那契数列的 Python 代码时，直接运行它。若解释器抛出 SyntaxError，就说明输出有误。此时可将具体报错信息反馈给模型，促使其修正并重新生成。

以搜索为裁判：Agent 声称“2024 年奥运会在柏林举办”时，调用外部搜索工具核查。若搜索结果与生成内容不符，则立即触发修正机制，引导 Agent 更新输出以符合事实。

这正是第7章将讨论的 ReAct 模式核心逻辑：通过确定性环境反馈不断坍缩概率生成空间，引导模型输出趋向准确可靠。

### 3. 过程冗余：自洽性提升

如果单次生成不可靠，生成多次呢？通过采样与投票机制，让 Agent 对同一问题在 Temperature>0 设置下独立推理多次如5次。若多数路径输出42，少数输出100，则系统采纳多数结果。这种基于冗余计算的策略能显著提升系统鲁棒性。

由此可见，软件2.0 并未取代软件1.0，而是共生共存。现代 Agent 架构本质是用软件1.0 框架如代码、工具、流程包围软件2.0 内核如模型、推理。我们以确定性逻辑引导不确定性智慧，以刚性约束规范柔性生成。

## 小结：地基已夯实

第2章并未急于切入 Agent 本身，而是系统梳理软件工程为迎接 Agent 时代所做的长期准备。

函数与流让我们掌握无状态函数式与异步响应式编程范式，使软件契合 AI 思考节奏。分布式教会我们通过接口化与 Serverless 原子化构建灵活可扩展系统，为 Agent 提供无限延展的“手脚”。软件2.0 引导我们学会在拥抱概率性的同时施加工程化约束，从而在不确定性中建立对确定性的信心。

历史铺垫已完，Agent 登场水到渠成。Transformer、Docker、API、向量数据库等关键技术积木如今都已就绪。现在需要一种全新架构思想，将这些组件有机整合，构建出具备感知、记忆、思考与行动能力的“新物种”。

这个新物种不再是冰冷的代码工具，而是人类意志的延伸，是数字世界的原住民。

地基已然夯实，肉身业已铸就。如今躯壳只差最后一样东西——灵魂。

是什么让一堆无状态的函数涌现出“智能”？又是什么将概率性预测转化为有目的“决策”？要回答这些，必须深入躯壳内部，解剖那个被称为“模型”的黑盒。

## 从设计转向培育：步入 Agent 时代

当我们把 LLM 引入软件架构核心时，奇点已然临近。软件不再仅仅是对人类指令的响应，而是开始展现意图和自主性。

我们不再是在设计系统，而是在培育物种，见图3-1。

### 3.1 从工具到伙伴：Agent 的本质

什么是 Agent？技术上看，可能只是不断调用 LLM API 的死循环脚本。然而从交互哲学看，它标志人机关系根本重构：从“命令与控制”转向“意图与协作”。

### 3.1.1 交互升级：从命令到对话

现在，你也许不会对下面这样的对话感到惊讶。

开发者：我在设计一个图书推荐系统，但不确定该使用协同过滤还是内容过滤。

Agent：让我帮你分析一下。你的用户规模有多大？是否已经积累了足够的历史交互数据？

开发者：大约有 5000 名用户，系统刚上线 3 个月。

Agent：考虑到你的用户规模和当前的数据量，我建议采用混合推荐策略。在初期以内容过滤为主，因为若采用协同过滤，很可能面临冷启动问题。你可以按照如下步骤设计。

首先，基于图书的内容特征如类别、作者、主题词等构建内容相似度模型。

其次，在收集用户行为数据的同时，逐步引入协同过滤机制。

最后，当用户交互数据足够密集时，例如每名用户有20条以上评分或行为记录，再逐步提高协同过滤权重。

需要我为你写一个初始的实现框架吗？

开发者：好的，但我还在纠结是否要引入时间衰减因素。

Agent：这是一个很好的考量！时间衰减确实重要，特别是对于图书推荐。不过要注意区分。

经典作品：用户兴趣通常持久，衰减应该很慢，甚至可以忽略。

时事相关书籍：热度随时间快速下降，应采用较快的衰减函数。
