**4.使用流程示例**

假设 MCP 服务端内有一个“数据库智能查询”工具，接收到用户用自然语言提出的问题后，服务端需要把问题转成 SQL。开发者通常希望借助大模型完成这一步的 SQL 生成。因此该工具被触发时，会执行一次 sampling/createMessage，把原始问题及相关上下文发送给客户端，请其生成对应的 SQL。整个采样的交互链路如下。

（1）服务端向客户端发出采样请求，并附带上下文信息，如原始问题等。
（2）客户端接收到请求后，会弹出界面请用户进行审批。
（3）用户确认通过后，客户端调用本地大模型执行实际生成。
（4）大模型把生成结果返回给客户端。
（5）客户端再次把生成内容展示给用户核对，例如让用户检查生成的 SQL 是否安全可执行。
（6）用户确认无误后，客户端把审核通过的结果发回服务端。
（7）服务端据此进行后续处理，比如把 SQL 发送到数据库执行，并将查询结果作为工具输出返回给客户端。

借助采样能力，服务端在需要时可以回调客户端的大模型，实现更高阶的 AI 辅助，相当于在工具内部嵌套调用了大模型，从而获得一定的智能。整个过程中客户端始终掌控模型调用的主动权，包括选择使用哪款模型、是否获得用户同意等，这避免了模型被滥用。同时服务端开发者无需关心具体的模型接口如 OpenAI API 等，实现了开发上的解耦。

MCP 规范还定义了一些通用辅助能力，例如 ping、心跳检测、进度通知等，具体将在高级开发部分即第五章中展开说明。

# **基于 SDK 开发 MCP 服务端**

## **3.1 认识 MCP SDK**

### **3.1.1 关于 MCP SDK 及准备**

MCP SDK 是官方发布的开发工具包，目前覆盖 Python、TypeScript、Java、C# 等语言，已完整实现 MCP 规范。借助它，开发者可以便捷地完成：

（3）使用标准传输方式，如 stdio 或 SSE 进行通信。
（4）自动处理交互消息格式及会话生命周期等底层细节。

依托这些能力，可以开发企业内部端到端的智能体。例如，先用 MCP 服务端封装公司内部的数据库查询、文件检索等功能，再让智能体连接该服务端，使得智能体内部的大模型能够安全调用这些能力获取最新数据，从而增强应用效果。

### **3.1.2 了解 MCP SDK 的层次结构**

不论使用哪种语言，MCP SDK 都遵循统一的分层设计。以 Python SDK 为例，各层职责清晰、接口明确，通过协同实现完整的 MCP 集成架构与协议规范。其分层示意图如图 3-1。

[PRE2]

图 3-1

先做一个概览，后续开发中会逐步深入。

**1.应用层（Application）**

这是开发者最常操作的层。客户端可在此开发带用户界面的聊天机器人或智能体；MCP 服务端则在此实现与外部数据的交互逻辑，完成工具、资源、提示等功能的内部实现，并通过符合规范的接口向客户端开放。

应用层通过会话层提供的 API 发起请求并接收响应，或接收请求并做出回应。为提升开发效率，SDK 在这一层提供了若干便捷函数与装饰器。

**2.会话层（Session）**

会话层负责客户端与 MCP 服务端之间会话的维护与交互，主要完成请求消息的发送与响应、通知消息的收发。例如需要推送 listChanged 或 progress 通知时，就可调用会话层提供的接口。

**3.传输层（Transport）**

传输层实现基于 stdio 本地或 HTTP 远程的传输，具体包括 HTTP POST 与 SSE 通道的建立和消息传输。例如建立 SSE 连接时可使用传输层的 sse_client 接口，建立 stdio 连接时可使用 stdio_client 接口。

### **3.2.2 开发工具功能**

工具是 MCP 服务端提供的可执行函数或操作。客户端可通过标准方法 tools/call 调用工具以执行操作、查询数据，从而扩展自身能力。与资源不同，工具通常涉及计算或产生副作用，例如修改文件、调用外部 API，功能上类似于 RESTful API 中的 POST。

在 FastMCP 框架中，只需对普通 Python 函数加上 @mcp.tool() 装饰器，即可将其注册为工具。框架会利用函数的类型注解推断参数类型与返回值类型，并把文档字符串用作工具描述。因此建议为每个工具函数撰写清晰的 docstring，以便框架准确理解其用途。
