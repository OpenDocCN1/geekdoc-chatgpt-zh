要意识到，意图分类往往是强业务定制的活儿，用公开数据集来做校验，很难代表真实使用效果，分数的参考价值也有限。更稳妥的做法是在训练前就准备一套专属的业务校验集，这套数据最好具备以下特质：

· 紧贴业务场景：覆盖实际会出现的典型意图和边缘情况。
· 与训练数据隔离：保证检验结果能真实体现泛化水平，而非记忆回放。
· 体量适中可控：在保障覆盖率的前提下，避免检验成本失控。

用定制化的检验集，就能更精准地衡量模型在目标业务环境下的分类效果，也为后期的优化迭代提供可靠依据。

**2．基于 Prompt 分流**

在意图数量不多、对准确率要求不高的轻量场景里，用提示词工程来完成分类是可行的。相比训练小模型，这种方式省掉了数据采集和训练环节，上线很快，特别适合做原型验证或低成本试点。提示词的核心作用是告诉模型该如何理解问题，例如可以这样写：

请判断以下用户输入属于哪一类：

【意图类别】查询天气、点餐服务、订单查询、闲聊

【用户输入】帮我看看今天上海的天气

模型收到提示后，会借助自身的语言理解能力进行匹配归纳，最终输出“查询天气”之类的分类结果。这种做法轻量灵活，很适合业务早期还没有积累大量标注数据的阶段。只要持续迭代提示词，效果就能逐步提升。

迭代中最有效的方式就是加入关键示例，也就是 Few-shot Prompting，例如：

请判断以下用户输入属于哪一类：

【意图类别】查询天气、点餐服务、订单查询、闲聊

## 示例：

用户输入：今天深圳下雨吗？ → 查询天气

用户输入：帮我点一份牛肉盖饭 → 点餐服务

现在请判断：

用户输入：帮我查一下昨天的订单状态

有了示例引导，模型更容易得出“订单查询”的结论。但基于提示词的方案也有局限：表现高度依赖提示词的质量与设计思路，表述不清或类别边界模糊时容易出错；当业务意图不断扩容时，单纯靠枚举提示词很难保持稳定和可扩展。

因此在工程实践里，提示词更像一种轻量验证手段，适合快速试错和需求验证；规模化落地时，通常需要结合小模型训练或混合策略来进一步提升准确率和鲁棒性。

**8.5.2** **Human** **in** **the** **Loop**

除了让模型自动分类，引入人机协同的 Human in the Loop 机制是另一条重要优化路径。核心思路是让人工在模型易错、判断模糊或高风险的场景下介入，保证系统整体可靠可控。

· 逻辑规则法：组合关键词、正则、上下文状态等形成精细计算逻辑。

更重要的是，HITL 的价值不止于兜底补救，更在于反馈优化。人工在分流时的操作会被记录，作为新标注数据回流到训练集或评测集。循环迭代后，模型在原本模糊的边界意图上会越来越稳定，自动化覆盖率和准确率随之提升。

比如智能家居助手，“关掉灯”通常能被准确识别，但“帮我调暗一点”对“暗”的理解因人而异，容易歧义。这类模糊表达可以通过 HITL 推送到人工后台确认，再把结果反馈给模型学习。又如在线医疗咨询，用户输入“最近胸口有点闷，是不是心脏病？”这类高风险问题，即使模型识别准确，也应强制转人工医生确认，避免误判酿成严重后果。

从应用角度看，HITL 通常出现在两类场景：一是高风险行业如金融、医疗、政务，错误成本高必须人工兜底；二是新业务冷启动期，数据不足模型不稳，人工参与可快速填补空白并积累数据。因此 HITL 不是削弱模型，而是增强策略，让智能体具备弹性边界，高频低风险任务保持自动化，关键环节靠人工保障质量。

**8.5.3** **自回归机制**

在置信度与人工接入之外，自回归机制是另一条常见的优化思路。这里的自回归指模型生成结果后对自身输出进行校验与迭代修正。每次产生候选答案的同时系统会做合理性验证，通过则保留，不通过就重试或转人工，多轮自检提升最终准确度。

电商客服中用户说“我想退货”，模型首次输出“售后问题”，校验规则发现缺少商品或订单号等关键信息，就触发一次重试，修正为更明确的“投诉售后（退货）”。这样无需人工也能对模糊或信息不足的意图做自动纠偏。

**8.5.4** **记忆机制**

记忆机制是保持上下文连续性和积累经验的关键。相比单轮处理，记忆让系统能在多轮交互中记住用户的历史输入、语境和反馈，并在后续任务中利用，提升一致性、个性化并避免重复询问和逻辑冲突。

电商客服记住用户曾反馈“配送地址错误”，下次咨询时可主动核对；医疗问诊中记录过往症状和诊断建议，保证交流连贯。

技术上常见三类：

· 短期记忆：保存当前会话上下文，保证多轮对话连贯。
· 长期记忆：通过向量数据库或结构化存储保留用户历史，供未来调用。
· 动态更新：结合新反馈动态调整记忆，避免过时信息累积。

**8.5.5** **安全边界**

构建智能体时，安全边界不可或缺。它为系统设定合理限制，防止越界行为和潜在风险。模型能力虽强，缺少边界就可能输出错误、敏感或有害内容，带来业务与合规隐患。

常见策略有三类：

1. 权限边界：明确模型调用外部工具、访问数据库或执行动作的权限范围，避免随意读写关键数据。例如金融场景只能读取用户授权的交易信息。
2. 内容边界：通过过滤规则、敏感词检测、正则约束或 Prompt 指令防止不当内容生成。电商客服需避免因恶意输入产生攻击性话术，常采用硬边界与软边界结合。
3. 行为边界：为模型动作设定流程化约束，确保输出和操作符合业务规则。医疗问诊仅限健康建议不能替代诊断；电商客服只能处理预定义动作，超出范围转人工。

安全边界需随业务场景、更新频率和敏感程度动态调整。常见实现方式包括 Prompt 约束、训练或微调、规则与模型混合机制。

例如电商客服只允许回答订单查询、售后投诉等合法业务问题，超出范围一律拒绝。可通过 Prompt 约束实现，示例如下：

**8.6** **成本优化策略**

大模型驱动的 Agent 系统成本优化必须长期关注。Agent 涉及多轮对话、工具调用、上下文追踪，token 消耗和 API 费用很容易失控。合理优化既能省预算，也能提升响应效率和体验。本节从 Prompt token 消耗优化、上下文与工具缓存、合理使用不同模型三个角度展开。

**8.6.1** **Prompt** **token 消耗优化**

大模型按 token 计费，多轮对话若每次都把完整历史、工具记录和系统提示一起输入，冗余会很高。优化 Prompt 是最直接的成本控制手段，常见策略包括：

· 模板精简：删掉系统提示里冗长但非必要的指令。
· 上下文裁剪：只保留与当前任务相关的最近几轮，而不是全量历史。
· 关键信息提取：把影响推理的要点浓缩重写，而非照搬原文。
· 分块拼接：外部知识库过长时分块存储，调用时只注入最相关部分。

其中上下文裁剪应用最广。通过控制保留轮数可显著降低 token。例如智能客服提问通常只和最近几轮相关，早期对话可安全裁剪。示例代码如下：

**8.6.2** **上下文与工具缓存**

Agent 系统中外部工具调用不可少，但短时间内常重复。若不做优化，每次重复查询并注入模型会增加 token 消耗和延迟。

缓存机制是有效解法，常见方式：

· 上下文缓存：保存历史回答或中间结果，相同问题直接命中，避免重复调用模型。
· 工具结果缓存：对短时间内变化不大的数据如天气、汇率、商品价格等做本地或内存缓存，超时后再查询。
· 中间推理缓存：在多步任务中缓存检索结果，避免每一步都重复检索。
