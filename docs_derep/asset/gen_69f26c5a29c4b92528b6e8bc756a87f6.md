(4) StructuredOutputParser：能够产出结构化结果，却不需要事先创建对象模型。它的定位跟 PydanticOutputParser 接近，只是省掉了定义对象的环节。

(5) PydanticOutputParser：先定义好一个对象模型，让大模型按该模型的结构返回数据。可以先写一个 Pydantic 模型，再借助该解析器把模型输出转成对应对象的实例。

### 6.2.4 索引

索引本质上是给文档做结构化整理，让模型能更顺畅地与文档交互，比如在问答、知识库等场景中直接从文档里拿到答案。

LangChain 围绕索引提供了不少实用的函数和组件，用于加载与检索各类文档资料，具体可用的组件主要有：

+   (1) Document Loaders（文档加载工具）：负责从不同来源拉取文档。读取数据源后，需要把原始内容转成 Document 对象，方便后续环节使用。

+   (2) Text Splitter（文本分割工具）：负责切分文本。无论是把文本作为提示喂给 OpenAI API，还是使用其嵌入功能，都存在字符上限，所以必须先用分割工具把加载器拿到的文档切成小块。

+   (3) Vector Store（向量存储工具）：负责把文档以向量形态保存。因为相关性搜索本质上是向量运算，无论调用 OpenAI 的嵌入接口还是直接连向量数据库，都需要先把文档转成向量。转换过程很直接，只要把数据写入对应的向量库即可，如图 6-2 所示。

### 6.2.5 内存

默认情况下，代理和链都是无状态的，处理完一次查询后不会保留之前的对话内容，每次请求彼此独立。

但在聊天等需要记忆上下文的场景里，保留历史对话就变得很重要。为此 LangChain 提供了对应的工具类。

这些工具类可以在代理和链之间传递上下文信息，保证连续对话的状态不丢失。例如，用上下文工具类保存并提取上一次对话的内容，下一次查询就能利用这些信息给出更精准的回答。

借助 LangChain 提供的工具类，可以在需要记忆历史对话的应用里实现更强的对话能力，从而提供更连贯、个性化的用户体验。

### 6.2.6 链

链的核心思想是把多个组件拼装成一个完整应用。比如可以构建一条链，先用提示模板把用户输入格式化为提示，再把提示送入语言模型。

同时，多个链也可以串联，搭建更复杂的流程。每个链负责特定的功能或任务，整体应用通过链的组合实现更复杂完整的能力。

组合链后，可以实现更高级的对话流程与逻辑。各个链分别承担输入处理、语义解析、上下文管理等职责，这种方式让应用构建更灵活，也便于按需定制与扩展。简单来说，链就是一个接收提示模板、根据用户输入做格式化、再把结果传给语言模型获取响应的工具，如图6-3所示。

### 6.2.7 代理

代理把语言模型当作思考引擎来决定下一步该做什么操作。使用者会给代理一组工具，代理依据用户输入判断哪些工具能达成目标，并持续调用工具直至目标完成。

某种程度上，代理是链的进阶版：它不仅绑定了提示模板和语言模型，还能挂载外部工具。

代理是一个智能体，职责是在用户输入和应用场景的约束下，从可用工具池中挑选合适的工具执行操作。面对不同复杂度的任务，代理会采用不同的策略来决定执行方式，也就是说它能根据实际情况选择最合适的工具，以实现高效准确的执行。

总体而言，代理是用语言模型做推理的智能体，可依据输入和场景选择工具，并按任务复杂度采取不同策略，从而更灵活智能地完成各类任务。

目前主要有两类代理。

(1) 动作代理（Action Agent）：每次只执行一个动作，根据执行结果再决定下一步。

(2) 计划执行代理（Plan-and-Execute Agent）：先规划出一系列待执行操作，再按预定顺序逐个执行。

对简单任务来说，动作代理更常见也更容易实现。对复杂或长期运行的任务，计划执行代理的初始规划有助于保持长期目标的聚焦。不过计划执行代理会增加调用次数并带来更高延迟。这两类代理并不冲突，可以让动作代理来执行计划执行代理制定的计划。

代理内部涉及的核心概念如下。

+   (1) 代理：应用的主要逻辑，接收用户输入和已执行的操作列表，返回 AgentAction 或 AgentFinish。

+   (2) 工具：代理可调用的动作，如发起 HTTP 请求、发送邮件、执行命令等。

+   (3) 工具包：为特定用途设计的一组工具集合。例如让代理与 SQL 数据库交互时，可能需要查询工具和查看表结构的工具。工具包可以看作工具的组合。

+   (4) 代理执行器：把代理和工具集合在一起，负责循环运行代理直至满足停止条件。
