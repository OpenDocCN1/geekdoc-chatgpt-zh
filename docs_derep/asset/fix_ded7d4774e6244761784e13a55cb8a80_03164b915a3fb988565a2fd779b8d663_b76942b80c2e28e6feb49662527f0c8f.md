剪枝能不能真正变快，核心就看目标硬件支不支持。同一套压缩思路放到不同平台，结果会截然不同。

GPU 这边，本质上是为大批量稠密矩阵运算打造的，偏爱规则且可并行的计算模式。保持计算规则的结构化裁剪自然吃得顺手。以 NVIDIA 安培架构为例，RTX 3090 之类的卡原生支持 N:M 半结构稀疏[128]，在算力几乎不打折的情况下压缩比例就能超过 50%。

CPU 的指令粒度更细，基本到乘加层级。它更在意模型最后能瘦成什么样，而不强调裁剪是否规整。像 Deep Compression[67] 这类无结构方案，以及专门为 CPU 打造的半结构方案[129]，在 CPU 上都能高效运行。

专用芯片则会从调度策略和数据格式入手来消化裁剪后的模型。比如 ESE[90] 就用计算负载均衡来平滑无结构裁剪带来的单元负载不均，明显提升处理速度。值得注意的是，这类硬件通常同时兼容结构化裁剪，具体用哪种裁剪要结合模型实际表现来定。

### 4.8.3 影响压缩比例的关键因素

想在精度不掉的前提下摸清能压到什么程度，通常会从任务类别、数据规模、主干网络这三个维度拆开看，并用控制变量的方式逐个分析。

任务类别差异明显。同样用一套裁剪方法处理 ResNet-50，分类任务的压缩空间往往比目标检测更大。分类场景下的 ResNet-50 有时能做到超过 90% 的压缩[130]，而检测场景下的 ResNet-50 一般只能到约 70%[131]。

数据规模同样关键。训练样本越多，可被有效利用的参数越多，可裁剪的余量就越小。同一网络用 ImageNet 训练得到的压缩比例，通常会比用 CIFAR 训练时更低。

主干网络的冗余度也决定上限。以 VOC 数据集上的 SSD 通道裁剪为例，主干换成 MobileNet 时压缩比例可能只有 30% 左右[132]，换成 ResNet-50 时则能轻松超过 75%[133]。总体规律是冗余越多的结构越好裁，VGG 的可裁空间大于 ResNet，ResNet 又大于 MobileNet[77, 133]。

def prune_conv_bn_relu(old_conv2d, old_batchnorm2d, threshold, in_channels=3, in_idx=None):

    # 创建掩码，2-范数大于阈值的滤波器保留

def _fix_mask_for_one_depen(masks, dset):

    channel_remain = set()

    out_channels = None

    # 定义一个标志来表示依赖集合中的所有层是否全部被剪枝

    all_pruned = True

    # 遍历依赖集合中的卷积层

    for name in dset:

        if name not in masks:

            # 若当前层无对应掩码，则不被剪枝

            all_pruned = False

            continue

        # 提取当前层掩码

        w_mask = masks[name]['weight']

        if out_channels is None:

            out_channels = w_mask.size(0)

        shape = w_mask.size()

        count = np.prod(shape[1:])

        # 计算当前层的保留及被剪枝的滤波器索引

        all_ones = (w_mask.flatten(1).sum(-1) == count).nonzero().squeeze(1).tolist()

        all_zeros = (w_mask.flatten(1).sum(-1) == 0).nonzero().squeeze(1).tolist()

        # 将当前层保留的滤波器索引加入channel_remain集合中

        channel_remain.update(all_ones)

        # 若依赖集合中存在未被剪枝的卷积层，则集合中所有卷积层均不被剪枝

        if not all_pruned:

            channel_remain.update(range(out_channels))

    # 遍历结束后，更新依赖集合中所有卷积层的权重掩码

    self.set_mask_for_dset(dset, channel_remain)
