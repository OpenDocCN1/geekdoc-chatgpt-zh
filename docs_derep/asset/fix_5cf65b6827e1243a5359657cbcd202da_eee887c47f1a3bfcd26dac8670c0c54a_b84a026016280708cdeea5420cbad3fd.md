NanoClaw 架构与落地实战全景

先看 Channels 通道注册表。NanoClaw 采用工厂自注册的方式，把 Telegram 等不同平台的协议收敛成统一的消息对象。用户发出指令时，系统坚持先持久化，把消息元数据立刻写入 SQLite。这种先写库的做法让中断恢复成为天性：进程异常退出后重启，会调用 `recoverPendingMessages()`，以 `router_state` 表中的 `lastAgentTimestamp` 作为游标，重新入队游标之后的所有未处理记录，达成至少一次的执行保证。

**（2）主循环与消息处理。** 该环节由编排器负责，主要完成从数据库拉取新消息并进行分发调度。全局调度中枢是 `index.ts` 中的编排器，主循环 `startMessageLoop` 每 2 秒扫库一次，按时间戳把各房间的新数据捞出。对每条记录会做两项判断：该房间是否开启了唤醒词限制，消息本身是否携带唤醒词。

这里的设计很讲究。若房间开启 @ 模式，只有带唤醒词的条目才会触发 Agent。触发时 NanoClaw 并不会孤立处理当前条目，而是把唤醒词之前累积的上下文一并带入。如此既避免无关闲聊被 Agent 读到，又能保留完整的意图演进，保证对话连贯。

**（3）定时任务的调度。** 对应模块是 task-scheduler，负责定时任务的计算与下发。调度类型共三种：cron 表达式，如每日 9 点一次；固定间隔，如每 5 分钟一次；一次性任务，到点触发即结束。

执行上下文可选两种：isolated 隔离模式为每个任务新建会话，历史不可见；group 群组模式复用对应房间的当前会话，可感知历史对话。计算下次触发点时调度器采用锚定计划时间的策略。举例：一个每 5 分钟的任务因维护停了 2 小时，恢复后不会从当前时刻开始堆叠触发导致连发追赶，而是从本应执行的时间点继续，保证不漂移。

**（4）并发控制与容器分配。** 该层由 group-queue 与 container-runner 协作，完成任务下发、容器的创建与关闭。主循环拿到待处理消息后不会直接起容器，而是先交给 group-queue 评估并发能力。

group-queue 是并发闸门，默认上限为 5 个 Docker 容器，可配置。消息到来时先查是否有现成容器可用：有则通过管道把消息写入该容器的 stdin，Agent 立即响应实现实时对话；无则入队等待并触发新容器创建。

group-queue 同时跟踪状态：房间容器处于处理中、空闲待命或执行定时任务。空闲待命指 Agent 已完成工作在等输入，超过 30 分钟的 IDLE_TIMEOUT 后会发送 `_close` 指令让容器优雅退出释放资源。容器执行层由 container-runner 实现主机目录挂载与容器创建。

## （5）IPC通信与容器内处理。

该功能由 IPC Watcher 承担，解决容器内外进程间通信。NanoClaw 为每个房间分配独立的 IPC 命名空间，内含 3 个子目录：input 用于主进程向容器发送消息或关闭指令；messages 用于容器向主进程回传待发送的消息；tasks 用于容器向调度器提交定时任务的增删改请求。基于文件系统的 IPC 简洁可靠，目录路径本身构成权限边界，普通房间的容器只能操作自己的 IPC 目录，无法干预他处。

主进程把消息写入 input 后，容器内的 Agent Loop 读取处理，结果写入 messages，定时任务请求写入 tasks。

## （6）结果路由与回复发送。

该功能由 IPC Watcher 与路由器共同完成，把容器处理结果送回对应的 IM。主进程的 IPC Watcher 监控 messages 目录，发现新文件即读取内容交给路由器。路由器根据来源定位对应 Channel，由 Channel 把 Agent 的回复发回即时通信软件，完成闭环。
