JavaScript 归属动态类型阵营，和 Java 这类静态类型语言相比，IDE 做全自动重构的门槛明显更高。Copilot 出世前，VS Code 对 JavaScript/TypeScript 的重构能力基本停留在抽取变量、抽取函数、移动变量、移动函数等初级操作。Copilot 出现后打破了这一局限，本节演示的把 context 改写成属性钻取只是典型场景之一，反向把属性钻取收回 context、借助它完成状态上提也都能实现，可探索的玩法还有不少。需要提醒的是，当前 AI 辅助仍不稳健，笔者用编辑模式做重构实验共跑了 5 次，其中 1 次出错，把 gotoChatView 错误地透传下去，所以接受修改前务必仔细核对生成代码。

到这里，本节已经讲完 Copilot 的三种工作形态：询问 Ask、编辑 Edit、代理 Agent。询问模式直观，主要是问答；编辑和代理的界限不太好把握，容易混淆，主要区别如下。

- 控制粒度：编辑模式由开发者精确定位改动边界，代理模式则自行决定动哪里。
- 时间成本：代理模式一次对话内部会多次调用大模型，通常比编辑模式更耗时。
- 可预测性：编辑模式结果更稳定，代理模式会依据中间产物动态调整上下文，不确定性更高。
- 费用：主流 AI IDE 多按大模型调用次数计价，代理模式调用更频繁，成本也更高。

随着 AI 辅助编程的演进，主流 AI IDE 的设计正趋同。曾以 Composer 模式著称的 Cursor，已经把 Composer 功能并入聊天视图，提供询问、手动、代理三种形态，与 Copilot 一一对应。这种趋同显著降低了开发者在不同 AI IDE 间切换的成本。

## 5.5 React 单向数据流

本小节尝试从更高层梳理 React 的数据思路，核心就是单向数据流。数据流的范畴比组件间通信更宽，也更抽象，理解它的设计思想尤其是 React 的单向做法，有助于把数据的构造与使用放在全局来看，也为后续学习其他前端框架打基础。

### 5.5.1 数据流是什么
谈数据流前，先回顾函数响应式编程 Functional Reactive Programming。顾名思义，它是用函数式部件来做响应式编程的一种范式。

**数据流 Data Flow 是响应式编程的关键概念，它把程序逻辑抽象为数据在不同运算之间流动并随之变化的过程。**

以 `b = a * 2` 为例，把 `a * 2` 看作一次运算，当输入 `a` 变化时，`b` 会自动跟随更新。

这很容易联想到 React 的设计哲学 `UI = f(state)`。在一个函数组件 `({ a }) => (<div>{ a * 2 }</div>)` 中，只要 prop `a` 改变，渲染出的 `<div>` 内容就会自动刷新。

真实程序通常包含多道运算，每道运算只负责自己的片段，整体像工厂流水线。类比到 React，基本单元是组件，运行时形成组件树，根组件沿树逐层分发数据，从根到叶的任意路径都可视为一条流水线，每个组件则是流水线上的一个工位，对经过的数据做处理并完成自身职责。

### 5.5.2 React 如何实现单向数据流
在 React 里，props、state、context 三者共同构成组件的数据流。作为声明式框架，React 的数据流也是声明式的。典型场景下，开发者通过声明这三种数据来规划应用的数据流，进而控制交互逻辑。

只有这三种数据的变更会触发 React 的重新渲染机制。若在数据流中混入不属于它们的外部数据，常被戏称为“跳出三界之外”，容易引发难以察觉的 Bug，比如数据已更新但视图未刷新。

这类问题在小型项目中还好定位，随着代码量和复杂度上升，数据源容易混淆，调试成本会大幅增加。顺带一提，“三界之外”这个说法来自笔者同事，当时她就栽在这种 Bug 上，排查耗时许久才恍然大悟。

props、state、context 看似不同，但在组件树中，同一份数据在引用不变的前提下会多次换身份。例如，最初在组件 A 的 state，传给子组件 B 作为 props，就成了 B 的 prop。再如，从组件 A 的 state 通过 A 声明的 context 传递到子孙树，最后被组件 B 的子组件 C 消费。

第 4 章和第 5 章介绍了数据在 React 内部的流转，但尚未涉及数据的源头与去向。在经典 B/S 架构中，业务数据常存于服务器数据库，由服务端程序读取并通过 HTTP 传输到浏览器，浏览器也需把新数据提交回服务器持久化。尽管现代浏览器已有 IndexedDB 等本地持久化能力，但鉴于分布式应用的需求，浏览器与服务器交互的 Web 应用仍占主流。

这就引出关键问题：在 React Web 应用中，如何书写与服务器交互的代码？比如组件显示时拉取最新数据、翻页时加载下一页、离开视图时关闭轮询等。

这类代码大致分属事件处理和副作用。前者已在 1.4 节和 4.3.3 节有所涉及，如 `<a>`、`<button>` 的 onClick，具体将在 7.1 节展开。后者是本章重点。

副作用是 React 的重要概念，不仅包含服务器交互，任何与外部系统的协同都可视作副作用，通常通过核心 Hook useEffect 实现。它也是 React 响应式特性的重要体现。

## 6.1 认识副作用

### 6.1.1 前端视角下的副作用
维基百科对计算机领域的副作用定义为：函数在执行过程中，除返回计算结果外，还对调用方产生额外影响，例如修改全局变量、改变入参、向终端或管道输出、更新外部存储等。

简言之，副作用是让函数不再保持纯粹的操作。副作用并非贬义，在特定场景下不可避免，识别它的目的不是彻底消除，而是确保可控、可预期，从而写出更可靠的程序。

对前端同样适用。假设一个完全自给自足、与外部系统零交互的前端应用，可类比为纯函数。一旦加入网络请求、用户输入、浏览器存储等功能，与外部的交互就会引入副作用。这些副作用对“好用”的应用是必要的，需要被明确定义和管理。

事实上前端无处不在副作用，但这一概念直到 Elm 框架出现后才进入开发者视野。随着 React 社区采纳推广，副作用管理逐渐成为主流范式。

### 6.1.2 React 语境中的副作用
3.2.2.1 节提到，纯函数定义的 React 组件中，诸如 useState、useContext 等 Hooks API 本质是在处理纯函数的副作用。当时是为了简化理解。学习 state、context 后，我们需要把对这些内部数据的读写视为一个整体——由于它们不涉及外部系统，属于自给自足的情形，因此修改 state 或 context 不再计为副作用。除此之外，所有与外部系统交互的行为都应视为副作用，例如设置定时器、操作真实 DOM、请求远程数据、在 console 打印调试信息等。

触发方式分两种：一种由 onClick 等事件引发，另一种由 React 渲染过程本身引发。其中，由渲染本身引发的副作用在 React 中被专门称为 Effect。例如“每次渲染组件就要从服务器获取最新数据”这类需求，与用户点击无关，却与渲染存在因果关系，就是典型的 Effect。

考虑到中文社区习惯，若无特别说明，本书后文的“副作用”均指由渲染引起的 Effect。

### 6.1.3 渲染与提交两阶段
React 的副作用由渲染引起，那么渲染具体指什么？

前文多次提到渲染，如 JSX 最终生成 DOM 树，修改 state 或 context 会触发重渲染。这些说法是为了便于理解而做的简化。实际上 React 中渲染是一个独立阶段，在渲染与真实 DOM 生成之间还有提交阶段。

渲染阶段，React 按顺序执行各个组件的定义函数，在内存中构建虚拟 DOM 中间模型。当所有组件执行完毕、组件树搭建完成，React 进入提交阶段，此时才调用浏览器 DOM API 创建真实节点。只有提交完成，用户才能看到页面变化。初次渲染和重新渲染都会经历这两个阶段，区别在于前者全量、后者增量。

渲染与提交的细节将在第 9 章组件生命周期详细讲解。这里简要介绍是为了帮助理解副作用触发时机。副作用在提交阶段接近尾声、真实 DOM 更新后才触发，这与“副作用由渲染引起”并不矛盾，后文会进一步解释。
