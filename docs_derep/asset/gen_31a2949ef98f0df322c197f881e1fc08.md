零运行时方案的核心做法是在编译阶段借助 AST 解析，把 JavaScript 里写的 CSS 抽离成静态样式文件，再在页面里引用。

开源社区里常见的 CSS-in-JS 库，底层都是上面一种或多种技术的组合。具体怎么在 oh-my-chat 里接入 CSS-in-JS，会在 8.4 节展开，这里先不细讲。

### 8.2.4 原子化 CSS 模式

在解决组件化样式冲突的探索中，有一种思路是把 CSS 规则的粒度做得更细，从而绕过样式污染，这就是原子化 CSS。它的本质是一套 CSS 架构思想，核心理念是让每个类只负责一个样式点，并用语义化的类名表达用途，开发者在 HTML 标签上叠加一个或多个类来拼出最终效果。下面是一个不依赖第三方库的最小示例：

从示例能看出，CSS 里定义了 3 个类，各自只做一件事，而 HTML 的 div 通过组合这 3 个类得到最终呈现。视觉结果和把 3 个属性写进同一个类没区别，但编程视角变了：样式的决策权从 CSS 文件转移到了 HTML 结构上。

原子化 CSS 也常被称作函数式 CSS，这些单一职责的类可以类比成函数，在 HTML 里通过 class 属性“调用”并按需组合。因为原子化类是 CSS 的最小单元，作用域和副作用都很容易掌控，基本杜绝了页面不同区域间的样式互相影响。无论怎么调整类名的组合方式，都不会波及到其它标签，从而实现了样式隔离。

这个概念最早在 2013 年被提出，随后出现了多个落地方案。2017 年发布的 Tailwind CSS 以“工具优先”为定位，内置了海量且强大的原子化类，并搭配现代构建工具和 IDE 插件，给前端样式开发带来很高的效率体验，很快成为该方向的标杆。Tailwind 同样能用在 React 上，例如：

## 8.4 实战：给 oh-my-chat 做 CSS 组件化

在前 7 章里，oh-my-chat 仍在使用最原始的 CSS 写法，所有样式都堆在 App.css。随着功能扩展，这个文件会越来越臃肿难以维护，而且很容易出现类名重复引发的冲突，这类问题在大型项目里排查成本很高。因此需要为项目选定合适的 CSS 方案，并对现有样式进行重构。

### 8.4.1 技术选型为何是 Linaria

根据我在多个 React 项目里的实际统计，按代码量来看使用率最高的三类是 CSS Modules、emotion 和 linaria，后两者都属于 CSS-in-JS。实践证明 CSS-in-JS 能显著提升 React 项目的开发体验。其中 linaria 作为零运行时 CSS-in-JS 的代表，在保持与传统 CSS-in-JS 相近的 API 的同时，运行时性能更好，所以我把它选作 oh-my-chat 的样式方案。从使用感受看，linaria 功能完整，API 与 styled-components、emotion 高度兼容，而且比起其它偏向 JS/TS 语法写样式的方案，它更贴近原生 CSS 的书写习惯。
