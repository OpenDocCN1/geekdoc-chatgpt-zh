从 SQL 到对话：构建可信查询管道

[PRE0]
先把底座搭好。execute_sql 作为统一入口，负责发起查询、使用绑定变量、捕获异常以及把结果整理成标准形态，让数据访问既稳妥又规范。在此之上抽出三类高频操作封装成方法：query_scenic_spots 能够对景区做组合条件检索，譬如按城市、评级、当月客流过滤；query_city_info 提供城市资料的弹性读取，可指定排序维度；cross_table_query 则把景区表与城市表关联起来的逻辑包成一体。这三项即是依据业务提前固化的 SQL-Data-Function。

[PRE1]
这批方法在安全上做了双重加固。全部采用绑定参数机制来阻断注入风险，同时以枚举约束对入参做校验，例如景区评级只允许 AAAA、AAAAA 两档。返回体统一用 QueryResult 结构体封装，固定包含状态码 success、载荷 data 与提示 message，并附带详细运行日志。异常也做统一收口，保留原始错误信息，让整个查询过程更透明、排错也更顺畅。

随后借助 LLM 的 Tool Calls 能力做工具分发，每个工具都对应一套预置的 SQL-Data-Function 模板。调用完成后，结果会自动写入会话记忆，便于后续追问衔接。

define_tools 将三项查询注册为结构化工具：query_scenic_spots 用来检索景区信息，支持按所在城市、评级和当月客流筛选；query_city_info 用来调取城市信息，支持按年度文旅收入或特色美食排序；cross_table_query 用来跨表检索，能够把景区与城市信息关联起来。

process_query 完成了一个两阶段的对话检索。

第一阶段：把用户提问与库结构一并交给 LLM，由它挑选合适的工具；随后按选择执行对应的数据库检索。

##### 第二阶段：把检索结果再回传给 LLM，生成口语化的回复。

[PRE2]
[PRE3]
到这套链路就完整了，可以直接用口语化表达提问。LLM 会先把疑问映射为工具调用，随后在对应 Data-Function 内部执行 SQL，最后把结果带回作为回复。

[PRE4]
[PRE5]
完整调用链条如下。

1. LLM 先读懂用户意图，决定调用 query_scenic_spots。
2. 参数映射：city = "太原市", level = "AAAAA", min_visitors = 40000。
3. 运行已固化的查询：

   SELECT ... WHERE city ='太原市' AND level = 'AAAAA' AND monthly_visitors >= 40000。
4. 把结果写入会话记忆。
5. LLM 综合原始提问与检索结果，产出最终答案。
