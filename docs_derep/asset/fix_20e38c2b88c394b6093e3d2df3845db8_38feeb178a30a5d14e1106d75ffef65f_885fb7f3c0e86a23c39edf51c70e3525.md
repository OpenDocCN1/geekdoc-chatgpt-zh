### 2.1 为什么分块非常重要

咖哥很认可维基百科对分块的表述，这个定义在 RAG 与认知心理学里都适用。维基百科指出，分块是将一组信息的细小单元聚合的过程，其目的是改善短期记忆留存，绕过工作记忆的容量限制，让记忆更高效。

把大集合拆成更小且语义自洽的片段，一方面可以更好地利用大模型的非参数记忆。图2-3 首先，检索会更精确，系统能更精细地匹配关键词与语义，提升搜索效果。其次，模型运行更顺畅，过长的文本容易让大模型吃力，切分后理解与响应效率都会提升，答案也更可靠。图2-3 长文本的分块

[PRE5]

因此分块的核心目标是让进入向量化流程的内容尽可能降低噪声，同时保持语义连贯性，这是为 RAG 系统准备数据时不可或缺的预处理。

另外，分块也受大模型语境窗口限制的影响。

#### 2.1.1 上下文窗口限制了块最大长度

RAG 运行依赖两类模型：编码型嵌入模型与解码型生成模型，两者都有窗口上限。

每段文本都要先通过嵌入模型生成向量表示，所以必须遵守嵌入模型的窗口限制。不同模型上限不同，商业模型通常在官网文档说明，开源模型常在 Hugging Face Hub 的模型卡中给出，如图2-4所示。

明确嵌入模型后，就能确定切分长度的上限，按 token 计算而非字符或单词。一般嵌入模型的窗口限制在8000 token 以内。

检索到的片段会作为上下文输入到生成模型的提示中以生成回答，这意味着所有检索片段的总长度不能超过生成模型的窗口上限。小模型能处理的量更少，实际使用还要预留空间给指令、角色设定或少量示例。因此检索来的知识上下文越紧凑越好。必要时需压缩提示，第7章会介绍压缩方法。

随着模型发展，这个瓶颈在减弱，现代大模型提供极大窗口，例如 GPT-4o 可接受128 000 token。但即便窗口不再是问题，使用过大块仍需谨慎，冗余信息过多会削弱对话的相关性。

#### 2.1.2 分块大小对检索精度的影响

嵌入模型规定了单块的最大 token 数，并不意味着要用到上限。实践中为了提升检索精度，通常会把文本切得更细。

##### 1. 分块与嵌入过程

先“剧透”一下嵌入向量的生成过程。大多数嵌入模型基于仅编码器的Transformer架构，通过池化层把输入映射为固定维度的向量，如768维，如图2-6所示。图2-6 文本嵌入的生成过程（平均池化）

[PRE7]

首先对输入文本分词，并在开头加入特殊标记[CLS]；随后 Transformer 为每个 token 生成向量表示。接下来通过以下一种池化方式把所有 token 向量压缩为单个向量，得到最终的文本嵌入。池化本质上是一种压缩。

- **CLS 池化**：用特殊标记[CLS]的向量表示整个序列。
- **Mean 池化**：取所有 token 向量的均值。
- **Max 池化**：取各维度最大值作为序列表示。

因此无论输入是10个词的句子还是1000个词的段落，输出向量维度都相同。

该过程必然存在信息损失。对于较大的块，向量表示会过于笼统，关键细节容易被模糊。因此不应直接把分块大小设为嵌入模型的最大承受值。

##### 2. 分块与主题稀释

大块文本可能涵盖多个主题，部分相关部分无关。单一向量试图表征多个主题会导致焦点被稀释，检索精度下降。

小块能保持上下文更集中，更易实现精准匹配。把文档拆成有意义的小片段，检索器可以更准确地定位到特定片段或事实，从而提升RAG性能。

例如，山西文旅建立了一个覆盖全省景点与活动的知识库。若一个块里混写了“五台山、云冈石窟、太原游乐场”，用户问“带小孩适合去哪玩”时，这个综合块的检索得分可能不高。

但若每个景点独立成块，如“五台山：佛教名山”“云冈石窟：唐代造像代表”“太原游乐场：暑期攻略”，RAG就能更准确地命中相关信息，避免无关内容干扰相似度计算。

不过块也不能过小。比如用户问“太原游乐场几点开门”，若把游乐场介绍与开放时间拆到不同块，检索结果可能混入其他景区的开放时间。因为缺乏元数据，时间信息与景区信息的关联就被切断了。

#### 2.1.3 分块大小对生成质量的影响

从生成角度看，即便新模型窗口很大，填满窗口仍可能出现“大海捞针”，即关键信息淹没在大量文本中。RAG领域称为“lost in the middle”，信息越多越难提取重点。

以医疗问答为例，若块过大，用户问“高血压患者能服用哪些降压药”，系统可能返回大量与高血压相关但夹杂其他内容的杂讯，包括诊断、治疗方案、用药禁忌等，不仅阅读负担重，还会掩盖关键答案。

采用合理切分策略，把知识库拆成主题清晰的小块，如“高血压：常用药物”“高血压：用药禁忌”“高血压：生活方式建议”，每块控制在约500字符左右。检索就能更精准地抓取每个主题的核心，并传递给生成模型，形成准确回答，如“常用的降压药包括药物A和药物B，需在医生指导下服用”。

小冰：那块能小到什么程度还能保留足够上下文？

咖哥：取决于文档性质和项目需求。切分逻辑和尺寸要结合具体场景，通常需要实验调优。若目标只是定位到文档层面，块可以大一些甚至不分块；若要精确定位到句子或段落，就需要更细。约500 token 是一个合理的起点。
