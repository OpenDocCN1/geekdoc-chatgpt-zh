面对真实的业务能力缺口，领域专家通常会与知识工程师协同，先行搭建出面向行业的初始本体，也就是模式层，在此层面上把关核心实体、关联关系和属性特征。博世 ^(⁶⁸) 与空客的落地案例表明，这一环节本质上是多轮研讨的迭代磨合，需要反复与工程师及管理者对齐。做好这一步，是驯服制造业复杂性的关键前提。

**●需求分析**：先厘清知识图谱要解决的业务场景，比如合规核查、参数化设计、材料选型等。场景的明确决定了图谱需要承载哪些知识内容。
**●范围界定**：划定知识的边界范围。以制造业图谱为例，可覆盖“产品”“零部件”“材料”“供应商”“设备”“工艺”等核心概念，却不必收录“娱乐明星”等无关信息。
**●本体构建**：相当于图谱的骨架与蓝图。知识工程师在此定义图谱中出现的实体类型、属性字段以及实体之间可能的关系。例如，将“企业”和“产品”设为两种实体，并规定它们之间存在“生产”关系。

（2）多源数据集成与知识获取

该阶段的任务是汇集构建图谱所需的原始素材，来源往往呈现多样化特征。

**●结构化数据**：多来自企业内部业务系统，如 ERP、PLM 等，以及关系型数据库。这是获取路径最直接、质量相对最高的一类数据。
**●半结构化数据**：例如网页表格、JSON、XML 文件、电子表格、百科类站点等。
**●非结构化数据**：占比最大且处理难度最高，典型形式包括 PDF 设计方案、专利文献、学术论文、设备维护日志等。

数据获取可借助多种工具和连接器实现。对结构化数据，可采用 API 集成或直接映射的方式，如 RDB2RDF。对非结构化数据，则要依赖下一阶段介绍的自然语言处理技术进行转化。

（3）自动化知识抽取

核心目标是把非结构化和半结构化内容转化为可机器读取的三元组，这正是 NLP 在图谱构建中的关键应用。

**●实体识别**：大语言模型可以直接从设计方案、设计规范、质量流程等文本中抽取出业务关键实体，例如材料名称、工艺参数、设备编号、企业名称等。
**●关系抽取**：识别实体间的语义关联。例如从工艺文件中抽取出“涡轮叶片”采用“Ti-6Al-4V”材料制造这一关系。具体实现路径多样：①基于规则/模式匹配，对格式高度规范的文档如规格表非常有效；②传统机器学习，在标注语料上训练有监督或无监督模型来识别关系；③深度学习，利用 CNN、RNN、Transformers 等模型自动学习文本特征，处理复杂语言现象。
**●属性抽取**：提取实体的固有属性。例如从材料数据表中抽取材料“Ti-6Al-4V”具备“高比强度”等属性。
**●事件抽取**：捕捉更复杂的动态信息，如“质量故障”事件，并抽取出故障表现、特征、涉及部件及因果关系等要素。

（4）知识融合与验证

抽取后的知识往往零散，存在冗余、冲突或不完整。融合的目的是形成统一、干净、连贯的知识库。

**●实体链接/消歧**：把文本中提及的实体，如“博世”，映射到图谱中唯一正确的实体对象上。解决同名异义，比如“捷豹”指汽车品牌还是动物，以及异名同义，比如“大众”“VW”“Volkswagen AG”指向同一家公司。
**●知识合并**：将不同数据源关于同一实体的信息整合，化解模式层与数据层可能出现的冲突。例如把 PLM 中零件 A-123 的设计信息与 ERP 中物料号 123 的库存、成本信息合并，使实体信息更完整。
**●关系归一化**：大模型能够理解“供应商是”“提供者为”“由……供应”等多种表述，并统一归一为标准关系如“hasSupplier”。
**●质量评估**：引入“人在回路”机制验证抽取结果的准确性，包含人工审核与修正，通常采用主动学习策略，优先把系统不确定的抽取结果推送给领域专家审核，以消除冲突与冗余。这对工程应用要求的知识可靠性至关重要。

（5）知识推理与发现

此阶段图谱从静态事实库转变为能够产生新洞察的推理引擎。

**●演绎推理**：基于本体中定义的规则推导出隐含的新知识。例如已知：①部件 A 由材料 X 制成；②材料 X 属于金属；③所有金属都导电。系统即可自动推断部件 A 具有导电性，即使该事实未被显式录入。
**●归纳推理（链接预测）**：借助图机器学习技术，如知识图谱嵌入 Knowledge Graph Embedding，KGE，来预测缺失链接或发现潜在新关系。例如依据新材料与图谱中已有成功应用材料的相似性，推荐其可能适用的应用场景。

（6）RAG 驱动的迭代验证与增强

这是让图谱“活起来”并持续进化的关键，也是 RAG 技术发挥核心作用之处。

**●知识应用与验证**：图谱初步成型后，可接入上层应用或 RAG 系统供员工使用，如智能问答、搜索引擎、推荐系统。例如工程师用自然语言提问：“制造涡轮叶片可用的材料有哪些？”使用过程中，工程师可反馈答案准确性，从而提升图谱中相关知识的置信度；同时能发现图谱的缺失或错误，进行补充修正，形成良性循环。
**●知识更新与迭代**：知识会随时间变化，需要建立持续更新机制，定期从数据源获取新知识并重复抽取、融合、验证流程。通过这种迭代，图谱不再是静态数据库，而是一个在用户交互中不断自我完善的“知识智能体”。

如图 6-6 所示，制造业知识图谱的构建并非一次性线性项目，而是一个持续循环的过程，融合了知识抽取、融合、推理和人工反馈。通过循环，企业集体知识得以逐步丰富完善。在此过程中，LLM 负责从海量数据中自动化“开采”知识，RAG 则提供高效的应用与验证通道，让真实业务需求驱动图谱的精准构建与持续迭代。

3.图数据库引擎分析

对于存储和查询高度关联的研发数据，原生图数据库相比传统关系型数据库具有天然优势。其“无索引邻接”特性使关系遍历效率极高，这对供应链追溯或设计变更影响分析等场景尤为关键。

以下对主流图数据库进行比较，聚焦制造业关注的核心指标。

**●Neo4j**：成熟易用，适合项目启动和中小规模图模型，采用 Cypher 查询语言。但在超大规模、分布式场景下，性能与可扩展性会受限。
**●TigerGraph**：为大规模并行处理 MPP 设计的高性能分布式原生图数据库。在大规模、深层链接分析如超过 10 跳的基准测试中表现通常领先，适用于企业级欺诈检测、供应链优化、复杂分析，使用 GSQL 查询语言。
**●JanusGraph**：开源、高可扩展的分布式图数据库，支持多种存储后端如 Cassandra、HBase。灵活性强，但部署维护投入较大，使用 Gremlin 查询语言。
**●云原生选项（Amazon Neptune、Azure Cosmos DB）**：全托管服务，与云生态深度集成。例如 Neptune 同时支持属性图 Gremlin、openCypher 和 RDF SPARQL，具有较强通用性。

与知识图谱的交互方式决定了其价值能否被有效获取。

**●形式化查询语言**：①SPARQL 是 W3C 为 RDF 图制定的标准查询语言 ^(⁶⁹)，功能强大标准化但语法繁琐；②Cypher/GQL 为声明式、采用“ASCII-art”风格的查询语言，如（person）-->（city），对开发者更直观。Cypher 源于 Neo4j，GQL 为新兴 ISO 标准 ^(⁷⁰)。
**●迈向自然语言接口**：终极目标是让工程师用日常语言提问。需通过“语义搜索”或“智能问答”层，将自然语言自动翻译为形式化图查询如 SPARQL。这是知识图谱的核心应用场景，也是 LLM 与图谱融合的重点。

图数据库的选择是影响长远的关键架构决策，需在易用性/成熟度 Neo4j、原生性能/可扩展性 TigerGraph、开源灵活性/复杂性 JanusGraph 之间权衡。表 6-2 给出了主流图数据库的对比。对于大型制造企业，深层分析的性能和可扩展性至关重要。一个典型的研发知识图谱庞大、复杂且需深度多跳查询，例如“查找所有使用某供应商零部件的产品，而该供应商的母公司在过去 5 年内涉及召回事件”。基准测试显示，对此类深链接查询，TigerGraph 这类 MPP 架构比单机或分布式不足的模型快数个数量级。尽管 Neo4j 对初期项目友好，但面向未来的企业级系统需建立在可应对未来规模与复杂性而不出现性能瓶颈的平台上。因此，选择应基于概念验证 PoC，用第一阶段识别出的最高价值、最复杂的“能力问题”对候选数据库进行压力测试。

## 6.6 模型服务层：工业机理的算法载体

模型服务层是现代机器学习与 AI 平台架构的核心组件，扮演 AI 能力调度中心的角色。其根本任务是将开发环境中训练好的 AI 模型转化为稳定、高效、可管理、可被上层业务便捷调用的在线服务。没有这一层，模型仅是实验室里的静态文件，无法产生业务价值。

### 6.6.1 模型开发框架与协作环境

模型服务层需为 AI 开发团队提供高效协作的开发环境，通常包括以下内容。

**●模型开发框架**：指为规范化、标准化、高效化 AI 模型生产而建立的工具、流程与最佳实践集合。它像“模型的工业化流水线”，无缝支持 TensorFlow、PyTorch 等主流机器学习框架及 Python 语言，确保企业能利用广泛的开源工具与社区资源。
**●协作开发环境**：为团队提供的统一工作空间，集成交互式 IDE、深度集成的 Git 版本控制、共享计算与数据资源池、中央模型注册表与知识库，打破单兵作战模式。借助容器化技术保证开发、测试、生产环境一致，提升协作效率、资源利用率与模型可复现性。

在模型开发框架层面，TensorFlow 与 PyTorch 是当今两大主导框架。

TensorFlow 由 Google Brain 开发，2015 年发布，面向可扩展的生产级机器学习工作流 ^(⁷¹)。其最大优势是成熟强大的端到端生产部署生态。核心组件包括：①TensorFlow Extended TFX，提供生产级 ML 管道平台；②TensorFlow Serving，专为生产环境设计的高性能模型服务系统；③TensorFlow Lite，用于边缘与移动设备部署，对机器端 AI 至关重要；④TensorBoard，强大的可视化工具帮助理解与调试训练过程。TensorFlow 一直被视为更适合大规模生产部署的选择。

PyTorch 由 Meta 前 Facebook 人工智能研究实验室 FAIR 于 2016 年推出 ^(⁷²)，以 Torch 概念为基础但使用 Python 提升可访问性。其优势在于灵活性、与 Python 的深度融合及在学术研究的统治地位。核心优势如下。

**●动态计算图**：模型构建与调试更直观灵活，适合复杂结构。
**●强大的生态系统**：与 Python 数据科学生态无缝集成，是 Hugging Face Transformers 等前沿 NLP 与生成式 AI 库的首选框架。
**●TorchScript 与 ONNX**：提供将模型导出为高性能可部署格式的机制，弥补了早期生产部署短板。
**●压力测试**：使用最复杂的“能力问题”来对候选数据库进行压力测试。

### 6.6.2 模型的部署与服务化

模型的部署与服务化是将训练好的静态模型转变为持续产生业务价值的动态在线服务，是数据科学成果产品化的关键工程阶段。

1.统一的服务接口

为不同框架如 TensorFlow、PyTorch 等训练的模型提供统一 API 网关，将模型封装为可调用服务接口，通常为 RESTful API。这样实现模型与业务应用解耦，上层应用无需关心内部实现，按标准格式请求即可获得预测结果。

根据实时性要求，通常有三种主流部署模式。

（1）实时/在线推理
**●应用场景**：需即时获得预测结果，如人脸识别、机器视觉质检、实时推荐等。
**●工作方式**：模型加载到服务器内存，通过持久化 API 端点随时响应请求。单次请求响应速度即延迟为关键指标。

（2）批量推理
**●应用场景**：对海量数据进行周期性非实时处理，如每日用户画像更新、每周销售预测、每月客户分群等。
**●工作方式**：通过定时任务如每晚执行启动，模型一次性处理大批量数据，结果写入数据库或文件系统。处理总时长和吞吐量比单次延迟更重要。

（3）边缘部署
**●应用场景**：需超低延迟、网络不稳定或注重数据隐私的终端设备，如智能工厂摄像头质检、自动驾驶环境感知、现场维修智能终端等。
**●工作方式**：需对模型轻量化处理后部署到物联网设备、手机等资源受限硬件，在数据产生源头直接计算。

实现上述功能，离不开现代化基础设施和技术。

**●容器化**：将模型及其依赖打包成标准可移植容器镜像，解决“在我的机器能跑”的环境不一致问题。
**●容器编排**：自动化管理、扩展和调度成百上千模型服务容器。Kubernetes 能实现服务自动扩缩容、故障自愈和负载均衡，是大规模部署 AI 服务的行业标准。

2.模型服务框架

模型服务框架构建于 Kubernetes 之上，为模型服务提供更高级功能，如开箱即用部署模式、多模型编排、可解释性等，进一步简化部署流程。

模型的部署与服务化是一个系统性工程，综合运用多种部署模式、更新策略和底层技术，将模型从算法产出转变为企业可依赖的高可用、可扩展、易管理的 AI 服务，是实现 AI 价值闭环的“最后一公里”。

### 6.6.3 模型的生命周期管理与治理

模型并非一次性产物，需对其全生命周期进行有效管理，这部分通常由 MLOps 平台支撑。

1.MLOps 的核心特征

MLOps 是将 DevOps 原则应用于 AI 领域的实践体系，融合机器学习 ML、软件开发 Dev 和 IT 运维 Ops 的最佳实践，旨在解决模型从开发到生产部署的生命周期管理问题。MLOps 的核心是解决 AI 应用普遍存在的“试点困境”，即数据科学家在孤立试验环境开发的模型难以在复杂生产环境中成功部署、稳定运行和持续维护。在制造业，这意味着模型不仅要在测试表现良好，更要在 7×24h 生产环境中面对真实嘈杂数据持续创造价值。

MLOps 实践比传统 DevOps 更复杂，因其需同时管理三个动态实体：代码 Code、模型 Model 和数据 Data。传统 DevOps 主要关注代码生命周期。但在 MLOps 中，三者相互交织：数据变化可能要求模型重训，即便代码未变；代码更新需要重训模型；模型本身作为二进制产物需版本化管理。这种独特的“三体问题”正是 MLOps 引入“持续训练 CT”等新概念的原因，也解释了为何不能简单套用现有 CI/CD 工具，而必须构建能理解并自动化复杂三元生命周期的专属 MLOps 平台。

MLOps 的核心在于持续性，将 AI 模型生命周期变成自动化的不断迭代优化闭环。

**●持续集成 CI**：不仅自动化代码构建测试，更重要的是自动化数据和模型的验证，确保新数据或模型版本不破坏现有系统稳定性。
**●持续交付 CD**：自动化地将通过测试的训练好模型打包并部署为可供调用的预测服务。
