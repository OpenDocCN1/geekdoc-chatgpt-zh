### 6.1 为什么要给 OpenClaw 做风控？

很多人对 OpenClaw 的风控缺乏概念，甚至认为：“这不就是个 AI 工具吗？我装在自己电脑里，不碰公司东西，能有什么风险？”“我只是写写文案、整理资料，不碰运维、不连数据库，风控是多此一举。”

但随着使用人数增加，一些意外的经历不断出现。

#### 1. 那些你从没想过的风险已上演

有网友分享惊险经历：他把工作邮箱交给 OpenClaw 管理，指令是“检查收件箱，提出你想归档或删除的邮件”，并强调“未经许可不要有任何操作”。结果这只“龙虾”误判指令逻辑，未经确认就擅自执行删除，即便用户连续发出“停下来”的指令，数百封重要工作邮件仍在短时间内被删。

另外，《新消费日报》报道深圳一名程序员的案例：安装 OpenClaw 第三天，他将 OpenClaw 接入自有大模型 API，本想借助自动化能力完成代码整理与信息查询，却因 API Key 疑似泄露，凌晨收到超 1.2 万元的 Token 调用账单。具备自动执行权限的 OpenClaw 在用户不知情的情况下持续后台调用接口，造成巨额意外消费。

某公司也爆出员工私自安装 OpenClaw 引发的严重网络安全事件。涉事员工违规将办公电脑直连公网，导致黑客入侵植入勒索病毒，公司内网全线沦陷，核心业务停摆、关键数据丢失，造成巨额损失。

必须意识到，从接入 API Key、授予系统权限的那一刻起，风险就已存在。

#### 2. 为什么用 OpenClaw，就必须做风控？

首次接触 OpenClaw 时，常有疑问：平时用 ChatGPT、豆包等对话式 AI 不需要专门风控，为何 OpenClaw 就必须做？

原因在于，OpenClaw 并非单纯聊天工具，而是把大模型接入了消息通道、工具与系统资源。官方安全文档强调，OpenClaw 的安全重点不在于“回答对不对”，而在于三件事：谁能和它对话，它可以去哪里行动，它能碰到什么资源。一旦具备文件访问、浏览器操作、消息发送、脚本执行或自动任务执行等能力，风险就不再是“答错一句话”，而可能把一次理解偏差放大为真实错误操作。官方明确提醒，OpenClaw 没有绝对安全的默认形态，正确做法是先赋予最小权限，再随经验与需求逐步放开。

##### （1）AI 对任务的理解，本身就具有概率性

OpenClaw 核心仍是大语言模型，其理解依赖语义推断与概率预测，而非传统软件的严格确定执行。在聊天场景下很方便，但在执行场景下风险显现。你说“帮我整理一下邮箱”，模型可能理解为归档、筛选、标记，也可能触发删除、移动、批量处理等动作。此时理解偏差会转化为操作偏差。官方安全建议指出，涉及配置修改、私密数据与系统操作时，最好在系统提示词中加入验证与确认机制，让模型在不确定时先询问再执行。

##### （2）自动化执行会把单点错误迅速放大

传统软件的关键操作多由人一步步执行，而 OpenClaw 强调把多步任务串联成连续流程自动执行。只要某一步理解错误，后续步骤会连锁出错。官方文档核心态度明确：当模型已连上真实工具与真实环境，就不能再当普通聊天窗口看待，因为一次错误调用影响的是整条执行链，而非一条回复。

##### （3）权限边界如果不收紧，风险会超出预期

OpenClaw 通过代理配置工具策略与沙箱机制控制权限边界。官方建议遵循“最小可用权限”原则，并给出只读、消息型、编码型、完全开放等不同边界。换言之，OpenClaw 能做什么由用户配置决定。权限越松，出问题的影响面越大。

##### （4）网关一旦被多人共享，风险会明显上升

官方文档明确指出，OpenClaw 不适合作为面向多名互不信任用户的共享安全边界使用。若多个用户都能与同一带工具权限的代理交互，本质上是共享同一套被委托的工具权限。问题不仅是“谁来问”，更是“谁都可能驱动这套权限去行动”。一旦机器人被拉进群、频道或共享工作流，风控强度必须同步提升。

##### （5）OpenClaw 的工具链越丰富，越需要系统化风控

OpenClaw 工具体系包括文件读写、命令执行、浏览器使用、消息发送、自动任务执行、网关控制等。官方对这些工具做了清晰分组，并反复强调：越能碰文件、执行命令、使用浏览器和修改配置的工具，越要依赖严格的审批策略与隔离设计。能力越强，越不能仅靠“模型自己懂分寸”来保障安全。
