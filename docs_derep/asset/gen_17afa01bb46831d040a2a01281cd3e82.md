### 4.1 编程模型：数据流图范式

TensorFlow 一名直指本质：**Tensor（张量，N 维数组）** 在 **Flow（流，数据流图）** 中流动计算。这便是其独特的编程模型——基于数据流图的张量计算。

#### 4.1.1 核心机制：定义与执行分离

TensorFlow 运行机制的核心在于**“构建图”**与**“运行图”**的解耦。从操作视角看，分为两个截然不同的阶段：

1.  **模型构建期：** 定义张量、变量、占位符、操作节点，搭建计算拓扑结构。
2.  **模型运行期：** 在会话中启动图，分发算子至硬件，执行计算并获取结果。

构建期涉及四大基础概念（见表 4-1）：

| 概念 | 角色定位 |
| :--- | :--- |
| **张量** | 数据载体，本质为多维数组 |
| **变量** | 模型可训练参数，随迭代更新 |
| **占位符** | 输入数据入口，类似函数形参 |
| **操作** | 计算单元，消费张量产出张量 |

这些定义均在 **“计算图”** 容器内完成。关于计算图，需把握三点：
- 一个图对应一个计算任务；
- 图必须在会话中启动才能运行；
- 会话负责将算子调度至 CPU/GPU，执行后返回张量（Python 侧为 NumPy ndarray，C++ 侧为 TensorFlow::Tensor）。

[PRE6]

**三大运行场景的图执行差异：**

| 场景 | 核心逻辑 | 数据流向 |
| :--- | :--- | :--- |
| **训练** | 从无到有，通过反向传播更新参数拟合数据 | 正向推理 → 计算损失 → **反向梯度更新** → 循环迭代 |
| **测试** | 评估现有模型性能 | 仅 **正向推理** → 对比真值计算指标 |
| **推理** | 实际业务调用 | 仅 **正向推理** → 直接输出预测结果 |

测试与推理在计算图层面同构：均为纯正向传播。这极像普通函数调用——**样本=实参，占位符=形参，图拓扑=函数体，输出=返回值**。

会话与图的交互还依赖两大数据流机制：
- **Feed（注入）：** 通过占位符向图灌入实时数据，生命周期随 `run` 调用始终。
- **Fetch（取回）：** 从图中提取指定节点的计算结果。

### 4.1.7 GPU 设备指定策略

安装 GPU 版 TensorFlow 后，运行时会自动探测并优先占用第一张 GPU (`gpu:0`)。

**多卡场景下的显式指派：** 需用 `with tf.device('/device:GPU:1'):` 将指定算子钉死到目标设备。设备标识规范：
- `/cpu:0`：主机 CPU
- `/gpu:0`：第一张 GPU
- `/gpu:1`：第二张 GPU，以此类推

**进阶配置：** 通过 `tf.ConfigProto` 构建配置对象，传入 `Session(config=config)` 实现更细粒度控制。核心参数：
- `log_device_placement=True`：打印算子设备分配日志，调试利器。
- `allow_soft_placement=True`：指定设备不可用时（如指定 GPU 但无 GPU），允许 TF 自动回退分配，防止报错崩溃。

### 4.1.8 GPU 显存精细化管理

默认情况下 TF 会几乎占满所有 GPU 显存。`ConfigProto` 允许调整分配策略：

**策略一：按需增长 —— 推荐共享环境**
```python
config.gpu_options.allow_growth = True
```
启动时仅分配少量显存，随模型规模动态申请，**不回收**，长期运行易产生碎片。
[PRE14]

**策略二：构建 Config 时直接指定**
[PRE15]

**策略三：固定比例限额**
```python
gpu_options = tf.GPUOptions(per_process_gpu_memory_fraction=0.7)
config = tf.ConfigProto(gpu_options=gpu_options)
```
强制限制进程最多占用物理显存 70%。（现代 TF 版本多推荐 `allow_growth`，此写法了解即可）
