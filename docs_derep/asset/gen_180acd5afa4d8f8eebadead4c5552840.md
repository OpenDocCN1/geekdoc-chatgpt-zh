### 6.1.3 动态组建与自解散的团队机制

固定的Agent编组难以应对真实业务里任务类型与规模的快速变化。动态团队机制的核心在于按需临时拉起专案组，任务结束即自动解散并归还资源。这种弹性组织既提升了资源利用率，也让系统对复杂多变的需求更有韧性。

一个动态团队的完整生命周期可拆为四个环节。需求分析阶段先判断任务的类型、复杂度与时效，明确所需的能力集合。组建阶段从Agent池挑选合适成员，并配置协作规则与通信方式。执行阶段团队进入活跃状态，各成员协同推进直到交付。解散阶段则把Agent释放回池，保留必要的执行记录供后续复盘优化。

Agent重要性评分是实现智能组队的抓手。该方法基于历史任务贡献度为每个Agent建立动态能力画像。新任务到来时，系统据任务特征与Agent能力匹配度打分排序，优先召入高分Agent组队。相比静态规则，数据驱动的选择更能适应任务多样性。

团队规模并非越大越好，过多成员会因通信开销拖慢整体效率。引入早停机制可解决这一问题，当成员对结果达成高度共识时提前结束多余讨论轮次，在保证质量的前提下节省算力。

### 6.1.4 跨团队协作与公共资源共享

单一团队的内部协同已不足以完成跨领域的复杂任务。跨团队协作机制让不同团队的Agent在需要时交换信息、协同处置；资源共享机制则保证知识库、工具服务等公共资产被多团队高效复用。

典型场景包括：研发团队的代码生成Agent需要调阅测试团队沉淀的用例；运维团队发现生产异常可能关联近期代码变更，需与研发联合排查。协作的前提是保持团队边界清晰，同时打通有效的跨团队通信通道。

共享资源的访问控制涉及三大问题。向量数据库里的知识片段、API调用配额、计算资源时片等均属公共资产，需解决资源发现、访问授权与并发控制。

### 6.2.1 LLM API并发调用的优化实践

随着Agent数量增至数十上百，API调用的并发管理成为稳定性的关键。大多数LLM厂商都设有速率限制，包含每分钟请求数RPM与每分钟Token数TPM两个维度，超限请求会被拒或延迟。

优化需从三层入手：请求队列统一收集并按优先级排序，避免洪峰直击API；限流算法在客户端主动控速，保证调用频率合规；错误重试机制针对限流或服务端错误采用指数退避，避免重试风暴。

令牌桶与漏桶是两种经典方案。令牌桶以固定速率补充令牌，每个请求消耗令牌，允许一定突发，适合偶发高峰。漏桶以固定速率泄漏处理请求，多余请求排队等待，保证流出速率平稳，适用于对调用频率要求严格的场景。

async def acquire(self, token_count: int) -> bool:
    self._refill()
    if self.request_tokens >= 1 and self.token_tokens >= token_count:
        self.request_tokens -= 1
        self.token_tokens -= token_count
        return True
    wait_time = max((1-self.request_tokens)*60/self.rpm,

    await asyncio.sleep(wait_time)
    return await self.acquire(token_count)
