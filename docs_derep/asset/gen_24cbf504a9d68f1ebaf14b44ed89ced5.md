## 1.5 React 的技术生态

1.4 节用 React 为 oh-my-chat 搭建了基础功能，但对一个完整 Web 应用来说这只是冰山一角。**仅靠 React 框架很难构建符合生产标准的完整 Web 应用**。这点容易让初学者困惑，却恰恰反映了当前前端开发的真实情况。相较 10 年前，前端复杂度显著提升，与之对应的是技术能力实现质的飞跃，应用场景也大幅拓展。这种演进既带来挑战，也创造了机遇。React 正是在这样的背景下脱颖而出。正如 1.1 节所述，与主流框架相比，React 自带的功能并非最多，但克制的设计理念和对第三方库的开放性，造就了繁荣的 **React 技术生态**。用 React 的开发者越多，可用的第三方开源库就越丰富；生态越繁荣，又会吸引更多开发者选择 React，形成了 **React 的马太效应**。

因此不必担心学习 React 与开发完整应用之间的差距。以 React 为核心，结合其强大的技术生态，完全可以应对各种规模和复杂度的 Web 应用开发。这也带来一个新课题：明确 React 框架的能力边界，并了解生态中的关键组成，从而针对不同场景选择合适的技术方案。

### 1.5.1 一些开源 React 组件库

HTML 和 DOM API 最初为网页设计而生。尽管 HTML 标准化已取得进展，新增了许多标签和 API，但面对现代富交互 Web 应用的需求，仍缺乏开箱即用的前端组件。

React 框架虽然封装了 DOM API 的细节，但面向用户的组件仍基于 HTML 原生元素，如 `<button>`、`<input>`、`<select>` 和 `<div>` 等。更高级的组件需求，如 `<Tab>`、`<ToggleButton>` 和 `<Tree>` 等，需要开发者自行实现。若想统一视觉风格、交互行为和编程接口，往往需要对基础组件进行深度封装或重写。更高效的做法是使用现成的 React 组件库。

组件库本质上是经过系统设计、风格统一、封装完善、接口一致的可复用前端组件集合。React 组件库，尤其是开源组件库，是 React 生态的重要组成部分。以下列出 2023 年 11 月 npm 单周下载量前三的 React 组件库。

- MUI，前身为 material-ui，基于 Google 的 Material Design 设计语言，提供丰富的组件和稳定的接口。MUI 官方已拆分出 Base UI，支持脱离质感设计定制主题。

- AntD，全称 Ant Design，由蚂蚁集团开源，提供完整设计体系、丰富组件及数十种国际化语言支持。

- React Bootstrap，基于传统前端组件库 Bootstrap，重写了 JavaScript 部分以适配 React，摒弃了 jQuery 依赖。组件种类齐全，保留了传统 Bootstrap 的栅格布局和主题定制能力。

以上三个开源组件库均采用商用友好的 MIT 协议，在各类 Web 项目中广泛应用。考虑到组件开发是 React 学习的关键环节，本书后续章节不会使用现成开源组件库。如需了解具体用法，可参考各项目官网。

### 1.5.2 什么是“React 全家桶”

开发 Web 应用时，除了组件库，还需关注以下领域。

- 应用状态管理框架：Zustand、Redux、MobX 等。
- 服务器通信：浏览器标准的 fetch API、Axios，以及 React Query。
- 表单处理：React Hook Form、Formik。
- 前端路由：事实标准的 React Router。
- 组件样式：多种 CSS-in-JS 方案，Linaria 等。
- 打包编译工具：Webpack、Babel，以及集成 Webpack、Babel 的 Create React App 脚手架，目前 Vite 因性能出色成为许多新项目的首选构建工具。
- 自动化测试框架：Jest、React Testing Library。

这些工具与框架的组合，在中文技术社区常被称为“React 全家桶”。例如 React+Zustand+React Router+Axios+Vite+Jest。

上述框架工具在现代 Web 应用开发中大多是必需的，后续章节会详细介绍其用法并在 oh-my-chat 项目中实践。

### 1.5.3 React Native 简介

移动互联网的兴起对 React 的技术演进产生深远影响。自 iOS 和 Android 主导移动端以来，跨平台代码复用成为关键方向，即一份代码同时运行于 iOS、Android 和 Web。目前主流方案为 Flutter 和 React Native，后者凭借独特优势占据重要地位。

oh-my-chat 的 package.json 中有两个依赖：react 和 react-dom，前者是 React 核心逻辑，后者实现 React 在 Web 端的特有接口和功能。这种架构自然引出一个问题：是否还有其他平台的实现？React Native 就是移动端的接口和实现，对应 npm 包为 react-native，与 Web 端共享 React 内核。跨平台能力的基础正是 React 的虚拟 DOM，具体原理会在后续章节展开。

React Native 秉承 “Learn once, write anywhere” 的理念。它创新性地将 JavaScript 和 iOS/Android 原生组件结合，既把 JavaScript 和 React 引入移动端开发，又利用原生组件提升渲染和交互性能，并通过组件接口抽象屏蔽 iOS 与 Android 的差异，实现高效跨平台复用。对业务导向且对原生功能依赖较低的应用，React Native 是理想方案。

Facebook 早期推广 React 时，React Native 曾助力生态扩张。时至今日，React 的架构设计与功能实现都充分兼顾 Web 端和移动端需求。

需要说明的是，本书聚焦 Web 前端开发，后续不会深入探讨 React Native 接口的具体应用。如需了解移动端开发，可参考 React Native 官方文档。

## 1.6 AI 辅助的前端开发概述

要理解 AI 辅助的前端开发模式，首先需要了解 **AI 辅助软件开发生命周期** 的运行机制。

本章在配置开发环境和编写基础应用代码时，以 GitHub Copilot 为例演示了 AI 辅助编程的部分功能。初次接触这类工具的开发者可能会留下深刻印象。但需明确，无论是 Copilot 还是其他 AI 辅助编程工具，都只是 AI 辅助在软件开发生命周期中的一部分体现。

**软件开发生命周期** 通常包括计划、设计、实现、测试、部署和维护 6 个阶段，每个阶段包含大量任务，其自动化程度直接影响开发效率。在生成式 AI 出现前，软件开发自动化工具和实践已相对成熟，效率提升空间有限。而生成式 AI 为整个领域注入新活力，几乎在每个阶段都能提供智能化支持。
