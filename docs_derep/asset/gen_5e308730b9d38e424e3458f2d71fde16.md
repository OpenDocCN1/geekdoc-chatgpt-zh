# GitHub Desktop 从安装到协作完整攻略

## 安装与初始化

第一阶段是拿到安装程序。

1. 用浏览器打开 GitHub Desktop 官网：https://desktop.github.com。
2. 页面会自动识别当前系统并展示对应的下载入口。
3. 点击下载，等待安装包保存完成。

接下来是把程序装到电脑里。

Windows 系统的安装方式：
1. 在“下载”文件夹里找到刚保存的安装文件。
2. 双击文件启动向导。
3. 出现系统安全询问时点“是”允许运行。
4. 保持默认设置等待安装结束，无需额外操作。

macOS 系统的安装方式：
1. 打开下载好的 .dmg 镜像。
2. 将 GitHub Desktop 图标拖入 Applications 文件夹。
3. 首次启动时若系统提示信任应用，点击“打开”即可。

最后完成账号关联。

1. 先准备 GitHub 账号，没有的话按下面操作：
   - 访问 https://github.com；
   - 右上角点击 Sign up 注册；
   - 按提示填入邮箱、用户名和密码，完成注册。
2. 在桌面客户端登录：
   - 启动 GitHub Desktop；
   - 点击 Sign in to GitHub.com；
   - 输入账号密码并授权客户端访问权限。
3. 设定个人身份信息：
   - 填写希望显示的用户名；
   - 填写邮箱地址；
   - 这两项会作为提交标记，相当于在作业上署名。

完成以上步骤后，GitHub Desktop 就能作为管理代码的得力工具，帮你处理版本控制。

### 新手要点
- 环境先行：确认电脑系统满足运行要求
- 官方下载：只使用官网提供的安装包
- 跟随提示：按系统引导一步步完成安装
- 安全注册：用可靠邮箱创建 GitHub 账号
- 信息准确：用户名和邮箱务必填写正确
- 账号加固：建议开启双重验证提升安全

## 3.4.3 仓库创建与管理实操
GitHub Desktop 装好后，就可以开创属于自己的第一个代码仓库了。可以把它想象成图书馆里为你定制的智能书架，既能安全存放代码，又能完整记录每次改动，还能多人协同不冲突，这就是仓库的核心价值。

先了解仓库是什么。仓库相当于自带时光机的智能文件夹，具备三项关键能力。

第一，完整保存历史。代码一旦修改，仓库就会像相机一样拍下当时的快照，让你随时回到任一历史版本。

第二，多人协作。多个开发者可以同时在同一个仓库里工作，系统会自动记录每个人贡献的部分，并协调冲突，避免覆盖。

第三，分支机制。分支好比平行宇宙，在不触动主线的前提下，你可以在分支里试验新想法，成功再合并，失败就丢弃，不影响主版本。

创建仓库有两种常用途径。

通过网页创建：
1. 登录 GitHub 官网。
2. 右上角点击 “+” 选择 New repository。
3. 填写仓库信息：
   - Repository name：建议全英文小写，用连字符分隔；
   - Description：简要说明用途；
   - Public/Private：选择公开或私有；
   - 建议勾选 Add a README file，自动生成说明文档。
4. 点击 Create repository 完成。

通过桌面客户端创建：
1. 打开 GitHub Desktop。
2. 菜单 File 选择 New repository。
3. 填写：
   - Name：仓库名称；
   - Description：项目简介；
   - Local path：本地保存位置；
   - 视情况勾选初始化 README。
4. 点击 Create repository 完成。

建好仓库后要注意：
1. 命名规范：
   - 用有意义的英文命名；
   - 单词间用 “-” 连接；
   - 避免中文和特殊符号；
   - 名称能体现项目功能。
2. 说明文档维护：
   - README.md 要写清项目基本信息；
   - 描述用途和特点；
   - 列出使用步骤和注意事项；
   - 附上示例和文档链接。
3. 权限管理：
   - 私有项目谨慎添加协作者；
   - 定期复查访问权限；
   - 及时移除不再需要的成员；
   - 重要代码定期备份。

### 新手要点
- 仓库本质：智能化的代码托管空间
- 提交习惯：每次改动都要留下记录
- 命名规则：英文命名，简洁易懂
- 文档维护：README 需要及时更新
- 权限控制：设置审慎，定期复检
- 备份策略：核心代码做双重保护
- 协作纪律：遵守团队开发流程

## 3.4.4 仓库克隆操作指南
创建完自己的仓库后，GitHub 上还有海量开源项目等待探索。把远程项目复制到本地使用的功能就是克隆。克隆相当于把图书馆里的书复印一份带回家，可以随意做笔记、加书签甚至改写，本地与远程各自独立。

GitHub Desktop 提供了两种克隆方式。

### 1. 网页端发起克隆
1. 在浏览器打开目标仓库页面。
2. 点击绿色 Code 按钮。
3. 菜单中选择 Open with GitHub Desktop。
4. 客户端自动启动。
5. 选择本地保存路径。
6. 点击 Clone 等待完成。

### 2. 客户端直接克隆
1. 打开 GitHub Desktop，选择 File → Clone Repository。
2. 在弹出的窗口中：
   - 在 GitHub.com 标签浏览仓库；
   - 或直接输入仓库 URL；
   - 或选择已有的本地仓库。
3. 指定本地文件夹位置。
4. 点击 Clone 开始复制。

克隆完成后建议注意：
1. 事前准备：
   - 确保磁盘空间充足，建议预留项目大小 2~3 倍；
   - 选择合适的本地路径，避免中文路径；
   - 检查网络是否稳定，克隆依赖网络下载。
2. 克隆中：
   - 耐心等待，不要中途关闭程序；
   - 观察进度条是否正常；
   - 失败时可删除残留文件后重试。
3. 完成检查：
   - 确认文件完整；
   - 核对配置文件和依赖是否齐全；
   - 记住本地存储位置以便后续查找。
4. 日常建议：
   - 定期用 Fetch 同步远程更新；
   - 修改重要文件前先备份；
   - 保持本地仓库整洁，及时清理无用文件。

### 新手要点
- 克隆前提：先确认磁盘空间足够
- 路径选择：避免使用中文及特殊字符
- 网络要求：保持连接稳定
- 更新策略：定期拉取远程最新内容
- 文件整理：维持本地仓库有序
- 备份建议：修改关键文件前先备份

## 3.4.5 代码提交流程
创建与克隆之后，最核心的操作就是提交代码。把提交想象成写日记，每完成一段重要内容就保存一次。每次 Commit 都会为代码拍张照片，记录完整状态，方便随时回溯。

提交不仅是保存，更是留下清晰的工作轨迹。好的提交习惯能帮助你追踪项目演进，也让协作者快速理解你的改动，就像日记里写清日期和事件一样。

具体操作：
修改文件后，GitHub Desktop 会在左侧 Changes 面板列出变化，每个文件旁有状态标识：
- 黄点表示文件被修改；
- 绿色加号表示新增文件；
- 红色减号表示文件被删除。

核对内容：
1. 点击文件，右侧会显示具体差异。
2. 绿色底是新增内容，红色底是删除内容。
3. 确认所有改动都是预期内的。

填写提交信息：
1. 在左下角 Summary 框用一句话概括本次改动，例如“添加用户登录功能”，避免“更新代码”这类模糊描述。
2. 在 Description 框写更详细的说明，列出改动点、改动原因，如有关联任务编号也一并标注。

最后点击蓝色的 Commit to main 完成本地提交。注意提交仅保存在本地，若想让他人看到，需点击顶部 Push origin 推送到远程 GitHub，相当于把日记放到图书馆架子上共享。

### 新手要点
- 提交原则：一次提交只解决一个问题
- 描述规范：说明简洁明了
- 提交前核查：仔细确认改动内容
- 推送及时：本地提交后尽快推送远程
- 提交频率：小功能完成后即提交
- 说明结构：概述加详细描述
- 改动归类：相关修改合并同一次提交

## 3.4.6 Pull Request 与忽略文件配置
团队开发中，代码不能直接合入主分支，需要经过审查，这时就要用到 Pull Request。

可以把 PR 理想成多人合著书籍的审稿流程。你完成章节后提交给主编审核，审核通过才正式收录。Pull Request 就是这样一个规范的代码协作申请。

### 1. Pull Request 的含义
PR 相当于一份正式的代码合并申请。当你在自己的分支完成功能开发后，需要发起申请，由维护者审核通过后才合并到主分支。

好处在于：
- 允许他人审查代码；
- 便于讨论和交流；
- 保证代码质量达标；
- 避免直接改动主分支的风险。

### 2. 创建 Pull Request
1. 准备工作：
   - 代码完成并通过测试；
   - 将修改提交到自己的分支；
   - 推送分支到远程仓库。
2. 发起申请：
   - 在 GitHub Desktop 点击 Create Pull Request；
   - 浏览器打开 GitHub 页面；
   - 填写标题，简述改动；
   - 在描述中详细说明修改内容和原因；
   - 点击 Create pull request。
3. 等待审查：
   - 维护者收到通知并审阅；
   - 可能提出修改意见；
   - 根据反馈调整代码。
4. 合并与收尾：
   - 审查通过后由维护者合并；
   - 合并后可删除分支；
   - 同步本地代码。

### 3. 忽略文件配置
项目中有些文件不需要进入仓库，如编译临时文件、含密码的配置文件、开发工具生成的文件、系统缓存等。这时需要 .gitignore 告诉 Git 忽略它们，相当于给仓库管理员一份免管清单。

配置方式：
方法一，图形界面：
1. 在 Changes 面板找到需忽略的文件；
2. 右键选择 Ignore file；
3. 选择忽略单个文件或同类型文件；
4. 客户端会自动更新 .gitignore。

方法二，手动编辑：
1. 在项目根目录创建 .gitignore 文件；
2. 用文本编辑器打开，写入需要忽略的规则。

## 3.4.7 分支管理基础
分支是 Git 中非常重要的概念。就像写小说，主体情节已定，但想尝试新创意，不会直接改主稿，而是在单独文档里试验。Git 的分支就提供这种安全试验空间。

分支像项目的平行宇宙，各自独立演进。满意就合并，不满意就丢弃，主分支始终不受影响。

以电商开发为例：
- main 分支承载稳定上线版本；
- 想加入新支付功能；
- 不确定是否影响现有系统；
- 创建独立分支开发，测试通过后再合并。

在 GitHub Desktop 中管理分支：
### 1）新建分支
- 点击当前分支名，通常是 main；
- 点击 New Branch；
- 输入名称如 feature-payment；
- 点击 Create Branch 完成。

### 3）切换分支
- 点击当前分支名；
- 在列表中选择目标分支；
- 确认切换。

### 4）切换注意事项
- 确保当前工作已保存并提交；
- 有未提交修改时系统会提示；
- 可选择提交或暂存后再切换；
- 切换前确认当前分支任务完成。

分支管理原则：
### 1）主分支保护
- 主分支保持稳定可用；
- 不要直接在主分支开发新功能；
- 重要变更走 Pull Request；
- 定期备份主分支。

### 2）开发分支使用
- 每个新功能使用独立分支；
- 名称要能反映内容；
- 及时同步主分支更新；
- 完成后及时合并或删除。

### 3）团队协作
- 遵循团队命名规范；
- 定期同步分支状态；
- 重要变更及时通知；
- 合并前充分测试。

### 新手要点
- 主分支原则：保持稳定
- 命名规范：用途前缀加功能描述
- 开发流程：先建分支再编码
- 切换准则：保存工作后再切换
- 协作要点：规范统一及时同步
- 合并原则：测试通过才合并
- 清理策略：及时删除已完成分支

## 3.4.8 分支合并操作
分支管理后，下一步是把功能分支的成果整合回主线。好比作者在笔记本上试写的内容满意后，需要收入主稿。Git 中的合并就是将一个分支的改动整合到另一个分支，通常把功能分支合并到主分支。

以 feature-payment 为例，支付功能已完成测试，现在需要让所有用户可用，于是把该分支合并到主分支。

合并过程像两条河流汇合，若无冲突则顺畅，若同一位置都有改动，则需要手动解决冲突。

### 1. 基本合并步骤
在开始合并前，需要做一些准备工作。
