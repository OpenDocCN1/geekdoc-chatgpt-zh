### 5.4 小结

预检索阶段的这些手段并非 RAG 的必备环节，但对提升性能和搭建更复杂的系统很有启发。

把结构化数据融进 RAG 是个关键难题。业务里光靠非结构化数据的情况很少见，用户通常要连上现有的关系型数据库，或者去查 Excel、CSV 这类文件。所以引入结构化数据时，核心是要保持其原有结构不被破坏。

直接把结构化数据嵌入后再检索，效果往往不好，容易丢信息，也很难处理时序。Text-to-Query 能用大模型或规则引擎读懂问题里的实体、意图和条件，再映射到表的结构、字段、关系和查询逻辑，让 RAG 流程里也能规范地查结构化数据。咖哥强调过这点，正因为要操作数据库内部，指令必须精确，SQL 能解决的问题向量检索做不到，这也是 Text-to-SQL 需求爆炸的原因。

不过 Text-to-SQL、Text-to-Cypher 这类技术在简单场景还行，复杂逻辑下稳定性不足。折中做法是先抽取数据库元数据，包括字段、表结构、视图描述，并人工补充说明后嵌入；再预定义通用和特定数据函数来封装复杂查询；最后借助 Agent 的 Tool Calls，在模型读懂意图后，基于元数据和数据函数动态拼装 SQL 并执行。

值得单独说的是 Self-query Retriever。它能自动从问题里生成元数据过滤条件。先定义好每个字段的类型和含义，让检索器理解意图，再自动生成一批基于元数据的结构化过滤语句，在检索前先做一轮结构化筛选。这样就形成了双重过滤：一边用向量做语义搜索，一边用提取出的条件比如“观看次数超过100000”做精确过滤。查询既能抓相关性，又能做精确筛选。Self-query Retriever 在构建查询时额外生成这些过滤器，把基于关键字段的检索和语义检索结合，体现了混合检索的思路。

经过预检索的处理，系统能更准地构建查询、拆分问题、清洗噪声，从而让查询更广也更准。

最后，查询路由是复杂系统里混合查询的基础。数据源多样时，先用路由或意图识别锁定目标，再决定去哪条路径，比如是否用 Text-to-SQL、Text-to-Cypher 去查结构化库，这样才能提升检索和生成的准确率与效率。这些做法为跨结构化与非结构化、或多种多级向量库的智能混合查询奠定了基础，也体现了更复杂的系统设计。

### 6.1 小到大检索：句子窗口与父子块

一般来说，文本块越小，检索越精细。块太大，嵌入后检索和合成时会夹带太多无关信息，语义细节就被掩盖了。所以有人会把句子当作基本单元。但只把单个句子交给大模型，上下文不足，答案容易不完整或跑偏。

从小到大策略就是为了解决这个矛盾。核心是把检索和生成解耦，先用小块检索提精度，再在生成时引用更大更完整的块提供上下文。

> 不只是这里，后面很多检索策略都体现了检索与生成分离的思路。

LlamaIndex 和 LangChain 都支持这种“从小到大”方式。

- LlamaIndex 的节点-句子滑动窗口检索：检索时只用单个句子，返回时带上该句子的窗口文本作上下文。
- LangChain 的父子文本块检索：先用小的子块检索，找到相关子块后再调取对应的父块用于合成。

总结起来，就是用精细切分提升召回精度，同时在生成阶段保留足够上下文。

每个节点被切成单独的句子，同时在该节点的元数据里保留前后若干句，形成一个窗口。检索时通过元数据替换，把命中句子换成整个窗口，让模型基于扩展上下文做处理。

实现上会用到 SentenceWindowNodeParser 和 MetadataReplacementNodePostProcessor。前者把文档解析成以句子为单位的节点，后者在检索到句子后把它替换为包含邻居句子的窗口。

实验时会建两套索引：一套用“从小到大”策略，另一套是普通索引，用来对比检索效果。
