LangGraph 归属 LangChain 生态体系，聚焦于 Agent 工程化落地，采用图状态机思路驱动 Agent 流程编排，强调可控性。企业侧验证较为充分，Klarna 的客服机器人即以 LangGraph 为底座，覆盖超 8500 万活跃用户，并把问题解决周期压降了约 80%。借助 LangSmith 完成监控与排错，并依托检查点机制实现长时间运行工作流的状态保存与恢复。

AutoGen 由微软研究院推出，是面向多 Agent 对话的框架，底层遵循 Actor 模型并支持 Agent 间异步消息传递。其核心竞争力在于协作的灵活性，兼顾 Python 与 .NET 的跨语言开发。落地案例众多，诺和诺德的数据科学团队借助该框架显著降低了技术分析的门槛。AutoGen Studio 提供低代码编排面板，进一步简化了多 Agent 应用的构建过程。

CrewAI 采用角色扮演思路，为每个 Agent 分配明确角色与职责以完成协同任务。该方案不依赖 LangChain，设计更为轻简。项目在 GitHub 累计星标超 32000，月度下载量逼近百万次，已形成活跃的开发者社区。典型用途集中在客服自动化和内容生产流程。

MetaGPT 将传统软件研发团队的组织结构映射到 Agent 体系，覆盖产品经理到开发工程师的完整角色链路。该框架可把需求分析到代码落地的全链路自动化，体现了多 Agent 在复杂知识工作中的潜力。

MCP 与 A2A 是互补关系。MCP 解决 Agent 与工具的垂直连接，A2A 解决 Agent 间的水平协作。构建多 Agent 系统时二者可组合使用，形成完整互操作能力。跟踪两大协议的标准化进展，对把握技术方向具有重要意义。

# 第2章 Agent的协同通信机制

传统多 Agent 系统的通信依赖严格定义的协议与消息格式。大模型时代彻底改变了这一范式。基于 LLM 的 Agent 能够像人类一样用自然语言交流，不仅降低了系统构建复杂度，更赋予了前所未有的灵活与适应性。本章将深入剖析协同通信的核心机制。

## 2.1 基于自然语言的Agent协同

【学习目标】

- 1) 理解自然语言协同与传统协议通信的本质区别
- 2) 掌握Prompt链的设计原则和实现方法
- 3) 学会上下文窗口的管理策略
- 4) 能够通过System Prompt定义Agent角色

自然语言协同是 LLM-based Agent 相较传统 Agent 的核心差异，使交互从刚性协议转向柔性对话。

### 2.1.1 从协议到对话：协同范式的转变

传统多 Agent 系统的通信建立在严格的协议规范之上。以 FIPA-ACL 为代表的通信语言，要求 Agent 遵循预定义的消息类型、语义规则与交互协议交换信息。该方式虽保证了确定性与可验证性，却限制了扩展性与表达力，新增场景需扩展协议规范。

LLM-based Agent 的出现从根本上改变了局面。LLM 具备自然语言理解与生成能力，Agent 可直接使用人类语言交流。这不仅是格式变化，更是协同范式的革新。在自然语言协同模式下，Agent 无需预先约定结构，可随上下文动态调整表达；能理解隐含意图，而非仅解析显式指令；面对未预见情况，可通过对话协商求解。

图2-1 清晰对比了传统协议通信与自然语言通信两种模式。

从图2-1可见，传统协议通信要求严格遵循预定义消息格式，如 FIPA-ACL 的 performative 结构，机器解析方便但限制表达。自然语言通信则允许使用人类可读语句交流，降低开发门槛，同时使 Agent 能表达复杂意图与上下文信息。

自然语言协同并非没有挑战。缺乏形式化约束可能导致理解偏差，语言模糊性或带来执行不确定性。因此实际设计中常通过精细的 Prompt 模板与对话协议规范交互，在保持灵活性的同时确保通信可靠性。

### 2.1.2 Prompt链：Agent间的对话设计

Prompt 链是实现多 Agent 协同的核心模式。与单次 Prompt 调用不同，Prompt 链将复杂任务拆解为多个关联步骤，步骤输出成为下一步输入，形成完整处理流程。在多 Agent 场景下，Prompt 链既连接同一 Agent 的多次调用，也串联不同 Agent 间的协作。

Prompt 链设计遵循若干原则：单一职责原则要求每个节点只负责明确子任务，避免过度复杂；接口清晰原则要求明确输入输出格式，确保数据传递准确；容错设计原则要求在链路中设置验证点与回退机制，节点失败时可优雅处理。
