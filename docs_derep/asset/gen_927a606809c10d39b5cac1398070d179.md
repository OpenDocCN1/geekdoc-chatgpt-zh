MCP 双核架构与协作全解

MCP 的运行骨架由两大主体构成：客户端 Client 与服务端 Server。客户端通常以连接器的形态嵌入宿主应用，负责发起调用并把结果带回；服务端独立存在，提供上下文供应、工具调用等能力，对来自客户端的请求做出响应。

1. 客户端核心职能
客户端在整体协作里承担三大要务。
- 初始化连线：负责与服务端建立可靠安全的通信通道。
- 构造请求：结合宿主应用的需求，组装符合 MCP 规范的消息体发送给服务端。
- 接收反馈：把服务端返回的响应解析后交还给宿主应用做后续处理或展示。

2. 服务端核心职能
服务端侧主要完成以下工作。
- 解析请求：接收客户端报文并拆解，按需提供上下文信息或调用外部工具。
- 资源工具供给：统一管理可被调用的资源与工具，支撑复杂任务的执行。
- 会话保持：在需要时维护与客户端的会话状态，保证多轮交互的一致性与连贯性。

4. 传输层落地方式
MCP 支持多种传输方式以适配不同场景：
- 标准输入/输出 stdio：适配本地集成和命令行工具，通过标准输入输出流收发消息。
- 服务端发送事件 SSE：借助 HTTP 协议实现服务端到客户端的单向事件流，适合需要实时更新的场景。
除此之外，开发者还能按需实现自定义传输，以保持协议的灵活与可扩展。

5. 典型协作流程
真实应用中的交互通常按以下顺序展开：
- 建立连接：客户端初始化并与服务端搭起通信通道。
- 功能协商：双方交换各自能力列表，确定可用操作范围。
- 请求处理：客户端发送具体请求，服务端接收并执行。
- 响应返回：服务端把结果封装成响应消息回传客户端。
- 会话管理：按需由服务端维护会话状态，支持多轮对话。
通过上述机制，MCP 实现了高效协作，支撑复杂上下文管理与工具集成，满足大模型应用的多样化需求。

2.3.2 通信协议与数据格式全景
在 MCP 中，通信协议和数据格式是客户端与服务端交互的基础。MCP 以 JSON-RPC 2.0 作为消息传输格式，定义请求、响应、通知三种类型，确保消息传递标准化与一致。传输层负责把 MCP 消息转成 JSON-RPC 格式发出，并把收到的 JSON-RPC 消息解析回 MCP 消息。

MCP 内建标准输入输出 stdio 与服务端发送事件 SSE 两种传输。stdio 通过标准输入输出流通信，适用于本地集成与命令行工具。SSE 通过 HTTP POST 实现服务端到客户端的流式传输与客户端到服务端的通信，适用于需要流式推送的场景。

协议允许开发者按需实现自定义传输，只要符合传输接口规范即可。实现时需兼顾错误处理、资源清理、超时机制等最佳实践，并确保传输安全，包含身份验证、数据加密与网络安全。通过规范的协议与格式，MCP 为复杂 AI 应用提供了高效可靠的交互基础。

1. 通信机制的设计思路
MCP 采用面向消息驱动的异步通信架构，协议基于 JSON-RPC 2.0 构建，用以规范客户端与服务端之间的请求-响应及事件通知行为。该层核心目标是为上下文构造、工具调用、资源获取等操作建立统一且可扩展的远程过程调用语义，保证多组件协作时行为一致与语义稳定。

2. 消息结构规范
MCP 所有消息在传输时均遵循 JSON-RPC 2.0 标准格式，每条消息可以是：
请求 Request：发起操作并等待结果；
响应 Response：对应请求的返回结果；
通知 Notification：不需要响应的单向消息，用于状态变更或事件广播。

3. 上下文 Slot 构成
MCP 的上下文通过 Slot 注入实现，每个 Slot 包含以下关键字段。
- role：语义角色，如 user、system、tool、memory 等；
- name：可选标识名，用于引用、模板调用或版本控制；
- content：实际注入的文本或结构化数据内容；
- options：可选控制项，如是否参与推理、是否只读、是否持久化等。
Slot 定义了模型输入的精细语义结构，是 MCP 通信中最核心的上下文载体。所有 Slot 按序排列，最终构成模型调用时的 Prompt 流，保证语境一致与语义清晰。

4. 传输方式与实现接口
MCP 支持多种传输实现，通过统一的传输接口 Transport Interface 定义标准的 read、write、close 等方法，开发者可自定义传输逻辑。官方提供两种内建方式。
- 标准输入/输出 stdio：适用于本地部署、CLI 交互或嵌入式调用；使用标准输入输出流收发消息；延迟低、部署简便。
- 服务端发送事件 SSE：通过 HTTP POST 与客户端建立单向推送通道；适用于需要推理结果流式输出的 Web 场景；支持增量响应与连接保持。
所有传输方式均可自动检测与动态注册，使用 MCP SDK 时只需指定传输类型，系统会自动完成协议握手与数据通道初始化。

5. 错误处理与完整性保障
为保证通信安全与鲁棒性，MCP 内置错误处理机制，包括：
- 标准化的错误码体系，如 -32600 表示非法请求、-32000 表示服务端内部错误；
- 超时控制与自动重试机制；
- 消息体完整性校验与格式验证，防止非法 Payload 影响流程；
- 对上下文 Slot 与参数字段进行 Schema 校验，确保数据规范性。

2.3.3 能力协商与版本管理
随着 LLM 生态演进，不同 MCP 服务端、客户端及模型服务在实现细节、支持能力与版本策略上存在差异。若缺乏标准化能力协商与版本管理机制，将制约 MCP 在多模型多平台环境下的可扩展性与互操作性。为此，MCP 在通信初始化阶段引入能力声明与版本对齐机制，确保协同运行前达成协议层共识。

1. 能力协商如何进行
能力协商是通信初始化的关键步骤。客户端建立连接后向服务端发起能力声明请求，表明自身支持的功能范围、传输格式、工具结构、上下文特性等。服务端作为响应方返回自身支持的功能子集，并在必要时指明功能版本范围或约束条件。协商不仅涉及基础功能如工具调用、资源管理、消息格式，也涵盖传输层支持、Slot 类型扩展、语言支持能力、流式响应能力等增强特性。

协议中规定的能力字段包括但不限于：
- supports_tools：是否支持 Tool 调用；
- supports_streaming：是否支持流式输出；
- supports_dynamic_slots：是否支持动态 Slot 生成与更新；
- supports_templates：是否支持 Slot 模板化注入；
- transport_modes：支持的传输方式列表；
