# 5.10 装饰器模式：动态加装新功能

装饰器模式归属于结构型设计范式，核心诉求是在不改动原对象内部结构的前提下，为其在运行期灵活附加新行为。它把目标对象裹进一个装饰器封装层，由装饰器在保留原有调用的基础上植入额外逻辑，从而实现能力的扩充。

这种扩展的思路是依赖组合而非继承。我们可以把一个对象套进一个或多个装饰器中，随时决定挂上或卸掉某些能力。装饰器与被装饰对象遵循同一接口，于是调用方能够透明地把装饰后的对象当作原对象使用。

类中植入附加逻辑，以此完成对原始能力的增强。

采用组合替代继承来扩展功能，是该模式的核心理念。通过把对象层层嵌套在不同装饰器里，能够在运行期动态增减行为。装饰器类与原始类共享接口，保证了装饰对象可以无缝替代原始对象。

# 5.10.1 什么时候用

装饰器模式主要适用于以下情境。

+   (1) 需要在不改动已有结构的前提下动态增添能力时：当业务要求对对象临时扩展功能，又不想触碰源码时，可选用装饰器。借助不同装饰器的组合，可以在不影响原对象的情况下自由增减行为。
+   (2) 功能存在多层叠加需求时：如果存在多个层次的功能增强，每个层次的诉求不同，可以用装饰器。每一层装饰器负责特定的增强，然后把装饰后的结果交给下一层装饰器，逐步累积能力。
+   (3) 运行时需要撤销已添加功能时：装饰器支持在运行期动态剥离能力。移除指定的装饰器层，就能回退到对象初始状态。
+   (4) 继承会导致类爆炸时：当用继承来叠加功能会产生大量子类、代码重复或维护困难时，装饰器提供一种替代方案。它通过组合实现扩展，避免了继承带来的弊端。

总体来看，装饰器模式适合需要动态扩展、多层组合、动态撤销以及规避继承问题的场景，提供一种灵活可维护的扩展手段。

# 5.10.2 核心组成

装饰器模式包含以下角色。

+   * 抽象构件：为被装饰对象与装饰器定义统一的接口或抽象类，作为双方的共同规范。
+   * 具体构件：实现抽象构件，是实际被装饰的目标对象，提供了最基础的功能。
+   * 抽象装饰：继承抽象构件，并持有对抽象构件的引用，定义装饰器的公共契约，可在运行期为具体构件附加行为。
+   * 具体装饰：实现抽象装饰的契约，同样持有构件引用。通过在调用前后注入额外逻辑，对具体构件进行包装。

这样的构成允许对具体构件按需叠加功能，装饰器可以任意组合，无需为每种组合单独创建子类。

# 5.11 组合模式：树形管理整体与部分

组合模式是一种结构型设计模式，它把对象组织成树状结构，用来表达部分与整体的层级关系。该模式让客户端可以用同一套方式对待单个对象和对象集合，实现对单一节点与复合节点的统一操作。

(1) 需要表达对象的部分-整体层级时：当系统存在可拆分的层次结构，既有叶子节点也有组合节点，并且希望统一对待它们时，可采用组合模式。例如文件系统中的文件与文件夹就存在这样的关系。

(2) 希望客户端统一处理个体与集合时：组合模式提供统一接口，客户端无需关心操作的是叶子还是组合，可以简化调用代码，并在不影响客户端的前提下增添新的叶子或组合。

(3) 需要对整个层级进行递归操作时：组合模式天然支持遍历整棵树，对其中元素进行搜索、求和、打印等操作。

总的来说，组合模式适合表达部分-整体结构、统一操作个体与集合、以及需要递归处理层级的情况。它能简化代码、提升可维护性和可扩展性，常见于文件系统、菜单系统、组织架构等场景。

# 5.11.2 角色划分

组合模式的关键角色如下。

+   • 构件：组合模式的抽象基类或接口，定义叶子与组合的共同行为，为客户端提供统一操作方法。
+   • 叶子：表示结构中的最小单元，没有子对象，实现构件接口定义的操作。
+   • 组合：表示包含子对象的复杂节点，实现构件接口并维护一组子构件，可对其进行增删。

组合模式通过树形组织对象，让单个对象与组合对象被一致对待。组合节点可递归包含其他组合或叶子，形成层级结构，客户端无需区分具体类型即可操作。

# 5.11.3 优劣点

组合模式的优点包括以下几个方面。

(1) 简化客户端代码：组合模式通过统一的接口对待单个对象和组合对象，客户端无须区分它们，可以简化客户端代码的编写。

(2) 提高灵活性和可扩展性：组合模式可以灵活地增加、删除和修改对象，使系统具有较好的可扩展性。通过组合多个对象形成层次结构，可以快速构建复杂的对象结构。

(3) 统一的操作接口：组合模式定义统一的操作接口，使客户端可以一致地操作单个对象和组合对象，不需要区分它们的具体类型。

(4) 简化对象间的耦合关系：组合模式将对象的层次结构封装在一个类中，可以减少对象之间的直接关联，降低耦合性。

组合模式的缺点包括以下几个方面。

(1) 限制特定操作：由于组合模式会统一操作接口，某些特定操作可能不适用于所有对象，需要在客户端进行类型判断，可能会增加代码的复杂性。

(2) 增加系统复杂性：使用组合模式会增加系统的类和对象数量，进而增加系统的复杂性和理解难度。

(3) 不适合频繁修改层次结构：如果对象的层次结构经常变化，频繁地增加、删除、修改对象，可能会导致系统变得复杂且难以维护。

总的来说，组合模式适用于需要组织对象为层次结构并对其进行统一操作的场景，可以简化客户端代码，提高系统的灵活性和可扩展性。但需要注意不适用于频繁修改层次结构的情况，并且需要权衡好统一操作接口带来的限制。

# 5.12 外观模式：为子系统建门面

外观模式是一种结构型设计模式，它提供一个统一的入口，用于访问系统中一组接口或子系统，从而简化客户端与子系统之间的交互。

# 5.12.1 适用时机

外观模式通常在以下场景中使用。

+   - (1)简化复杂系统：当一个系统由多个子系统或组件组成，并且客户端需要与这些子系统进行交互时，可以使用外观模式来创建一个简化的接口，将复杂的系统细节隐藏起来，提供一个更简单的接口给客户端使用。\n- (2)隔离系统变化：当系统内部的子系统发生变化时，可以使用外观模式来隔离客户端与子系统之间的直接依赖关系。通过外观接口来封装子系统的变化，客户端无须修改代码即可适应变化。\n- (3)提供高层接口：当需要为一组相关接口提供一个更高层次的接口时，可以使用外观模式。这样做可以降低客户端与子系统之间的耦合度，同时提供更简洁、易于使用的接口。

# 5.12.2 组成角色

外观模式包含以下几个角色。

+   - 外观(Facade)：提供一个简化的接口，封装对子系统的访问，隐藏子系统的复杂性。\n- 子系统(Subsystem)：实现系统的功能，处理具体的业务逻辑。\n- 客户端(Client)：通过外观数访问子系统，简化与子系统的交互。

图5-10展示了外观模式的结构，其中，“SubsystemA”“SubsystemB”和“SubsystemC”表示子系统类，“Facade”表示外观类，外观类通过组合子系统类的实例来封装复杂的子系统操作。

# 5.12.3 优劣点

外观模式的优点包括以下几个方面。

(1) 简化客户端与子系统之间的交互: 外观模式提供一个统一的接口，将复杂的子系统操作封装起来，使客户端可以更简单地与子系统进行交互，而无须了解子系统的内部细节。

(2) 提高系统的灵活性和可扩展性: 通过外观类与子系统之间的解耦，可以更方便地修改或扩展子系统的实现，而不会影响客户端的代码。

(3) 提供一个高层接口: 外观模式可以将一组相关的操作封装成一个高层接口，提供给客户端使用，使客户端更加清晰地理解系统的功能。

(4) 降低了客户端的复杂性: 客户端只需要与外观类进行交互，无须直接与多个子系统类进行交互，从而降低客户端的复杂性。
