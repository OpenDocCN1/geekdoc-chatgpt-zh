# GitHub Desktop 合并与回滚实操笔记

先把合并前的底子打牢
1）把要并入的代码线比如 feature-payment 的开发收尾，功能已经测试通过。
2）本地所有改动都已经 commit，别留未保存的状态。
3）本地仓库和远端保持同步，先拉取最新。

合并的具体操作
1）换到目标线，一般是主干。
- 在 GitHub Desktop 左侧点当前分支名；
- 在弹出的分支列表里选中 main 或 master。

2）执行合并。
- 打开顶部的 Branch 菜单；
- 点 Merge into current branch；
- 在弹出的对话框里指定来源线，例如 feature-payment；
- 按下 Merge 完成合并。

### 2. 处理合并冲突
当两条线改到同一个文件的同一段时就会冲突，就像两个人同时改同一段文字要抉择。

处理思路
- 仔细对比两边代码的改动；
- 决定最终保留哪些内容；
- 把冲突标识 <<<<<<< HEAD、=======、>>>>>>> 删除干净；
- 保存文件后提交一次解决记录。

### 3. 合并策略
不同场景适合不同的方式。

1) 普通合并 Merge commit
- 保留完整的分支历史轨迹；
- 适合需要追溯演进的情况；
- 会在主干上多生成一条合并提交。

2) 快进合并 Fast-forward
- 只在主干没有新提交时可用；
- 不会额外产生合并提交；
- 历史看起来更干净。

3) 压缩合并 Squash and merge
- 把功能线的多次提交压成一次；
- 让主干历史更简洁；
- 适合功能完成后的最终收口。

### 小白必记
- 合并前先测，确认代码线已通过测试再操作
- 冲突要细看，逐行对比后再谨慎取舍
- 策略看场景，按需求挑选合适方式
- 提交信息写清楚，说明合并了哪些改动
- 重要合并走评审，建议团队先审核
- 先备份再动手，关键代码合并前备份
- 合并后立刻验证，确保功能正常

## 3.4.9 撤回分支
创建、合并之后，有时需要放弃某条开发线。像写稿时放弃一个思路，Git 也能撤回。撤回有风险，删掉后恢复困难，下面给出安全做法。

先了解三类常见情形。
第一种是删本地分支，相当于删电脑里的草稿，不影响已发布内容。操作如下
1. 先切到其它分支，通常是主干。
2. 点顶部的分支名下拉按钮。
3. 找到目标分支，右键。
4. 选 Delete 删除。
5. 若分支上还有未合并改动，系统会给出警告。

第二种是删远程分支，类似从共享书架撤书，要更谨慎。
1. 在客户端打开 Branch 菜单。
2. 选 Delete branch。
3. 若该分支已推到远端，会询问是否一并删除远端。
4. 确认无误后点确认完成。

第三种是放弃分支里的修改，回到初始状态。
1. 在 Changes 面板选中要丢弃的文件。
2. 对这些文件右键。
3. 选 Discard changes。
4. 在确认框再次确认。

操作注意
(1) 删除前的自检
- 重要代码已合并或已备份；
- 当前不在要删除的分支上；
- 已和团队确认该分支不再使用。

(2) 数据安全建议
- 关键分支先复制一个备份分支再动手；
- 不确定是否删除可先改名保留；
- 删除前在本地跑通代码确认正常。

(3) 团队协作注意
- 删除共享分支前要通知相关成员；
- 确认没有人正在使用该分支；
- 在团队文档里记录删除原因和时间。

### 小白必记
- 删除要确认无用才执行
- 重要分支先备份再操作
- 共享分支删除前先告知团队
- 确保代码已合并或已备份
- 先删本地再删远端
- 保留关键节点的备份分支
- 记录重要分支的删除原因

## 3.4.10 如何回滚代码
分支管理和合并后，难免出现合并后有问题或功能失败需要放弃。这时就需要回滚。Git 就像时光机，能把代码拉回任意历史点。

### 1. 场景一：撤销还没有提交的修改
开发新功能时发现思路不对，想丢弃未提交的改动回到上次提交状态。

#### 1）放弃单个文件的修改
- 在 Changes 面板找到目标文件；
- 对该文件右键；
- 选 Discard changes；
- 在确认框再次确认。

#### 2）放弃所有文件的修改
- 在 Changes 面板全选；
- 右键选 Discard all changes；
- 确认真的要丢弃这些改动。

### 2. 场景二：撤销最近的一次提交
刚提交后发现有严重 bug，需要回退。

#### 1）撤销最新的提交
- 切到 History 标签；
- 在最新提交上右键；
- 选 Revert changes in commit；
- 客户端会自动生成一条新提交抵消上次修改。

#### 2）修改最新提交的说明文字
- 在最新提交上右键；
- 选 Amend commit；
- 编辑说明；
- 点 Amend 确认。

### 3. 场景三：回到特定的历史版本
想回到某个里程碑，比如功能完成前或合并前的状态。

#### 1）通过创建新分支来回滚
- 在历史记录里找到目标版本；
- 右键选 Create branch from commit；
- 输入新分支名比如 rollback-to-v1.0；
- 在新分支上继续开发或合并到主干。

#### 2）直接还原到特定版本
- 定位到目标提交记录；
- 右键选 Revert changes in commit，如图 3-1 所示；
- 这会新建一条提交把代码恢复到选中版本。

操作注意
1) 数据安全
- 重要回滚前先建备份分支；
- 不确定是否合适时先在新分支试验；
- 回滚前确保重要修改已提交。

2) 团队协作
- 回滚公共分支的代码前提前通知团队；
- 确认回滚不会影响他人工作；
- 回滚完成后及时推送到远端。

3) 代码管理
- 养成小批量提交习惯，便于精准回滚；
- 每次提交写清楚说明，方便定位回滚点；
- 定期推送到远端，避免本地丢失。

### 小白必记
- 重要操作前先做备份分支
- 小步提交，说明清晰完整
- 不确定时用新分支试验回滚
- 回滚公共代码先通知成员
- 定期推送，避免数据丢失
- 保持提交历史整洁有序
- 关键回滚前必须先备份

## 3.4.11 如何打开项目文件夹和编辑器
管理版本和回滚之后，日常开发最常用的是查看和编辑代码。桌面客户端除了版本控制，还能快速打开项目和编辑器。

### 1. 打开项目文件夹
1) 右键快捷菜单访问
- 在仓库列表找到项目；
- 对项目名称右键；
- 选 Show in Explorer 或 Show in Finder；
- 文件管理器会直接打开项目目录。

2) 顶部菜单访问
- 先在客户端选中项目；
- 点 Repository 菜单；
- 选 Show in Explorer/Finder；
- 系统打开对应文件夹。

### 2. 使用 Cursor 编辑项目
Cursor 是 AI 辅助编程工具，能提升编码效率。

1) 直接从客户端打开
- 选中项目；
- 点 Repository 菜单；
- 选 Open in Cursor；
- Cursor 启动并加载项目。

2) 设为默认编辑器
- 打开客户端设置；
- 进入 Integrations 集成；
- 在 External Editor 下拉里选 Cursor；
- 设置后可用快捷键快速打开。

3) 未看到 Cursor 选项的处理
- 确认 Cursor 已正确安装；
- 重启客户端；
- 通过 Open in External Editor 手动指定程序。

## 3.4.12 如何使用开源项目
除了管好自己的代码，学会利用开源社区也很重要。开源项目像开放的图书馆，可直接使用或在此基础上改写。主要分直接使用和二次开发两种。

### 1. 直接使用开源项目
1) 寻找合适的项目
- 打开 GitHub，在搜索框输入关键词；
- 看 Star 数量，越多越受欢迎；
- 检查最近更新时间；
- 阅读 README 了解功能。

2) 评估质量
- Star 很多通常更可靠；
- 半年内有更新说明活跃；
- 看 Issues 区问题处理是否及时；
- 文档是否完整，使用说明是否清晰。

3) 正确引入
- 仔细阅读安装说明；
- 用包管理器如 npm 安装依赖；
- 按文档完成配置；
- 在自己代码里引入使用。

### 2. 二次开发 Fork
1) Fork 项目
- 打开项目主页，点右上角 Fork；
- 选择保存到自己的账号下；
- 等待完成。

2) 克隆到本地
- 用客户端克隆到本地；
- 新建分支进行开发；
- 按需修改代码；
- 定期从原项目同步更新。

使用注意
1) 开源协议
- MIT 最宽松，基本可自由使用；
- Apache 可商用，需保留版权信息；
- GPL 修改后代码也必须开源；
- 商业项目务必仔细核对协议要求。

2) 技术兼容性
- 检查支持的编程语言版本；
- 确认运行环境要求；
- 评估与现有项目是否兼容；
- 注意可能的依赖冲突。

3) 使用成本
- 评估学习难度；
- 考量维护成本；
- 确认团队能否维护；
- 查看社区是否活跃。

### 小白必记
- 优先选 Star 多更新频繁的项目
- 使用前必须确认协议
- 确保与现有项目兼容
- 先看文档和示例再上手
- 评估团队技术储备
- 定期同步原项目更新
- 挑选活跃社区的项目

## 3.4.13 实用建议和最佳实践
把前面的知识点串起来，下面总结项目管理、提交、分支和协作的最佳实践。

项目文件管理，项目像书柜，要分类摆放。好的结构要清晰易懂。

规范目录一般包括
- src 目录放源码；
- docs 目录放文档；
- tests 目录放测试；
- assets 目录放静态资源；
- build 或 dist 目录放构建产物。

文件命名建议
- 用有意义的英文名；
- 全小写，单词用连字符；
- 避免中文和特殊字符；
- 名字要能表达内容。

代码提交最佳习惯
1) 提交频率
- 小功能完成就提交；
- 修复一个 bug 就提交；
- 不要攒大量改动再提交；
- 每天至少提交一次。

2) 提交说明写法
- 标题简洁，不超过 50 字；
- 细节用要点列出；
- 说明改动原因和影响；
- 有任务编号时标注。

示例
## 添加用户登录功能
- 新增登录页和表单校验
- 实现用户名密码加密存储
- 增加登录失败提示
- 关联任务 TASK-123

分支管理建议
1) 主干管理
- 保持主干随时可发布；
- 不要直接在主干开发；
- 定期部署到测试环境；
- 合并到主干需代码审查。

2) 功能分支管理
- 每个新功能单独建分支；
- 命名规范如 feature/login；
- 及时同步主干更新；
- 完成后及时合并或删除。

团队协作注意
1) 代码审查 Pull Request
- 提交 PR 前自查一遍；
- 认真对待审查意见；
- 及时回复评论并修改；
- 保持礼貌专业的沟通。

2) 文档维护
- 及时更新 README；
- 在代码里写必要注释；
- 记录重要配置说明；
- 保持文档与代码同步。

安全方面
1) 账号安全
- 开启双因素认证；
- 定期更换密码；
- 不在公共场所保持登录；
- 及时清理过期访问令牌。

2) 代码安全
- 用 .gitignore 过滤敏感信息；
- 不提交配置文件里的密码；
- 定期更新依赖包版本；
- 及时修复已知安全漏洞。

### 小白必记
- 目录分明，分类有序
- 小步提交，说明详细
- 主干稳定，功能分支灵活
- 互相尊重，积极沟通
- 及时更新，清晰易懂
- 定期检查，及时修复
- 命名简洁明了，见名知意

## 3.5 如何部署 Node.js 环境

### 3.5.1 Node.js 是什么
JavaScript 以前只能在浏览器里运行，像只在特定场地玩的积木。Node.js 的出现让这些积木脱离浏览器，到任何环境都能搭建。

Node.js 最大的优势是自带的包商店 NPM，里面有超过 200 万个现成积木包。每个包实现特定功能，组合起来就能搭出各种应用。

Node.js 可做的应用类型
1. 网站应用：比如开发类似微信朋友圈的社交平台，Node.js 能处理文字图片上传、管理用户互动、保障数据安全。LinkedIn 这类求职平台就基于 Node.js 构建。
