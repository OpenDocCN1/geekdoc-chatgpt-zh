OpenClaw Agent 触发、路由与记忆实战拆解

想把 OpenClaw 接进自研前端或工作流，第一件事是弄清 Agent Loop 怎么被唤起。Gateway 只暴露两类入口。

异步投递 agent：发完即走。请求发出后 Gateway 立刻回传运行编号 runId 和接收时刻 acceptedAt，Agent 在后台自行推进，调用方不用阻塞也不用保持长连接，适合消息渠道的日常投递。

同步等待 agent.wait：请求会卡住，直到对应 runId 的任务完成或报错才放行，返回 status、startedAt、endedAt 以及可能的 error。等待上限默认 30 秒，这只是调用方的等待窗口，不会把后台任务强行停掉，任务照跑，只是调用方先拿到超时信号。

### Loop 内部四步
官方把一次循环拆成四段。

第一步 RPC 入口校验。Gateway 收到 agent 请求后先验参，解析 sessionKey 或 sessionId，落盘会话元数据，随后立刻返回 runId 与 acceptedAt，不等 Agent 真正启动，保证开跑前信息齐备。

第二步 agentCommand 准备。解析模型配置与 thinking/verbose 默认值，拉取当前 Skills 快照，调用 pi-agent-core 的 runEmbeddedPiAgent，并在任务结束后补发缺失的生命周期结束或错误事件，保持事件序列完整。

第三步 runEmbeddedPiAgent 推理。调度采用会话通道串行叠加全局通道串行的策略，避免同一会话并发工具调用破坏状态一致性；解析最终生效的模型配置与认证 profile；组建底层 pi session，订阅 pi 事件并把增量内容流式推送；超时时强制中止并带回完整 payload 与用量。

第四步 事件桥接。subscribeEmbeddedPiSession 把 pi-agent-core 内部事件转译为 OpenClaw 流式事件：工具类映射为 stream: "tool"，助手增量输出映射为 stream: "assistant"，运行阶段映射为 stream: "lifecycle"，phase 为 start | end | error。事件经 Gateway 转发到目标消息渠道，用户能看到实时回复。

### 队列与并发
同一会话的多次运行按 session lane 严格串行，前一条处理时后一条排队，保证历史强一致。

渠道的 queueMode 决定新消息的处理方式：

collect 会在当前轮次收集新消息，轮次结束后再把收集内容合并成下一轮入口，适合批量处理。

steer 会把新消息当作引导注入正在运行的对话，在下一次 LLM 调用前送达，但不会跳过已排队的工具调用，适合实时修正行为。

followup 与 collect 思路相近，等当前轮次彻底结束后再启动新轮次，适合大多数对话场景。

### 超时与提前终止
超时有两个独立旋钮。调用方等待超时由 agent.wait 控制，默认 30 秒；Agent 本身运行超时由 agents.defaults.timeoutSeconds 控制，默认 600 秒，在 runEmbeddedPiAgent 内部执行。前者管等多久，后者管跑多久，互不影响。

提前终止常见于三种情形：Agent 运行超时被中止、AbortSignal 发出取消信号、Gateway 断连或 RPC 超时。每种情形都会发出对应生命周期事件，让调用方感知状态变化。

### 回复塑形与 NO_REPLY
最终 payload 由三部分拼装：助手文本含推理内容、verbose 且策略允许时的内联工具摘要、模型错误文本。

NO_REPLY 是一个静默标记，若回复里出现该标记，内容在发出前会被过滤，不会送达用户，常用于心跳确认或无需回应的内部操作。若 message 工具已发出可见回复，重复文本会被自动剔除。若 Agent 无有效输出且工具也报错，OpenClaw 会发出兜底错误回复，避免用户空等。

## 15.3 多 Agent、记忆与系统提示词

#### Multi-Agent 路由：各司其职
当场景变复杂，单 Agent 容易捉襟见肘。OpenClaw 的多 Agent 体系通过三重隔离划定边界：

[PRE0]
Workspace 工作空间：独立的文件系统根目录，包含 AGENTS.md/OUL.md/USER.md 等引导文件与本地笔记，每个 Agent 有自己的家。
State directory 状态目录 agentDir：独立状态存储，路径 ~/.openclaw/agents/<agentId>/agent，保存认证 profile、模型注册表与单 Agent 专属配置，认证 profile 严格单 Agent 隔离。
Session store 会话存储：独立的聊天历史与路由状态，路径 ~/.openclaw/agents/<agentId>/sessions，每个 Agent 的对话记录互不污染。

Skills 隔离是另一维度：工作空间 skills/ 目录的 Skills 只对本 Agent 可见，~/.openclaw/skills/ 下的 Skills 对本机所有 Agent 共享，既能定制专属能力，也能复用通用能力。

#### 路由规则：越具体越优先
消息投给哪个 Agent 由 Bindings 决定，优先级从高到低为：peer 精确匹配 DM/group/channel id；parentPeer 线程继承；guildId + roles；guildId；teamId；渠道 accountId 匹配；渠道级通配 accountId: "*"；最后回退默认 Agent，即 agents.list[].default 标记或首个条目。

同优先级多条绑定时取配置文件中出现的第一条。单条绑定含多个字段时所有字段必须同时满足，采用 AND 语义。

#### 账户与 Agent 解耦
accountId 代表渠道的账户实例，例如两个 WhatsApp 号码对应两个 accountId。一个 agentId 可服务多个 accountId，也可一对一绑定。省略 accountId 的绑定只匹配默认账户，accountId: "*" 为该渠道所有账户的兜底规则。

典型配置场景：按发件人分流，同一 WhatsApp 号收到的不同联系人私信，通过 bindings.match.peer 匹配 E.164 号码路由到不同 Agent；按渠道分流，WhatsApp 用日常 Agent，Telegram 用深度工作 Agent；家庭群组专属 Agent，绑定到家庭群、配置 @提及触发、沙盒与工具白名单，遵循最小权限。

创建新 Agent 用 openclaw agents add <agentName>，会自动生成工作空间与 agentDir 并引导配置 bindings。上线前用 openclaw agents list --bindings 验证路由。

#### Memory：文件才是真实记忆
OpenClaw 的记忆设计很坦诚：模型本身没有跨会话记忆，记忆实体是工作空间文件。官方表述为 The files are the source of truth; the model only remembers what gets written to disk。

基于文件的记忆可直接查看、可 Git 版本控制、可手工编辑，比向量数据库更可控。

[PRE1]
#### 两层记忆结构
第一层是每日日志 memory/YYYY-MM-DD.md，按追加方式记录当日事件、对话摘要与临时笔记，不会自动注入上下文，需通过 memory_search 或 memory_get 主动检索。

第二层是长期记忆 MEMORY.md，存放重要决策、用户偏好与长期事实，作为引导文件只在主私人会话启动时自动注入，群组等共享上下文不加载，防止私密信息泄露。若根目录同时存在 MEMORY.md 与 memory.md，OpenClaw 会自动去重。

#### 记忆操作的两个核心工具
memory_search 对 MEMORY.md 与 memory/*.md 做语义搜索，返回相关片段，底层向量索引可理解措辞变化。
memory_get 精准读取指定 Markdown 文件的行范围，通常配合搜索结果使用。文件不存在时优雅降级返回 { text: "", path }，无需 try/catch。

写入时机：重要决策、用户偏好、需长期保留的事实写入 MEMORY.md；日常笔记与运行上下文写入 memory/YYYY-MM-DD.md；用户明确说“记住这件事”时立即落盘，不能只依赖模型的短时记忆，会话结束即丢失。

#### 自动记忆刷新：Pre-Compaction Ping
上下文窗口有限，积累到阈值会触发自动压缩。为避免细节丢失，压缩前会发起一次静默 Agent 轮次，提醒模型把关键信息写入持久文件，即预压缩记忆刷新。

由 agents.defaults.compaction.memoryFlush 控制：enabled 默认 true、softThresholdTokens、systemPrompt 与 prompt，默认提示含 NO_REPLY 对用户不可见。每个压缩周期只触发一次，workspaceAccess 为 ro 或 none 时自动跳过。

#### 向量搜索与高级配置
MEMORY.md 与 memory/*.md 可构建小型向量索引，支持 BM25 关键词与向量语义混合搜索。嵌入提供商支持 OpenAI、Gemini、Voyage、本地 Ollama，并支持 MMR 多样性重排与时间衰减后处理，使结果既相关又多样。

#### 系统提示词：行为的权威入口
系统提示词在用户消息前设定上下文，OpenClaw 为每次运行构建完全自定义的系统提示，不使用任何 LLM 提供商默认提示，完全掌控行为定义。

#### 系统提示词的固定章节
- Tooling 列出当前可用工具及简要描述。

## OpenClaw 开源实战

- Safety 安全护栏指引，引导模型规避权力寻求、监管绕过、自我复制等不安全行为。
- Skills 若有可用 Skill，则以紧凑 XML 格式注入精简列表指导按需加载 SKILL.md，无 Skill 时整章省略。
- OpenClaw Self-Update 说明 config.apply 与 update.run 的执行要求，防止误用更新功能。
- Workspace 当前工作目录路径。
- Documentation 本地文档位置、镜像地址、源码仓库与社区链接。
- Workspace Files 已注入上下文的引导文件清单。
- Sandbox 启用沙盒时包含沙盒路径、权限说明与高权限 exec 可用性。
- Current Date & Time 用户时区信息，不含动态时钟以保证提示词缓存稳定。
- Reply Tags 当前渠道支持的回复标签语法。
- Heartbeats 心跳提示词与 ACK 行为说明。
- Runtime 主机信息、操作系统、Node 版本、当前模型、代码仓库路径等运行时元数据。
- Reasoning 推理可见级别说明与 /reasoning 切换命令。

提示词模式有三种：full 默认完整提示，适用于主会话；minimal 子 Agent 专用，省略 Skills 列表、记忆召回指引、自更新说明与用户身份等，只保留核心模块，内容标记为 Subagent Context；none 仅保留最基本身份标识，适用于极简集成。

安全护栏本质是建议，非硬性约束，可能被提示词攻击绕过。真正的安全来自下层机制：工具策略 allow/deny 白名单、exec 审批强制人工确认、沙盒隔离、渠道白名单。对公众部署不应仅依赖提示词护栏，硬性机制才是防线。

## 15.4 Skills 体系、沙盒安全与最佳实践
Skills 通过文件化工具教学定义 Agent 能力边界，完全开放，任何文件夹都能为 Agent 新增能力。若说工作空间定义记忆，系统提示定义行为规范，Skills 就定义能力本身。
