通道注册与断点续传
入口就是 Channels 通道注册表。NanoClaw 用工厂自注册的方式，把 Telegram 等异构平台的协议都收敛成统一的消息结构。用户发出指令的瞬间，系统走先落库的思路，把消息元信息立刻写入 SQLite。先写库的机制让系统天然具备断点续传：即便进程意外崩溃，重启后会调用 `recoverPendingMessages()`，依据 `router_state` 表里记录的 `lastAgentTimestamp` 游标，找出游标之后仍未处理的记录重新入队，保证至少一次的处理语义。

（2）编排循环与消息处理
负责这一块的是编排器，主要工作是扫库取新消息并落地调度。调度中枢是 `index.ts` 里的编排器，主循环 `startMessageLoop` 承担全局调度。每隔两秒扫描一次数据库，按时间戳把各群组的新消息捞出来。对每条消息会校验两点：该群组是否要求带唤醒词才能触发 Agent，消息本身是否携带了唤醒词。

这里有个细节：如果群组开启了 @ 模式，只有包含唤醒词的条目才会真正唤醒 Agent。唤醒时不会只处理当前这一条，而是把唤醒词之前累积的上下文一起打包带入。这样既能避免无关闲聊被 Agent 看到保护隐私，又能让 Agent 拿到完整的意图演变保持连贯。

（3）定时任务调度
这一块由 task-scheduler 负责，专门处理定时任务的计算与下发。调度类型有三种：cron 表达式，例如每天 9 点执行一次；固定间隔，例如每 5 分钟一次；一次性任务，只触发一次。执行时可选两种上下文：isolated 隔离模式为每个任务新建会话，Agent 看不到历史；group 群组模式则复用对应群组的当前会话，能感知之前的对话。

下次执行时间的计算采用以原定时刻为基准的策略。举例一个每 5 分钟的任务，因维护中断 2 小时，恢复后不会从当前时刻开始往后堆叠触发以致连发追赶，而是从原本应执行的时间点继续往后走。这种做法防止了时间漂移，保持调度精度。

（4）并发控制与容器分配
这一层由 group-queue 与 container-runner 共同完成，负责任务下发、容器的创建与关闭。主循环找到待处理消息后不会直接起容器，而是先交给 group-queue 评估并发。group-queue 是并发闸门，默认同时最多跑 5 个 Docker 实例，可通过配置调整。消息到来时先检查是否有可用实例，有就把消息通过管道送进该容器的 stdin，Agent 立即消费并返回，实现实时对话；没有空闲实例时消息进入排队，同时触发新容器启动。

group-queue 同时负责状态跟踪，会记录每个群组的容器状态：正在处理消息、空闲待命、正在跑定时任务。空闲待命是指 Agent 已完成工作在等输入，超过 30 分钟的 IDLE_TIMEOUT 后，group-queue 会发送 `_close` 指令让容器优雅退出释放资源。

容器执行层面由 container-runner 实现，负责把主机目录挂载进容器并完成容器的创建。

（5）IPC 通信与容器内处理
该功能由 IPC Watcher 承担，解决容器内外进程间通信。容器内外交互靠 IPC Watcher。为每个群组划分独立的 IPC 空间，内部有 3 个子目录：input 用作主进程向容器发消息或关闭指令；messages 用作容器向主进程回传待发送的消息；tasks 用作容器向调度器提交定时任务的增删改操作。基于文件系统的 IPC 方案简洁可靠，目录路径本身就构成了隔离边界，普通群组的容器只能操作自己的 IPC 目录，无法窥探其他群组。

主进程把消息写进 input 目录后，容器内的 Agent Loop 读取并处理，处理完的结果写入 messages，定时任务请求写入 tasks。

（6）结果路由与回复发送
该功能由 IPC Watcher 与路由器协作完成，负责把容器处理完的结果送回正确的 IM。主进程的 IPC Watcher 监控 messages 目录，发现新输出文件就读取内容交给路由器。路由器根据消息来源定位对应 Channel，由 Channel 把 Agent 的回复发回 IM 软件，完成回路。
