与 Prefill 类似，图 11-2 仍采用两条流水线并发运行，用来把通信开销藏在计算背后。单条流水线的先后顺序为：ATTN-0 运算→ATTN-1 运算→MoE 层的分发通信→MLP 层的路由专家运算→MoE 层的汇聚通信→Shared 层的共享专家运算。

把 H100 的 132 个共享内存全部投入计算，执行节奏如下。

1）在分支 A 执行 MoE 分发通信的同时，分支 A 进行共享专家计算，分支 B 进行 ATTN-0 计算。
2）分支 A 执行路由专家的计算。
3）在分支 B 尚未开始汇聚通信前，先完成分支 B 的 ATTN-1 计算。
4）在分支 B 执行分发通信的同时，分支 B 进行共享专家计算，分支 A 进行 ATTN-0 计算。
5）分支 B 执行路由专家的计算。
6）在分支 B 执行汇聚通信的同时，分支 A 进行 ATTN-1 计算。

**3.动态负载均衡**

在数据并行与专家并行大规模叠加的场景下，任一 GPU 若出现计算或通信过载，就会成为系统瓶颈拖慢整体，同时其他设备空等导致利用率下降。因此必须让每个 GPU 的计算与通信负载尽可能均衡。

（1）Prefill 阶段的负载均衡
●核心问题：不同数据并行实例上的请求数量与长度不一，导致 Core-attention 计算量和分发通信量不一致。
●优化目标：各 GPU 的计算量趋同，即 Core-attention 负载均衡；进入的 Token 数量趋同，即分发通信负载均衡，避免个别 GPU 耗时过长。

（2）Decode 阶段的负载均衡
●核心问题：不同数据并行实例的请求数量、长度差异，造成 Core-attention 计算量受 KV-cache 占用影响而不同，分发通信量也不同。
●优化目标：各 GPU 的 KV-cache 占用尽量一致，达到 Core-attention 负载均衡；请求数量尽量一致，实现分发通信负载均衡。

（3）专家负载均衡器
●核心问题：MoE 模型天然存在少数高负载专家，导致不同 GPU 的专家计算不均。
●优化目标：各 GPU 上专家计算量均衡，实质是最小化所有 GPU 中分发通信量的最大值。

### **11.2 推理阶段的综合解读**

**1.采取 PD 分离技术**
PD 分离是指 Prefill 与 Decode 放在不同设备上并采用不同策略。Prefill 计算密集，只需一次并行，扩大 BatchSize 来保证效率，一个 DeepSeek 部署单元的 Prefill 使用 4 个节点。Decode 为访存密集，优先保证 I/O 速度，需要缩小 BatchSize，也可选用带宽高、算力低的设备，一个 Decode 共用了 14 个节点。

**2.“专家”并行推理**
大模型推理中 Decode 耗时占比大，采用专家并行能够降低单卡访存压力，同时提升每个专家并行处理 Token 的数量。

**3.张量并行数比较小**
分布式训练经验表明张量并行的通信量高于流水线并行与数据并行，设置 TP<8 可让张量并行在一张卡内完成。对 MoE 层的单个专家而言 TP=1，因为单个专家参数量大幅下降，可在单卡内完成计算。

**4.设置“冗余专家”**
冗余专家即高负载专家，其作用是减少通信。以极端情况为例，设备 A 上的专家 a 负载 100%，所有 Token 都要发往它，设备 B 上有专家 b。若一个 Token 同时需要 a 与 b 计算，就必须分发到 A、B 两地。若把高负载专家 a 复制到设备 B 作为冗余专家，该 Token 仅需发往设备 A，省去一次通信。

### **11.3 Prefill 阶段的推理设计及优化**

**1.硬件部署与并行策略**
●最小部署单元：4 个节点共 32 个 GPU，单节点 8 卡，支持 EP 与 DP 结合的多维计算。
●注意力计算层：采用 TP4、SP、DP8 分布式方式，小规模 TP=4 降低通信开销，SP 优化长序列。
●MoE 层专家并行：EP32，每张 GPU 托管 8 个共享专家和 1 个冗余专家，共 32 个冗余专家动态分配，确保每个专家获得足够大的批量提升效率。
●浅层优化：前 3 层密集 MLP 使用 TP1，进一步压降通信。

**2.路由机制设计**
●动态冗余路由：基于在线负载统计如 Token 处理量、GPU 利用率，每 10 分钟扫描一次高负载专家并复制冗余实例，通过节点内 GPU 间专家重排实现均衡。
●专家分配策略：每张 GPU 除 8 个共享专家外再托管 1 个冗余专家，用冗余覆盖热点负载，避免跨节点通信增加。
●全局路由探索：研究动态激活策略，例如每卡托管 16 个共享专家但每次推理只激活其中 9 个，结合 Prefill 的计算余量实时优化路由。

**3.通信架构设计**
●分层通信协议：跨节点通过 InfiniBand 传输 Token，节点内通过 NVLink 低延迟转发，完成 MoE 层 All-to-all 的高效执行。
●计算-通信重叠：并行处理两个微批次，将注意力计算与 MoE 分发/汇聚通信交错，隐藏延迟。
●量化通信优化：MoE 层激活值以 FP8 传输，配合 IB 直连减少数据量，提升带宽利用率，需与训练量化策略兼容。

**4.冗余策略与容错机制**
●动态冗余调整：根据实时监控的专家负载如 Token 分配数、显存占用，每 10 分钟调整冗余专家集合并重排物理位置。
●容错设计：冗余专家覆盖高负载模块，单 GPU 故障时可快速切换到备用专家，保证服务连续。
●内存优化：探索专家参数的 FP8 混合精度存储，权衡冗余专家的显存占用与精度。

**5.性能优化**
●通信瓶颈优化：跨节点 All-to-all 延迟占比高，可优化 IB 调度，引入 IBGDA 技术绕过 CPU，直接通过 GPU 内存交换数据。
●负载不均衡优化：动态路由易因专家热度差异产生长尾延迟，可开发轻量贪心算法如 Top K 剪枝或预编译路由表，降低实时计算开销。
●内存带宽限制优化：微批次较小时专家计算受显存带宽制约，可采用块稀疏矩阵乘法如 MegaBlocks 方案优化访问模式。

### **11.4 Decode 阶段的推理设计及优化**

**1.硬件部署与并行策略**
●最小部署单元：40 个节点共 320 个 GPU，单节点 8 卡，支持大规模并行。
●注意力计算层：TP4、SP、DP80 分布式部署，多维切分提升效率。
●MoE 专家并行：EP320，每张 GPU 独立托管 1 个专家，共 320 个，其中 64 张 GPU 固定托管 64 个冗余专家与共享专家，其余 256 张 GPU 动态分配领域专家。

**2.路由机制设计**
●强制路由规则：共享专家作为高负载专家，在 Token 级路由时必选，其余专家从动态池选取。
●负载均衡：基于历史负载统计定期调整冗余专家组规模，因每卡仅承载 1 个专家，无需重排物理位置。
●动态冗余探索：研究全局最优路由算法，需与分发通信内核融合以降低调度开销，如通过稀疏化计算或硬件加速优化决策。

**3.通信架构设计**
●低延迟调度：通过 IB 网络多对多直连传输，实现多对多通信，避免传统协议栈开销。
●IBGDA 技术增强：利用 NVIDIA IBGDA 绕过 CPU，直接通过 GPU 内存交换数据，降低端到端延迟并提升带宽利用率。
●计算-通信重叠：异步执行微批次的注意力计算与 MoE 层通信，隐藏延迟。

**4.冗余策略与容错机制**
●静态冗余配置：根据实时监控的专家负载如 Token 处理量、GPU 利用率，动态调整冗余专家数量应对热点。
●专家动态激活：探索仅激活部分专家如每次推理在 16 个本地专家中激活 9 个的轻量化策略，优化内存访问模式如 FP8 混合精度存储。
●容错设计：冗余专家覆盖关键功能模块，确保单 GPU 故障时服务不中断。

**5.性能优化**
●内存优化：Decode 阶段 Token 批量小通常≤256，专家计算受内存带宽而非算力限制，可采用稀疏存储或 FP8 量化降低内存占用。
●动态路由复杂度优化：全局最优路由需实时计算分配，可能引入额外延迟。可设计轻量贪心算法如 Top K 剪枝或预编译路由表，用局部最优替代全局最优，降低计算复杂度。
