这个比喻把 Skills 在 Claude Code 中的角色锚得非常清楚。官方给出的定义很克制：Skill 是一个装着指令的文件夹，以简洁的目录结构打包，用来“教” Claude 去完成某项具体任务或工作流。定义里有两个词值得细究。

其一是“文件夹”——从文本提示到工程化。Skill 不止是一段 Prompt 或一枚配置，它是一个可落地的工程目录，能容纳代码库、领域文档、模板、甚至可执行脚本。

其二是“教”——从限制到内化。选用“教”而非“命令”“约束”，点出了运行机理。Skill 是在赋能与内化能力，Claude 因此不再是被动执行指令的工具，而成了该领域的熟练使用者。

## 3.2 解剖一个 Skill：骨骼与纹理

[PRE1]

这些看起来繁琐的规矩，实际上是工程实践里用教训换来的防错机制。

文件名：SKILL.md 是唯一的触发器。文件名必须是全大写，skill.md、Skill.md、SKILL.MD 都无效。加载器扫描时做的是精确字符串匹配，不是模糊查找。

目录名：kebab-case，是跨平台通用语。目录名用全小写加连字符，如 api-doc-generator，长度不超过 64 个字符，字符集仅限 [a-z0-9-]。禁止空格、下划线、大写、首尾连字符和连续连字符。为抹平系统差异，Windows 不区分大小写，Linux 严格区分，kebab-case 能保证 Skill 在任何环境下被无损识别。

禁入 README.md——保持指令空间纯净。Skill 目录里不能放 README.md，人类阅读的说明放到父目录即可。激活时 Claude 会读取目录下所有 Markdown 作为上下文，SKILL.md 是给模型看的指令，README.md 是给人看的介绍，混在一起会引入噪声，干扰理解。

命名中立：拒绝品牌词。name 字段里不能出现 claude 或 anthropic。Skill 是一种开放的知识封装方式，保持品牌中立才利于知识流动，而不是绑定某个产品。

### 3.2.2 YAML 前置元数据：Skill 的“身份证”

SKILL.md 顶部的 YAML Frontmatter 决定了 Skill 的身份与行为边界。完整字段可归为三类，对应设计的三个维度：触发、权限、运行。

[PRE2]

- 身份字段，触发机制：name、description、argument-hint。用来说明 Skill 是什么、做什么、怎么调用，是触发逻辑的基础。
- 权限字段，权限控制：disable-model-invocation、user-invocable、allowed-tools、model。规定谁能调用、能做什么，通过限制调用来源、可用工具与模型划定安全与资源边界。
- 执行字段，运行时环境：context、agent、hooks。决定在哪里执行、执行过程中发生什么，用来配置隔离环境、子智能体类型与生命周期钩子，保证任务在预期上下文里运行。

掌握这三类，就掌握了 Skill 架构设计的完整框架。

> 咖哥发言

disable-model-invocation 与 user-invocable 容易混淆，却控制两个正交方向。disable-model-invocation: true 表示 Claude 不能自动触发，必须由用户通过 /skill-name 手动执行。适合有副作用或高风险操作，如 /commit、/deploy，确保显式确认。默认值是 false。

user-invocable: false 表示 Skill 不会出现在 / 菜单里，用户无法手动触发，但 Claude 仍可在内部逻辑中自动调用。适合纯知识型或辅助型参考 Skill，隐藏菜单以减少干扰，同时保留自动加载能力。默认值是 true。

默认情况下，Skill 对 Claude 与用户都是双向开放的。

### 3.3.2 description 的预算机制

渐进披露的第一层是所有 Skill 的 description，它以常驻方式注入上下文，必须瓜分一个有限预算，形成系统瓶颈。

官方规则：description 总预算上限为上下文窗口的 2%，未指定或计算异常时默认固定为 16 000 个字符。预算由全部已安装 Skill 平分，而非按需分配。

单个 Skill 可用字符数 = 总预算 / Skill 的总数

假设安装 20 个 Skill，在默认 16 000 字符预算下，每个 description 平均只有 800 字符，见图 3-4。

[PRE4]

若某个 description 超过 800 字符，它会被静默排除。Claude Code 完全感知不到该 Skill，既不会在扫描阶段看到，也无法后续加载。对用户而言，这个 Skill 就像消失了。

避坑可参考三点。技巧 1，在配置里设 disable-model-invocation: true，该 Skill 的 description 不会被注入上下文。技巧 2，运行诊断命令 /context，可查看是否有 Skill 被静默排除。技巧 3，通过环境变量 SLASH_COMMAND_TOOL_CHAR_BUDGET 手动扩大预算池。

这揭示了工程哲学：不要盲目堆 Skill，要做少而精的架构。超过 20 个 Skill 通常是信号，需要重新审视策略：

合并同类项，把碎片 Skill 合成综合体；隐藏内部工具，把纯内部调用的子任务标记为 disable-model-invocation: true，减少预算占用；用 Token 投资回报率思维看待 description，每个字符都很贵，投得准才换来高效检索与准确执行，投得浪费不仅浪费自身配额，还挤占他人的生存空间。

## 3.4 触发机制：Claude Code 如何抉择 Skills 的调用

触发机制是整个系统最关键的一环，比内容本身更重要。触发不了，再好的内容也无效。

### 3.4.1 双通道激活机制

每个 Skill 都有两种激活路径。

1. 显式调用
用户在对话中输入 /skill-name，Claude Code 立刻加载执行，像终端命令一样明确无歧义。若定义了 argument-hint，还可带参数调用，如 /commit fix login bug 或 /review src/auth/login.ts。

2. 语义匹配
Claude 理解用户意图后自主判断哪个 Skill 最匹配，然后自动加载。这是日常核心价值：用户只需描述需求，Claude 在幕后决策是否调用、如何调用，过程透明，实现所想即所得。
