比如一个 Agent 往往会同时挂载多套大模型，比如擅长多模态识别的 Doubao-Seed-2.0-Pro、推理能力更强的 Qwen3-Max，以及代码生成突出的 GLM-4.7。感知层会先解析用户意图，再挑出最匹配的模型去响应，这样就能避免因模型选型不当导致效果打折或浪费 Token。

#### 2. 规划模块：编排上下文的执行骨架
规划模块的核心工作是产出解决问题的思维链。因为真实任务多是多轮思考的结果，这个模块实际上为整段上下文搭建了逻辑主干，它决定任务该按怎样的步骤拆分和推进。目前工程化落地的思路主要有下面几种。
- ReAct 模式：以“推理-行动-观察”闭环驱动上下文动态演进。
- PlanAct 模式：先生成完整执行计划，或由人工注入标准作业流程 SOP，再让 LLM 按序执行。
- Sequential Thinking：这是一个开源的 MCP 模型上下文协议 Server，能让 LLM 做多轮自主规划与反思，显著提升复杂任务成功率。扣子原扣子空间在升级到 2.0 后改名，底层就基于 MCP Server 来构建思维链。

#### 3. 执行模块：注入实时上下文
执行模块通过调用外部 API 或运行代码型 Agent，来获取物理世界的即时数据，比如最新的行业参数、价格波动。上下文工程里最具动态性的就是这一块，每次工具调用的返回都会被加工成新的上下文片段，实时喂给模型，驱动下一轮推理。

#### 4. 反思模块：防止上下文遗漏失误
“吾日三省吾身”的思路同样适用于 Agent。反思模块会对规划和执行的结果做复盘，检查是否存在错误或不完善，给出纠正建议并重新引导规划进入新一轮。在工程实现上，既可以通过设计反思提示词来赋能 Agent，也能借助 Sequential Thinking 工具完成规划到反思的闭环。

### 1.2.2 上下文管理的核心策略
LLM 的上下文窗口受限，光构建还不够，还得做管理，让窗口被高效利用。下面从记忆管理和上下文卸载两方面展开。

#### 1. 记忆管理
记忆管理解决的是窗口有限、长对话易断档的问题。短期记忆和长期记忆结合，可以让 Agent 在多轮交互中保持连贯，避免重复提问。记忆模块还能维护用户长期偏好、历史行为以及从外部检索来的专业知识。落地方式因场景而异，短期记忆常把对话历史存在内存临时使用，长期记忆则把历史保存在文件或向量库中，配合 RAG 存取，比如 Mem0 就是基于 Agentic RAG 的方案。

#### 2. 上下文卸载
工程实践里，上下文并非越多越好，过剩信息会变成噪声拖累性能。上下文卸载就是只保留当前任务最相关的关键信息。

如图1-5所示，AI 编程工具 Cursor 在分析复杂项目时，会把详尽分析写入独立的 Markdown 文件，对话窗口里只保留文件路径和摘要。这种引用而非堆砌的方式有效遏制上下文膨胀。

## 1.3 从简单工具调用到复杂 Agent：技术演进路线图
本节梳理 Agent 自 2023 年以来的发展脉络，看看架构、能力与应用场景如何演进，上下文工程又是如何随之变化。

### 1.3.1 轻量工具调用 Agent 的原理与特点
Agent 概念在 2023 年迎来关注。LLM 虽有丰富通用知识，但在垂直专业问题或需要实时信息时，比如“今日北京天气如何”，很容易出错或产生幻觉。为此研究者探索让模型与外部环境交互，通过调用数据库、API、搜索引擎等获取最新相关信息，再融入推理，提升准确性和时效。

#### 1. Function Calling
2023 年 6 月，OpenAI 正式推出 Function Calling，并在 GPT 系列中原生支持。其思想是在预训练或微调时引入结构化工具交互数据，让模型学会在合适情境下触发工具调用。典型训练样例如下。

#### 2. ReAct
为绕开 Function Calling 的改造成本，研究者转向无需改模型结构的方案。2023 年论文 ReAct: Synergizing Reasoning and Acting in Language Models 提出的思路很快被工程化，至今仍是 Claude Code 等强力 Agent 的底层范式。

ReAct 的优势是零训练依赖，只靠提示词就能让 LLM 在推理中交替进行思考和行动，且思考过程会随对话返回。开发者准备好任务目标、工具列表和交互格式的模板后，模型可在运行时自动完成以下循环，流程见图1-6。
1. 理解问题并进行推理。

3. 选工具并生成调用参数。
4. 接收工具执行反馈。
5. 用新信息更新上下文，继续推理或输出答案。

### 1.3.2 深度思考型 Agent 的原理与特点
ReAct 在生产中暴露出局限：
- 对底层 LLM 能力高度依赖，推理或格式能力不足会导致流程中断。
- 执行效率低，复杂任务需多次调用，延迟和成本累积。
- 提示词脆弱，细微改动会影响行为，且模型对格式保持不稳。
- 缺乏全局视角，易陷入局部最优或原地循环。

为此出现了新的设计范式。

#### 1. Agent 设计模式
常见的有：
（1）CodeAct 模式。将工具抽象为 Python 执行器，LLM 生成可执行代码片段而非调用预定义 API，适合运维自动化、数据处理等场景。
（2）计划-执行 模式。先由规划 Agent 做全局拆解生成多步计划，再交执行 Agent 按步骤调用工具并推进，提升长程任务一致性。
（3）反思 模式。执行后由独立反思 Agent 评估输出是否存在逻辑漏洞、信息遗漏或误用，必要时重试或调整策略，提升准确性和鲁棒性。
（4）人机协作 模式。在关键决策或高风险操作处嵌入人工审核点，系统暂停请求授权，降低错误成本并增强可控性。

#### 2. 深度思考型 Agent 的出现
2025 年上半年，深度思考型 Agent 成为研究热点，如 OpenAI 的 DeepResearch、智谱的沉思、扣子系列产品等。它们不再满足于单轮工具调用，而是融合多种设计模式，形成持续迭代、自我修正的认知闭环。

### 1.3.4 多 Agent 的原理与特点
SubAgent 近期很热，也称子 Agent 或专家 Agent，负责特定子任务或领域。典型多 Agent 系统由多个 SubAgent 加一个协调者 Manager Agent 构成，前者执行，后者负责分解、调度、仲裁与整合。

传统说法认为多 Agent 解决单 Agent 面对大量工具时选错问题，这有道理。更本质的视角是上下文污染问题。上下文污染指单 Agent 在任务复杂时，上下文混杂推理轨迹、工具描述、中间结果、历史记录和原始意图等异构信息，缺乏结构会相互干扰，造成认知噪声、聚焦下降，还会迅速耗尽 Token 窗口导致截断。
