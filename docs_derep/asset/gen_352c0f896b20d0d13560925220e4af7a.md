# 渐进式免密 + 沙盒隔离：OpenClaw 安全运维的全套思路

官方把这套做法命名为“加法式”设计，不是粗暴替换，而是按需叠加。明文配置依然可用，你可以挑字段把部分项升级成 SecretRef，无须一次性全改。这样的逐步迁移路径，把从明文到安全配置的门槛降到很低。

核心好处在于 openclaw.json 可以放心提交到 Git，哪怕是私有库，文件里也不含真实凭证。真实凭证落在环境变量、本地文件或外部密钥库如 1Password、HashiCorp Vault 等，配置文件与秘密彻底解耦。换机器时只需重新配置凭据，而不是拷贝密钥。

#### SecretRef 三种取值来源

无论来源如何，SecretRef 都用同一套 JSON 结构：`{ source: "env" | "file" | "exec", provider: "...", id: "..." }`。差别在取值位置和校验规则。

**source: "env" 从环境变量读取**

最轻量的方式。示例：`{ "source": "env", "provider": "default", "id": "OPENAI_API_KEY" }`。id 即环境变量名，必须符合 `^[A-Z][A-Z0-9_]{0,127}$` 的命名规范。以大写字母开头，合法字符受限。若变量不存在或值为空，解析会直接失败。

**source: "file" 从本地文件读取**

示例：`{ "source": "file", "provider": "filemain", "id": "/providers/openai/apiKey" }`。读取本地 JSON 或单值文件。id 采用 RFC6901 JSON Pointer 指向目标字段。mode 为 "json" 时解析对象并按指针定位；mode 为 "singleValue" 时 id 必须为 "value"，直接返回文件全部内容。文件路径要通过权限检查，Windows 下若 ACL 验证不可用，解析会 fail-closed。

**source: "exec" 通过外部程序读取**

示例：`{ "source": "exec", "provider": "vault", "id": "providers/openai/apiKey" }`。OpenClaw 启动外部可执行程序，通过 stdin 传请求、从 stdout 读响应，全程不经过 Shell，避免命令注入。典型用于对接 1Password CLI、Vault CLI、sops 等。默认 command 必须指向普通文件而非符号链接，若需兼容 Homebrew 等产生的软链接，可打开 `allowSymlinkCommand: true`，并用 `trustedDirs` 限定可信目录范围。

#### Secrets 解析的四个可靠性承诺

OpenClaw 的解析机制围绕四条原则构建：

第一，解析是急切的而非惰性的。Gateway 启动或重载时就立即解析所有活跃的 SecretRef，而不是等到首次使用。故障因此发生在启动/重载的冷路径，而非请求处理的热路径，保护可用性。

第二，重载执行原子交换。先完整生成新的 secrets 快照，全部校验通过后再一次性替换旧快照。若中途失败，继续使用上一个健康快照，不会出现半更新不一致。

第三，活跃面过滤。只有真正启用的 Channel、已选中的工具等活跃配置面的 SecretRef 必须解析。未激活面解析失败仅发出 `SECRETS_REF_IGNORED_INACTIVE_SURFACE` 非致命诊断，不阻断启动。

第四，降级与恢复有明确信号。重载失败后 Gateway 进入降级态，发出 `SECRETS_RELOADER_DEGRADED` 事件并保留旧快照继续服务；下次重载成功后发出 `SECRETS_RELOADER_RECOVERED`，运营可据此监控凭据健康。

### 16.4 沙盒安全机制——给 Agent 划定行动边界

#### 为什么需要沙盒，能做什么做不到什么

即便完全信任自部署的 Agent，仍存在两类风险：模型被精心设计的输入诱导执行不当操作，即提示注入；模型在无恶意输入时也可能误操作，误删文件或生成破坏性脚本。沙盒是系统级的应对手段。

官方表述很务实：“This is not a perfect security boundary, but it materially limits filesystem and process access when the model does something dumb”。意即并非无懈可击，却能在模型犯错时实质限制文件系统和进程访问范围。

边界说明：沙盒仅覆盖工具执行，如 exec、read、write、edit、apply_patch 等，Gateway 进程本身始终在宿主机运行，不受沙盒限制。这样保证 Gateway 稳定性，同时把安全隔离聚焦在最有价值的工具调用层。

#### 三种沙盒模式，按需选择强度

通过 `agents.defaults.sandbox.mode` 全局配置，也可在 `agents.list[].sandbox.mode` 为单个 Agent 指定：

- **off**：关闭沙盒，所有工具直连宿主机。默认值，适合开发测试或完全可信的单用户本地部署。
- **non-main**：仅对非主会话沙盒化。主会话即 `session.mainKey` 为 "main" 的会话不受限，来自群组聊天、消息渠道的会话被沙盒化。判断依据是 `session.mainKey` 而非 agent id，群组和渠道会话使用独立 session key，会被自动归为 non-main。
- **all**：所有会话均沙盒化，提供最强隔离，适合面向不可信用户公开部署或高安全企业场景。

#### 三种沙盒范围，容器生命周期如何计

范围决定容器创建粒度与存活时长，在隔离与性能间权衡：

- **session**（默认）：每个会话一个独立容器，会话结束即销毁。隔离最彻底，但新会话需创建容器，有启动开销。
- **agent**：同一 Agent 的所有沙盒会话共享一个容器，容器随 Agent 生命周期持续存在。可在多次对话间保留中间产物，适合需积累临时结果的工作流。
- **shared**：所有沙盒会话共享同一个容器，创建成本最低，但隔离最弱，不同会话操作互相可见，不适合多用户或存在不可信输入的场景。

#### Docker 后端，最常用的默认实现

Docker 是默认后端，提供基于 Linux 的完整文件系统和网络隔离。关键项：

- **image**：镜像名，默认 `openclaw-sandbox:bookworm-slim`，通过 `scripts/sandbox-setup.sh` 构建。需 Node.js 环境时可构建 `openclaw-sandbox-common`。
- **network**：容器网络，默认 `none` 完全禁止外网。若工具需访问网络，可改为 `bridge` 或自定义网络。
- **setupCommand**：容器创建后执行一次，常用于安装 Skills 依赖的 CLI 工具。
- **binds**：额外挂载，格式 `{ hostPath, containerPath, mode: "ro"|"rw" }`。全局与 per-agent binds 会合并而非覆盖。
- **workspaceAccess**：容器对真实工作区的访问级别，见下节。

#### SSH 后端与 OpenShell 后端

SSH 后端把 exec、文件工具和媒体读取卸载到远程主机执行，适合把计算密集型调用从轻量 Gateway 如树莓派转移到更强服务器。采用“远程规范”模型：首次使用时把本地工作区同步到远程，之后远程成为权威，本地后续改动不会自动同步，需主动管理差异。SSH 认证材料 identityData、certificateData、knownHostsData 支持 SecretRef，沙盒激活时解析后写入临时文件用于连接。

OpenShell 后端是 OpenClaw 托管的远程沙盒服务，复用 SSH 传输核心并增加生命周期管理。支持两种同步模式：mirror 模式本地始终权威，每次 exec 前把本地增量同步到远程、执行后再同步回本地，双向但开销更高；remote 模式初次 seed 后远程权威，后续不自动回传，成本更低，适合以沙盒为主工作区。

#### 工作空间访问三档权限

`workspaceAccess` 控制容器能看到的 Agent 工作区范围：

- **none**（默认）：完全隔离。容器仅能看到 `~/.openclaw/sandboxes` 下的独立沙盒工作区，与真实工作区断开。OpenClaw 会自动镜像符合条件的 Skills 目录，保证 SKILL.md 可加载。
- **ro**（只读）：以只读方式挂载真实工作区到容器 `/agent`。write、edit、apply_patch 等写操作被禁用，适合只读上下文场景。
- **rw**（读写）：以读写方式挂载真实工作区到容器 `/workspace`。文件修改直接作用于真实工作区，行为与非沙盒一致，安全性稍弱但最便利。

#### 工具策略与沙盒的分工协作

工具策略 `tools.allow/deny` 与沙盒是两层独立防护。工具策略先于沙盒生效，决定“是否允许使用该工具”的逻辑层；沙盒负责“允许的工具在何种环境运行”的系统层隔离。二者互不替代，沙盒不会让被 deny 的工具复活，策略也不会穿透沙盒物理边界。

`tools.elevated` 是高权限逃生舱：授权发件人可让特定 exec 调用绕过沙盒直接在宿主机运行，适用于 Docker 管理、系统配置等宿主机专属操作，应谨慎授予。

### 16.5 Cron 任务调度——让 Agent 主动做事

#### 从被动响应到主动执行

多数 AI 助手被动等待消息。OpenClaw 的 Cron 打破这一模式，可定义“每天 9 点整理待办”、“每小时检查指标”、“周五提醒提交报告”等任务，无需人工触发，Gateway 按计划自动执行并推送结果。

官方定位 Cron 为“proactive automation”核心机制，由 Gateway 管理，独立于用户主会话运行，可后台静默执行，也可推送到指定消息渠道。

#### 任务完整结构

一个 Cron 任务由六个字段定义：

- **name**（可选）：任务名称，便于 `cron list` 与日志识别。
- **schedule**（必需）：触发时间规则，决定何时执行。
- **payload**（必需）：执行内容，决定执行什么。
