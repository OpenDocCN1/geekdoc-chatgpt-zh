torch.compile 的本质是在运行期监听 PyTorch 程序，把模型执行的轨迹实时转成计算图，再经一系列变换生成加速后的执行代码。最打动人的地方在于它能在碰到无法图变换的片段时优雅地退回 Python 解释器执行，既保留了易用性又换来了性能。接口做得很轻，值得每个人先试一试。

这部分内容分两层展开。只想拿来提速的读者，看看 9.3.1 的使用示例和大概的优化思路就够了。对内部原理和调试手段感兴趣的，可以继续往下看，后面会讲清楚 torch.compile 大致是怎么实现的，以及如何打开调试开关观察它生成的底层代码。

#### 9.3.2 如何抽取计算图
对基于图的优化来说，最难的往往不是怎么优化图，而是怎么从动态图风格的代码里把图稳稳地抽出来。核心在于把 PyTorch 的调用和普通的 Python 逻辑剥离。编译器不可能理解所有 Python 语法，所以必须筛出与张量和算子相关的操作来构建可优化的图。抽取主要有两种思路：运行时跟踪和源码静态分析。下面用一段代码对比这两种方式：

基于 Python 运行时的跟踪，本质是模型跑起来时动态记录操作，通过监听算子执行来还原依赖关系。这种方式能忠实反映实际运行轨迹，对控制流很宽容，只记录真正走到的分支，未执行的分支不会进入图。如图 9-7 左侧所示，只有 linear2 被捕捉到，linear3 因为分支未触发而缺席。JIT tracing、lazy tensor 以及 torch.compile 都属于这一类。

基于源码分析则是不跑模型，直接解析源代码的静态结构来组装图。因为不需要执行，就能看到包含 if-else、for 等 Python 控制流在内的完整视图。如图 9-5 右侧所示，linear2、linear3 及其控制逻辑都被收进同一张图里。

源码分析能识别控制流并把相关操作聚到一张图里，图越完整优化越有利。代表工具是 TorchScript。代价是它对 Python 特性的支持有限，往往需要改写代码，牺牲灵活性和可读性。能跑起来时性能很强，但为此付出的代码妥协也很大。

torch.compile 具体是怎么做的？它在程序运行时动态分析 Python 字节码，通过 CPython 提供的内部接口，借助 TorchDynamo 把张量操作捕获并转成计算图。随后图会被优化并生成更高效的代码来替换原来的 Python 函数调用。遇到无法图化的代码，构建会中断并回退到标准 Python 解释器处理。因此生成的图是随实际数据和操作动态产生的，创建、优化、代码生成对用户是透明的。写代码的体验仍是 Python，背后却自动完成优化，可谓近乎免费的加速。值得一提的是，结合 AOT Autograd，torch.compile 不仅能捕获前向，还能捕获反向图，从而优化完整的前后向流程。

和所有基于运行期跟踪的方法一样，torch.compile 有几处局限：

- 只能记录执行期间真正走过的路径，依赖输入数据的分支在跟踪时未触发就不会被捕获。
- 主要聚焦 PyTorch 操作，倚赖外部库或特殊 Python 功能的部分可能无法被有效图化与优化。
- 在 Python 中直接访问张量值会打断图构建，导致图被切碎、信息变少。

源码分析能给出最精确简洁的图，但获取成本极高。运行时跟踪获取容易，却难以完全复现 Python 的高级控制流，循环或递归展开后图会变得臃肿，分析与优化难度上升。取舍就在这里。

#### 9.4 本章小结
本章介绍的高级优化手段，都是在 GPU 已满载的基础上再榨取效率。它们普遍涉及底层机制，要求使用者具备一定高性能计算背景，调试难度不低，离了对底层如指掌很难用顺手。基于训练经验，建议按顺序尝试。

首先推荐 torch.compile，开启成本低且副作用小。只需要在模型外层包一层 torch.compile，观察速度变化即可。若出现性能倒退或提示回退到 Eager 模式，说明当前结构暂时不适合图优化；一旦提速明显，那就相当于是白赚的性能。
