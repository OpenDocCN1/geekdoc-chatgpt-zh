### 5.2.2 Agent间对话协议的设计与优化

多 Agent 协同中，Agent 间通信的效率与准确性直接影响整体性能。良好的对话协议要兼顾结构化以便程序解析，和自然语言表达以发挥 LLM 优势。当前主流的 A2A、ACP 等协议均以 JSON 为消息基底，同时在关键字段保留自然语言描述。

设计需遵循三原则。第一 消息结构标准化，所有 Agent 使用统一格式，包含发送者、接收者、消息类型、内容、元数据等必填字段。第二 语义明确化，消息类型采用预定义动作枚举如 REQUEST、RESPONSE、HANDOFF、ERROR，避免歧义。第三 上下文完整性，转交任务时必须携带足够上下文，确保接收方可无缝接续。

图5-5 展示了标准消息结构与四种消息类型。左侧为完整 JSON 结构，含消息 ID、时间戳、路由信息、消息类型、业务内容与上下文。右侧说明四种类型用途与必含字段：REQUEST 发起任务请求，RESPONSE 返回处理结果，HANDOFF 任务转交，ERROR 报告异常。每种类型均有明确字段要求。底部强调设计原则：结构化 JSON 保证可解析，自然语言 content 发挥 LLM 理解优势。

对话5-1 展示完整任务转交流程。用户向订单 Agent 提出退款请求后，Agent 先查询订单信息，再识别出退款意图超出职责。转交时构造含完整上下文的 HANDOFF 消息，content 描述任务内容与原因，context 包含订单状态、配送天数、用户情绪等关键信息。售后 Agent 收到后即可基于上下文直接响应，无需重复询问，实现无缝交接。

## 消息类型定义

- **REQUEST-请求消息**
  - 用途：发起任务请求或询问
  - 必含：task（任务描述）、input（输入数据）
- **RESPONSE-响应消息**
  - 用途：返回处理结果
  - 必含：status（状态）、result（结果）、reply_to
- **HANDOFF-转交消息**
  - 用途：将任务转交给其他Agent
  - 必含：reason（转交原因）、context（完整上下文）
- **ERROR-错误消息**
  - 用途：报告处理异常
  - 必含：error_code、error_msg、recoverable

### 5.2.3 动态Prompt调整与个性化定制

静态 System Prompt 难以适应多变的业务场景。动态 Prompt 调整允许系统依据运行期上下文、用户特征和历史交互实时修改或扩展 Prompt，实现更精准个性化服务，在客服、推荐、教育等领域尤为重要。

核心机制是 Prompt 注入，即在基础 System Prompt 上根据条件动态添加指令或上下文。注入内容可来自用户画像信息、会话上下文、业务规则、实时数据等维度。注入机制需设计清晰优先级，避免动态内容与基础 Prompt 冲突。

### 5.2.4 多语言与跨文化Agent的适配策略

面向全球市场的 Agent 系统需支持多语言，不仅是翻译，还涉及文化背景、表达习惯与本地化规范。主要挑战为语言能力差异、文化理解差异、格式本地化差异。

适配策略分为三种。原生多语言策略直接使用多语言 LLM 并在 Prompt 中指定响应语言，适用于覆盖广但文化要求不高的场景。翻译桥接策略将非英语输入译为英语处理再译回目标语言，可利用英语模型能力但可能损失文化语境。本地化分支策略为不同语言地区维护独立 Prompt 版本，实现深度文化适配但维护成本高。

### 表5-4 多语言Agent适配策略对比

| 适配策略 | 实现方式 | 主要优势 | 主要劣势 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 原生多语言策略 | 使用多语言LLM、Prompt指定语言、自动语言检测、统一Prompt模板 | 实现简单、延迟低、维护成本低、一致性好 | 小语种能力弱、文化适配差、本地化不足、表达可能生硬 | 通用客服、信息查询、技术支持 |
| 翻译桥接策略 | 输入翻译为英语、英语处理核心逻辑、输出翻译回目标语、保留原始上下文 | 英语能力强、推理质量高、工具调用稳定、Prompt复用 | 延迟增加、翻译误差累积、文化语境丢失、成本翻倍 | 复杂推理任务、专业领域Agent、工具调用密集 |
| 本地化分支策略 | 分语言Prompt版本、文化特定示例、本地格式适配、地区专属规则 | 深度文化适配、表达自然流畅、用户体验最优、合规性强 | 维护成本高、版本同步困难、需本地化团队、测试工作量大 | 品牌形象重要、法规严格地区、高端服务场景 |
