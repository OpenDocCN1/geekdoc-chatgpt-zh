拿图像生成来做评测就是很直观的一个例子。用同一条提示词分别让 Nano Banana Pro 和 Nano Banana 各自出图，就能从生成耗时、成图质量、文字排版这三个角度做横向对比。除了基础指标，还可以喂更复杂的场景描述，观察哪款模型更懂你的意图；也可以做多轮对话式微调，看模型在接连修改要求时是否能精准响应。

只要按这种方式做系统化对比，很快就能对不同模型形成肌肉记忆。更关键的是，测试结果能直接指导选型。应用并不需要顶级推理能力的话，Gemini 2.5 Flash 就能把成本压得很低；如果图像任务对分辨率没硬性要求，Nano Banana 的免费 API Key 已经够用。靠实测做决策，既保住应用表现，又把开销控制在合理区间。

#### 3. 在 Playground 里调校提示词与能力组合
正式写代码前，Playground 就是验证系统提示词和模型搭配的最佳沙盒。

比如你想做一个“智能行业研究助手”，帮助用户快速掌握行业最新动向和数据解读，可以先在 Playground 里按部就班地试跑：

- 在模型设置区的“System instructions”里先给出角色定位：“你是一位经验丰富的行业分析师，擅长搜集最新信息、分析数据趋势，用清晰的语言解释复杂的行业现象。”
- 用几类典型提问做压力测试，例如问“分析一下新能源汽车行业最近的发展趋势”，看返回内容是否符合预期。
- 若发现回答过于笼统，就回到“System instructions”里补充约束，比如加上“回答时要引用具体数据及数据来源”。

除了提示词打磨，Playground 也是测试模型能力组合的实验室。不同场景需要不同的能力支持，常用适配方式如下。

- Grounding with Google Search（Google 搜索增强）：适合需要实时信息的场景，如新闻摘要、股价解读、行业研究。测试时可以提时间敏感的问法，例如“最近一周科技圈有什么重要新闻”，检验搜索增强能否给出准确的最新内容。
- Code execution（代码执行）：适合涉及计算或数据处理的场景，如数据分析、财务计算、统计工具。可以用“分析这组销售数据的增长趋势并绘制图表”这类需要编程的问题来验证，AI 是否能自动写码并执行。
- Structured outputs（结构化输出）：适合需要固定格式的场景，如表单生成、数据抽取、API 中间件。先定义好 JSON Schema，再测试，确认输出是否可以直接被程序解析。
- Function calling（函数调用）：适合需要对接外部服务的场景，如智能家居控制、订单查询、CRM 助手。在 Playground 中先定义函数，再测试 AI 是否能在合适情境下识别需求并调用对应函数。
- URL context（URL 上下文）：适合基于特定网页作答的场景，如文档问答、竞品分析、论文阅读。提供目标链接后测试，确认 AI 能否准确抓取并理解网页核心信息。

以行业研究助手为例，通常要同时打开 Google Search 拿最新动态、Code execution 做数据趋势分析、URL context 读取特定研报。逐项在 Playground 中验证效果，就能找到最合适的组合。

另外借助模型对比功能可以更快锁定性价比方案。点开 Playground 导航栏的 ✨ 按钮，同时在 Gemini 3 和 Gemini 2.5 Flash 上跑同一问题，你会发现简单的信息收集用 Gemini 2.5 Flash 就够了，只有复杂的数据分析才值得用 Gemini 3 的推理能力。

#### 4. Playground 与 Build 的协作流
第 1 章讲的产品说明书这类前期工作，都可以在 Playground 完成。你可以上传竞品文档让 AI 拆解核心功能和创新点，粘贴用户访谈记录让 AI 提取关键需求，也可以把产品构想丢进去让 AI 生成功能规划。

方向明确后，先在 Playground 测不同模型的能力和性能，确定最合适的组合。如果 Gemini 2.5 Flash 就能满足对话需求，就没必要上成本更高的 Gemini 3。前期试跑能让正式开发时做出更经济的技术选型。

2.2 节会讲如何用 Google AI Studio Build 搭建完整应用。但 Playground 的价值不止在开发前。Build 里把应用搭好后，如果需要微调 AI 行为，比如优化系统提示词的表述、开关某些模型能力、调整参数，这时就回到 Playground 调试。

在 Playground 里你可以自由改系统指令、开关 Google Search、Code execution 等功能，用真实用户问题做验证，观察回答是否达标。满意后点右上角的“Get code”，所有配置会打包成代码，直接复制到 Build 中替换原配置，就能立刻看到改进效果。

“Build 发现问题 → Playground 调试 → Get code 导出 → 应用到 Build”的闭环，是 Google AI Studio 最高效的用法。在 Playground 里可以大胆尝试各种想法，不担心消耗 API 或影响线上环境，确认无误后再推到正式环境。

这种协同方式让 Vibe Coding 变得高效。你不用在代码里反复试错，也不用为了微调一句系统提示词就重新部署，因为 Playground 已提供一个沙盒，可以快速验证任何想法。

## 2.2 Google AI Studio Build：打造你的首个应用
在 Playground 熟悉完 Google AI Studio 的基本操作后，就可以进入真正的应用开发了。

### 2.2.1 Build 模式能做什么
Google AI Studio 内置的 Build 模式是一个面向前端应用的前期孵化器，能把创意直接变成可运行的应用。前端应用指的是用户在浏览器或手机上能直接看到、操作的界面和交互部分，包括按钮、图片、表单、动画以及点击后的响应逻辑。用餐厅来比喻，前端像装修、菜单和服务员，是顾客能直接接触的表层体验；后端则像厨房和仓库，支撑运转但不可见。

借助 Build 可以做出天气查询、待办工具、照片画廊、产品介绍页等多类前端应用，都在浏览器中运行，聚焦直观交互。

前端应用还能通过接入各类 API 拓展边界，例如接 Supabase 做数据存储、接入支付接口完成交易、接入地图服务展示位置、接入 AI 接口实现智能对话。复杂业务逻辑由外部服务承载，用户仍能获得流畅体验。

#### 1. Build 模式的限制及对应解法
需要先明确，Build 只支持前端开发，没有后端能力，主要限制有两点。

- 不能在服务器上读写文件。文件可以上传到浏览器内存中处理，但无法持久化保存到服务器。
- 不能使用 Node.js 的后端能力。无法运行持续在服务器上的程序，不能做定时任务，也不能直接操作服务器文件系统或系统资源。

这些限制会约束某些应用，例如需要服务器端处理大视频的转码工具，或需要每天定时发送报表的系统。但并非不可实现，前端可以调用外部 API 来完成复杂逻辑。

让前端负责界面和交互，复杂业务交给第三方专业服务，反而更高效可靠。对新手而言，这也意味着不用学习服务器管理和后端开发，就能搭建出专业级功能的应用。

#### 2. Build 模式的独特优势
相比市面上其他 Vibe Coding 平台，Build 的最大区别是 AI 能力自动接入。大多数平台在实现大模型对话、文生图、语音合成等功能时，需要用户自行申请 API Key、读文档、写调用代码。没有编程经验，光是理解 API、获取 Key、处理请求响应就是一道门槛。

Build 去掉了这道门槛。当你描述“我要一个 AI 对话功能”或“加上图片生成功能”时，Google AI Studio 会自动帮你接入具备各种能力的 AI 模型。你不用关心用哪个模型、怎么配参数、怎么处理返回数据，后台会自动完成适配。你只需聚焦“应用要实现什么功能”，让 Vibe Coding 回归本质：用自然语言描述想法，由 AI 完成落地。

#### 1. AI 建议
图 2-11 左下角的“AI 给的建议”区域包含两类按钮：“AI Features”和后面的一串标签。它们是快速扩展功能的重要入口。

点开“AI Features”会弹出功能面板，展示 Google AI Studio 为开发者预置的 AI 能力，包括图像处理、语音识别、数据检索等，例如用 Nano Banana 做图片编辑、用 Gemini Live API 做语音对话、用 Google Search 数据实现智能搜索。

标签则是基于当前应用情况的优化建议。初步开发完成后，AI 会自动分析功能并提出改进方向。例如你做了一个简单的雅思学习应用，AI 可能会建议“Add True/False/Not Given”或“Improve word selection”。点标签后，建议会直接变成完整需求语句填入输入框，你可以修改完善后再提交迭代。

这里要强调一个原则：你才是项目的主导者。AI 的建议仅供参考，能帮你发现更多可能性，但决策权在你。审视建议是否符合产品构想，避免让产品变得臃肿。记住，是你在控制 AI，而不是反过来。保持独立思考，只选真正有价值的功能。

#### 2. 切换预览和代码
图 2-11 顶部有“Preview”和“Code”两个切换按钮，是理解 Build 的关键。

- Preview 模式是产品经理视角，展示应用的实际运行效果，与用户访问网页时看到的界面一致。可点击按钮、填表单、测试交互，确认用户体验。
- Code 模式是工程师视角。切换后进入完整的代码编辑器。界面左侧显示项目完整文件结构，右侧是代码编辑区。支持直接查看、修改任意文件，也可右键上传文件、创建新文件或新建文件夹。

在实际开发中，文件上传很实用。例如要做博客网站需要大量配图，可在 Code 模式下把图片批量上传到项目的 public 文件夹，再告诉 AI“在文章列表中引用 public 文件夹内的图片”。

选择 public 文件夹的原因是：在前端项目里，public 就像应用的公共展示柜，里面文件可直接访问，无需编译。用户打开网站时，浏览器可通过简单路径如 /image.png 直接获取。若放在其他文件夹，则需要复杂的导入语句调用。

图 2-12 界面中，除了 public 还有 components、pages 等文件夹，以及 index.html 等文件。这些是前端项目的基础，理解它们有助于更好地与 AI 协作。

- index.html：应用入口文件，像一本书的封面，定义页面基本框架与加载规则。用户访问时浏览器会优先读取它。

#### 3. 设备预览
在 Preview 模式下，点击右上角“Device”按钮，可切换查看应用在电脑、平板、手机等不同设备的显示效果，这就是设备预览，用于适配测试。

不同屏幕尺寸下，同样的页面在手机上可能出现布局错乱、按钮过小、文字截断。设备预览能让你在开发阶段实时检查各种设备的表现。例如切到平板模式可模拟横竖屏切换，发现手机端按钮尺寸不合理时可立即让 AI 调整。

两个实用技巧：

- 全屏模式：笔记本屏幕小、预览区域不足时，点击“Fullscreen”可全屏查看完整布局，更便于检查细节。
- 内置刷新按钮：“Device”按钮右侧的刷新按钮使用频率很高。界面显示异常时，不必去浏览器地址栏刷新，直接点 Build 界面内置的刷新按钮即可，该按钮只重载预览区，不影响对话历史和代码编辑器，使用起来更顺手。

#### 4. 打印日志
图 2-11 右下方是打印日志区。日志是程序运行过程中输出的文字，用来记录执行进度和关键信息，可把日志看作程序的“自言自语”。

通常项目异常时，Google AI Studio 会自动检测并在日志区输出提示，日常无需刻意关注。但部分隐性问题无法自动检测，例如功能执行后结果不对，或某段代码根本没被执行。这类问题不会触发明显错误，却会导致行为与预期不符。

针对隐性问题，可以让 AI 在代码关键位置插入打印日志。例如发现点击按钮后页面无响应，可以要求 AI“在按钮点击事件中添加日志打印，输出‘按钮被点击了’，并打印相关变量的值”。AI 会插入 console.log() 语句。再次点击后，若日志区出现“按钮被点击了”，说明事件已触发，问题在后续逻辑；若无输出，则事件未绑定，问题在事件绑定环节。这样能逐步缩小排查范围，精准定位根源。

### 2.2.3 用注释功能指导 AI 修改
有些修改需求很难用文字精确描述。例如想调整按钮位置，或在页面某区域新增功能，用文字说“把左上角按钮右移 50 像素”或“在第二、第三个卡片之间加一个输入框”，表达困难且易被误解。就像让装修师傅调整家具，现场指一下比电话里反复描述更清楚。

Build 的注释模式就是为了解决这个问题。你可以像批改作业一样，直接在界面上标注，用箭头、矩形、文字标出想改的地方，AI 会理解意图并执行修改。这种“指哪改哪”的方式比纯文字更直观准确。
