很多开源模型和市面上的聊天机器人，比如 ChatGLM2、ChatGLM3 还有 ChatGPT，都在用一种基础的对话框架。这个框架默认只有两个身份，用户和模型，交互方式就是用户提问、模型作答。逻辑简单，上手快，理解成本很低。

2. 进阶对话：多角色协作模式

如图8-2所示，多角色对话是一种更进一步的对话范式。默认会同时出现四个角色：用户 User、模型 Model、系统 System、工具 Tool。响应更灵活、拓展空间更大，消息展示也更清晰。相比传统模式，它要求模型以更复杂的运行逻辑来处理对话，对推理能力的要求明显抬高，所以在执行时需要更多的算力和时间，但换来的是更智能、更个性化的交互体验。

[PRE0]

目前，GPT-3.5、GPT-4 API 等领先的自然语言处理模型都已采用多角色对话模式，国产大模型 ChatGLM3 也首次跟进，为用户带来了更全面高效的服务体验。随后开源的 GLM-4-9B-chat 特别强化了函数调用能力，这在构建智能体时是核心要素之一。该能力既体现了模型捕捉用户意图的强度，也直接影响智能体的运行稳定度。因此在评测 GLM-4 系列时，函数调用往往成为关键考察点。表现令人欣慰，GLM-4-9B-chat 在这方面的水平已与 GPT-4-Turbo-2024-04-09 版本相当，换句话说，其函数调用能力极强，完全不输 GPT-4，这个结果非常惊喜。

多角色对话模式带来的实际变化如下。

1. API 调用会稍微复杂一点。开发者需要更细致地打理消息的收发，确保不同角色之间的信息流畅通。
2. 对模型推理的要求更高。模型要能理解不同角色发来的多条信息，并给出对应的回应。
3. 对话实现形态极大丰富。可以灵活搭建模型的短期和长期记忆，模型能更好地把握上下文，并在需要时调取相关信息，从而给出更个性化、更智能的回复。
4. 能实现 Function Calling。借助多角色框架，模型可以像调用函数一样去调用各类工具完成任务，大幅提升服务的便捷与效率，也提升了模型的可用性。比如 ChatGLM3 就能依靠 Function Calling 快速调用外部工具帮助用户办事，实现了质的飞跃。

Function Calling 是衡量大模型推理能力和复杂问题处理能力的核心指标，也是搭建 AI Agent 的关键能力之一。

### 8.3.1 messages 参数结构与用法

### 8.3.2 messages 中的角色分工

- 1. user role 和 assistant role

user role 和 assistant role 主要用于向 AI 助理提交需求。

从之前的简单例子就能看出，Chat 模型里用户和助手是两大核心角色。用户以 user 身份发送消息提问或表达需求，模型则以 assistant 身份作出回应。这两个角色名是固定的，在 messages 参数里不能随意改名。

在实际对话中，user 代表发起方，把问题、建议请求、求助等信息发给模型；模型收到后以 assistant 身份先做语义理解和推理，再生成文本回答。回答可以是问题的解释、需求的满足、建议或其他形式的交流。

为了便于理解和处理，Chat 模型把这两个角色固定下来。最简调用方式就是在 messages 里先放一条 role 为 user 的消息，在 content 里写对话内容，模型就会以 assistant 的身份回复，比如问“请问什么是机器学习？”，就能得到对应解释。

需要注意的是，即便 messages 里包含多条历史消息，模型只会针对最后一条 user 消息作答，如图8-4所示。

[PRE3]

也就是说 assistant 消息和 user 消息基本是一一对应的，一般情况下 assistant 只会围绕 messages 中最后一条 user 消息来回应。

- 2. system role

system role 用来在这个会话里设定 AI 助手的个性和在整段对话中的行为规范。

用户和助手之间的互动虽然清晰，但有时会显得单调。给机器人设定一个身份，能有效引导出更丰富、更有深度的回答。比如把模型设为“一名资深的粤菜大厨”，回答就会更专业、更见解，对话也更有趣。可以如图8-5的方式提问。

不难看出，模型的回复立刻变得更详尽、更严谨，语气也更像一位粤菜大厨，说明身份设定是起效的。

最后要提醒的是，目前大模型在多轮对话中容易逐渐淡忘系统设定的身份，长期保持关注仍是限制。

除了 user、assistant、system，messages 参数还可选 observation 等角色，它们主要服务于 Function Calling 功能。

## 8.4 Function Calling 功能全解析

大模型知识储备庞大、生成能力惊人，但在实际使用中局限也很明显，比如无法获取实时信息，也无法直接完成自动回邮件、查航班这类特定任务。这些限制制约了它们的落地价值。2023 年 4 月推出的 AutoGPT 提出了一个很有潜力的思路：让大模型调用外部工具 API，从而大幅拓宽应用边界。让 GPT 调用 Bing 搜索 API，就能实时拿到搜索结果结合知识库作答；调用谷歌邮箱 API，就能自动阅读邮件并回复。虽然看起来复杂，但在 AutoGPT 的思路下并非难事。

### 8.4.1 Function Calling 演进史

2023 年 6 月 13 日，OpenAI 宣布重大更新，把 Function Calling 功能整合进 Chat 模型。这意味着不再依赖 LangChain 等外部框架，模型内部就能直接调用外部工具 API，构建以 LLM 为核心的 AI 应用变得更便捷。此次更新还伴随 16k 对话长度模型的全面开放以及调用资费下调。

Function Calling 的引入标志着更灵活的 AI 应用开发时代到来，也直接推动了 AI Agent 的发展。如今它已成为 Agent 开发的标配工具，开发者可以借助它接入各类外部工具实现复杂操作。

ChatGLM3-6B 是首个集成 Function Calling 的国产开源模型，遵循了 GPT 系列的工具调用流程和 function 参数语法，让基于 Function Calling 的 Agent 生态能够无缝接入，为后续发展铺路。

Function Calling 的核心在于让 Chat 模型调用外部函数，不再仅依赖内置知识，而是可以挂载一个函数库。用户提问时，模型在函数库中检索并调用合适的外部函数，再基于结果作答，从而提供更丰富多样的服务。基本流程如图8-6所示。

Function Calling 允许挂载外部函数库，库里可以是简单的自定义函数，也可以是封装了外部工具 API 的函数，比如调用 Bing 搜索或查询天气。大模型内置了一套精巧的机制来实现这一过程，操作并不复杂。只需要在调用 completions.create 时设置相关参数并提前定义好函数库，模型就能根据用户问题的语义自动搜索并选择合适的函数执行，全程无需人工指定。

借助外部函数库，Chat 模型的问题解决能力得到明显提升。相比过去用 LangChain 的 Agent 模块来做 LLM 与外部工具的协同，内置的 Function Calling 让实现更简单、门槛更低，必将推动新一轮以大模型为核心的 AI 应用爆发。

Function Calling 实现的基本步骤如下。

- 1. 构建一个字典对象存储：{"方法1": 方法1,...}。
- 2. 在 Prompt 中加入方法定义。
- 3. 根据 LLM 的返回，判断是否包含“function_call”，决定是调用函数还是直接把信息返回给用户。
- 4. 如需调用函数，则执行 LLM 指定的函数，并把结果连同调用信息一起放回 Prompt 再次请求 LLM。
