想要把 OpenClaw 接进自有前端或自动化流程，开发者首先要弄清楚 Agent Loop 是怎么被触发的。Loop 只有两种点火方式，对应两条 Gateway RPC。

agent 命令是典型的“发了就不管”异步模式。请求发出后 Gateway 马上回 { runId, acceptedAt }，Agent 在后台自己跑，调用方无需等待也不用保持连接，适合消息渠道的日常使用。

agent.wait 命令是同步等待模式。请求会阻塞到指定 runId 的 Agent 运行结束或报错才返回，返回结构为 { status: ok|error|timeout, startedAt, endedAt, error? }。默认等待上限 30 秒，注意这只是调用方的等待上限，不会把 Agent 本身停掉，Agent 会继续跑，只是调用方先拿到超时信号。

### 一次 Loop 的内部拆解
官方把一次 Agent Loop 拆成四步。

第一步 agent RPC 校验。Gateway 收到 agent 命令后先做参数合法性检查，解析 sessionKey 或 sessionId，持久化会话元数据，随后立刻返回 { runId, acceptedAt }，不等待 Agent 真正开始。这一步保证运行前所有必要信息都已就位。

第二步 agentCommand 运行。解析模型配置以及 thinking/verbose 的默认值，加载当期的 Skills 快照，调用 runEmbeddedPiAgent，即 pi-agent-core 运行时，并在运行结束后补发可能缺失的生命周期结束或错误事件，维护事件序列的完整性。

第三步 runEmbeddedPiAgent 执行。这是推理核心。调度遵循“会话 lane 串行 + 全局 lane 串行”，防止同一会话并发工具调用破坏状态一致性；解析最终生效的模型配置和认证 profile；构建底层 pi session，订阅 pi 事件并流式推送增量内容；超时时强制中止并返回完整 payload 与用量元数据。

第四步 事件桥接。subscribeEmbeddedPiSession 把 pi-agent-core 的内部事件映射为 OpenClaw 的流式事件：工具相关映射为 stream: "tool"，助手输出增量映射为 stream: "assistant"，运行阶段事件映射为 stream: "lifecycle"，phase 为 start | end | error。事件经 Gateway 转发到对应消息渠道，用户就能看到实时回复。

### 并发与队列控制
同一会话的多次运行会按 session lane 严格串行，第一条消息处理时第二条会被排队等待，保证历史强一致。

消息渠道用 queueMode 决定新消息的处置方式，有三种：

collect 当前轮次收集新消息，轮次结束后把收集到的消息合并成下一轮的入口，适合批量处理。

steer 把新消息作为引导注入正在运行的对话，在下一次 LLM 调用前送达，但不跳过剩余工具调用，适合实时修正行为。

followup 与 collect 类似，等当前轮次完全结束后再以新轮次启动，适合大多数对话场景。

### 超时与提前终止
运行超时有两个独立旋钮：agent.wait 的等待超时，默认 30 秒，控制调用方等多久；Agent 运行超时由 agents.defaults.timeoutSeconds 控制，默认 600 秒，在 runEmbeddedPiAgent 内部强制执行。前者是等待时长，后者是运行时长，各自配置。

提前终止会有三种触发：Agent 运行超时中止、AbortSignal 取消信号、Gateway 断连或 RPC 超时。每种情况都会发出对应的生命周期事件，让调用方感知状态。

### 回复塑形与 NO_REPLY
最终发出的 payload 由三部分拼装：助手文本含推理内容、verbose 模式且策略允许时的内联工具摘要、模型错误文本。

NO_REPLY 是一个静默 Token，若 Agent 回复中包含它，该内容在发出前会被过滤，不会传给用户，用于心跳确认或无需回复的内部操作。若 message 工具已发送可见回复，重复文本会被自动剔除。若 Agent 没有有效输出且工具也报错，OpenClaw 会发出兜底错误回复，避免用户收不到任何反馈。

### 15.3 多 Agent、记忆与系统提示词

#### Multi-Agent 路由：让每个 Agent 各守其职
场景复杂时单 Agent 会捉襟见肘。OpenClaw 的多 Agent 系统通过三重隔离划定边界：

[PRE0]
Workspace 工作空间：独立的文件系统根目录，包含 AGENTS.md/OUL.md/USER.md 等引导文件和本地笔记，每个 Agent 有自己的家。
State directory 状态目录 agentDir：独立状态存储，路径 ~/.openclaw/agents/<agentId>/agent，存放认证 profile、模型注册表与单 Agent 专属配置，认证 profile 严格单 Agent 隔离。
Session store 会话存储：独立的聊天历史与路由状态，路径 ~/.openclaw/agents/<agentId>/sessions，每个 Agent 的对话记录互不污染。

Skills 隔离是另一维度：工作空间 skills/ 目录的 Skills 仅本 Agent 可见，~/.openclaw/skills/ 下的 Skills 对本机所有 Agent 共享，既能定制专属能力，也能复用通用能力。

#### 路由规则：最具体优先
消息路由由 Bindings 决定，优先级从高到低：peer 匹配精确 DM/group/channel id；parentPeer 匹配线程继承；guildId + roles；guildId；teamId；渠道 accountId 匹配；渠道级匹配 accountId: "*"；回退默认 Agent，即 agents.list[].default 标记或首个条目。

同优先级多个 binding 时取配置文件中出现的第一个。单个 binding 包含多个字段时所有字段必须同时满足，AND 语义。

#### 账户与 Agent 解耦
accountId 代表渠道的账户实例，如两个 WhatsApp 号码对应两个 accountId。一个 agentId 可服务多个 accountId，也可一对一绑定。省略 accountId 的 binding 仅匹配默认账户，accountId: "*" 为该渠道所有账户的兜底通配。

#### 典型多 Agent 配置场景
按发件人分流：同一 WhatsApp 号收到的不同联系人私信，通过 bindings.match.peer 匹配 E.164 号码路由到不同 Agent，实现真正隔离的家庭服务。
按渠道分流：WhatsApp 用日常生活 Agent，Telegram 用深度工作 Agent，各自独立人格与工具权限。
家庭群组专属 Agent：绑定到家庭 WhatsApp 群组，配置 @提及触发、沙盒与工具白名单，遵循最小权限。

创建新 Agent 用 openclaw agents add <agentName>，会自动创建工作空间和 agentDir 并引导配置 bindings。上线前用 openclaw agents list --bindings 验证路由。

#### Memory：文件是 Agent 唯一真实的记忆
OpenClaw 对记忆的表述很直接：模型本身没有跨会话记忆，有记忆的是工作空间文件。官方说明 “The files are the source of truth; the model only remembers what gets written to disk”。

基于文件的记忆可透明查看、可 Git 版本控制、可直接编辑，比向量数据库记忆更可控。

[PRE1]
#### 两层记忆架构
第一层是每日日志 memory/YYYY-MM-DD.md，按追加方式记录当日事件、对话摘要和临时笔记，不会自动注入上下文，需通过 memory_search 或 memory_get 主动检索。

第二层是长期记忆 MEMORY.md，存放重要决策、用户偏好和长期事实，作为引导文件只在主私人会话启动时自动注入，群组等共享上下文不加载，防止私密信息泄露。

若根目录同时存在 MEMORY.md 和 memory.md，OpenClaw 会自动去重，避免重复注入浪费 Token。

#### 记忆操作的两个核心工具
memory_search 对 MEMORY.md 和 memory/*.md 做语义搜索，返回相关片段，底层向量索引支持措辞变化。

memory_get 精准读取指定 Markdown 文件的行范围，通常配合搜索结果使用。文件不存在时优雅降级返回 { text: "", path }，无需 try/catch。

#### 记忆写入的时机与原则
重要决策、用户偏好、需长期保留的事实写入 MEMORY.md；日常笔记和运行上下文写入 memory/YYYY-MM-DD.md；用户明确说“记住这件事”时立即落盘，不能仅依赖模型的短时记忆，会话结束即消失。

#### 自动记忆刷新：Pre-Compaction Ping
LLM 上下文窗口有限，积累到阈值会触发自动压缩。压缩前 OpenClaw 会发起一次静默 Agent 轮次，提醒模型把关键信息写入持久文件，即预压缩记忆刷新。

由 agents.defaults.compaction.memoryFlush 控制：enabled 默认 true、softThresholdTokens、systemPrompt 与 prompt，默认提示含 NO_REPLY 对用户不可见。每个压缩周期只触发一次，workspaceAccess 为 ro 或 none 时自动跳过。

#### 向量记忆搜索与高级配置
MEMORY.md 与 memory/*.md 可构建小型向量索引，支持 BM25 关键词与向量语义混合搜索。嵌入提供商支持 OpenAI、Gemini、Voyage、本地 Ollama，并支持 MMR 多样性重排序和时间衰减后处理，使结果既相关又多样。

#### 系统提示词：Agent 行为的权威控制入口
系统提示词在用户消息前设定上下文，OpenClaw 为每次运行构建完全自定义的系统提示，不使用任何 LLM 提供商默认提示，完全掌控行为定义。

#### 系统提示词的固定章节结构
OpenClaw 的系统提示由固定章节构成：

- Tooling 列出当前可用工具及简要描述。

## OpenClaw 开源实战

- Safety 安全护栏指引，引导模型规避权力寻求、监管绕过、自我复制等不安全行为。
- Skills 若有可用 Skill，则以紧凑 XML 格式注入精简列表指导按需加载 SKILL.md，无 Skill 时整章省略。
- OpenClaw Self-Update 说明 config.apply 与 update.run 的执行要求，防止误用更新功能。
- Workspace 当前工作目录路径。
- Documentation 本地文档位置、镜像地址、源码仓库和社区链接。
- Workspace Files 已注入上下文的引导文件清单。
- Sandbox 启用沙盒时包含沙盒路径、权限说明与高权限 exec 可用性。
- Current Date & Time 用户时区信息，不含动态时钟以保证提示词缓存稳定。
- Reply Tags 当前渠道支持的回复标签语法。
- Heartbeats 心跳提示词与 ACK 行为说明。
- Runtime 主机信息、操作系统、Node 版本、当前模型、代码仓库路径等运行时元数据。
- Reasoning 推理可见级别说明与 /reasoning 切换命令。

提示词模式：full 默认完整提示，适用于主会话；minimal 子 Agent 专用，省略 Skills 列表、记忆召回指引、自更新说明和用户身份等，只保留核心模块，注入内容标记为 Subagent Context；none 仅保留最基本身份标识，适用于极简集成。

安全护栏的本质是建议，不是约束。系统提示中的护栏可被提示词攻击绕过。真正的安全来自下层机制：工具策略 allow/deny 白名单、exec 审批强制人工确认、沙盒隔离、渠道白名单。对公众部署不建议仅依赖提示词护栏，硬性机制才是防线。

### 15.4 Skills 体系、沙盒安全与最佳实践
Skills 通过文件化工具教学定义 Agent 能力边界，完全开放，任何文件夹都能为 Agent 新增能力。若说工作空间定义记忆，系统提示定义行为规范，Skills 就定义能力本身。
