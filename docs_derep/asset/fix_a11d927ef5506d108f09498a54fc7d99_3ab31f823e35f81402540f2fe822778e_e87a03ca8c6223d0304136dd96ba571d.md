# CentOS 环境下部署 gh 并联动三 Agent 自动化开发

本次实践以 CentOS 为演示机，其他 Linux 发行版原理相近。本文采用 GitHub 官方 RPM 源完成安装，该方案规范统一，适用于 CentOS 7、CentOS 8 以及 CentOS Stream 等分支。

在终端中粘贴并运行以下命令添加官方源：

sudo dnf config-manager --add-repo https://cli.github.com/packages/rpm/gh-cli.repo

执行后系统会把 GitHub 官方仓库登记进软件源清单，包管理器就能准确定位并获取 gh 安装包。

**注意：** 若提示 `dnf: command not found`，说明当前环境未自带 dnf，可先执行 `sudo yum install dnf -y` 完成安装，再重复上述添加源操作。

源配置完毕后正式安装客户端：

sudo dnf install gh -y

末尾的 `-y` 用于自动确认，无需手动交互。安装完成后用版本命令检查结果：

gh --version

若输出形如 `gh version 2.88.1 (2026-03-12)` 的信息，即表示部署成功，如图 13-1 所示。

2**．授权登录**GitHub**账号**

完成安装后仍需对 GitHub 账号进行授权，才能让 gh 具备仓库操作权限。在终端执行：

gh auth login

随后会进入交互式向导，按提示逐步确认即可，整体流程如图 13-2 所示。

[PRE1]
图 13-2 gh 账号授权登录流程

向导要点如下。

1．选择要登录的 GitHub 服务。
默认是 GitHub.com，即全球公开站点，个人开发者通常直接回车即可。

2．选择 Git 通信协议。
推荐使用 SSH，安全性更高，后续推送代码无需反复输入凭证。gh 会自动检测本地 SSH 密钥，缺失时会引导生成并自动上传至 GitHub。
HTTPS 方式依赖用户名加个人访问令牌，配置更轻量，但在部分场景下会频繁要求二次验证。
追求规范选 SSH，追求上手速度可选 HTTPS。

3．选择 GitHub CLI 的验证方式。
推荐 Login with a web browser，通过浏览器完成授权：gh 会生成一次性验证码并自动打开浏览器，用户在网页中确认授权即可，操作简便。
Paste an authentication token 属于令牌登录，需要手动填入事先在 GitHub 创建的访问令牌，适用于无图形界面的服务器。日常使用建议优先浏览器授权。

4．完成网页授权。
终端会输出一次性验证码，复制后回车，浏览器自动跳转到 GitHub 授权页，粘贴验证码并确认，随后关闭页面返回终端即可。

5．登录成功校验。
终端出现以下提示即表示授权完成。

✓ Authentication complete.
- gh config set -h github.com git_protocol https
✓ Configured git protocol
! Authentication credentials saved in plain text
✓ Logged in as aacedar

## **13.3**** 详细操作步骤与配置指南**

下面演示如何搭建由 3 个 Agent 组成的自动化开发链路。

### **13.3.2 创建多智能体工作空间与 SOUL.md**

使用 openclaw agents add 为三个 Agent 分别建立独立工作空间：

openclaw agents add coder --workspace "~/.openclaw/workspace-coder"

openclaw agents add reviewer --workspace "~/.openclaw/workspace-reviewer"

openclaw agents add tester --workspace "~/.openclaw/workspace-tester"

1**．**Coder Agent**的**SOUL.md

Coder 是开发流程的核心执行者，需要明确其编码规范和协作流程，对应的 SOUL.md（路径为~/.openclaw/workspace-coder/SOUL.md）内容如下：

# 角色定义

你是一位经验丰富的全栈工程师，精通 HTML5、JavaScript 和前端游戏开发。你负责根据用户需求编写高质量、可维护的代码。

## 核心职责

- 接收用户的开发需求，使用 github 技能拉取最新代码并创建新分支（分支名需具有描述性，如 feature/snake-game）,必要时创建一个项目。

- 编写核心业务逻辑代码。在编写代码时，需要考虑系统的完整性和用户体验。

- 代码编写完成后，必须使用 agent_send 工具将代码文件路径和修改说明发送给 reviewer 进行代码审查。

## 协作与修复准则

- 当收到 Reviewer 的修改建议时，必须虚心接受，仔细分析并修改代码，然后再次提交审查，直到 reviewer 批准。

- 当收到 Tester 反馈的测试失败日志时，必须优先处理。分析错误堆栈，定位 Bug，修复代码后通知 Tester 重新运行测试。

- 严禁在未经过 Reviewer 批准和 Tester 测试通过的情况下，私自提交代码或创建 PR。

2**．**Reviewer Agent**的**SOUL.md

Reviewer 负责把控代码质量，充当“守门员”的角色，对应的 SOUL.md（路径为~/.openclaw/workspace-reviewer/SOUL.md）的内容如下：

# 角色定义

你是一位极其严苛的资深架构师，负责对团队提交的代码进行静态审查（Code Review）。你对代码的整洁度、性能和安全性有着极高的要求。

## 审查准则

- 收到 Coder 发来的代码审查请求后，仔细阅读其修改的代码。

- 重点检查以下几个方面：

  1. 变量命名是否语义化，是否滥用全局变量。

  2. 核心逻辑（如贪吃蛇的碰撞检测）是否存在边界条件漏洞。

  3. 是否存在内存泄漏风险。

  4. 代码是否包含必要的注释。

- 如果发现问题，使用 agent_send 工具将具体的修改建议（需包含指出错误的代码行和改进方案）发送回 Coder，要求其修改完善。

- 如果代码完全符合规范，回复 Coder 审查通过，并使用 agent_send 通知 Tester 开始编写测试用例并运行测‍试。

3**．**Tester Agent**的**SOUL.md

Tester 负责编写测试用例并触发 Lobster 管道，对应的 SOUL.md（路径为~/.openclaw/ workspace-tester/SOUL.md）内容如下：

# 角色定义

你是一位专业的自动化测试工程师，负责为业务代码编写单元测试，并管理持续集成（CI）管道。

## 工作流准则

- 收到 Reviewer 的审查通过通知后，仔细阅读 Coder 编写的业务代码。

- 使用 Jest 或 Mocha 等测试框架，为核心逻辑（如贪吃蛇的初始状态、移动逻辑、碰撞判定）编写覆盖率至少达到 80%的单元测试用例。

- 测试用例编写完成后，必须调用 Lobster 工具运行项目根目录下的 dev-pipeline.lobster 文件。

- 如果 Lobster 返回了测试失败的错误日志，使用 agent_send 将详细的错误信息发送给 Coder，要求其修复。

- 如果 Lobster 返回 needs_approval 状态，说明所有测试已通过，管道正在等待人类审批。此时，你必须向飞书用户发送一条消息，汇报测试已全部通过，并提醒用户在飞书中点击批准以创建 PR。

### **13.3.3 编写 Lobster 工作流文件**

在项目根目录创建一个名为 dev-pipeline.lobster 的文件，用于定义确定性的代码审查和测试流程。

YAML

# dev-pipeline.lobster

name: code-review-and-test

steps:

  - id: lint

    command: npm run lint --silent

  - id: test

    command: npm run test --silent

    stdin: $lint.stdout # 仅当 lint 通过时执行

  - id: approve_pr

    command: echo "All tests passed. Ready to create PR."

    approval: required # 在这里暂停，等待人类在飞书中点击批准

  - id: create_pr

    command: gh pr create --title "Feature: Snake Game" --body "Automated PR created by OpenClaw Pipeline"

    condition: $approve_pr.approved # 只有人类批准后才执行

该文件逻辑清晰：先执行代码检查，再运行单元测试。若均通过则暂停请求人工审批，批准后自动调用 GitHub CLI 创建 PR。

## **13.4**** 飞书交互与效果验证**

重启 Gateway 服务后，在飞书中输入“你好”，OpenClaw 会返回一段一次性配对码，例如 BUFLH4AH：

在 OpenClaw 服务器的终端中，执行以下完整的配对命令（将末尾替换为实际收到的配对码）：

执行成功后，飞书机器人与 OpenClaw 完成绑定。

随后向飞书中的 coder 机器人发送开发指令“@coder 请在当前项目中开发一个基于 HTML5 Canvas 的贪吃蛇游戏。要求包含计分系统、食物随机生成逻辑以及碰撞检测（撞墙或撞自己即游戏结束）”。发送界面如图 13-5 所示。

从代码编写、审查、测试到最终合并，所有环节由多智能体自主协作完成，具体执行过程如下。

1．编码阶段：Coder Agent 收到指令后，自动创建 feature/snake-game 分支，编写 index.html 和 snake.js，实现 Canvas 渲染和游戏循环逻辑。代码编写完成后，调用 agent_send 将文件发给 Reviewer 进行审查。

2．审查阶段：Reviewer Agent 检查发现 Coder 在生成食物时没有检查食物是否与蛇身重叠，存在运行缺陷，随即打回代码并给出修改建议。Coder 完成修复后再次提交，Reviewer 确认通过，并通知 Tester 进入测试环节。

3．测试阶段：Tester 基于碰撞检测、计分逻辑编写 Jest 测试用例，然后调用 Lobster 运行 dev-pipeline.lobster 管道。如果测试失败，错误日志会自动发给 Coder 进行修复；如果测试通过，管道进入等待审批状态。

4．审批与合并：当测试通过后，Lobster 管道在 approve_pr 步骤暂停，并向飞书发送交互式审批卡片，提示“贪吃蛇游戏的所有测试已通过，是否批准创建 PR”。当在飞书中点击“批准”后，OpenClaw 使用 resumeToken 恢复 Lobster 管道，执行 gh pr create 命令，自动在 GitHub 上创建 PR，并在群内同步结果。

如果需要查看各 Agent 之间的完整交互日志，可执行 openclaw logs --follow 命令实时监听。
