多代理协同：匹配、权限制与模型选择

让多名专长不同的小助手一起工作，核心在于自动判定谁合适、允许做什么、用什么模型来跑。

匹配与自动分派的逻辑
用户发出任务请求后，主控会先把所有已注册小助手的 description 取出来，与用户表述做语义相似度计算，来判断这项工作是否落在某助手的职责范围。相似度达标时，例如 code-reviewer 的描述覆盖代码评审和风险核查，主控会把完整上下文打包直接移交，全程不需要用户点名指定具体助手。

工具白名单作为安全底线
tools 实质上是工具白名单，从底层贯彻最小权限。以 code-reviewer 为例，名单只放三项只读能力：Read 读取文件内容、Grep 在文件中检索模式、Glob 匹配文件路径。诸如 Edit、Write、Bash 这类写入或执行类工具，对该助手而言完全不可见、无法调用。

模型是隐形的成本杠杆
model 字段常被忽略，却直接影响费用与质量。格式检查、日志过滤这类规律性强的轻任务，选用 Haiku 这类响应快的小模型即可；架构设计、风险核查这类需要深度理解与复杂推理的场景，则更适合 Sonnet、Opus 等高性能模型。合理配对能在控制开销的同时保证交付水准。

权限模式提供第二层兜底
permissionMode 用来调节授权边界。设为 plan 时，助手进入系统级的只读保护，比单纯的工具白名单更严格的全局约束；保持默认值 default，则沿用常规权限流程。

执行型助手的权衡
测试运行器就是偏执行的代表。它必须通过 Bash 跑命令，所以可调用的工具集合比评审类更宽，但对返回结果的格式规范要求更高。

你是一名测试执行专家。你的核心价值是从海量测试输出中提炼关键信息，为主对话提供精准的测试摘要

## 执行流程

1. 确认项目的测试命令（查阅 package.json 或 CLAUDE.md）

2. 运行测试套件

3. 分析输出结果，区分通过和失败的测试用例

4. 针对失败的测试，定位具体失败原因

## 输出格式（严格遵守）

### 测试摘要

- 总计：x个测试

- 通过：x个

- 失败：x 个

- 跳过：x 个
