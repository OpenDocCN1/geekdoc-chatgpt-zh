在个人常用的轻量场景里，单靠一个 Agent 就能跑通。但当使用越来越深入，就会明显感受到不同工作需要不同的人设和权限边界：处理工作的助手不该能打开私人日记，写代码的助手不需要触碰财务数据，而面向社群的机器人要对所有人可见，却必须把操作权限拧得很紧。

OpenClaw 的多智能体路由就是为这种分工而设计的。它允许在同一个 Gateway 下并行运行多个相互隔离的 Agent，每个实例拥有独立的工作空间、工具集合和会话历史，再通过灵活的绑定规则把来自不同渠道的消息精准投递到对应的智能体。

**3.4.1** **多智能体的配置与隔离**

在 openclaw.json 中，全部 Agent 均通过 agents.list 数组进行声明。每个对象至少需要一个唯一的 id，其余字段都可以回退到 agents.defaults 里的全局默认值：

{

"agents": {

"defaults": {

"model": "claude-sonnet-4-20250514",

"tools": {

"profile": "coding"

}

},

"list": [

{

"id": "main",

"agentDir": "~/.openclaw/agents/main",

"workspace": "~/projects/main-workspace",

"bindings": [

{ "channel": "whatsapp" },

{ "channel": "telegram" }

]

},

{

"id": "work",

"agentDir": "~/.openclaw/agents/work",

"workspace": "~/projects/work-workspace",

"model": "gpt-4.1",

"tools": {

"profile": "full",

"allow": ["group:nodes", "group:automation"]

},

"bindings": [

{ "channel": "slack" },

{ "channel": "discord", "guildId": "my-work-server-id" }

]

},

{

"id": "community-bot",

"agentDir": "~/.openclaw/agents/community",

"workspace": "~/projects/community-workspace",

"model": "gpt-4.1-mini",

"tools": {

"profile": "messaging",

"deny": ["group:fs", "group:runtime", "group:automation"]

},

"sandbox": {

"mode": "all",

"scope": "session"

},

"bindings": [

{ "channel": "discord", "guildId": "my-community-server-id" }

]

}

]

}

}

以上配置落地了三组完全独立的 Agent。

• main 负责个人助理职能，接收 WhatsApp 和 Telegram 的私信，并借助内置的文件读写等工具处理日常事务。
• work 面向职业场景，收敛 Slack 以及指定 Discord 服务器的工作消息，采用更强的 GPT-4.1 模型，并开放更完整的工具使用权限。
• community-bot 是社区专用机器人，只处理来自社区 Discord 服务器的消息。为了控制成本使用更经济的 GPT-4.1 Mini，工具权限被严格收紧，并在隔离的沙箱中运行，以杜绝潜在安全风险。

每一个 Agent 都拥有专属的 workspace，由此实现物理隔离。比如 main 的核心记忆文件 MEMORY.md 与协作文件 AGENTS.md 对 work 完全不可见，个人信息与工作信息被清晰分隔。work 的全部对话历史以 .jsonl 形式保存在 ~/.openclaw/agents/work/sessions/ 下，与 main 的历史记录互不干扰。

同时，每个 Agent 都可以配置专属的 SOUL.md，让同一套系统在不同场景下呈现截然不同的交互风格，使用体验更自然、更专业。

模型也可以按 Agent 区分，这带来了很高的灵活性。需要强推理的任务如代码评审、复杂分析，优先选用 Claude Sonnet 或 GPT-4.1 等旗舰模型；高频低复杂度的任务如社区问答、简单查询，则可切换到 GPT-4.1 Mini 或 Gemini 2.5 Flash，在保证可用性的前提下显著降低成本。对于涉及隐私或商业机密的场景，还可以配置通过 Ollama 本地运行的开源模型如 Llama 3 或 Qwen，从源头消除数据外泄风险。

**3.4.2** **子 Agent 与任务委派**

OpenClaw 还支持更进阶的协作形态：子 Agent。主 Agent 在处理复杂任务时，能把特定子任务拆分给更专业的 Agent 执行，等待结果返回后再继续推理。

子 Agent 的创建依赖 sessions_spawn 工具，整体流程如下。

1．系统为子任务新建一个独立会话，sessionKey 采用 agent:<childAgentId>:sub:<parentRunId> 的格式，保证上下文完全隔离。
2．主 Agent 把任务描述推送给子 Agent，触发其独立的 Agent Loop。
3．子 Agent 在自己的上下文中完成执行，完成后通过 sessions_send 安全回传结果。
4．主 Agent 接收结果并将其融合进自身推理上下文，续推后续逻辑。

以个人助理 main 和专业编码 Agent coder 为例，用户在 WhatsApp 说“帮我写一个爬取 Hacker News 首页的 Python 爬虫”时：

用户（WhatsApp）: 帮我写一个爬取 Hacker News 首页的 Python 爬虫

main Agent 思考：
这属于代码类任务，应该交给 coder Agent。

main Agent 调用工具：
sessions_spawn({
agentId: "coder",
message: "请编写一个 Python 爬虫，爬取 Hacker News 首页（https://news.ycombinator.com）的所有文章标题、链接和评论数，并将结果保存为 CSV 文件。要求：使用 requests+BeautifulSoup，代码需要有完整的错误处理，并在沙箱中测试通过。",
waitForCompletion: true,
timeoutMs: 300000
})

coder Agent 运行：
1. 读取 Hacker News 首页 HTML
2. 编写解析代码
3. 沙箱内执行测试
4. 修复 Bug
5. 返回完成的<|message|> 代码与测试结果

main Agent 接收结果后整理格式回复用户。

这种分层协作带来多重收益。

• 专业化：每个 Agent 可针对特定领域优化 System Prompt 与工具集，在职责范围内发挥最大效能。
• 安全隔离：高风险操作如代码执行被关进专属 coder Agent 的独立沙箱，避免污染主 Agent 工作空间。
• 并行潜力：理论上主 Agent 可同时向多个子 Agent 派发相互独立的子任务，当前以串行为主，但已为未来并行化打好架构基础。

实际调用时可参考以下参数示例：

{
"tool": "sessions_spawn",
"params": {
"agentId": "coder",
"sessionKey": "optional-custom-session-key",
"message": "任务描述",
"waitForCompletion": true,
"timeoutMs": 300000,
"context": {
"parentRunId": "run-abc123",
"sharedFiles": ["/path/to/shared/file.txt"]
}
}
}

子智能体的工具权限由自身配置决定，不会继承自父级。这是重要的安全设计：即便主 Agent 拥有完整权限，也无法通过子 Agent 绕过限制。若希望子 Agent 权限高于主 Agent，必须在子 Agent 配置中显式授权。

**3.4.3** **群组与渠道的精细化路由**

除了私聊 DM，OpenClaw 还能对群组消息做精细化路由，这对管理 Discord 或 Telegram 群组尤为实用。群组路由配置示例：

{
"channels": {
"discord": {
"accounts": [
{
"id": "my-bot",
"token": "${DISCORD_BOT_TOKEN}",
"dmPolicy": "pairing",
"groups": {
"*": {
"requireMention": true,
"agentId": "community-bot"
},
"admin-channel-id": {
"requireMention": false,
"agentId": "work",
"allowFrom": ["admin-role-id", "moderator-role-id"]
}
}
}
]
}
}
}

在此策略下，所有 Discord 群组消息默认交给 community-bot，且必须以 @ 明确提及机器人才会触发响应，避免机器人过度发言浪费 Token。

对于特定的管理员频道 admin-channel-id，消息直接路由给权限更高的 work Agent，无需 @ 即可触发，但系统会通过角色过滤仅允许拥有 admin-role-id 或 moderator-role-id 的用户交互。

群组场景中 requireMention: true 是关键安全开关。它确保 Agent 只响应被明确 @ 的消息，不会处理群组里每一条流言，既省 Token，也能有效防御间接提示词注入攻击。

OpenClaw 还支持基于内容过滤消息，例如：

{
"channels": {
"telegram": {
"groups": {
"*": {
"requireMention": true,
"filter": {
"minLength": 10,
"maxLength": 2000,
"allowMedia": false
}
}
}
}
}
}

该规则只处理长度在 10~2000 字符之间的纯文本消息，忽略图片、视频、语音等媒体，可有效防止通过大量媒体消耗 Token 的攻击行为。

**3.5** **工具系统深度解析**

工具是 Agent 与外部世界交互的唯一通道。理解工具体系，有助于更合理地分配权限，也为后续开发自定义工具提供清晰思路。

1．文件系统工具
提供文件的全生命周期操作，支持读取、覆盖写入、精准编辑、补丁应用、路径匹配与内容检索，满足代码修改、配置更新、日志查询等需求。该组受 tools.fs.workspaceOnly 约束，开启后仅能访问工作空间目录，形成严格路径隔离。文件系统工具详情如表 3-3 所示。
