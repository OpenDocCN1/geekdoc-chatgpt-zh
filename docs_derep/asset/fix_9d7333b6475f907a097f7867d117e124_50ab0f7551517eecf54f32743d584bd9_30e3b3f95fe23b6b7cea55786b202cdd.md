### 2.1 意图识别：让模型先读懂真实需求

第1章从多个角度讨论了 Agent 的构建思路，核心可以归纳为：能够自然对话、完成具体任务、调用外部能力，并在多轮交互中保持上下文连贯。

其中自然对话看似基础，实则关键。前提是安全与边界意识——并非所有提问都应被回应，必须在合规、伦理和业务规则范围内处理。在此基础上，模型还要穿透表层表述，捕捉用户真正想解决的问题。这种对输入进行深层语义理解并判定意图的能力，就是本节要展开的核心技术。

#### 2.1.1 意图识别的价值

在产品化过程中，企业常被一个痛点卡住：用户提问自由度极高。比如一个聚焦白酒品鉴知识的智能体，仍可能收到“如何利用系统后台漏洞提高茅台打新中签概率”之类的请求。这类问题严重偏离业务范畴，且涉及安全与合规风险，必须在入口处通过意图判定及时拦截，避免被滥用或引发法律风险。

另一类常见情况是语义模糊。以“贵州茅台怎么样”为例，潜在指向差异很大：可能是礼品体面度、口感醇厚感、工艺独特性或收藏价值，也可能是想了解股价走势和投资前景。歧义正是意图识别需要在上下文工程中解决的核心课题。

成熟的系统需要融合当前对话、用户画像、历史交互等多维线索，对表面问句做深层推断，才能给出相关、准确且安全的回复。

此外，LLM 的选型本身也属于意图范畴。不同模型各有侧重，例如豆包在多模态任务上表现突出，智谱的 GLM-5 在代码生成上更强，为同一提问匹配合适的模型，本质上也是意图识别的延伸。

总体看，意图识别既是保障智能体在生产环境中可控运行的第一道防线，也是提升交互智能和整体效率的关键。

目前意图识别已成为企业级智能体的标配。以纳米 AI 搜索为例，用户输入“潮汕适合几月份去旅游？”时，系统先执行“分析问题分类”流程，随后把问题归入“旅游交通”类，再触发相应的知识检索与生成。

#### 2.1.2 基于 Arch-Router 实现意图识别

技术上讲，意图识别就是让模型判断用户问题属于预设的哪一类并输出标签。比如系统预设了“编程”“旅游”“财经”等标签，面对“如何用Go语言写一个 Kubernetes Pod 查询功能”时，就应返回“编程”。

业界主要有几条路径：
- 用精心设计的提示词引导大模型做分类；
- 训练独立的轻量级路由模型做判断；
- 对1.5B、3B、6B等小模型进行领域微调，让其在特定业务里达到高精度。

本节先介绍应用较广的开源轻量级路由模型 Arch-Router。

##### 1. Arch-Router 是什么
Arch-Router 是一个开源轻量级路由框架，可在魔搭社区搜索“Arch-Router-1.5B”获取。其思路是把用户查询与预定义的领域或操作类型匹配，动态把请求路由到最合适的下游模型或工具，实现可配置的调度与偏好编码。

它引入了两个关键抽象：
- 领域 Domain：请求的高层主题，如法律、医疗健康、编程等。
- 操作 Operation：用户希望执行的任务类型，如摘要生成、代码编写、预约预订、文本翻译等。

每个领域和操作都能绑定一个或多个首选模型。推理时模型会结合语义相似度、任务关键词和上下文线索，推断出领域与操作，再按路由规则选择最适配的模型。

参数仅1.5B，能在 CPU 上高效运行，兼容 Hugging Face Transformers，也可通过 Ollama 快速部署，集成成本很低。

#### 2.1.3 小模型微调 + 大模型兜底实现意图识别

Arch-Router 在通用场景表现不错，但面对金融风控、医疗问诊、工业设备运维等高度垂直的业务时，通用知识往往不够精细，容易出现误判。

业界常用的做法是小模型与大模型并行：
- 小模型微调：用企业自有业务数据对 1.5B、3B 等小参数模型如 Qwen2.5-1.5B 进行针对性微调，在特定场景下获得更高分类精度。
- 大模型少样本兜底：当微调模型覆盖不足时，用提示词工程让大参数模型如 Qwen3-Max 做二次判断，提升准确率。

这种组合既保证效率又兼顾覆盖，是垂直领域意图识别的常见架构。
