假设一个 Agent 的上下文可以装下整个世界、推理和算力也都无限放开，它其实没必要进化出真正的智能——直接暴力穷举、把所有可能性挨个试一遍就能得到答案。

正是“身体”的硬约束逼着 Agent 长出能力。

- 抽象，把海量信息压成精简表征，换来上下文里的喘息空间。
- 规划，把冗长的行为链剪掉冗余，让每一步都更省力。
- 启发式决策，用经验捷径换算力，用有限资源迅速收敛。

身体不是装心智的箱子，而是塑造心智的模具。它决定了 Agent 如何感知世界、如何理解问题、如何生成解法。

这一节要谈的是 Agent 的动力学。它不是一个静止的输入输出黑盒，而是一个在时间里不断展开的感知—推理—行动回路。

感知负责打开眼睛，推理负责拼凑情境，行动负责在世界里留下痕迹，回路则让它不断演化、生生不息。

正是这种具身化的回路，在重新定义软件的未来。

感知—推理—行动循环不只是工程架构，还藏着几层哲学含义。

- 存在就是循环。Agent 的存在不是一种静态状态，而是一场持续进行的动态过程。回路停了，存在也就消失了。
- 认知就是预测。每次循环都在做对未来的预判，预测与现实的差距驱动学习，学习再反过来优化下一次预测。
- 智能就是适应。环境变化带来新感知，新感知触发新推理，新推理指向新行动，形成持续的适应性演进。
- 自主就是闭环。真正的自主来自完整闭环：能感知自己行动的后果，并据此动态调整策略。

感知—推理—行动就是智能的心跳。一次循环是一次微小觉醒，无数次累积才有了我们说的“智能”奇迹。

但单独的回路很脆弱。任务一旦复杂到超出单个回路的承载范围，单打独斗就不够用了。这时候需要把多个回路连起来，织成一张协同的网络。

## 3.3 从单体到社会：多 Agent 协作的语法
当视角从单个 Agent 切换到 Agent 网络时，软件的隐喻发生了跃迁：从机械装置变成社会组织。

单体 Agent 的思路是造一个全知全能的上帝，自己感知全局、推理全局、执行全局。

多 Agent 的思路是承认个体的局限，组建一个各司其职、协同共进的团队。

这不是数量的堆砌，而是复杂度管理的范式切换：从追求全能个体转向设计高效协作的集体智能。

自 2023 年以来，AI 给了我们一个清晰的启示：

Agent 是孤岛，协作才是大陆。

下面从协作本质出发，梳理协作模式、通信协议与冲突解决，搭建多 Agent 协作系统的基础语法。

### 3.3.1 为何必须分工：认知负荷的分流
2023 年 3 月 14 日，OpenAI 发布 GPT-4。当天，一位研究者就在社交平台抛出一个问题：“如果让多个 GPT-4 实例互相对话，会发生什么？”

48 小时后，AutoGPT 上线。随后 BabyAGI、AgentGPT、SuperAGI 等项目接连涌现。大家猛然意识到：真正的增益不在于单体有多聪明，而在于多个 Agent 如何配合。

那一刻的共识是：智能不是单个模型的属性，而是互动的产物。把模型拆成 Researcher、Coder、Reviewer 等角色，让每个角色只做一件事，整体能力反超了单模型上限。这个现象在下面的代码示例里得到了直观体现。

早期实验如 CAMEL、MetaGPT 揭示了一个转折：Agent 不再只是工具，而是承担特定职责的“角色”。单 LLM 能干杂活，却容易出错、幻觉、丢上下文；而角色间的对话与协作，更接近人类团队的思考结构。

为什么不能用一个超长 Prompt 把所有要求塞给一个 LLM？答案是认知的边际效应递减。

- 上下文稀释效应：System Prompt 越长，关键指令越容易被淹没，模型遵循核心任务的能力明显下降。
- 角色泛化陷阱：又写代码又写文档还要做测试的通用 Agent，往往样样平庸。它想面面俱到，却难做专业。
- 角色冲突与思维不兼容：不同任务需要不同思维模式。创造者需要较高的 Temperature 来发散探索，审查者需要较低的 Temperature 来收敛严谨。让一个 Agent 同时当运动员和裁判员，会产生内在目标冲突，甚至出现自我欺骗——在缺乏外部校验时把自己的错误合理化。

架构师的解法是垂直切分。把“开发一款游戏”这类庞大目标按领域拆成策划、美术、程序等子域，由专注的 Narrow Agent 各自负责。

多 Agent 的本质，是用组织架构弥补单体 Agent 在认知、专注度和可靠性上的短板。

从 AutoGPT 到 CrewAI，从 AutoGen 到 LangGraph，多 Agent 编排正成为下一代软件架构的默认范式。

### 3.3.2 如何协作：角色、协议与拓扑
让一群 Agent 真正高效配合，不能只把它们扔进一个聊天室。要从角色、协议、拓扑三个维度定义协作语法。

### 1.角色：把 SOP 内化为人格
传统开发里，标准作业程序是外部文档。在 Agent 架构里，SOP 被内化为角色本身。

- 产品经理 Agent：只把模糊需求转成清晰的 PRD。
- 架构师 Agent：基于 PRD 输出接口定义与技术方案。
- 工程师 Agent：依据接口定义生成可运行代码。

角色的核心是关注点分离。每个 Agent 只接收处理与职责相关信息，保持上下文纯净与专注。

### 2.协议：让沟通可解析
Agent 之间怎么高效交流，取决于“语言”选择。

- 自然语言：通用、自由，适合内部推理，但传输效率低、歧义多，不适合作为可靠的跨 Agent 通道。
- 结构化 Schema：现代多 Agent 架构倾向用标准化数据格式如 JSON 交互。

  - Agent A 输出：{"task": "review_code", "status": "pending"}
  - Agent B 响应：{"action": "approve", "comments": "Fix line 42"}

“用自然语言思考，用结构化语言交流”的模式，既保留 LLM 的推理弹性，又保证系统通信的精确与可解析，已成为稳定可扩展多 Agent 系统的基石。

因此协作离不开语言，真正托起协作的是明确定义的通信协议。

> 很多人以为 Agent 协作是 2024-2025 年才兴起的概念，其实早在 1993-1998 年，KQML 与 FIPA ACL 就已提出“Agent 必须通过语言沟通”。当时已系统定义了 INFORM、REQUEST、PROPOSE、ACCEPT、REJECT 等标准化通信行为，构建了早期多 Agent 交互协议框架。只是受限于底层推理生成能力，思想未能落地。

## 3.3.2 双轨协议：A2A 与 MCP
Agent 的真正工业级突破在于 A2A 协议和 MCP，它们为 2024-2025 年的多 Agent 发展确立了双轨制标准。

- MCP：模型与工具的协议——连接世界的“手”。它解决大脑如何指挥手脚的问题，把数据库、文件系统、SaaS 接口等外部资源抽象为统一上下文资源，让工具调用变成通用的结构化 RPC。可以说 MCP 是 Agent 操作外部世界的 USB 接口，即插即用、协议统一、能力可扩展。
- A2A 协议：Agent 之间的协议——连接思想的“网络”。它解决大脑如何与大脑协作的问题，定义了握手、协商、拒绝、任务交付等标准流程，消息结构里不仅有内容，还有意图元数据。如同 TCP/IP 之于互联网，A2A 是多 Agent 系统的基础通信层，让不同角色、不同来源的 Agent 互联互通、协同推理、可靠交付。

MCP 解决模型—工具交互，A2A 解决模型—模型与 Agent—Agent 协作。MCP 让 Agent 能“操作世界”，A2A 让 Agent 能“彼此协作”。

### 3.3.3 拓扑决定权力：三种连接形态
Agent 间的连接方式，从根本上决定系统的协作性质与边界。

- 流水线 Chain：信息单向流动，结构清晰、延迟低、效率高，适合流程明确、确定性强的任务。代价是灵活性差，难以应对动态反馈。
- 层级式 Hierarchy：一个 Manager Agent 统筹多个 Worker Agent，适合需要复杂规划、任务分解与资源协调的场景。集中控制带来强管理能力，但牺牲节点平等，可能抑制底层主动性。
- 联合式 Mesh：多个 Agent 以圆桌形式平等交互，通过辩论、协商、投票达成共识，适合创意生成、战略决策等开放任务，能激发群体智能与涌现创新。代价是通信开销大、收敛慢。

拓扑不只是连线方式，更是权力与决策逻辑的具象化。架构师的核心职责，是根据业务对确定性与创造性的权衡，在这三种权力形态中做出审慎选择。

### 3.3.4 秩序的维持者：编排器的五大职责
当 Agent 增多，系统需要一个“大脑”来维持秩序，这就是编排器 Orchestrator。

多 Agent 的核心挑战已从“单体够不够强”变成“多个 Agent 能否高效可靠有序协作”。编排器本身不仅是 Agent，更是一种运行时。

- 协调角色边界、调度任务流转与依赖、监控执行状态与异常、推动团队向目标收敛。

多 Agent 编排遵循传统工程原则，只是模块变成了 Agent，函数调用变成结构化语言对话，接口契约演变为通信协议，异常处理体现为协商、重试或角色介入。

编排器承担五大核心职责。

1. 调用顺序
Agent 按预设或动态生成的协作流程介入，例如搜索→阅读→分析→写作→批判→修订。编排器像工厂调度中枢，保证每个 Agent 在正确时机接手，维持工作流连贯。

2. 数据流动
编排器维护全局上下文作为“共享记忆”，结构化承载协作成果。检索结果传给阅读，摘要传给分析，洞察传给写作，初稿传给审校。信息在角色间精准流转、无损继承、可追溯演化，避免重复推理或上下文断裂。

3. Agent 选择
任务存在多个可选执行者时，编排器综合能力、负载、成本、可靠性进行动态匹配。未来这一机制将融入 A2A 协议，每个 Agent 广播结构化能力描述，编排器实现实时自动化匹配。

4. 条件分支与循环
真实任务是非线性的：测试失败需回退开发，审稿不达标需重写。编排器像状态机，根据执行结果动态跳转，支持循环、回退、重试直至收敛。系统不再是僵化流水线，而是有反馈、自省、演进的活组织。

5. 并行与资源管理
处理 50 篇文献不必串行阅读，可并行检索、并行分析、并行核查。编排器高效调度认知资源，让多 Agent 结构发挥多核 CPU 效应，整体吞吐与效率指数级提升。

单体 Agent 负责能力，编排器负责流程：谁在何时做什么、如何组合结果、如何应对异常。协作结构的设计与动态调控，是多 Agent 系统从混乱聊天迈向可控可靠工程系统的关键跃迁。

### 3.3.5 冲突与共识：智能的张力
冲突是智能的副产物，也是复杂系统生命力的来源。若所有 Agent 总是意见一致，那只是回音室。多 Agent 系统的冲突处理大致分为四类。

### 1. 投票机制：快速而实用
适合单步决策、方案差异小、成本敏感场景。常见策略有多数投票、加权投票、基于置信度的投票。多数 LLM 系统用此提升稳定性，例如三模型生成方案后投票选出最可信答案，或在 ReAct 工具调用中避免幻觉错误。

### 2. 辩论机制：提升答案质量
DeepMind 与 OpenAI 多次验证有效：让两个或多个 Agent 围绕同一问题辩论、质疑、反驳、完善，最终得到质量更高、偏差更小的结论。

优势在于推理链被主动暴露，谬误与认知偏差更易被纠正，结构化冲突激发更深洞察。适用于复杂推理、模糊任务和高解释性需求场景。
