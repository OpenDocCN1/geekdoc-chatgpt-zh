实际部署时，智能体常会同时挂载多套基座大模型，例如多模态识别能力突出的 Doubao-Seed-2.0-Pro、擅长逻辑推演的 Qwen3-Max，以及代码生成表现优异的 GLM-4.7。感知层先对用户意图进行拆解，再从模型池中选取最契合的能力单元投入，借此规避选型失误带来的质量波动与不必要的 Token 消耗。

#### 2. 规划模块，串联上下文执行逻辑
规划模块的核心任务是产出解决问题的思维链。现实任务往往需要多轮推演才能落地，因此它实际上为整段交互提供了逻辑骨架，决定步骤如何设计与推进。工程化落地时常参考的做法有：

- ReAct 模式：以“推理-行动-观察”为闭环，推动对话状态动态演进。
- PlanAct 模式：先一次性生成完整计划，或由人工注入标准作业流程 SOP，再驱动 LLM 按序执行。
- Sequential Thinking：这是一个开源的 MCP 模型上下文协议 Server，能够辅助 LLM 实现多轮自主规划与反思，对复杂任务成功率有明显提升。目前扣子在升级 2.0 后更名，其思维链构建即基于 MCP Server 完成。

#### 3. 执行模块，提供实时上下文
执行模块通过调用外部 API 或运行代码型智能体，获取物理世界的实时数据，例如最新的行业参数与价格动态。这是整个上下文构建体系里最具动态性的环节，每一次工具调用的返回结果都会被加工成新的信息片段，实时注入模型输入端，驱动下一轮推理。

#### 4. 反思模块，确保上下文信息不遗漏
“吾日三省吾身”的思路同样适用于智能体。反思模块要对规划与执行的结果进行复盘，检查是否存在错误或不完善之处，进而提出修正建议并重新引导规划进入新一轮。工程实现上，既可以依靠设计反思提示词赋予智能体自检能力，也可以借助 Sequential Thinking 工具完成从规划到反思的闭环。

### 1.2.2 上下文管理的核心策略
由于 LLM 的上下文窗口有限，构建之外还需要管理，让窗口被高效利用。下面从记忆管理与上下文卸载两方面说明。

#### 1. 记忆管理
记忆管理解决窗口受限、长对话易出现断层的问题。短期记忆与长期记忆结合，可以让智能体在多轮交互中保持连贯，避免重复提问。记忆模块还能维护用户的长期偏好、历史行为，以及从外部检索到的专业知识。落地方式因场景而异，短期记忆常把对话历史放在内存临时使用，长期记忆则把历史对话存入文件或向量库，结合 RAG 进行存取，例如 Mem0 就是基于 Agentic RAG 的设计。

#### 2. 上下文卸载
工程实践中，上下文并非越多越好，过剩信息会形成噪声拖累性能。上下文卸载的关键在于只保留当前任务最相关的核心信息。

如图1-5所示，AI 编程工具 Cursor 在处理复杂项目时，会把详尽的分析结果写入独立的 Markdown 文件，对话窗口内仅保留文件路径与摘要。这种引用而非堆砌的方式，有效抑制了上下文膨胀。

[PRE0]

Skills 也是上下文卸载的典型范式。智能体启动时仅加载 Skills 的元数据，即名称与描述；确认需要调用时才加载详细的 SKILL.md 说明，若涉及更深操作再读取关联资源文档。按需加载避免了将大量暂时用不到的工具描述塞入模型上下文，减少对判断的干扰。

## 1.3 简单工具调用到复杂Agent：Agent技术发展路线图
本节梳理 Agent 技术自 2023 年以来的演进脉络，回顾架构、能力与应用场景的关键变化，理解上下文工程如何随之发展。

### 1.3.1 简单工具调用Agent的原理与特点
Agent 概念在 2023 年开始受到广泛关注。尽管 LLM 具备丰富的通用知识，但在垂直专业问题或依赖实时信息时，例如“今日北京天气状况如何”，往往会出错甚至产生幻觉。为此研究者探索让模型与外部环境交互，通过调用数据库、API、搜索引擎等获取最新相关信息，再融入推理，提升准确性与时效。

#### 1. Function Calling
2023 年 6 月，OpenAI 正式推出 Function Calling，并在 GPT 系列中提供原生支持。其核心思想是在预训练或微调阶段引入结构化工具交互数据，让模型学会在合适情境下触发工具调用。典型训练样例如下。

受限于需要在训练阶段加入结构化数据，技术门槛较高，并非所有模型都原生支持。即使支持，模型输出也仅限工具调用指令与最终答案，决策时为何选用某工具的内部推理对开发者仍是黑盒，可解释性与调试难度受限。

#### 2. ReAct
为绕开 Function Calling 的改造成本，研究者转向无需改动模型结构的方案。2023 年发表的论文 ReAct: Synergizing Reasoning and Acting in Language Models 提出的思路迅速工程化，至今仍是 Claude Code 等强力 Agent 的底层范式。

ReAct 的优势是零训练依赖，仅靠提示词即可引导 LLM 在推理中交替进行思考与行动，且思考内容会随对话返回。开发者准备好任务目标、工具列表与交互格式的模板后，模型可在运行时自动完成以下循环，流程见图1-6。

1. 理解问题并进行推理。
2. 判断是否需要调用外部工具。
3. 选择合适工具并生成调用参数。
4. 接收工具执行后的反馈。
5. 基于新信息更新上下文，继续推理或输出最终答案。

### 1.3.2 深度思考型Agent的原理与特点
随着 Agent 在生产环境中的普及，开发者意识到仅靠 ReAct 已难以满足复杂业务需求。ReAct 虽灵活易用，却暴露出局限：

- 对底层 LLM 能力高度依赖，推理或格式不足会导致流程中断。
- 执行效率低，复杂任务需多次调用，延迟与成本累积。
- 提示词脆弱，细微改动会影响行为，且模型对格式保持不稳定。
- 缺乏全局视角，易陷入局部最优或原地循环。

#### 1. Agent设计模式
常见设计模式包括：

（1）CodeAct 模式。将工具抽象为 Python 执行器，LLM 生成可执行代码片段而非调用预定义 API，适合运维自动化、数据处理等场景。
（2）计划-执行 模式。先由规划 Agent 对问题做全局拆解生成多步计划，再交执行 Agent 按步骤调用工具并推进，提升长程任务一致性。
（3）反思 模式。执行后由独立反思 Agent 评估输出是否存在逻辑漏洞、信息遗漏或误用，必要时重试或调整策略，提升准确性与鲁棒性。
（4）人机协作 模式。在关键决策或高风险操作处嵌入人工审核点，系统暂停请求授权，降低错误成本并增强可控性。

#### 2. 深度思考型Agent的出现
2025 年上半年，深度思考型 Agent 成为研究热点，例如 OpenAI 的 DeepResearch、智谱的沉思、扣子系列产品等。它们不再满足于单轮工具调用，而是融合多种设计模式，形成持续迭代、自我修正的认知闭环。

### 1.3.4 多Agent的原理与特点
近期 SubAgent 十分热门，也称子 Agent 或专家 Agent，负责特定子任务或领域。典型多 Agent 系统由多个 SubAgent 加一个协调者 Manager Agent 构成，前者执行，后者负责分解、调度、仲裁与整合。

常说多 Agent 解决单 Agent 面对大量工具时选错问题，这有道理。更本质的视角是上下文污染问题。上下文污染指单 Agent 在任务复杂时，上下文混杂推理轨迹、工具描述、中间结果、历史记录与原始意图等异构信息，缺乏结构会相互干扰，造成认知噪声、聚焦下降，还会迅速耗尽 Token 窗口导致截断。
