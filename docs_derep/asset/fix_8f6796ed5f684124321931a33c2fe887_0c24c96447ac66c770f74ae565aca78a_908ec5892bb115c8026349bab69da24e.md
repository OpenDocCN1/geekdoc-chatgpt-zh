## 9.2 Plugin 的物理结构

Plugin 本质上是一个遵循约定目录规范的文件夹，日常多以 Git 仓库形式托管，其核心凭证是置于 .claude-plugin/ 子目录下的 plugin.json 清单。

这里存在一个必须遵守的物理限制：清单 plugin.json 只能且必须落进 .claude-plugin/ 这个固定子目录，其余功能目录 commands、agents、skills、hooks 以及配置文件 .mcp.json 全部直接放在 Plugin 根目录下。

由于这种安排，Plugin 根目录本身即是一个合法的 Claude Code 项目目录。开发者可在该目录内直接编码与自测，无需切换到特殊开发模式。

| 字段 | 必需 | 说明 |

| keywords | 否 | 用于检索的搜索关键词 |

需要重点提醒 name 字段。它不仅是展示名，更决定了命名空间。安装后，Plugin 内部所有组件都会自动加上该名前缀以避免冲突。因此名称要选得简洁清晰且不易重复。推荐如 react-workflow、pr-reviewer、db-tools；不推荐 my-plugin 过于宽泛、tools 极易冲突、v2 带有版本号无意义。

## 9.4 命名空间：多 Plugin 共存

当多个 Plugin 同时存在且包含同名 Skill 或 Command，会怎样处理？系统借助命名空间机制自动化解冲突。

所有经 Plugin 安装的组件都会自动获得 plugin-name:component-name 的全限定名称，保证全局唯一。以安装 react-workflow 为例：

- 原 review Command 变为 /react-workflow:review。
- 原 code-reviewer Skill 变为 react-workflow:code-reviewer。
- 原 security-scanner Agent 变为 react-workflow:security-scanner。

若不存在冲突，直接使用简短命令名如 /review 即可，Claude Code 会自动解析到唯一组件。只有检测到同名冲突时，系统才要求使用完整命名空间限定符如 /plugin-a:review 来明确指定。

该机制的工程价值在于：团队可放心组合多个 Plugin，无需提前协调命名；开发者也不必刻意避让，降低维护成本。

#!/bin/bash

# Bash 命令安全拦截脚本

# 用于在 Claude Code 执行危险命令前进行阻断

INPUT=$(cat)

COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')

DANGEROUS_PATTERNS=("rm -rf /" "rm -rf ~" "sudo rm" "> /dev/" "chmod 777")

for pattern in "${DANGEROUS_PATTERNS[@]}"; do

    if echo "$COMMAND" | grep -qF "$pattern"; then

        cat << EOF

{"decision": "deny", "reason": "Blocked dangerous pattern: $pattern"}

EOF

        exit 1

    fi

done

exit 0
