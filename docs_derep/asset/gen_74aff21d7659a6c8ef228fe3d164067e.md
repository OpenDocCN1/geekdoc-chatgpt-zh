### 7.2 模型推理加速框架
部署 DeepSeek 模型前，先要认识一个关键工具：模型推理加速框架。

推理加速框架是提升大模型性能的核心手段，能够明显加快响应速度并降低对计算资源的需求，从而满足实时应用场景并减少部署成本。本节将阐述推理加速框架的价值与优势，并介绍三种常用框架。

#### 7.2.1 推理加速框架的必要性
大模型功能强劲，但在实际落地中仍存在诸多挑战。例如，大规模模型往往消耗大量计算资源和内存，在资源受限环境如移动设备或边缘计算中推理效率会明显下降。再者，语音助手、实时翻译等实时应用对响应时延要求极高，用户期待瞬时反馈。推理加速框架通过优化推理流程解决了这些痛点，显著提升实用性和经济性。其主要优势有四点。

1. 计算和内存优化
大规模模型完成复杂任务需要大量算力和内存，在受限场景下效率偏低。通过对 KV Cache 进行优化，推理加速框架可在保持模型效果的前提下，大幅减少计算量与内存占用，实现高效推理。

2. 实时性保障
在对响应速度要求极高的应用中，用户体验直接取决于推理速度。推理加速框架能够显著降低延迟，保证交互流畅无阻。

3. 降低部署成本
部署大模型通常依赖高性能 GPU 等昂贵硬件，推理加速框架可让模型在相对低成本的硬件平台上高效运行，从而降低硬件投入，扩大大模型技术的应用范围。

4. 系统层面的性能优化
大模型推理性能不仅受模型本身影响，还受系统架构如内存带宽、计算单元利用率等制约。通过全系统的优化策略，例如高效数据传输、缓存优化和算子融合等，推理加速框架能进一步提升整体推理速度与效率。

#### 7.2.2 BladeLLM
BladeLLM 是阿里云 PAI 平台提供的大模型推理引擎，专为帮助用户以高性能、低成本的方式部署大语言模型服务而设计，通过对模型推理和服务的全链路深度优化，确保不同模型在不同设备上都能达到最优性价比。

在实际业务中，高额的框架开销会严重制约系统吞吐量，尤其在高并发场景下易造成资源浪费和性能下滑。为此，BladeLLM 提出并实现了一套基于 Python 的纯异步大语言模型推理架构 TAG，即 Totally Asynchronous Generator 完全异步生成器，以最大化 GPU 利用率并提升引擎性能。

推理引擎的关键在于 Scheduler 与 ModelRunner 之间存在同步关系，该同步源于：Scheduler 在调度时为每个请求分配 KVCacheBlock，而分配决策依赖于请求的 Token；当前调度所需的 Token 需等待上一步 ModelRunner 运行结果返回给 Scheduler，从而形成依赖，导致两者必须串行同步执行。

在 TAG 架构中，各组件间消息传递均以异步方式完成，整体流程如下。

1. Web 服务器接收用户请求
请求经分词器处理后被加入 Scheduler 的请求队列；与此同时，系统并行从解码器接收响应并返回给用户。

2. 更新循环
更新循环主要处理 Model Runner 的返回消息队列，包括：
- 更新 Token 数：在 Model Runner 生成 Token 后，将实际生成数量反馈给 Scheduler，避免 KV Cache 分配浪费。
- Detokenize 处理：将生成的 Token 解码为可读文本并传给 WebServer。
- 判停处理：判断请求是否达到终止条件，如遇到结束标志或达到最大 Token 数，及时将已完成请求移出队列。
- 释放信号量：完成上述工作后释放信号量，使 Scheduler 能够进行下一次调度。

Scheduler 和更新循环：两者通过 Python 协同并行运行，可同时工作互不阻塞。Scheduler 每次调度前需先获取信号量，该信号量限制了同时进行调度步数，避免调度过载。Scheduler 的主循环为：获取信号量 → 预分配最大 Token Cache → 将调度结果发送给 Model Runner。

3. Model Runner
Scheduler 可同时向 Model Runner 发送多个调度请求，Model Runner 不会因等待某个请求完成而空闲，可持续接收并处理请求。因此其内部流程也完全异步设计，包括：接收并反序列化请求 → 调用模型进行推理生成 Token → 序列化结果并返回给 Update Loop。

#### 7.2.3 SGLang
开发和执行大语言模型任务时，开发者常面临系统效率不足的难题。这些任务涉及多次生成调用、复杂的提示策略、控制流程、结构化输入输出等。为应对这些挑战，开源社区提出了 SGLang，一种专为高效执行复杂语言模型程序设计的系统。SGLang 通过联合设计后端系统与前端语言，显著简化大模型应用开发，使模型运行更快、更可控。

SGLang 由前端与后端两部分组成协同工作，以提升复杂大语言模型程序的执行效率。

1. 后端：RadixAttention 技术
后端的核心是 RadixAttention，一种跨多个生成任务的 KV 缓存复用技术。面对大量用户会话请求，RadixAttention 通过自动高效地重用缓存，减少计算冗余和内存消耗。

- KV 缓存复用：在推理阶段 KV 缓存保存前向传递的中间张量，用于解码未来标记。RadixAttention 利用基数树管理这些缓存，使具有相同提示前缀的请求可共享同一 KV 缓存。
- 基数树的优势：与传统字典树相比，基数树的边可表示元素的连续序列，从而提升空间利用效率并加速数据处理。
- 缓存管理：GPU 内存有限，无法容纳无限 KV 缓存，因此需要驱逐策略。SGLang 采用 LRU 最近最少使用驱逐策略，递归驱逐叶节点，确保 GPU 内存有效利用。此外，RadixAttention 与连续批处理和分页注意力等技术兼容，可扩展至多模态模型。

图 7-4 展示了处理多个请求时基数树的维护方式。前端始终向后端发送完整提示词，后端自动进行前缀匹配、复用与缓存。树结构存储在 CPU 上，维护开销较低。

2. 前端：SGLang 领域特定语言
前端核心是嵌入 Python 的 DSL 领域特定语言，允许开发者编写高级提示词、控制流、多模态、解码约束和外部交互代码。

#### 7.2.4 vLLM
在大模型推理服务中，内存管理是影响性能的关键因素之一。现有服务多采用静态连续分布内存策略，导致显著内存浪费，限制推理性能提升。vLLM 是一个专为大语言模型推理服务设计的开源工具，通过优化内存管理和资源利用，显著提升推理性能。

现有大语言模型服务存在三类主要内存浪费问题。

- 预留浪费：为每个请求预留最大可能序列长度的内存，但实际长度往往远小于最大值。
- 内部碎片：内存分配效率低导致碎片，降低可用性。
- 外部碎片：部分内存块因过小而无法使用，直接造成浪费。

为解决这些问题，vLLM 提出创新的注意力机制 PagedAttention，并构建高效的 KV 缓存管理系统。该系统利用分页技术对 KV 缓存进行精细化管理，提升内存利用率，减少不必要浪费，并支持更复杂的解码算法。通过该方法，键值对可存储于非连续物理内存区域，同时保持逻辑连续性，使内存管理更灵活高效，更好应对大语言模型服务的内存挑战。

vLLM 采用集中式调度器协调分布式 GPU 工作站的执行。KV 缓存管理器通过 PagedAttention 以分页方式有效管理 KV 缓存。具体而言，KV 缓存管理器依据集中式调度程序发送的指令管理 GPU 工作节点上的物理 KV 缓存内存。

PagedAttention 的设计灵感来自操作系统中的虚拟内存分页机制，通过将 KV 缓存拆分为多个不连续内存块存储，有效减少内存碎片并提升利用率。基于此机制，PagedAttention 不仅显著提高推理吞吐量，最大限度减少内存浪费，还通过内存共享机制支持并行采样和波束搜索等复杂采样算法，从而增强整体模型服务性能。
