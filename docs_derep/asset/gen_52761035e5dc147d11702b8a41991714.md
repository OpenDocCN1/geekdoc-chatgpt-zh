这个例子里我们把前面提到的 MobileNet 模型在 Xcode 中打开，就是为了看 Xcode 如何和这个文件配合。该文件整体被切成三大块。

第一块是元数据，会展示模型的名称、类别和体积。本例里它是一个 17.1 MB 的名为 MobileNet 的神经网络分类器。这块还能放模型内部的补充信息，比如本例提供的作者、说明和许可，创建自己的模型时可以随意填充。

第二块是 Xcode 自动生成的模型类。读取 .mlmodel 后 Xcode 会自动造出交互所需的文件，这正是 CoreML 的便利之处。日常使用不需要改动这些文件，好奇的话可以检视一下，或者自己造一套来获得更精细的控制。我们后面会再细说这些生成文件，现在可以把它当成黑盒，它提供一个可实例化的类，里面带有一个 prediction 方法，用来完成和 .mlmodel 文件的一切交互。

最后一块是模型的输入输出。MobileNet 只有一个输入，即宽高均为 224 像素的彩色图像，两个输出分别是字符串 classLabel 和字典 class-LabelProbs。

以 MobileNet 为例，它被设计用于对象检测，这些输出给出了最可能的对象以及其他对象的概率。自己的模型里输入输出类型会不一样，思路是相同的：Xcode 展示了喂给模型所需的数据接口和预期的输出。

#### MLModel 格式

除非你要造自定义模型，否则不必纠结 .mlmodel 到底是什么。如果你想知道它的含义，苹果提供了一套帮助用户创建和转换模型的工具。

这里说的自定义模型，并不是指自己训练，而是指自己定义每个组件。

不过总有需要深入修改或自制工具的时候，这时就得了解模型格式了。

MLModel 格式建立在谷歌开发的 protocol buffer，也就是 protobuf 序列化数据格式之上。protobuf 和 JSON、XML 一样是序列化方案，但它不可读、不是文本，同时具备可扩展性，能存放几乎任何需要的数据。

protobuf 的目标是高效、跨语言支持、前后兼容。随着时间推移模型格式会不断迭代增加特性，但仍被期望长期保持稳定。另外当前绝大多数机器学习训练都在 Python 里进行。

种种原因让 protobuf 成为 MLModel 格式的理想选择。

[PRE2]如果你想在 App 里用 protobuf，苹果已经提供了一个 Swift 库可以试用。

MLmodel 格式里包含多种 message，也就是 protobuf 术语里的信息单元，可以理解为类或结构体，它们完整描述了构建各种机器学习模型所需的信息。

规范里最关键的 message 是 model，它像一个高级容器，包含版本号、模型描述和一个 Type。

模型的 Type 也是一个 message，里面装着描述该模型所需的一切。CoreML 支持的每种机器学习方法在文件格式里都有自己的自定义 Type 消息，封装对应方法需要的数据。

回到神经网络的例子，Type 就是 NeuralNetwork，内部含有 NeuralNetworkLayer 和 NeuralNetworkPreprocessing 消息。它们保存了神经网络所需的数据，每个 NeuralNetworkLayer 都记录了层类型例如卷积、池化或自定义、输入、输出、权重、偏置和激活函数。

所有信息被打包进一个 .mlmodel 文件，CoreML 之后可以读取它。

[PRE3]想深入了解 CoreML 模型格式的细节以及如何构建使用，苹果提供了完整规范可以阅读。

如果你在做自定义模型和工具，这个资料就是专门为你准备的，最合适不过。

大多数情况下，可以把 CoreML 模型当成描述完整模型的信息就好，不必关心它如何存储。

#### 为什么离线

苹果非常强调 CoreML 是在设备离线环境下完成，全部处理都在本地进行。

这和部分系统的处理方式很不一样，另一种常见做法是把数据从设备上传到可做处理的机器，再把结果返回设备。

苹果这样运行 CoreML 有利有弊。主要利点有：

• 始终可用。模型和数据都在用户设备上，没有信号也能跑机器学习。
• 节省流量。本地完成就不用上传下载，省下宝贵的移动数据。
• 无需基础设施。自己跑模型就不用自建服务器，也不用处理数据传输。
• 保护隐私。全部本地化，除非设备被入侵，否则没人能提取信息。

弊端则有：

• 更新更难。更新或重建模型需要推送给用户，或重新打包，或使用苹果的设备端个性化，限制不少。
• App 体积变大。把模型放在设备上后，应用会比只把数据发到另一台电脑要大。

[PRE4]根据你用机器学习做的事情，模型很容易变得非常大。

因此苹果发布了一些在部署前减小 .mlmodel 文件大小的指引。

苹果认为设备端处理的优点大于缺点，我们也认同这一点，尤其在隐私层面。机器学习能提供有时可怕的洞察和功能，但潜在风险同样惊人。

计算机并不在乎隐私，所以我们必须认真思考并时刻把用户隐私放在首位。

#### 了解 CoreML 的各个方面

CoreML 包含的内容很多，我们这里不想重写苹果的 CoreML API 参考文档。

CoreML 的核心是 MLModel。它封装并表示机器学习模型，提供预测功能以及读取元数据功能。

CoreML 还提供了 MLFeatureProvider，我们会在 11.1 节再详细讨论。它是一种便捷方式，用来向 CoreML 模型输入数据或从中提取数据。紧密相关的是 CoreML 提供的 MLMultiArray。它是一个多维数组，可作为模型的特征输入和特征输出。

[PRE5]多维数组在 AI 里很常见，从图像到简单数字都能很好表现。CoreML 用 MLMultiArray 表示图像，图像的通道、宽度和高度分别对应数组的各维度。

CoreML 里还有很多其他内容。建议逐步阅读本书，再查阅苹果文档填补感兴趣的空白。

既然对 CoreML 的认知已经比较清晰，就可以校验新学到的知识了。这正是本书第二部分要关注的内容。下面将介绍 CreateML，这是创建 CoreML 模型最常用的方法。

### 了解 CreateML 的各个方面

我们本想长篇介绍 CreateML 的全部内容，后来意识到那基本是在复制苹果的 CreateML API 参考和文档。

与其如此，不如总结 CreateML 的实用之处，希望你在第二部分的实践任务中遇到它时亲自探索。

CreateML 能用来训练模型的东西很多，例如：

- MLImageClassifier 用于对图像进行分类。
- MLObjectDetector 用于检测图像中的对象。
- MLTextClassifier 用于对自然语言文本进行分类。
- MLWordTagger 用于在词级别对文本进行分类。
- MLSoundClassifier 用于对音频进行分类。
- MLActivityClassifier 用于对行为数据进行分类。
- MLClassifier 用于对表格数据进行分类。
- MLRegressor 用于用回归而非分类来估计连续值。
- MLRecommender 用于推荐。

使用或训练模型时需要注意以下几件事：

- MLGazeteer 用于定义术语和标签，以增强 MLWordTagger。
- MLWordEmbedding 用于把字符串映射到向量，从而找到相邻字符串。
- MLClassifierMetrics 用于度量分类器性能。
- MLRegressorMetrics 用于度量回归器性能。
- MLCreateError 用于存储使用 CreateML 时发生的错误。

存储数据时需要注意以下几件事：

- MLDataTable 用于存储数据表。
- MLDataValue 用于存储 MLDataTable 中的数据单元。
- MLModelMetadata 用于存储有关模型的元数据，例如创建者和许可信息。

你可以在 CreateML 文档里了解所有这些内容，但本书几乎涵盖了它们，并将其作为贯穿全书的实践任务。
