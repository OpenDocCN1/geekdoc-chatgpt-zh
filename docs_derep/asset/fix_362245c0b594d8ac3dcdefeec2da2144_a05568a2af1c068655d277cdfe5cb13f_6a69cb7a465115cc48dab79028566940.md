在这种设定下，Claude 处理 src/services/order-service.ts 时，相关的测试规范会被静默；一旦切换到编辑 tests/order-service.test.ts，对应的规则会立刻被激活。这种按需唤醒的设计，跟编程里的懒加载思路是一致的：启动时不把所有潜在资源一次性载入，只有真正触达时才动态调取。

同样的思路可以迁移到别的工程场景里。比如只在碰到 Prisma 文件或数据访问层时才引入数据库规范，编辑路由或 Schema 文件时才让 API 设计规范生效。

## 本章小结

回到开篇的场景：小冰每次开启新会话，Claude 总是习惯用 Express 替代 Fastify，用 npm 替代 pnpm。现在明白了，这并非模型能力缺陷，而是缺少一份关键的入职手册。

CLAUDE.md 正是解决这个痛点的机制。它把团队的技术选型、编码规范、项目结构和常用命令固化为 Claude 可读的配置，每次会话启动时自动加载，从而跳过重复纠正，直接进入高效协作。

五层记忆体系的设计体现了软件工程中关注点分离的原则。
- 企业级：严守安全底线，由组织统一管理。
- 用户级：沉淀个人偏好，尊重个体差异。
- 项目级：承载团队共识，确保协作一致。
- 规则级：实现规则的模块化与条件化加载。
- 本地级：容纳私人备忘，提供灵活的临时上下文。

每一层都有明确的职责边界与管理主体，既支撑协作又尊重个人习惯。

其中条件化规则系统是精巧的工程设计。它用 Glob 模式精准限定规则作用域，实现了在恰当时刻把恰当信息投递进上下文的智能化机制，彻底摒弃了一股脑倾倒规则的粗放模式，保证上下文纯净高效。

关于写作范式，“少即是多”绝非口号。上下文窗口是模型最稀缺的战略资源，每个 Token 都有机会成本。把无关信息塞进 CLAUDE.md，就像高峰地铁硬塞不需要乘车的乘客，既占用空间又把关键信息挤出视野。

一份优秀的 CLAUDE.md 应像精炼的作战备忘录，遵循三条铁律：
- 必要性：每条都是 Claude 必须知道且无法自行推断的信息。
- 可操作性：每条都是具体、明确且可执行的指令。
- 脆弱性测试：删去后会直接导致 Claude 犯错或偏离预期。

下一章，我们将正式进入 Skills 的广阔世界。
如果说 CLAUDE.md 是赋予 Claude 基础认知的入职手册，那么 Skills 就是量身定制的专业培训教材。当入职手册越写越臃肿时，Skills 的按需加载机制就能在真正需要的那一刻，精准地把专业知识注入对话上下文。

## 思考题

1. 请梳理当前项目中 Claude 必须知晓的核心信息。试着用“三问框架”WHY、WHAT、HOW 拆解，并据此撰写一份不超过 30 行的 CLAUDE.md。成稿后逐行审视：若删除此行，Claude 会犯什么错？答不上来就说明该行多余。
2. 团队协作中若对 CLAUDE.md 规则产生分歧，如缩进用 2 空格还是 4 空格，应如何借助五层记忆体系化解？哪些规则必须置于项目层强制统一，哪些偏好适合下放到用户层或本地层以保留个人自由？
3. 在项目中执行 /init 命令自动生成 CLAUDE.md，再与手动版本对比：机器能准确推断出哪些显性信息？哪些隐性知识必须人工补充？
