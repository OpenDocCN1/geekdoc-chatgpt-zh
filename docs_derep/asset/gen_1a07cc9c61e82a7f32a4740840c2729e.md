## 4.4 活动图
活动图是用来图形化呈现系统行为的工具，主要用来刻画业务流程、工作流以及系统内部的活动与动作。它能清晰表达活动间的先后顺序、并行关系、决策点和分支点。借助活动图，需求分析、业务建模和系统设计会更直观。

活动图常被用在以下场景。

(1) 业务流程描述：用活动图把从起点到终点的业务步骤串起来，呈现活动的执行顺序和路径，帮助理清各步骤间的关联，从而分析和优化业务。

(2) 需求分析与系统设计：在需求阶段，活动图有助于梳理功能需求，识别系统内的各项活动及其逻辑顺序；在设计阶段，则用来规划业务流程和交互逻辑。

(3) 工作流建模：活动图可以描绘工作流中的活动、判断节点和分支，帮助理解执行路径，通过改进图示来提升效率和质量。

(4) 系统交互设计：活动图能展示用户与系统之间的交互流程，包括用户输入、系统响应与反馈，进而指导界面和交互体验的设计。

(5) 系统测试与验证：活动图可作为测试用例的依据，帮助测试人员把握系统功能和行为，设计覆盖全面的测试方案。

综合来看，活动图在需求分析、系统设计、流程建模、交互设计和测试验证等环节都能发挥重要作用，辅助理解、描述和优化系统的行为。

## 4.4.1 活动图要素
在软件实践中，活动图主要由以下要素构成。

(1) 活动 Activity：代表系统要完成的具体操作或任务，用矩形表示，矩形内写明活动名称。

(2) 控制流 Control Flow：表示活动执行的先后顺序，用带箭头的直线连接各活动。

(3) 分支 Decision：表示条件判断，根据不同条件走向不同路径，用菱形表示，菱形内写明判断条件。

(4) 合并 Merge：表示多条路径汇聚为一条，用菱形表示多个分支的汇合点。

(5) 并发 Concurrency：表示多项活动可同时进行，用横向双线表示，每条并发分支拥有独立的控制流。

(6) 起点 Start：活动图的开始，用实心圆表示。

(7) 终点 End：活动图的结束，通常用圆角实心矩形表示。

这些要素共同刻画了活动、顺序、条件判断和并行等行为，便于理解和设计操作流程。

## 4.5 时序图
时序图用于表现系统中对象间的交互时序。它展示了消息传递的顺序和时间关系，帮助理解对象间交互流程，捕捉时序特征，常用于系统设计、需求分析和开发阶段。

时序图由对象和它们之间的消息构成。对象以垂直的生命线呈现，生命线代表对象在图中的存在。消息以箭头表示，从发送方指向接收方，体现调用与响应。

时序图突出交互顺序和时序关系，能清晰呈现通信流程和事件触发顺序，帮助开发者可视化系统行为，检验正确性和性能。

常见用途包括：

- 描述系统时序交互，如方法调用、消息传递。
- 展示对象间消息的顺序和时序关系。
- 在多对象协作场景下分析、设计系统行为。
- 与用例图、类图等其他 UML 图结合，共同完善系统描述。

绘制时序图有助于更好地理解和优化系统交互，提升软件的可靠性和效率。

# 5.2.1 设计模式分类
设计模式总体可分为三类：创建型模式、结构型模式和行为型模式。

## 1. 创建型模式
创建型模式关注对象的创建过程，提供灵活的创建方式并隐藏实现细节。常见模式有：

- 单例模式 Singleton Pattern
- 工厂模式 Factory Pattern
- 抽象工厂模式 Abstract Factory Pattern
- 建造者模式 Builder Pattern
- 原型模式 Prototype Pattern

## 2. 结构型模式
结构型模式关注对象组合与关系，提供清晰、可维护的组织方式。常见模式有：

- 桥接模式 Bridge Pattern
- 适配器模式 Adapter Pattern
- 装饰器模式 Decorator Pattern
- 组合模式 Composite Pattern
- 外观模式 Facade Pattern
- 享元模式 Flyweight Pattern
- 代理模式 Proxy Pattern

## 3. 行为型模式
行为型模式关注对象间通信与协作，提供交互描述方法。常见模式有：

- 策略模式 Strategy Pattern
- 观察者模式 Observer Pattern
- 模板方法模式 Template Method Pattern
- 迭代器模式 Iterator Pattern
- 状态模式 State Pattern
- 责任链模式 Chain of Responsibility Pattern
- 命令模式 Command Pattern
- 解释器模式 Interpreter Pattern
- 中介者模式 Mediator Pattern

(1) 提供解决方案：设计模式给出针对特定问题的成熟方案，通过明确的结构和行为帮助构建高质量系统。

# 5.3 单例模式
单例模式是一种创建型模式，确保一个类仅产生一个实例，并提供全局访问入口，常用于需要全局访问、共享资源或控制特定操作的场景。

## 5.3.1 应用场景
单例模式适用于以下情况。

(1) 全局唯一实例：系统要求某个类只能存在一个实例，如日志记录器、配置管理器或数据库连接池。

(2) 资源共享与访问控制：确保多个对象共享同一实例，实现资源共享和访问管控，如多线程环境下共享资源的管理。

(3) 延迟初始化：实例推迟到真正需要时才创建，对资源消耗大或初始化耗时的对象很有用，如游戏中的管理器对象按需创建。

(4) 控制实例数量：限制类只能创建固定数量的实例，达到上限后阻止新实例生成。

总之，单例模式适合需要全局唯一、资源共享、延迟初始化或实例数量受控的场景，确保唯一性和全局可访问性。

## 5.3.2 结构
单例模式主要由两部分组成。

- 单例类 Singleton Class：只能有一个实例的类，通过限制创建与访问保证全局唯一。通常包含静态变量保存唯一实例，并提供静态方法供客户端获取实例。

- 客户端 Client：使用单例类的部分，通过调用静态方法获取唯一实例并进行操作。

## 5.3.3 优缺点
单例模式的优点包括：

(1) 全局可访问：提供全局访问点，系统任意位置均可调用。

(2) 资源共享：多个对象共享同一实例，节省资源，避免重复创建销毁开销。

(3) 延迟初始化：实例按需创建，提升性能和效率。

(4) 避免竞态：可解决多线程环境下的竞态条件，保证访问安全。

缺点包括：

(1) 全局状态：全局可访问导致状态可能被多处修改，增加复杂性和不可预测性。

(2) 扩展困难：单例特性使功能扩展需修改原类，灵活性受限。

(3) 单一职责违背：常承担过多职责，职责不清，违反单一职责原则。

(4) 生命周期管理：实例生命周期贯穿整个系统，可能长期占用内存，释放困难，增加内存压力。
