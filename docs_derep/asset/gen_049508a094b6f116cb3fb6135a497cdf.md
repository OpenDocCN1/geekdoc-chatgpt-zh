## **5.3 实现应用层的 ping 机制**

MCP 规范提供了一个可选的应用层 ping 机制，允许客户端或服务端发送 ping 请求来探测连接是否存活并据此做后续处理。虽然 HTTP 的 SSE 连接在协议层已有心跳，但 SDK 并没有把该信息暴露给应用层，导致 SSE 模式下应用层难以及时感知中断，也就无法执行必要的清理，例如让 lifespan 的退出逻辑得到保证。

本节聚焦于在服务端主动发起 ping 的实现。规范里 ping 是可选的双向机制，这里以服务端向客户端发起为例讲解。

### **5.3.1 预备知识：MCP 服务端的 ServerSession**

ping 机制依赖会话层的 API 发送请求，所以先要理解 MCP 服务端会话的概念。

如第三章所述，MCP SDK 按传输层、会话层、应用层做模块化分层，各层职责清晰。以往我们主要用应用层的 @call_tool、@list_tools 等装饰器开发工具功能，这些功能其实是建立在更低层接口之上的。各层关系如图 5-9。

[PRE15]

图 5-9

以客户端调用 tools/call 为例，消息先经传输层端点的 handle_post_message 初步处理，再交给会话层的 _received_request 方法处理，最终由应用层的 @call_tool 函数完成。处理完后由会话层的 _send_response 通过 SSE 通道返回。

在 SDK 中，会话层的抽象在服务端是 ServerSession，在客户端是 ClientSession。通常会话在连接建立后由 Server 实例创建。会话层负责请求与通知的收发，所以像服务端发起 Sampling 请求、ping 请求，以及列表变更通知、日志通知等标准机制，都必须通过调用 ServerSession 的 API 来实现。
