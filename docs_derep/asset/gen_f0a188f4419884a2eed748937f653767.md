启动验证与完整验收

保持程序运行 5～10 分钟，终端不出现报错即视为后台稳定，验证通过。若执行“openclaw start”返回命令不存在，先检查环境变量是否生效，修正后再重新启动验证。

Docker 安装的启动检查方式：
1. 打开终端执行“docker ps”，确认容器名称为 openclaw 且状态显示 Up，说明容器已成功启动；
2. 执行“docker logs openclaw”，日志里出现“OpenClaw started successfully on port 18789”且无错误，说明容器内部程序正常；
3. 在浏览器打开“http://localhost:18789”，或使用修改后的端口，若能正常呈现登录页，说明端口映射与 Web 访问正常；
4. 让容器持续运行 5～10 分钟后再次执行“docker ps”，状态仍为 Up 且日志无新增报错，则判定稳定。若启动失败，参照本章第四节 Docker 报错处理方法排查后重启验证。

启动验证的判定要点：
1. 程序或容器可正常启动且无报错；
2. 终端或容器日志出现“OpenClaw started successfully”类提示；
3. 浏览器可正常打开 OpenClaw Web 界面且无连接错误；
4. 运行 5～10 分钟不崩溃、不报错。四个条件齐全即视为通过。

基础功能验证
启动通过后，需确认核心基础功能是否可用，涵盖登录初始化、模型调用、基础工具使用。三个环节都可用才算安装效果达标。

第一步 登录与初始化设置验证。打开浏览器访问 Web 界面，首次安装会进入初始化向导，需创建管理员账号、设置用户名密码、选择模型类型云端 API 或本地模型、配置基础参数如语言时区，完成后再点提交进入主界面。若已初始化，用已创建账号密码登录，能进入主界面无卡顿即为正常。登录失败多为密码错误或配置文件权限设置不当，可重做初始化或修改配置文件。

第二步 模型调用验证。登录后点左侧“对话”进入对话页，输入简单指令例如“帮我写一封邮件”“安排今天日程”，发送后应能收到符合要求的回复且无乱码报错。选用云端模型时需确保 API 密钥正确且网络通畅，出现“API 调用失败”就检查密钥与网络。选用本地模型时需确认模型路径与加载参数正确，出现“本地模型加载失败”就核对路径配置。

第三步 基础工具使用验证。登录后点左侧“工具”，任选一个基础工具如“邮件整理”，按提示上传邮件文件或输入内容后点处理，应能生成整理结果且无报错缺失。同理验证日程规划、文档处理等。工具异常通常是依赖未装全或配置错误，源码安装用户可重装依赖，或检查配置文件中工具相关参数。

基础功能验证判定：
1. 初始化与登录均可完成无报错；
2. 模型可正常调用，回复符合指令；
3. 至少 2 个基础工具可正常使用且无缺失。三项满足即为通过。

环境兼容性验证
目的在于确认 OpenClaw 与系统、依赖、浏览器及数据存储的兼容性，保障长期稳定。

第一步 依赖版本兼容性验证。源码或包管理器安装用户分别执行“node -v”“pnpm -v”“git --version”，Docker 用户执行“docker exec openclaw node -v”“docker exec openclaw pnpm -v”，核对版本是否符合要求，不符则调整后重验。

第二步 系统环境兼容性验证。保持 OpenClaw 正常运行，同时打开浏览器、办公软件、终端等常用程序，观察是否出现卡顿崩溃报错。若出现问题可能是资源不足或环境冲突，关闭后台程序释放资源后重启验证。另需测试浏览器兼容性，分别用 Chrome、Firefox、Edge 访问 Web 界面操作对话与工具，确保显示与操作正常。

第三步 数据持久化验证。针对 Docker 用户及自定义数据路径的源码、包管理器用户。源码用户在 OpenClaw 中新建对话并上传文档，关闭程序后重启，数据仍可打开编辑即为正常。Docker 用户在容器内创建记录后执行“docker stop openclaw”再“docker start openclaw”，登录后数据仍在说明挂载与持久化生效。若丢失需检查挂载目录并重新配置。

第四步 端口稳定性验证。让程序或容器持续运行 1～2 小时，每 15 分钟访问一次 Web 界面执行简单操作，观察端口监听是否稳定。通过“netstat -ano | findstr 端口号”或“lsof -i:端口号”定期查看状态，若始终正常监听且无端口占用崩溃报错，则端口稳定。

环境兼容性判定标准：
1. 核心依赖版本达标无冲突；
2. 与系统其他常用程序共存无卡顿崩溃；
3. 主流浏览器下均可正常访问操作；
4. 数据可持久化存储读取不丢失；
5. 端口长期稳定监听无冲突。五项全部满足即通过。

长期稳定性建议
对需长期部署高频使用的用户，建议连续运行 24 小时，期间定期检查运行状态、日志与数据完整性。若 24 小时内无崩溃报错且数据无丢失，则说明安装配置完整可满足长期需求。

总体来看，安装后的验证缺一不可。启动验证确认能否跑起来，基础功能验证确认能否用起来，环境兼容性验证确认能否长期稳起来。不同安装方式步骤略有差异，核心逻辑一致，按部就班验证全部通过即可投入使用，未通过则参考常见报错排查后重试，为后续功能使用、插件扩展奠定基础。

# 第9章 从安装到首次运行

OpenClaw 安装完成后，首次启动与初始化是连接安装与实际使用的关键环节，直接影响体验与稳定性。无论源码、包管理器还是 Docker，首次启动都需要完成基础配置、环境适配与功能验证。本章围绕引导配置、后台守护与自启、核心配置说明、初始化失败排查、状态查看与管理五大模块，结合 macOS、Windows、Linux 场景，拆解从首次启动到稳定运行的完整流程。

### 9.1 onboard 引导流程与配置

onboard 是面向首次启动用户的分步引导，核心作用是确保关键配置准确规范。

启动触发分为自动与手动。自动触发为默认推荐，首次启动程序时系统自动检测配置。源码安装用户进入源码目录执行“openclaw gateway”后打开浏览器访问“http://localhost:18789”，会自动跳转到 onboard 页面。包管理器安装用户以管理员身份在终端执行“openclaw start”后访问默认端口即可进入。Docker 安装用户启动容器后访问映射端口，容器内程序自动检测并触发引导。

若未自动触发或需重新初始化，可手动触发。Web 手动触发适合有图形界面用户，打开登录页点击底部“初始化配置”进入引导。命令行手动触发适合服务器环境，源码用户执行“pnpm openclaw onboard --install-daemon”，包管理器用户执行“openclaw onboard --install-daemon”，进入交互式配置。注意若已有配置文件，系统会提示是否覆盖，选择是则清空重来，否则保留原配置，避免误操作。

命令行版 onboard 无需图形界面，适合无桌面的服务器部署，输入路径、API 密钥等关键信息时务必准确，否则初始化会失败。

### 9.2 后台守护进程与自启动设置

OpenClaw 需长期运行，后台守护可脱离终端持续工作，自启动可在设备重启后自动拉起，减少人工维护。结合三大平台说明主流方案。

主流实现有 PM2 进程管理工具、nohup 命令、Windows 服务。PM2 支持守护、自动重启、日志与开机自启，适配源码与包管理器安装，是最推荐的方案。

使用 PM2 先安装 Node.js，终端执行“npm install -g pm2”，国内可配置淘宝镜像加速，安装后用“pm2 -v”验证。源码用户进入源码目录执行“pnpm run build”编译，再执行“pm2 ecosystem”生成配置文件，修改进程名、入口路径、内存限制等，然后“pm2 start ecosystem.config.js”启动，状态为 online 即成功，最后“pm2 save”保存配置、“pm2 startup”设置开机自启，按提示执行对应命令。包管理器用户直接执行“pm2 start $(which openclaw) --name openclaw -- start”启动，再保存并设置自启。常用管理命令包括查看状态、停止、重启、查看日志。

Linux 与 macOS 可用 nohup 实现轻量守护。源码用户编译后执行“nohup pnpm start &”，通过“ps aux | grep pnpm”确认进程，日志写入“nohup.out”。包管理器用户执行“nohup openclaw start &”。停止时需查 PID 执行“kill -9 PID”。nohup 不支持自动重启且重启设备后需手动启动，适合临时或低稳定性要求场景。

Windows 系统推荐 Windows 服务。需管理员身份安装 node-windows： “npm install -g node-windows”，在安装目录创建 service.js 注册脚本，修改入口路径等参数执行注册并启动，通过“services.msc”查看状态为正在运行即成功。服务默认手动启动，需改为自动延迟启动以实现自启。也可通过任务计划程序实现自启。

除 PM2 自启外，各平台原生方案更贴合系统。Linux 使用 systemd 创建服务文件配置描述、启动命令、运行用户，执行重载配置、启动并设置开机自启。macOS 使用 LaunchAgents 创建用户级配置文件，无需 sudo，加载后实现开机自启。Windows 若服务配置受阻，可用任务计划程序创建任务并设置触发器实现启动自启。

### 9.3 首次启动的核心配置项说明

首次启动的核心配置决定运行稳定性与体验，主要通过 onboard 完成，后续可在 Web 系统设置或修改 openclaw.json 调整。分为模型、环境、安全、插件四大类。

模型配置直接影响核心体验，包含模型类型、参数与认证。默认云端模型如 OpenAI、Anthropic，无需本地部署，依赖第三方 API，密钥由用户自行获取填写。新手建议优先云端模型，配置简单响应快；注重隐私或网络不稳的用户可选本地模型，需按设备性能调整上下文长度与线程数。

访问权限默认仅本地访问，仅本机可打开。如需局域网访问，可在 onboard 或后续设置中改为局域网访问并填写本机 IP。公网访问需端口映射与防火墙规则，新手不建议开启以免安全风险。

插件配置为可选。核心插件邮件整理、日程规划、文档处理默认勾选，社区插件默认不勾选，需手动选择，系统会自动下载初始化。新手建议只保留核心插件，避免资源占用导致卡顿。进阶用户可按需勾选，部分插件如邮件插件需补充授权码等基础配置，可暂不配后续在插件设置中补全。
