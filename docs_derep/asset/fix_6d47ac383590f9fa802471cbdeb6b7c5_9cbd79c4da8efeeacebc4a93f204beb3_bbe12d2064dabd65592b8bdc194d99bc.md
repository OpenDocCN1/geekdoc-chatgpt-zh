**3.使用 MCP 服务端日志监控**

日志是定位故障的核心材料。MCP 服务端基于 Python 运行，借助标准 logging 模块记录运行状态与事件。善用日志功能，能追踪服务端行为、调节调试信息粒度，并在生产环境持续监控。下面做几点说明。

1）日志记录器

通过 logging.getLogger 即可拿到根记录器或模块记录器。用这些记录器写下关键信息，是跟踪与排错的常规做法。

[PRE3]

2）日志输出位置

一般而言，服务端的日志由 logging 在自身环境里记录并呈现。

（1）在调试状态下，用 mcp dev 命令启动 stdio 传输的服务端时，标准输出会被 MCP Inspector 捕获，并在 Inspector 界面左侧的日志区实时显示，方便观察。

（2）若直接用 python/uv/uvx 或 mcp run 启动，日志会打印到终端控制台。

（3）采用 HTTP 远程传输启动时，日志同样出现在服务端终端控制台。

（4）如有需要可把日志导向文件或日志系统，默认不会自动落盘，需要手动重定向或配置。

3）将日志发送至客户端

按照 MCP 规范，服务端可把关键日志通过通知推送给客户端，具体走远程 notifications/message 方法，由客户端自行处理，例如在界面展示。这样既能看到工具调用结果，也能了解中间过程。MCP 还允许客户端调用服务端的 logging/setLevel 方法动态调整日志级别。

4）调整日志级别

MCP 遵循 DEBUG、INFO、WARNING、ERROR 等标准级别，默认 INFO，会输出类似“Processing request of type X”的信息。开发期可降到 DEBUG 以获得更细内容；上线后可升到 WARNING 或 ERROR 降低开销。常见做法：

（1）在实例化 FastMCP 时指定 log_level：

（2）直接配置 Python 日志模块：

5）生产环境日志

开发阶段建议打开详细日志，与调试工具配合快速定位。DEBUG 会展示每个请求的入参细节、执行流程等。但在生产环境，过量记录会影响性能并可能泄露敏感信息，通常会提高级别，只保留警告和错误。部署时最好把日志重定向到文件或系统日志服务。

总的来说，养成查日志的习惯能大幅提升 MCP 服务端开发和运维效率。开发期借助 MCP Inspector 和控制台日志，上线后通过文件或系统日志监控运行状态，才能迅速定位并解决问题。

## **基于 SDK 开发客户端**

实际应用中，客户端通常是大模型所在的宿主应用，如 VS Code Copilot、聊天机器人、智能体等。本节介绍客户端开发方式。你可以不使用 SDK，直接通过 HTTP 接口调用服务端，或使用官方 MCP SDK 简化开发。

这里的客户端指完整客户端，可对应官方架构中的 MCP Host。

## **4.1 用 Python 库模拟客户端**

MCP 规范基于 JSON-RPC 2.0 实现客户端与服务端通信，无论是 stdio 还是 HTTP，核心都是传输 JSON 请求和响应。因此掌握原理后，理论上可不依赖 SDK，直接通过 HTTP 或 stdio 与服务端交互。

在学习 SDK 前，本节引导你仅用 Python 基础通信库，通过 HTTP 或 stdio 发送符合 MCP 规范的 JSON-RPC 2.0 消息，调用服务端开放的功能，以工具调用为例演示。

这部分不强制学习，但能加深对交互机制的理解，更好地使用 SDK。
