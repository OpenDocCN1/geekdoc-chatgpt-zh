[PRE0]

PromptNode 用来描述链路里的一个环节，它会记录节点名称、使用的 Prompt 模板以及可以衔接的下一个节点。PromptChain 则承担整个链路的调度与运行职责，凭借 context 字典来保存运行时的中间状态，让后面的节点能够调用前面节点产生的结果。execute 方法会锁定入口节点，按顺序逐个触发各节点的 Prompt 调用，直至链路走完。落地时通常还要补上异常处理、分支判断和并行调度等能力。

### 2.1.3 上下文管理：让对话不掉线

在多 Agent 协作里，上下文管理往往是最棘手的难题。模型上下文窗口虽在持续放大会，但容量终究有限。一旦 Agent 之间展开长时间的复杂交流，怎么在有限窗口里留住核心信息、剔除冗余，直接决定协同的质量和效率。

管理窗口主要有三大痛点：一是溢出风险，对话历史和参考文档一旦超出上限，就得截断或压缩；二是信息密度，窗口里要优先塞进对当前任务最有价值的内容；三是跨 Agent 传递，任务交接时必须高效带上必要的上下文。

图2-3展示了几种常用的上下文窗口管理策略。

[PRE1]

滑动窗口是最朴素的做法，只保留最近 N 轮对话，早期的记录直接抛弃，门槛低却容易丢掉关键的早期信息。摘要压缩则是让大模型把历史对话浓缩成简短摘要，再与最新对话拼接，能在有限空间里保留更多语义，但压缩也会带来细节损失。检索增强则把全部历史向量化保存，依据当前输入召回相关片段，精准度高但系统负担更重。Agent 之间交接上下文时，一般都要先对原始内容做提炼，挑出关键信息再交给下一个 Agent。

- 压缩时要先保住关键要素，重点保留任务目标、核心决策点、实体资料和错误日志。
- 各 Agent 对上下文的粒度需求不同，负责规划的 Agent 需要全景视角，负责执行的 Agent 只要局部片段即可。
- 要定期检查上下文健康度，防止“上下文中毒”让错误信息污染后续推理。

### 提示2-1 上下文长度与效率的权衡思路

实际落地时，上下文管理要因任务而异。像法律文本分析这类对历史细节引用要求高的场景，应优先保证信息完整；创意类生成则可以更激进地压缩历史，为新内容腾出空间。不少前沿方案会采用混合做法：近期对话完整保留，早期历史做摘要压缩，再配合向量检索实现按需召回。

### 2.1.4 角色塑造：用 System Prompt 定义 Agent

System Prompt 是塑造 Agent 角色与行为的底层机制。通过精细设计，可以为 Agent 赋予特定的专业身份、行动准则和协作方式，让它在多 Agent 系统中各司其职。一个合格的 System Prompt 通常涵盖四点：角色身份，说明 Agent 是谁、具备何种专业背景；能力边界，界定能做什么、不能碰什么；行为规范，规定回复方式和语气风格；协作协议，明确与其它 Agent 或用户的交互方式。

在多 Agent 协同场景里，各 Agent 的 System Prompt 需要协同设计，确保职责清晰、边界分明、配合顺畅。下面给出两个典型角色定义示例。

### Prompt 2-1 分析师 Agent 的 System Prompt 示例

[PRE2]

这份 Prompt 沿着四个维度展开：角色定位厘清专业身份与工作风格；能力范围划定职责边界，既点明擅长领域也说明不负责的部分；输出规范保障分析结果的质量与一致性；协作方式规定与其他 Agent 的交互模式。这种结构化定义能让 Agent 在协同中快速定位自身角色。

### Prompt 2-2 研究员 Agent 的 System Prompt 示例

> 你是一位专业研究员，负责信息搜集和知识整合。

【角色定位】

- 专业领域：文献检索、信息整合、知识提炼

- 工作风格：全面细致、追根溯源、客观中立

【能力范围】

- 擅长：多源信息搜集、文献综述、事实核查

- 不涉及：主观评价、预测判断、决策建议

【输出规范】

- 标注所有信息来源

- 区分事实陈述与推测内容

- 识别并报告信息冲突

【协作方式】

- 响应其他 Agent 的信息查询请求

- 主动补充相关背景知识

- 发现关键信息时通知规划 Agent

研究员 Agent 与分析师 Agent 的侧重点不同，前者聚焦信息搜集与知识整合，后者侧重数据分析。它更强调来源标注、事实与推测的区分。协作上呈现响应式特征，主要接听其他 Agent 的查询，同时会主动补全背景并把关键发现上报给规划 Agent。对比两份 Prompt 可见，不同角色在专业定位、输出要求和协作方式上差异明显，这种差异化正是专业分工有效运行的基础。

实际设计时，所有 Agent 的 System Prompt 应构成统一整体。规划 Agent 需要清楚各执行 Agent 的能力边界，才能合理派活；执行 Agent 之间的协作协议要相互契合，保障信息流转顺畅。同时，System Prompt 要随运行效果持续迭代，通过评估响应质量和协作效率，逐步细化角色定义。

## 2.2 Agent 协同的四种主流模式

### 【学习目标】

1) 弄懂顺序协同如何运作以及适合什么场景
2) 掌握并行协同的实现方式与同步机制
3) 学会搭建 Manager-Worker 分层协同架构
4) 了解竞争协同的方案评选机制

任务特性决定了协同模式的选择。下面系统介绍四种主流 Agent 协同模式及适用场景。

### 2.2.1 顺序协同：像接力一样传任务

顺序协同是最直观的协作形式，核心是把复杂任务拆成多个阶段，每个阶段由专属 Agent 负责，前一个环节的输出作为后一个环节的输入，像接力赛一样传递。这种方式特别适合存在明确先后依赖的流水线任务，比如信息收集→数据分析→报告撰写。

优点是职责分明、排查方便、追溯容易。每个 Agent 只需盯住自己的环节，不用管其它环节细节。出现问题也能迅速锁定责任 Agent。缺点也很明显：总耗时等于各环节之和，无法并行提速；任一环节失败就会拖垮全流程；后续 Agent 看不到全貌，容易做出次优判断。

### 2.2.2 并行协同：多 Agent 同步开工

并行协同允许多个 Agent 同时推进各自的子任务，最后再汇总整合。这样能明显压缩复杂任务的总耗时，尤其适合可拆分为相互独立的子问题。比如做全面市场分析时，可让不同 Agent 分别负责竞品分析、用户调研、技术趋势和政策环境的研究，最后合成完整报告。

并行协同的核心难点是结果同步与融合。需要协调机制等待所有 Agent 完成并把输出整合成一致结果。同时要考虑容错，当某个 Agent 失败或超时时，系统需决定是否重试、采用降级方案，还是在部分缺失的情况下继续整合。

### 2.2.3 层次协同：Manager-Worker 分层管理

层次协同更具组织性，通过引入管理层来统筹多个执行 Agent。Manager Agent 负责理解整体任务、制定计划、分配子任务并监督进度；Worker Agent 专注执行具体子任务并向 Manager 汇报。这种结构类似人类组织的层级管理，适合需要全局规划和精细控制的复杂任务。

该模式优势在于智能调度。Manager 可根据实际情况动态调整计划，某个 Worker 遇到困难时可重新分配任务或调其他 Worker 支援。同时天然支持扩展，新增能力只需加入对应的 Worker 即可。
