##### 多助手的价值

好处一：记忆隔离
工作助手的 MEMORY.md 与生活助手的 MEMORY.md 互不干扰。工作侧感知不到晚间私人活动，生活侧也看不到白天项目进展。

好处二：权限隔离
工作侧能访问公司邮箱与内部系统，生活侧无权；反过来也如此。权限分开更安全。

好处三：成本分摊
工作侧可配 Claude Sonnet 这类偏贵的模型，生活侧用 DeepSeek 这类便宜的模型，按用途分配预算。

#### 6.3.2 方案二：子助手临时协作

适用场景：主助手收到复杂任务，需要多线并行推进。

##### 子助手是什么
子助手是主助手临时派出的执行单元，完成指定任务后交回结果并自行消失。

典型例子：
你对主助手说：“帮我准备明天的会议材料。”
主助手拆解为三件事：
1. 从邮件里提取会议议程
2. 从上次纪要里提取未完成事项
3. 从项目文档里提取最新进展
串行太慢，主助手会同时派三个子助手分头处理。

##### 子助手的工作机制
OpenClaw 内部通过 sessions_spawn 命令创建子助手，无需人工触发，主助手会自行判断是否需要并行。

子助手的特征：
- 拥有独立的上下文与 token 消耗
- 不继承主会话的工具权限，更安全
- 可单独指定模型，主助手用贵的，子助手用便宜的
- 任务结束自动销毁

#### 6.3.3 省钱技巧：主助手与子助手降本

官方文档明确指出子助手可单独设置模型。

实操思路：
- 主助手使用 Claude、GPT 这类强模型负责推理与调度
- 子助手使用 DeepSeek、通义千问这类模型负责搜索、整理、重复劳动
既保证整体质量，又能压住成本。

##### 多助手 VS 子助手 怎么选

表 6-1 梳理了两种模式的差异。

表 6-1 多 agent 与子 agent 对比

| 维度 | 多 agent | 子 agent |
| :--- | :--- | :--- |
| 用途 | 长期分工 | 临时并行 |

- 需要长期角色分工如工作助手、生活助手、学习助手时，用多 agent
- 只是偶尔需要并行处理复杂任务，交给子 agent 自动处理即可

#### 6.3.4 实用建议

##### 建议一：别一开始就上多助手
刚上手 OpenClaw 时，一只“龙虾”足够。等出现工作生活串台或项目混淆的问题后再考虑多 agent。

##### 建议二：多助手要职责清晰
每个助手的分工必须明确，不要模糊。“工作助手管所有工作事务，生活助手管所有生活事务”，这种划分最简单有效。

##### 建议三：子助手交给 OpenClaw 自行决定
不要手动干预子助手的创建，把复杂任务交给主助手，由它自行判断是否派“小弟”。

##### 建议四：为不同助手配不同模型
重要任务配贵模型，琐碎任务配便宜模型，整体成本自然下降。

多“龙虾”协作的核心就两点：长期分工用多 agent，临时并行用子 agent。理解这一点，就能让几只“龙虾”有序干活，而不是乱成一团。

### 6.4 担心它乱动重要文件，如何给它设安全围栏？

OpenClaw 能读写文件、执行命令、操作浏览器，能力越强风险越高。

## 第六章 “龙虾”用熟了之后如何玩得更好

- exec – 执行系统命令
- bash – 运行 bash 脚本
- apply_patch – 应用代码补丁

这三项最容易造成破坏。禁止后，OpenClaw 仍能读写文件、搜索、调用 API，却无法直接操作系统。

#### 6.4.2 第二道围栏：Sandbox 沙箱

工具黑名单只管能否调用，调用后能访问哪些文件、能否跳出工作区，就靠 Sandbox 控制。

##### 什么是 Sandbox
Sandbox 是一个隔离环境，限制 OpenClaw 只能在指定目录活动。

启用 Sandbox：
[PRE4]
scope 设为 “workspace” 表示只能访问工作区目录，无法触及工作区外文件。

##### Sandbox 的局限

官方明确提醒：workspace 并非硬沙箱。它只是默认工作目录，不是安全边界。

即便开启 Sandbox，若工具权限放开且使用绝对路径，仍可能访问到工作区外。

真正隔离需要组合使用：
- 工具白名单/黑名单
- Sandbox scope 限制
- 不同 agent 拆到不同系统用户，甚至不同主机

#### 6.4.3 第三道围栏：拆分信任边界

当场景涉及不同部门、不同人、不同风险等级共用 OpenClaw 时，应该拆分 Gateway。

官方说明：OpenClaw 不适合让多个互不信任的人共享同一个高权限 Agent/Gateway。

正确做法：
- 个人用途：一个 Gateway，高权限，自行管理
- 团队用途：每个部门或风险等级一个 Gateway
- 公共服务：低权限、只读、沙箱、独立主机

举例：个人 agent 完整权限，部门 agent 可读写本部门文件但不能执行命令，公开 Bot 仅读和搜索。这样即使公开 Bot 被攻破，也影响不到个人数据。

#### 6.4.6 实用建议

**建议一：默认 deny 高危工具**
除非必须，否则把 exec、bash、apply_patch 加入 deny 列表。大多数日常任务不需要它们。

**建议二：测试环境用严格权限**
测试 agent 先只给 read 权限，功能验证后再放开 write。宁可麻烦，也别把生产数据改坏。

**建议三：每月跑一次 audit**
配置会随使用慢慢变化，定期审计能早发现风险点。

**建议四：重要数据提前备份**
再严的围栏也不保证 100% 安全，重要数据定期备份到 OpenClaw 访问不到的位置，是最后保险。

**建议五：别共享高权限 agent**
多人使用时，每人一个 agent 各自管理。不要图方便共用一个高权限 agent，风险太大。

安全围栏不是一次性工作，而是持续维护。初期权限严一点，用熟后再按需逐步放开。谨慎比事后补救更划算。
