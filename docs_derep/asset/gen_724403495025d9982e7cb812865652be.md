Context 像一个资源容器，统一托管 Stream、Event、设备显存等所有对象在昇腾上的生命周期。不同 Context 下的 Stream 和 Event 完全隔离，彼此无法同步等待。
Context 有两种形态：① 默认 Context，调用 aclrtSetDevice 绑定计算设备时，系统会自动隐式生成一个，设备与默认 Context 一一对应，且无法通过 aclrtDestroyContext 主动释放。② 显式 Context，推荐用法，在进程或线程里手动调用 aclrtCreateContext 创建。

Stream 用来保证异步任务的执行顺序，让 Device 上的操作严格按主机代码的调用顺序推进。基于 Stream 的 Kernel 执行与数据搬运，可以实现 Host 计算、Host 与 Device 之间搬运、Device 内部计算并行。
Stream 也有两种：① 默认 Stream，aclrtSetDevice 绑定设备时自动隐式产生，一个设备对应一个默认 Stream，无法通过 aclrtDestroyStream 释放。② 显式 Stream，推荐用法，调用 aclrtCreateStream 手动创建。

Event 用于在同一个设备上的多个 Stream 之间做任务同步。比如 Stream2 依赖 Stream1，先在 Stream1 末尾插入一个 Event，Stream2 启动前等待该 Event 完成即可。

AIPP 即 AI 预处理，在 AI Core 上完成图像格式转换、归一化、抠图等操作。AIPP 只有静态和动态两种模式，二选一不可兼得。① 静态 AIPP，模型转换时就固定参数，参数固化在离线模型 *.om 中，推理时始终使用同一套预处理，多 Batch 共用同一参数，无法改动。② 动态 AIPP，模型转换时设为动态，每次推理前可动态设定参数，模型执行时可使用不同参数，多 Batch 也可各自不同。

动态 Batch/动态分辨率 用于输入规格不固定的场景。① 动态 Batch，推理时 Batch Size 可变。② 动态分辨率，推理时单张图片的 H*W 可变。

动态维度 ND 格式 用于 Transformer 等维度不确定的网络，支持任意维度设置，当前上限 N≤4。

通道 在 RGB 模式下指 R、G、B 三个分量共同组成完整图像；在 HSV 色系下指色调 H、饱和度 S、亮度 V 三个分量。

标准形态 指 Device 以 EP 角色通过 PCIe 挂载在 x86、ARM 等主板上工作，Device 侧 CPU 资源只能由 Host 调用，推理程序跑在 Host，Device 只提供神经网络计算能力。

EP 模式 指昇腾 AI 处理器 PCIe 工作在从模式。

RC 模式 指昇腾 AI 处理器 PCIe 工作在主模式，可扩展外设。

### 1. Device、Context、Stream 关系
下面介绍 AscendCL 框架中 Device、Context、Stream 的职责与关联，并简述 Task/Kernel。

#### 1）Device
Device 用于指名计算设备。
Device 的生命周期始于第一次调用 aclrtSetDevice。每次调用该接口引用计数加 1，调用 aclrtResetDevice 引用计数减 1，计数归零后本进程中该设备的资源不可用。

[PRE0]

图 14.7.2

#### 2）Context
一个 Context 必然归属唯一的 Device。
Context 分隐式与显式。隐式即默认 Context，从 aclrtSetDevice 调用开始，到 aclrtResetDevice 使引用计数归零为止。默认 Context 只创建一次，反复对同一设备调用 aclrtSetDevice 只会增加引用计数。
显式 Context 从 aclrtCreateContext 调用开始，到 aclrtDestroyContext 调用结束。若一个进程内创建多个 Context，因 Stream 数量有限，建议用 aclrtSetCurrentContext 明确当前线程使用的 Context，提升可维护性。
进程内的 Context 是共享的，可通过 aclrtSetCurrentContext 切换。

#### 3）Stream
Stream 是 Device 上的执行流，同一 Stream 内任务严格有序。
Stream 也有隐式与显式。每個 Context 自带一个默认 Stream，隐式 Stream 的生命周期与所属 Context 一致。
用户可显式创建 Stream，生命周期从 aclrtCreateStream 开始到 aclrtDestroyStream 结束。若所属 Context 被销毁，Stream 虽未销毁也不可再用。

#### 4）Task/Kernel
Task/Kernel 是 Device 上实际承担任务执行的实体。

### 2. 线程、Context、Stream 关系
用户线程必定绑定一个 Context，Device 资源的使用与调度都基于 Context。线程内当前只有一个 Context 在生效，已关联本线程使用的 Device，可通过 aclrtSetCurrentContext 快速切换设备。
线程内可创建多个 Stream，不同 Stream 的计算可并行。多线程场景推荐每个线程持有一个 Stream，线程间 Stream 在 Device 上互相独立，每个 Stream 内部任务按下发顺序执行。
线程调度受操作系统控制，多 Stream 在 Device 侧的调度由设备调度组件完成。

### 3. 进程内多线程间 Context 切换
进程内 Context 工作流如图 14.7.3。
- 一个进程可创建多个 Context，但线程同一时刻只能使用一个。
- 线程中创建多个 Context 时，默认使用最后一次创建的那个。
- 进程内多个 Context 可通过 aclrtSetCurrentContext 指定当前使用。

### 4. 默认 Context 和默认 Stream
操作下发到 Device 前必须有 Context 和 Stream，可显式创建也可隐式创建，隐式即默认。
默认 Context 不允许调用 aclrtGetCurrentContext、aclrtSetCurrentContext，也不允许调用 aclrtDestroyContext。
默认 Stream 作为接口参数时直接传 NULL。
默认 Context、默认 Stream 适合单设备简单应用，多线程应用建议全部显式创建 Context 与 Stream。

### 5. 多线程、多 Stream 性能考虑
线程调度取决于操作系统，Stream 下发任务后由 Device 调度单元调度。若进程内多 Stream 在 Device 上出现资源争抢，性能可能低于单 Stream。
昇腾 AI 处理器内部有 AI Core、AI CPU、Vector Core 等不同执行部件，创建多 Stream 时建议按算子执行引擎划分。
单线程多 Stream 与多线程多 Stream 的性能优劣取决于应用逻辑，通常前者略优，因其少了线程调度开销。

## 14.7.3 基本开发流程
通过 AscendCL 接口可开发模型推理、媒体数据处理、单算子调用等应用，功能可独立也可组合。图 14.7.4 给出了典型接口调用流程。若模型对输入宽高有要求，需先对源图做裁剪等媒体处理；模型推理前需先加载，推理后需卸载；推理结果还可做后处理如找最大置信度类别。

[PRE2]

基本流程如下：
1. AscendCL 初始化：调用 aclInit。
2. 运行管理资源申请：申请 Device、Context、Stream 等资源。
3. 具体计算：分为模型推理、单算子调用、媒体数据处理。
    - 模型推理
        - 模型加载：推理前先加载适配昇腾的离线模型。
        - 可选媒体数据处理：JPEG 编解码、视频解码、抠图、缩放、格式转换等。
        - 模型执行：实现分类、目标识别等推理。
        - 可选数据后处理：按需处理推理结果，如写文件、找最大置信度类别。
        - 模型卸载：调用 aclmdlUnload。
    - 算子调用
        - 若应用除模型推理外还需 BLAS 等数学运算或数据类型转换，可直接通过 AscendCL 加载并执行单个算子，免去模型构建训练，更加轻量。
        - 自定义算子也可用单算子调用方式验证功能。
4. 运行管理资源释放：处理结束后依次释放资源。
5. AscendCL 去初始化：调用 aclFinalize。

## 小结与思考
- 高度抽象与兼容性：AscendCL 以统一 API 框架简化算子编译、加载与执行，减少 API 数量，降低开发复杂度，并保持向后兼容，旧版本编译的程序可在新版本上运行。
- 多场景应用：支持直接开发分类、目标识别等应用，供第三方框架调用，也可封装成第三方库提供运行与资源管理能力。
- 资源管理与开发流程：提供 Device、Context、Stream 的概念与关系及显式创建管理方法。基本流程涵盖初始化、资源申请、推理或算子调用、数据处理、资源释放与去初始化。
