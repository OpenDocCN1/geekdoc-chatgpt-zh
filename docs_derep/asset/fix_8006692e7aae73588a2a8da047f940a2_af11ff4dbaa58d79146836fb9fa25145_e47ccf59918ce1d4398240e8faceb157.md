RAG 知识库的即时同步与弹性治理

当业务对数据新鲜度要求很高时，可把消息中间件接入变更链路。以 Kafka、RabbitMQ 为代表的组件能够持续监听源系统产生的写入、修改或移除事件，捕捉到信号后即刻派发任务，让知识库完成近乎同步的刷新。

为了压缩更新开销，可借鉴增量式刷新思路。参考 3.6.3 节介绍的 LangChain 缓存嵌入做法，只针对变动范围内的记录重新生成向量，而非对整套索引进行重建。局部更新能明显减少计算资源消耗，提升整体效率。

性能优化往往是多维协同的结果。将多条写入或移除请求合并为批量提交，可降低对存储层的频繁打扰，提升吞吐并减轻系统负载；nlist、nprobe 等检索参数可依据实际负载动态微调，在查询时延与召回质量之间取得平衡，改善使用感受。对访问热度较高的对象启用内存层与高速缓存，能削减后端查询压力，缩短响应时间。这些手段共同确保服务在规模扩大后依然保持高效与稳定。

数据治理上建议采用分层思路。把资料划分为长期稳定、改动频率低的核心层，和随业务快速演化的动态层。日常的写入、更新与删除主要聚焦在动态层，核心层尽量保持只读或低频维护，分层后整体处理开销会明显下降。

为了保障稳健性，更新流程应引入版本化管理。每一次变更都保留历史快照，出现问题时能够迅速回滚。配合定期多份备份，可有效抵御硬件故障或人为误操作带来的丢失风险，保证系统的安全与连续可用。

#### 4.8.2 Milvus中向量的增删改操作
在 RAG 场景里，一旦上游原始资料发生变化，向量嵌入、元数据以及检索索引必须保持一致。Insert 主要用于扩充知识规模、修正历史错误、优化已有条目或响应新的业务需求。

from pymilvus import MilvusClient

import numpy as np

###### 连接已有Milvus（使用本地SQLite模式）

db_path = "./test_vector.db"

client = MilvusClient(db_path)

###### 集合名称（之前已创建的集合）

collection_name = "my_collection"

data_insert = [

    {"id": 100001, "vector": np.random.random(128).astype("float32").tolist()},

    {"id": 100002, "vector": np.random.random(128).astype("float32").tolist()}

]

res = client.insert(collection_name=collection_name, data=data_insert)
