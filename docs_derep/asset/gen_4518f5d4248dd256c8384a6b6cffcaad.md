归根结底，RAG 就是给大模型外接知识管道的增强手段。站在全局视角看，LLM 在语言理解与推理上很强，却受困于知识闭环，只能调用训练截止前的公开信息，这种“知识封闭性”让它在垂直领域与时效性场景中不够实用。要让模型能实时触达私有数据、按需注入背景信息，就必须搭建一条把高质量外部知识导入推理链路的信息通道，这正是 RAG 架构出现的初衷。整体搭建思路见图 8.6。

[PRE0]

图 8.6 概括了 RAG 的核心三步走。

- 索引（Index）：这是离线执行的预处理环节。先对原始素材做清洗与抽取，把 PDF、HTML、Word 等不同格式统一转成标准化纯文本；再按模型上下文限制切成更小可控的片段，即分块；随后用嵌入模型把片段映射为向量表示；最后把文本块与其向量以键值对形式存入索引，以支持高效可扩展的检索。

- 检索（Retrieval）：用户问题进来后，先由编码模型转为语义向量，再在向量库中做相似度搜索，取出前 k 个最接近的数据对象作为上下文。

- 生成（Generation）：把原问题与检索到的补充上下文填入提示模板，形成增强提示，再送入大语言模型生成最终回复。

手写这套链路代码量不小，LangChain 将其封装成简洁的接口。但要注意，照搬标准三步走在复杂任务里往往不够理想，优化是刚需。图 8.7 展示了 LangChain 已封装的高阶 RAG 实现方案。

##### 1. 翻译查询
自然语言提问常语义模糊、表达随意，直接检索命中率低。LangChain 在入口提供了问题改写机制，支持多查询生成等价表述以提升召回、RAG 融合把不同表述的检索结果聚合、分解把复杂复合问题拆成子问题等策略，核心是提升查询在语义层面与知识库的对齐度，让下游检索更精准。

##### 2. 路由
路由模块依据问题类型或语义特征挑选最合适的检索路径与提示模板，主要包括：
- 逻辑路由：基于问题结构决定调用哪个数据库或哪种查询方式。
- 语义路由：将问题嵌入向量空间，按语义相似度匹配合适的 Prompt 结构。

##### 3. 数据库的支持
在 LangChain 的高级构建流程中，底层可同时接入图数据库、关系型数据库和向量数据库。

[PRE1]

##### 4. 构建查询
面对自然语言问题，系统会先按目标库类型生成结构化指令。
- 关系型数据库：通过 Text-to-SQL 把自然语言转为 SQL 查询，并结合向量检索做增强。
- 图数据库：采用 Text-to-Cypher 生成如 Cypher 的图查询语言，从知识图谱中抓取语义关联。
- 向量数据库：使用 Self-query retriever 自动从问题中抽取意图与元数据过滤条件，生成向量检索请求。

##### 5. 索引
检索质量取决于索引质量。LangChain 在索引构建中引入了以下机制。
- 块优化：按字符、段落、语义断点切分原始文档，提升嵌入效果。
- 多表示索引：如 Parent + Summary + Dense 向量结构，使召回更全面。
- 专业嵌入：结合 Fine-tuning 或 ColBERT 等模型，生成更精准的领域向量。
- 层级索引：如 RAPTOR，构建跨层级、多抽象层的文档树，实现摘要层级的高效检索。

##### 6. 检索
路由确定后进入实际信息检索，具体包括：
- 排名：对候选文档做语义打分排序，常用 Re-Rank、RankGPT、RAG-Fusion 等。
- 细化：首轮结果不理想时可执行再检索或检索压缩。
- 主动检索：依据首轮回答质量自动判断是否重写问题并重新检索。

##### 7. 生成
检索到文档后，大模型结合用户原始问题与增强上下文生成回答。LangChain 在生成阶段引入 Self-RAG / RRR 优化，让模型主动校验问题理解是否正确、信息是否充分，不足时触发再检索与反馈闭环。
