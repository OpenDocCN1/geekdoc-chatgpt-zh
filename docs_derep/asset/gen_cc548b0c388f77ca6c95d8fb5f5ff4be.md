# React 性能：先找根因再动手优化

做应用性能优化时，书里主张一套可循环的工作方式：先写功能 → 运行中暴露性能问题 → 梳理问题表现并追踪到根因 → 针对性修复 → 回到继续开发。遇到问题第一步不是急着改代码，而是先判断它在用户侧呈现为什么样貌，再去定位背后的原因。

**慢的表象怎么找**
首次打开页面很慢、页面跳转拖沓，这类情况适合用浏览器开发者工具来拆解瓶颈，是连接建立慢、服务端响应等待久、资源下载慢，还是下载队列被卡住。Chrome DevTools 里的 Lighthouse 特别适合做这类诊断。
局部数据拉取慢、表单提交卡住，往往指向后端处理能力不足。
如果用户需要频繁刷新页面才能看到正确内容，那更像是交互设计或体验流程上的问题。

**卡的表象怎么找**
表单控件操作发顿、鼠标键盘交互的视觉反馈延迟，通常是因为页面里执行了耗时的同步 JavaScript，把渲染流程堵住了。
纵向滚动时画面不连贯，多见于 DOM 节点数量过高。
页面长时间无响应，第一反应应排查 JavaScript 是否进入了死循环。

这些判断方法并不专属于 React。从根因定位的过程就能看出，React 应用的性能问题未必出现在 React 本身，也未必需要靠 React 的手段来解。

确认问题确实落在了 React 范围内时，就可以用 React 浏览器插件 React Developer Tools 进一步深挖。插件自带的 Profiler 性能分析面板，如图 11-2 所示。上手前建议在设置里打开“记录每个组件渲染的原因”，这样后续分析会更清晰。

## 11.2 React 组件的性能优化

与 React 强相关的性能损耗，通常可以从下面几个方向入手解决。

### 11.2.1 useMemo：缓存计算，减少重复开销

当应用出现卡顿，通过 Profiler 判断问题是否源自 React 内部。如果发现某个组件的渲染耗时明显高于其他组件，就要检查它内部是否藏着繁重的计算。此时可以用“用空间换时间”的思路，把结果缓存起来。React 提供的 useMemo Hook 就是用来在渲染期间做缓存的。

这里要先理清记忆化 Memoization 的概念：对复杂函数的计算结果做缓存，避免重复运算，省时间、提速度。useMemo 的命名就源自这个思路。

useMemo 接收两个参数：一个工厂函数，和一个依赖项数组。它会返回记忆化的计算值。只有当依赖数组里的值发生变化时，才会重新执行工厂函数并更新缓存。

典型场景是把成本高的计算结果存下来，减少重复。现代 JavaScript 引擎执行效率很高，纯计算成为瓶颈的情况不多，除非涉及大量循环或深层递归。比如用递归实现斐波那契数列，从 state 读取 num 转成整数 n 后计算第 n 项：

[PRE2]

state num 初始是字符串 '0'，挂载时 useMemo 会执行一次 fibonacci(0) 并缓存 0。之后通过输入框把 num 改成 '40'，与上一次不同，useMemo 重新计算并返回 102334155。若之后其他 state 变化但 num 仍是 '40'，useMemo 直接返回缓存值，避免重复消耗。

任何时候 useMemo 只能当作性能手段，不能用来承载业务逻辑。它的接口和 useEffect 很像，尤其是依赖数组，但两者本质不同：执行时机就不一样，useMemo 在渲染阶段执行，useEffect 在提交阶段执行。别把它们互相替代。

### 11.2.2 React.memo：阻断无谓的重渲染

Profli er 有时显示不是单点耗时高，而是整棵子组件树都在花时间。这通常是因为出现了大量不必要的渲染或重复渲染。下面先看触发规律。

组件因自身 state 变化而重渲染时，其子组件和后代都会跟着重渲染，即使 props 并未改变。父组件、祖先组件以及同级分支则不会受影响，这是 React 的设计保证。若这个规律被破坏，就要检查是否不小心改动了其他组件的 state 或 context。如图 11-3 所示。

问题在于：能不能只让当前组件更新，同时阻止后代跟着更新？React 给出的优化手段是纯组件 Pure Component。它的规则很简单：当 props 和 state 都没变时，直接跳过本次渲染，沿用上次结果。注意和 useMemo 一样，纯组件也只是性能优化手段，不能依赖它实现业务逻辑。

这是一个高阶组件，接收原组件，返回一个新组件。每次渲染时纯组件会记录传入的 props，下次渲染时做浅比较，相等就跳过原组件的渲染。要注意，原组件内部若涉及 state 或 context 操作，即使 props 不变仍可能被迫重渲染。

### 11.2.4 区分低优先级的更新：startTransition 和 useTransition

前端里的交互都算关键交互吗？重要性是否相同？浏览器资源受限，JavaScript 单线程，同一时间可做的事有限。如果能人为区分优先级，就能为更关键的操作保留资源，比如文字输入、列表滚动。

如 9.3 节所述，Fiber 协调引擎把 React 的渲染拆成大量可中断、可恢复的细小工作单元，这为性能优化提供了空间。React 18 引入了 transition 概念，用于标记那些非关键的 state 更新。
