## **6.3 智能体框架接入 MCP 服务端的实操**

本节深入拆解如何把主流的智能体开发框架和 MCP 服务端结合起来，通过标准化协议去调用服务端提供的工具。随着可复用的 MCP 服务端越来越多，智能体的开发门槛会明显下降，效率会大幅提升，同时保持模块间松耦合、协作高效，系统的可维护性和可扩展性也随之增强。

智能体框架各自的抽象层级不同，并不能直接使用 list_tools 和 call_tool 去发现和使用 MCP 功能。好在现在大部分知名框架都已提供 MCP 适配器，把 MCP 服务端的工具接入框架变得非常顺滑，对智能体开发至关重要。

下面先以 LangGraph 为例，演示如何在框架内部快速搭建一个 ReAct 风格的 MCP 智能体。

工作流的大致流程是：

（1）借助大模型的函数调用能力或 ReAct 范式，引导模型判断是否需要外部工具，并确定调用所需的参数，节点为 agent。

（2）一旦判定需要工具，就用推理出的参数去调用工具并拿到结果，节点为 tool。

（3）把工具结果和之前的对话历史重新喂给大模型，由模型决定下一步动作，直至模型认为无需再调用工具，流程结束，节点为 END。

在示例代码中，对 MCP 服务端工具的使用方式和“1.快速创建 ReAct 范式的智能体”完全一致，只是更清晰地展示了工作流内部的工具使用细节。

（1）先连接 MCP 服务端，然后调用 get_tools 方法加载并转换所有工具，得到 mcp_tools。

（2）agent 节点：即 agent 函数，主要负责调用大模型。在调用前会为模型绑定一系列工具 bind_tools，实质是向模型注入函数调用信息，所以这里的模型需要支持函数调用，随后指引模型完成工具推理。

（3）tool 节点：利用 LangGraph 预置的 ToolNode 类型，快速实现对 MCP 服务端工具的调用。

（4）定义节点间的边，也就是任务流向。起始节点是 agent 节点，从 agent 到 tool 的边是一个条件边。

[PRE13]

意思是对 agent 节点的输出做条件判断，实际是检查返回的消息里是否带有工具调用的标记。判断逻辑由 LangGraph 提供的 tools_condition 函数实现。若返回 “tools”，说明需要调用工具，下一步进入 tool 节点；若返回 “END”，说明无需调用，流程在此终止。

从 tool 节点返回 agent 节点是必经路径，任何一次工具调用完成后都必须回到 agent 节点，以便重新发起推理并决定后续步骤。

通过适配器，MCP 服务端的工具能迅速嵌入 LangGraph 工作流，配合第三方丰富的 MCP 服务端，智能体的构建速度会显著提升。

## **6.4 实战：基于 MCP 集成架构的多文档 Agentic RAG 系统**

RAG 是一种借助外部知识为大模型补充上下文的应用范式。从这个角度看，RAG 与 MCP 有相似之处：都是给大模型补上下文以增强能力。MCP 更偏向提供外部工具，RAG 更偏向注入参考知识。类比考试，MCP 给学生的是计算器，RAG 给的是书。

两者侧重点不同，MCP 强调集成标准，RAG 强调完整应用实现，并不冲突，完全可以用 MCP 的方式来集成一个 RAG 应用。

本章用示例探讨如何以 MCP 形式实现 Agentic RAG，是一种有趣的融合尝试。

### **6.4.1 整体架构设计**

传统 RAG 通常只局限于查询单一数据源并做单次检索生成。在复杂企业场景下显然不够：一类查询往往需要跨多个文档、多个数据源，甚至多种索引类型综合检索。Agentic RAG 通过引入智能体，在一次任务中形成 RAG 循环，解决了这个问题。智能体可以规划查询计划和步骤，调用多个 RAG 管道完成多次检索，基于中间结果动态调整策略，最终给出答案。

（1）索引阶段。对所需数据源进行解析、切分并创建索引，常见的是向量索引，根据场景也可采用知识图谱索引、关键词索引等。

（2）生成阶段。在已建索引基础上搭建 RAG 管道和智能体，对外开放使用。

在基于 MCP 的集成架构下，无论是 SSE 传输还是 stdio 传输，都是客户端/服务端模式。编码前必须先设计好 MCP 服务端与客户端的分工与交互，例如：

（1）MCP 服务端提供的工具，包括功能边界、输入输出。

（2）服务粒度既不能过大导致模块化丧失，也不能过小导致复杂化。

（3）缓存与持久化设计，RAG 应用是数据密集型应用。

（4）客户端智能体设计，包括模型、 workflow、与 MCP 服务端的交互方式。

（5）多用户环境下，需考虑文档与索引的隔离。
