在既往介绍的两种生成思路之外，还可以借助网络搜索引擎来挖掘候选实体。日常使用搜索引擎时，人们往往把实体的指称直接作为查询词，依据排序后的结果跳转到想要的页面。这一过程本身就蕴含了先验信号：可以把系统难以直接识别的指称丢给搜索引擎，由返回的页面来辅助判断该指称是否能对应出实体。做法更进一步时，甚至能把包含指称的整段文本直接检索，再按规则筛选结果，比如只保留百度百科、维基百科等百科类页面。若检索结果中出现了知识库里的实体，就将其收录为候选。相较于依赖实体名称词典的方式，搜索引擎驱动的生成具备冷启动友好、容错率更高、候选更丰富的特点。

### 3. 候选实体排序
完成候选生成后，通常会得到一个包含多个实体的集合。研究[4]指出，在常见语料里候选集合的平均规模约为12.9个。因此必须借助多维特征对集合进行排序，才能挑选出真正与文本指称对应上的实体。实际上，排序环节是实体链接系统成败的关键，排序质量直接决定最终结论是否正确。现有方法大致可分为监督排序和非监督排序两类。

#### 1）监督排序方法
监督排序的核心是用标注数据训练模型来学习排序。实现方式主要有二分类、排序学习 Learning to Rank 以及端到端的方案。

#### 2）非监督排序方法
非监督排序无需标注数据即可工作。常见的有向量空间模型 Vector Space Model 以及基于信息检索的思路。

不论有监督还是无监督，几乎所有可行方案都依赖数据驱动，这就要求把文本信息转化为特征再输入模型。候选排序中常用的特征可分为上下文无关和上下文相关两类。上下文无关特征不需要看指称所在句子就能计算，例如指称与实体名称在字符层面的相似度、知识库中实体被激活的频率等。上下文相关特征则必须参考指称周围的上下文，最直接的做法是把指称上下文与知识库中描述实体的上下文进行对比，典型特征包括词袋特征、概念向量特征和语义特征等。实际落地时特征选择要结合数据特性与模型选型，同时兼顾准确率与效率的取舍。

前文提到监督排序是最常见的选择。它通常用已标注集训练模型，学习指称到知识库实体的映射关系。一种常见做法是把排序问题转化为二分类：给定一个指称—实体对，模型判断是否可映射。可映射的样本标记为正，反之为负。预测时对每个对给出判断。常用模型有支持向量机 SVM、逻辑回归 LR 或神经网络。流程上先按前面特征工程把每条数据向量化，再训练预测。

把排序归结为分类很直观，但在训练集中负样本往往远多于正样本，容易拖累判别力；而且当多个实体共享同一指称时，分类器可能全部判为匹配，需要额外机制裁决。为此研究者引入排序学习，通过对同一指称的所有候选实体进行可能性排序并取首位。排序学习能刻画候选之间的相对关系，也解决了二分类的一对多困境。

排序学习是一种以训练数据自动构建排序模型为目标的监督学习范式。应用于候选实体排序时目标会简化，只需确保排在第一位的实体是正确的。这样就避免了二分类中负样本过多的难题。构建时同样依赖特征工程。在模型层面，文献[5][6]对支持向量机的目标函数进行改造用于排序，L. Shen[7]等人提出的排序感知机网络也在该任务上取得不错效果。随着深度学习与自然语言处理的发展，越来越多工作尝试用端到端的深度模型完成排序。优势在于减少人工特征设计，用大量参数拟合数据并形成端到端流程。一种典型结构如图 6-12 所示：先把包含指称的文本或片段经词向量输入编码层，完成上下文编码；随后把编码结果与经知识表示学习得到的实体向量送入匹配层打分，按分数排序，分数最高的实体即为指称的对应对象。端到端排序融合了分类与排序的优点，具有强拟合能力，已成为该任务的新趋势。

在监督学习框架下，标注数据的获取至关重要。但在缺乏标注的场景里，无监督方法就显得很有价值。其中较为常用的是向量空间模型方法。

VSM 需要计算指称向量与实体向量之间的相似度，选择最相似的实体作为匹配。更具体地，Cucerzan 等人[8]从知识库实体来源文章中抽取特征以及文章标签作为实体向量的构建要素，同时用包含指称的文章信息构建指称向量，最后通过向量相似度完成排序。除此之外，基于信息检索的无监督排序也十分重要。该方法把每个候选实体视作独立文档，根据指称及其上下文生成查询请求，再用信息检索技术衡量请求与各候选的相似度，从而定位正确实体。

### 4. 无链接指称预测
前文主要讨论如何把文本中的指称链接到知识库实体。但现实中部分指称在知识库里并无对应项，这时需要判断或预测无链接情况。最简便的判断是候选生成阶段若未产生任何实体，就视为无法链接。更进一步可引入阈值限制排序结果。对分类模型而言，若指称对应的所有指称—实体对分数均未超过阈值，或全部被判为不匹配，则可判定为无链接。对排序模型而言，若第一名实体的分数低于设定阈值，也可认为无法链接。另外，在排序过程中加入一个特殊的“无法链接”实体，若该实体的得分最高，也能表示指称与任何知识库实体都不对应。

## 整体架构
在 Dexter 的整体架构中，Utils 模块封装了日志生成、压缩文件读写、资源管理、命令行等通用功能。Dexter eval 模块提供多种评估实体链接结果的方法。Dexter Webapp 模块对外暴露 RESTful 接口，用于响应外部请求，并提供一个简易 Web 界面便于展示和研究。除此之外，Dexter 还包含 JSON Wikipedia 和 Dexter-Core 两个核心模块。JSON Wikipedia 负责解析存储的 XML 格式维基百科数据，提取实体名称、消歧信息及属性等，并支持多语言页面的解析。解析完成后，每个词条会转换为 JSON 格式，供下游使用。Dexter Core 是最核心的部分，负责操作格式化文件、生成相关数据库并完成线上预测所需组件。图 6-14 描述了 Dexter Core 的主要结构，其中 Spot Repository 保存维基百科文章内部链接的全部锚点。对每个指称，Spot 索引会记录其基础链接概率及可表示的实体列表。Dexter Core 还包含基于 Lucene 构建的多字段文章索引 Article Index，以及表征实体间链接关系的 Entity Link Graph。预测时，Shingle Extractor 首先从文档中生成全部实体指称列表；随后 Spotter 利用 Spot Repository 将指称关联到候选实体；最后 Tagger 为每个指称挑选最匹配的实体，完成链接。Tagger 可输出匹配实体列表、置信度及原文位置。
