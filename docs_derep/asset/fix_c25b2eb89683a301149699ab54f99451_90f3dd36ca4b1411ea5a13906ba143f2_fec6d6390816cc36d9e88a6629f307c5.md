（4）程序一直保持循环监听的状态，默默等待下一次外部输入到来，直到被人工停止。

到这一步，MCP 规范里对供给侧与调用侧之间两种数据通道的说明已经收尾。工程实践中如果选用成熟的上层工具包，通常不需要亲自干预这些传输细节。可一旦要做精细化调控，对底层通道原理的理解就会显得很有价值。

### **2.4.2 第二步：正常对话与调用**
初始化完成后进入常规的请求响应交互。

首先调用侧可以去调用供给侧的方法，通常是 list 方法，来获取可用的功能清单，从而知道能调用哪些工具。

随后调用侧会根据具体场景执行常见操作。

（1）把可用功能呈现给用户或大模型。比如在 UI 上以列表展示供用户挑选，或把工具清单交给大模型做推理使用。
（2）发起调用请求。当大模型在输出中表示需要调用工具时，调用侧即可向供给侧发起对应工具调用并取回结果。
（3）借助持续交互，调用侧最终能调用供给侧能力完成智能体任务或普通用户请求。

某些情况下供给侧也会主动向调用侧发起请求，例如要求调用侧进行大模型调用。对供给侧发起的请求，调用侧通过回调处理，可能涉及唤起用户界面进行审批确认。供给侧拿到结果后继续后续处理。

若供给侧支持列表变更提醒，功能清单发生变化时会推送通知，调用侧可重新请求更新清单。

### **2.4.3 收尾：断开连接**
交互结束时双方可关闭协议连接。MCP 规范并未规定专门的关闭请求消息，通常靠底层传输断开来实现，比如断开 HTTP 连接或关闭 stdio 输入流，一般无需额外处理。

## **2.5 服务端三大核心能力**
MCP 规范定义了供给侧向调用侧提供的三大核心能力：工具、资源、提示，分别对应不同的上下文供给方式。下面逐一解析。

### **2.5.1 工具：可执行的复杂逻辑**

**1.概念与设计原则**
工具是供给侧提供的可执行函数或操作，供大模型调用以完成外部系统交互、计算等任务。

什么功能适合做成工具？简单说，就是需要交给大模型自行判断是否使用的外部能力，即遵循“大模型控制”原则。当然实际应用中部分工具调用可能需要人工审核以保障安全。借助工具，大模型可在可控范围内执行数据库查询、第三方 API 调用、计算等操作，从而拓展能力边界。

工具使用也是智能体最重要的能力之一，通常也是供给侧最核心的能力。常见类型有：

（1）各类数据与文件系统访问，如数据库、向量数据库、Excel 等。
（2）外部工具使用，如 GitHub 访问、Git 工具等。
（3）基于本地操作系统的界面与浏览器自动化操作。
（4）企业内部应用访问，如 ERP 模块访问与功能提供。
（5）互联网开放 API 访问，如搜索引擎、社交媒体、数据供给等。
（6）AI 接口与工具访问，如图像生成、自然语言处理、数据挖掘算法等。

### **2.5.2 资源：动态的上下文信息**

**1.概念与设计原则**
资源指供给侧提供的可读数据或上下文信息，包括文件内容、数据库记录、配置数据等。通常通过 URI 标识，便于调用侧和大模型引用。

资源与工具的区别在于资源不执行操作，只提供静态或可查询的数据。大模型可将其视作可读取的文件片段。资源设计强调“应用控制”，即由调用侧例如智能体或 Chatbot 决定何时、如何把资源作为上下文提供给大模型，而不是由大模型自行请求读取。

常见类型：

（1）文件内容，如配置数据、日志文件。
（2）数据库中的某条记录。
（3）图片等二进制数据。

资源可以是文本或二进制，并用 URI 标识，如 "file:///user/folder/resource.md"。MCP 规范未对 URI 做严格限制，定义了若干标准方案如 https://、file://、git://，也支持自定义方案如 doc://。

供给侧可利用资源模板提供参数化资源，如 "users://{user_id}/profile"。其中 {user_id} 为模板参数，由供给侧根据调用侧请求的 URI 自动识别。例如调用侧请求 "users://user1/profile" 时，供给侧会把 user1 识别为参数。
