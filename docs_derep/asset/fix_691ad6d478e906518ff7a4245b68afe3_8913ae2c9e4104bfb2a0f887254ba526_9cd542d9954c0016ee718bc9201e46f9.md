## 7.12 渐进式落地策略

> “讲了这么多技术点，”小冰追问，“若团队想引入 Headless 模式做 PR 审查，该如何逐步推进？”

咖哥建议走四阶段渐进路线。

阶段一：观察者模式。Claude 仅做只读分析，产出审查报告以评论形式挂在 PR 上，不阻断任何流程。本阶段重点是建立信任，让团队直观感受审查质量，同时捕捉局限性例如误报场景，并据此迭代提示词与参数配置。

阶段二：顾问模式。在获得足够正反馈后，将审查结果接入持续集成状态监控。发现 Critical 问题时，CI 标记为黄色警告但不阻断合并，最终裁决由人工审查员结合报告完成。该阶段核心是人机协作。

阶段三：门禁模式。审查成为代码合并的必要条件，检测到严重安全问题时 CI 立即变红并阻断合并。此阶段必须配套逃生通道，允许特定权限人员手动覆盖阻断，类似于跳过不稳定测试。

阶段四：主动修复模式。Claude 不只发现问题，还能自动修正格式错误、补全异常处理或生成单元测试。需开放 Write 工具权限，但所有改动须以新 Commit 提交，严禁直接修改 PR 作者的原始代码。

“切忌一步到位，”咖哥强调，“每个阶段至少运行 2 到 4 周，持续监控误报率、成本走势和团队接受度。AI 辅助审查的价值不在于完美替代人工，而在于让人类审查员把有限精力聚焦到最有价值的决策上。”

## 本章小结

Headless 模式让 Claude Code 从只能在终端交互的助手，进化为可嵌入各类工程流程的可编程组件。这一转变由四个参数维度定义。

- -p（入口）：把运行模式从交互式会话切到非交互式执行，为自动化奠基。
- --output-format（数据接口）：统一输出结构，让下游系统能高效解析调用结果。
- --allowedTools（安全边界）：严格限定工具权限，保证自动化环境合规可控。
- --max-turns 与 --max-budget-usd（成本护栏）：限制执行轮次与预算上限，避免无人值守时的资源失控。

从架构视角看，Headless 模式的最大意义是让 Claude Code 成为 CI/CD 生态的平等成员。像单元测试、静态分析或镜像构建一样，AI 审查成为流水线标准环节：需有明确输入定义、确定性输出格式、可量化成本预算，以及可版本化的配置文件。

落地建议从观察者模式起步，逐步演进到门禁模式。为团队预留信任建立、数据积累和配置优化的时间，不可急于求成。AI 审查的核心不是追求对人工的完美替代，而是通过智能过滤，让审查员集中精力在最关键的决策点。

第 8 章将从命令行参数转向编程接口智能体 SDK。你将学会用 TypeScript 或 Python 代码替代繁琐 CLI 参数，灵活掌控 Claude 行为，构建真正定制化、深度集成的 AI 应用系统。

# 第 8 章 器以载道：Agent SDK 智能体开发套件

“我们能否做一个内部工具，让非技术同事也能用 Claude Code 分析代码？比如产品经理输入用户故事，系统自动定位相关模块、评估实现复杂度并列出待改文件清单。”

小冰思索后说。虽然 Headless 模式能部分满足，但它本质是命令行工具，对不熟悉终端的产品经理门槛太高。他们需要的是带表单输入、进度反馈和历史记录的 Web 界面。这已不是单纯使用工具，而是要构建产品。

“Headless 模式用参数驱动 Claude，Agent SDK 用代码编排 Claude，”咖哥补充，“差别就像‘使用计算器’与‘为计算器编程’：前者只能用预设按钮，后者能自定义行为逻辑。”

## 8.1 Agent SDK 的定位：从工具到组件

前面介绍的 CLAUDE.md、子智能体、Skills、Hooks、MCP 以及 Headless 模式，都以“使用 Claude Code”为视角。开发者作为使用者，在既定框架内通过配置扩展行为。

Agent SDK 的思路完全不同。它假设开发者是应用构建者，目标是将 Claude Code 核心能力深度嵌入自有应用。何时启动、传什么参数、如何编排中间步骤、如何管理多轮对话状态，全部由代码自主掌控。这时你不是在用现成产品，而是在构建以 Claude 为智能引擎的新应用。
