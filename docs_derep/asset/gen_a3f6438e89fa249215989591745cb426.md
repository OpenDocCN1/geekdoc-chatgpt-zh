特别说明一下，手工编写时并未参考 AI 的代码。那 AI 为何能写出如此相近的代码？这与生成式 AI 的上下文 Prompt Context 有关，与 React 的 context 不同。

以 Copilot 为例，主流 AI IDE 的核心能力都基于生成式 AI。我们在聊天框输入的内容即提示语，可以是任意自然语言，中文英文皆可，上传原型图也算提示语的一种。点击发送后，Copilot 会把项目部分源文件作为上下文，结合提示语和内置的 Instruction 拼接成完整提示，发送给远程大模型，如 Anthropic 的 claude 3.5 Sonnet 或 OpenAI 的 GPT-4o。模型在预训练时已学习大量 JavaScript、React 知识，因此具备编程能力，返回分析过程和代码。

如果选择代理模式，Copilot 会多次调用模型，每次都带上更相关的上下文，并根据上一次返回结果动态调整下一次调用，直到得到满意结果。这种由模型自主决定执行步骤的程序在中文社区常被称作智能体 Agent 或 Intelligent Agent，比“代理”更准确。智能体还能主动调用外部工具，这里不展开。Copilot 的代理模式就是一个智能体，能处理更复杂需求并自动修改源文件。

回到相似性问题，关键在于 Copilot 把 1.4.1 节编写的 App.jsx 中聊天视图代码纳入了上下文，于是生成的命名、JSX 层级、样式习惯都接近聊天视图，也就是手工版的风格。在全新 React 项目里用相同提示语，风格就会不同。风格一致的代码更利于后续扩展和维护。

再看 AI 生成的不足，最明显的是右栏没生成，原因可能是提示语不够、上下文不足或模型能力限制。我曾换过不同模型和 IDE 如 Cursor，结果各不相同。有几次用 Cursor 成功生成了中栏和右栏的 JSX，并额外把 CSS 写进 App.css，这里不再详述。实际上，哪怕提示语、原型图、上下文完全相同，用同一 IDE 和模型多次生成也会得到不同结果，这种随机性源于 LLM 原理，本书不深入讨论。
