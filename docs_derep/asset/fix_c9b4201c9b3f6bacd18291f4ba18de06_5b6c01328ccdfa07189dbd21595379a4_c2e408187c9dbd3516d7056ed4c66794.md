当业务逻辑已经高度固化、且已有成熟系统在支撑时，例如风控模型、量化交易模型，智能体往往难以形成明显增益。它的长处在于理解自然语言、整合多源信息、处理非结构化内容，更适合放在需要综合研判的场景里，而不应该把智能体建立在拿不到甚至不存在的数据之上，比如未公开的内部交易流水。

### 11.1.2 步骤 2：为 AI 智能体制定工作流程
先为智能体写一份清晰的 **标准作业规范 SOP**，把人工分析师完成任务的每一步拆开来写。

这样能让开发者判断任务边界是否合理、所需工具是否齐备，为后续搭建打好基础。以金融投资分析类智能体为例，典型的工作流可以这样走：

（1）抓取并解析财经新闻、财报、行业报告等多元信息。
（2）提炼关键事件与核心财务指标，完成情感判断与影响评估。
（3）结合历史数据与市场走势，形成投资观点或风险提示。
（4）产出初稿报告，经分析师等安全审核节点确认后再发布。

### 11.1.3 步骤 3：利用提示词打造 MVP
切入点要选对。先按 SOP 完成架构设计，明确运行路径、决策点和推理环节。

随后聚焦大模型最核心的推理能力，比如分类、判断，用提示词把最小可用产品搭起来。绝大多数智能体失败都是推理跑不通，先手工喂数据验证提示词，能在完整系统落地前建立信心。提示词工程平台例如 LangSmith，可以帮助做版本管理、跨场景测试和迭代效果追踪。

MVP 的落地做法：

（1）先手工提供提示词所需的数据或上下文，自动化暂不考虑。
（2）参照 11.1.1 节列出的任务示例验证，观察常见用例的表现。

先锁定一个高价值的推理任务。对金融投资分析智能体来说，财报关键信息抽取与分类是基础，后续功能都依赖它。

例如输入一段财报原文，检验指标抽取和情绪判断是否可靠。

**·** 输入：本季度营收同比增长 15%，净利润下降 8%。
**·** 输出：关键指标 = {"营收增长率": "15%", "净利润变动": "−8%"}，情绪 = "中性偏负"。

手工测试确认推理稳定可靠后，再推进后续开发。

### 11.1.4 步骤 4：AI 智能体的构建
提示词可用后，就要把它和真实数据、用户输入连起来。

首先搭建系统消息框架。用基础系统提示定义智能体角色、元规则和工作边界，是保证按预期运行并抵御提示注入等风险的安全前提。

接着明确每个提示词需要哪些上下文或数据，例如内部外部数据、工作文档，并规划通过 API、数据库或文件系统等方式的程序化获取方式。

再编写工作流运行逻辑，把数据送入提示词。简单场景可直接传入，复杂场景则需要业务逻辑层来决定查询哪些数据源、何时调用、如何组合结果后再输入模型。

以金融投资分析智能体为例，本步可能调用 Bloomberg、Wind 等财经数据接口，联动内部库获取历史交易记录，并用网络爬虫获取实时新闻。

运行逻辑可设计为：

（1）定时触发或事件驱动，如财报发布即启动智能体。
（2）从多个渠道获取结构化与非结构化数据。
（3）调用大模型做信息抽取与情感分析。
（4）生成初步分析报告。
（5）经人工安全审核后推送到投资决策系统。

### 11.1.5 步骤 5：AI 智能体的测试与迭代
先用 11.1.1 节的任务示例手工测试 MVP，目标是核查核心用例能否输出合理准确的结果。若有多轮模型调用，可用 LangSmith 等工具追踪流程，直观调试各阶段决策。

手工稳定后转向自动化测试，保证一致性并捕捉边界情况。团队通常会把用例扩充到几十条，以便更清晰认识优势劣势，并在提升复杂度前量化表现。具体操作：

**·** 以编程方式批量运行智能体，覆盖原有与新增用例。
**·** 定义自动化成功指标，明确预期行为。
**·** 选择性人工复核，挖掘指标难以发现的问题。

以金融投资分析智能体为例，可用指标包括：

**·** 准确性：财务数据抽取是否无误。
**·** 及时性：能否在限定时间内完成分析。
**·** 合规性：输出是否符合金融监管要求。

随后扩展自动化测试，设定门槛如抽取准确率>95%，并借助 LangSmith 跟踪多步推理过程。

### 11.1.6 步骤 6：AI 智能体的部署、扩展与持续完善
MVP 稳定运行后可开始扩展范围，新增功能、覆盖更广场景，甚至构建多智能体协作流。每新增一项都要重复 11.1.5 节的测试流程，确保不破坏已有能力。

准备就绪后将智能体部署到生产环境供用户使用。可选用外部云平台，例如 LangGraph 平台支持一键部署，便于发布、管理和扩容。

观察真实使用情况。LangSmith 等工具可实时跟踪操作，帮助发现成本飙升、准确率下降等问题。实际使用往往与预期有差异，这些洞察能揭示不足、发现隐性需求，指导下一步迭代优先级。

关键在于把上线视作迭代的起点而非终点。

以金融投资分析智能体为例，上线后通过监控流量与高频用例，可能发现未覆盖场景如特定行业的分析需求，需逐步扩展：

**·** 增加新兴市场分析模块；
**·** 支持多语言财报处理；
**·** 引入多智能体流程，如风险预警智能体+投资建议智能体。

这些新需求意味着可以扩大功能边界。开发者可逐步新增能力、更新提示词与运行逻辑，并在进一步扩展前始终通过测试与用户反馈验证。这不仅保证可用，更能打造贴合真实工作方式、可靠好用的智能体。

扩展过程中要始终关注数据隐私、输出合规与潜在偏见，通过持续的人机协同设计和反馈机制，把安全与信任作为核心特质。

### 11.2.1 DACA 设计模式与项目介绍
DACA 即 Dapr Agentic Cloud Ascent 设计模式，为用智能体打造大规模系统提供了解法。

该模式融合 OpenAI Agents SDK 的智能体引擎与 Dapr 的分布式能力如状态管理、服务调用，支持 Kubernetes 动态扩缩容与千万级并发，适用于高并发企业级应用，例如实时金融交易分析、自动化财报解析。凭借巧妙的架构与灵活组合，它成为开发部署大型多智能体系统的首选。无状态、容器化部署策略也大幅提升了可扩展性。

DACA 的创新在于用 OpenAI Agents SDK 承担核心逻辑，结合 MCP 与 A2A 协议，实现工具标准化和智能体间无缝通信。

越来越多行业需要在创新与成本效益间取得平衡，DACA 为开发者和架构师提供了一套稳健灵活的框架，助力构建复杂云原生智能体。

作为云原生智能体设计模式，DACA 整合：

**·** OpenAI Agents SDK，提供核心代理逻辑；
**·** MCP，标准化工具调用接口；
**·** A2A 协议，实现智能体间无缝协作；
**·** Dapr 分布式框架，提供底层支撑。

该模式强调“AI 优先”和“云优先”原则，采用无状态容器化部署，可从本地开发平滑扩展到全球规模。

核心设计理念：

（1）**开发环境无关**。通过容器化技术 Docker/OCI 实现跨平台一致性，提供隔离的开发环境如 VS Code Dev Containers，采用开源技术栈如 Python、Dapr、Kubernetes。
（2）**云环境可移植**。基于 Kubernetes 的标准化部署实现多云/混合云兼容，Dapr 简化分布式系统开发，Helm/Argo CD 实现自动化交付。
（3）**开放核心与托管边缘**。核心系统采用开源技术如 Kubernetes、Dapr；边缘服务采用托管数据库/AI API；兼顾成本、掌控力和性能。

DACA 为构建大型并发智能体系统提供了完整技术框架。通过云原生与智能体范式的深度融合，解决了可扩展性、可靠性与成本效益问题，有望成为下一代智能体系统的标准范式。
