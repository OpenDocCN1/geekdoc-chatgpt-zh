属性表既绕开了三元组表的单表自连尴尬，又遏制了水平表列爆炸的局面。极限来看，水平表就是把所有主语归为一类的属性表，所以空值比例会明显下降。但局限同样突出：真实图谱的主体类型往往在几千到上万个，按此方案就要建几千到上万张表，很容易触及关系库的上限；查询一旦跨类型，就仍需多表连接；同一类型内部不同主语的谓语集合差异仍会产生空值；一对多或多值属性、以及水平表里固有的存储难题并不会消失。采用这种思路的代表系统是 RDF 三元组库 Jena[26]。

# 4. 垂直划分

垂直划分由麻省理工学院 Abadi 等人在 2007 年提出[27]。划分维度取自三元组的谓语，为每个不同的谓语建一张只保留主语、宾语两列的表，表数量等于图谱中谓语的种类。图 3-10 显示的示例中 13 个谓语对应 13 张表，每张表结构都是 主语、宾语。图 3-5 的 SPARQL 在此方案下的 SQL 需要把 born、died、founder 三张谓语表连接起来。由于每张谓语表按主语列有序，主语到主语的连接可以快速完成，而这恰是常见模式。

## 5. 六重索引

六重索引是对三元组表的一种扩展，以空间换时间的典型做法。它为三元组的全部六种排列各建一张表：spo、pos、osp、sop、pso、ops，其中 spo 即原来的三元组表。通过多表连接它在一定程度上缓解了三元组表自连的压力，并加速了部分常用查询。代表系统有 RDF-3X[28]和 Hexastore[29]。

具体优势在于，图谱查询的每种三元组模式都能直接用对应的索引表做前缀范围查找，表 3 - 3 列出了八种模式可用的索引；不同索引表之间还能直接连接加速连接查询，例如“找出生于 1850 年的人创办的公司的业务领域”这一链式 SPARQL，可以利用 spo 与 pso 的连接完成 ?person founder ?company 与 ?company industry ?ind 的关联，避免单表自连。

### 表 3 - 3 三元组模式查询能够使用的索引表

| ---- | ------------------ | ------------------------------ |

| 2    | (s, p, ?x)         | spo, pso                        |

六重索引的代价也很明显：存储开销、索引维护成本以及更新时的一致性维护都要乘以六，且随图谱规模放大；查询复杂度上升时，索引表的连接数量激增，自连问题依然无法根除。

## 6. DB2RDF

DB2RDF 是 IBM 研究院 2013 年提出的一种面向实体的存储折中方案[30]。它保留了三元组表在行维度上的灵活，同时把灵活性延伸到列维度：表的列用来存放谓语和宾语，但列并不固定绑定某个谓语。数据写入时谓语被动态映射到某一列，并且相同谓语会始终映射到同一组列上。

该方案由四张表构成：dph、rph、ds、rs；图3-13 给出了对应示例。dph 即 direct primary hash，是主表，一行保存一个主语及其若干谓语、宾语对 predi、vali，i 从 0 到 k，k 为图着色结果或设定值。若一个主语的谓语数超过 k，则溢出到下一行继续存放 k+1 到 2k 的对。spill 是溢出标记，能放下的一行标记为 0，溢出实体所有行标记为 1。示例中除 Android 溢出外，其余实体都只占一行。

多值谓语通过 ds 表处理。dph 遇到多值谓语时，在宾语位生成唯一 id，再把 id 与各个具体宾语写入 ds。例如 Google 的 industry 为多值，dph 中 val1 存放 lid:1，ds 中关联 Software、Internet。

dph 实现了列共享：相同谓语总是落到同一列，不同谓语也可以共用同一列。Charles_Flint 与 Larry_Page 的 founder 都落在 pred3 列，该列同时容纳了 Android 的 kernel 与 graphics。正因为列共享，在列数上限受限的关系库里也能容纳远超上限的谓语数，有效缓解了水平表式的谓语稀疏空值问题。真实图谱中不同主语的谓语集合差异很大，这种机制更具实用价值。
