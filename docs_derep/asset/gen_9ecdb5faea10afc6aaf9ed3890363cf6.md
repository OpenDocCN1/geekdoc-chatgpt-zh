有时候我们需要把大模型的输出按照自己的规则整理成特定格式，这时就需要自定义解析器。实现思路主要有两种：一种是在 LCEL 链路里直接使用 RunnableLambda 或 RunnableGenerator，这是最常用也最推荐的做法；另一种则是通过继承输出解析相关的基类来搭建，门槛相对比较高。两种方式在本质上差异不大，主要区别体现在回调的触发点上，比如 on_chain_start 与 on_parser_start 会不一样，同时在 LangSmith 等可视化追踪平台中，runnable lambda 和解析器呈现的形态也会有所不同。

### 3.3 RAG 检索增强实践

不少大语言模型应用都需要调用模型训练之外的私有数据，而最主流的办法就是检索增强生成。简单来说，就是先从外部把相关资料找出来，再把这些资料一起交给模型去生成答案。

#### 3.3.1 核心组件一览

LangChain 为 RAG 提供了从基础到进阶的完整积木。这一节聚焦在检索环节的数据准备上。看似简单，实际涉及的流程不少，如图3-2所示，主要包含下面几个关键部分。

（1）文档加载器。负责从不同渠道把原始文档读进来。LangChain 自带上百种加载器，还接入了 AirByte、Unstructured 等生态。无论是私有 S3 桶里的文件，还是公开网站的内容，都能加载，支持 HTML、PDF、代码等多种格式。

（6）索引。LangChain 的索引 API 能把任意来源的数据同步到向量库，避免重复写入、避免对未变动内容重算嵌入，并能在文档分块后保持与源文档的一致性。

#### 3.3.3 文本分割器

文档加载后通常要做转换，让它更适合模型处理。典型需求是把长文本切成小块以适配上下文窗口。LangChain 内置了多种文档转换工具，支持切分、合并、过滤等操作，大大简化预处理。

切分长文本看似简单，实则有不少细节。理想做法是保持语义连贯的片段在一起，语义相关的定义会随文本类型变化。基本思路是先把文本拆成句子等小单元，再组合成目标大小的块，并在块与块之间保留少量重叠以维持连贯。

LangChain 提供多种分割器供定制策略，并可在 langchain-text-splitters 中找到。用户可以根据需求调整切分方式和块大小计算方法，如表3-1所示。可借助 Chunkviz 工具可视化分割效果，帮助调参。

#### 3.3.5 检索器

检索器是根据非结构化查询返回文档的抽象接口。它不一定负责存储，只负责检索。向量库可以作为底层，但检索器形态更多。输入是字符串查询，输出是文档列表。LangChain 提供了多种高级检索方式，如表3-2所示。

## 表3-2 检索类型列表

| 名称 | 索引类型 | 使用 LLM | 何时使用 | 描述 |

| :--- | :--- | :--- | :--- | :--- |

| Vectorstore | Vectorstore | 否 | 当有大量文本数据需要快速、高效检索，且对语义理解要求不是特别高时 | 将文本转换为向量表示，通过计算向量相似度来检索相关文档。适合处理大规模数据，检索速度快，但可能忽略上下文语义 |

| ParentDocument | Vectorstore + Documentstore | 否 | 当文档结构复杂，包含多个小的信息片段，但需要保持整体上下文时 | 将文档分割成小块进行索引，但在检索时返回完整的父文档。这种方法平衡了精确检索和保持上下文的需求 |

| Multi Vector | Vectorstore + Documentstore | 有时在索引期间使用 | 当单一向量表示不足以捕捉文档的全部重要特征时 | 为每个文档创建多个向量表示，可能包括文本摘要、假设问题等。这种方法提高了检索的多样性和准确性，但增加了索引复杂度 |

| Self Query | Vectorstore | 是 | 当用户查询需要复杂的解释和转换，或者检索需要考虑元数据时 | 使用 LLM 将用户输入转换为语义查询和元数据过滤器。这种方法能更好地理解用户意图，提高检索精度 |

| Contextual Compression | 任何 | 有时 | 当检索结果包含大量冗余或不相关信息时 | 在检索后进行额外的处理，从检索到的文档中提取最相关的信息。这种方法可以大大提高返回信息的质量和相关性 |

| Time-Weighted Vectorstore | Vectorstore | 否 | 当文档的时效性很重要，需要考虑内容的新近程度时 | 结合语义相似性和时间因素进行检索。这种方法适合新闻、社交媒体等时效性强的内容检索 |

| Multi-Query Retriever | 任何 | 是 | 当面对复杂、多方面的查询，单一查询可能无法全面捕捉用户意图时 | 使用 LLM 从原始查询生成多个相关查询，然后综合这些查询的结果。这种方法可以提高检索的全面性和深度 |

| Ensemble | 任何 | 否 | 当单一检索方法无法满足复杂需求，需要结合多种方法的优势时 | 组合多个检索器的结果。这种方法可以平衡不同检索策略的优缺点，提高整体检索性能 |

| Long-Context Reorder | 任何 | 否 | 当使用能处理长文本的大语言模型，需要优化输入顺序以提高模型性能时 | 重新排序检索到的文档，使最相关的内容位于开头和结尾。这种方法利用了大语言模型对文本开头和结尾部分的特殊关注，以提高处理效果 |

#### 3.3.6 索引

LangChain 的索引 API 允许把任意来源的文档同步到向量存储，核心目标是避免重复写入、避免对未改动内容重算嵌入，从而节省成本并提升检索效果。索引过程中会保持文档经过多次转换后的溯源一致性。

其运行机制依赖记录管理器，用来追踪文档是否已写入。每个文档会计算哈希，并把哈希、写入时间、源 ID 等信息保存下来，便于后续判断是否变更或删除。如表3-3所示，索引 API 支持 None、Incremental、Full 三种清理模式，适应不同场景。

## 表3-3 索引API删除模式

| 清理模式 | 去重内容 | 可并行化 | 清理已删除的源文档 | 清理源文档和/或派生文档的变体 | 清理时间 |

| :--- | :---: | :---: | :---: | :---: | :---: |

| None | ✅ | ✅ | ❌ | ❌ | — |

| Incremental | ✅ | ✅ | ❌ | ✅ | 连续 |

| Full | ✅ | ❌ | ✅ | ✅ | 索引结束时 |
