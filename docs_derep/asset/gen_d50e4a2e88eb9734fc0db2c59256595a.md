图0-17 展示的工作流涵盖了输入处理、问题分类、检索以及答案生成等环节。下面简要说明各模块的作用。

- START 模块负责接收用户的查询和历史上下文，定义工作流的初始参数。
- QUESTION CLASSIFIER 模块基于 GPT-3.5-turbo 模型对问题进行分类，分为售后相关问题、产品定位与规划问题和其他问题三类。

- 对于可回答的问题，则进入 KNOWLEDGE RETRIEVAL 模块，根据分类结果选择对应的检索路径，从产品文档中拉取相关信息，随后调用大模型 API 进行文本生成。

这类低代码工具的优势在于流程可视、模块独立、功能清晰，支持条件分支和分类，适合构建复杂的检索-生成链路。系统上线后，大多数平台也会提供 API，方便开发者调用已生成的 AI 应用。

低代码确实让 RAG 和 AI 应用的开发更省事，但通常不会触及嵌入、索引与检索、生成等组件的算法级优化。要做出高质量的 RAG，仍需对每个环节做精细打磨。因此本书的重点不放在低代码工具的使用上，而是放在如何用代码、LangChain、LlamaIndex 等框架来优化 RAG 的各个环节和组件。

## RAG 系统优化从哪下手

怎么优化 RAG 系统是更实际的问题，也更考验经验。第一步是要先把优化目标和性能瓶颈找准。RAG 流程长、环节多，必须像侦探一样定位出真正拖后腿的关键组件。

下面咖哥用两张图来说明如何逐步排查出故障环节。

第一张图来自 ABACUS.AI，见图0-18。它既呈现了 RAG 的整体结构，也在每个环节标注了可能的优化方向。图0-18 RAG 系统的结构流程

[PRE5]

根据图0-19，优化的第一步可以从分块策略开始。分块决定了检索的粒度与上下文的完整度，直接影响检索和生成的质量。可以尝试调整块的大小和重叠比例。提高重叠能提升上下文连贯性，但会带来存储冗余；缩小块大小可以减少噪音，却可能切碎语义。

第二步是优化嵌入。选对任务适配的嵌入模型很关键，目前开源和商业模型众多，性能和语义捕捉能力差异明显。如果用的是 Transformer 开源模型，微调通常能进一步提升语义相关性。此外，领域专属的嵌入模型在特定场景下效果会更好。优化时要注意向量维度与计算效率的平衡。

第三步是检索器优化，涉及向量库的选择、索引结构和检索算法的调整。比如从朴素的扁平索引逐步过渡到 IVF 或 HNSW 等高效索引。Top K 和相似度阈值的调参有助于拿到更相关的片段并过滤噪音。动态检索策略，即根据用户问题实时调整检索参数，也能提升结果质量。

第四步是上下文组装策略的优化。检索到多个片段后，如何拼接并喂给大模型会直接影响答案。可以按语义相关性重排结果，对片段做压缩或扩充，并在片段间加入解释性连接词。上下文长度还需根据目标大模型的最大 token 限制来控制，避免过载。

大模型的选择与提示词设计也是关键。应选用更匹配任务的模型，并调整温度、Top-p、最大 token 等生成参数。提示词要给出明确指令或补充背景，引导模型产出更符合需求的回答。

最后一步是对最终响应的评估。生成后可用 BLEU、ROUGE、BERTScore 等自动化指标，结合人工评价，比较不同优化组合的表现。通过反复实验和评估，逐步找到最优配置，提升整体效率和准确率。

对于常见且重要的格式如 PDF，可以选用专用工具如 PyPDF2、PyMuPDF、Marker、MinerU 和 PDFPlumber 等，具体取决于应用场景，是结构化数据抽取、文本搜索、OCR 还是图像提取。

OCR (Optical Character Recognition, 光学字符识别) 是一种技术，用于将印刷文本或手写文本的图像转换为计算机可编辑的文本。它通常用于扫描纸质文档、识别图片中的文字、处理身份证或车牌号码等。

对于不常见的格式，要先弄清文件的生成工具、数据结构和使用目的。例如目录里出现 product_sales.jsonl，根据文件名可推测这是产品销售日志，采用 JSON Lines 格式，每行是一个独立 JSON 对象，行间没有逗号分隔，解析时需要特别注意。

遇到复杂文档时，可以先转成更易处理的中间格式。比如 PPT 先转成 PDF 再提取，因为 PDF 的提取工具更多；有时也可以把 PDF 统一转成 Markdown 再处理，Markdown 结构规范，便于提取标题、段落和列表，且大模型对 Markdown 有天然亲和力，更利于理解。

此外，大模型本身也能辅助解析结构化、半结构化和非结构化数据，在多模态等复杂场景下效果很好。

在 LangChain 里，Document 是核心数据结构，用来承载从外部文件或数据源加载的文本。它主要包含两部分。

- Metadata：记录文档的元信息，如来源路径、作者、日期等。
- page_content：保存实际的文本内容。

小冰：为什么要使用这个Document对象？

咖哥：首先，Document 里的元数据很重要。虽然它不是正文内容，却承载了来源、时间、类别等丰富信息，在 RAG 中可用于过滤、排序和分析。不同来源的数据形态各异，仅靠原始字符串无法追踪来源或获取附加信息。而在索引和问答任务里，结合元数据操作是常规需求。高级索引技术中，元数据还能存放摘要、父文档 ID 等。

另外，不同数据源的分块策略、段落间隔等特性不同，需要一个统一的结构来抽象和标准化。Document 对象把多样数据源抽象成统一形式，便于在 LangChain 中流转到嵌入模型、分类器或问答系统。
