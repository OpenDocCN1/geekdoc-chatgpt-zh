[PRE0]

（2）检索提速方案
向量检索的实时性直接决定了产品的使用体感，下面几类手段能够显著提速。

1）搜索参数调优：以 HNSW 为例，ef 决定检索阶段保留的候选池大小，调大可提升命中质量但会拉长延迟；需与 efConstruction 区分，后者是索引构建阶段使用的候选池大小。

2）请求合并：把多条查询合并为一次批量调用，降低网络往返开销。

3）融合检索：把硬条件筛选与向量相似度匹配结合，先过滤后计算相似度。

4）高频结果暂存：对频繁出现的向量查询结果进行缓存，下次直接命中。

（3）分布式部署思路
当数据规模增长后，向量库必须走向分布式。

1）水平分片：按 ID 区间或哈希将数据分散到多个节点。

2）读写分离：将查询节点与索引构建节点拆分，资源利用更合理。

3）多副本：为核心数据准备多份副本，提升可用性与并发能力。

4）增量维护：大规模场景下避免全量重建，采用增量方式更新索引。

向量库的选型与使用是构建生成式应用的关键，需结合业务特征、数据体量与性能目标综合评估。

### 5.1.2 知识库存储设计
知识库是智能应用的核心资产，存储设计是否合理直接影响可用性与模型表现。

#### 1. 知识库架构设计
一套完整体系需同时承载结构化与向量型数据，并支持多种查询与更新模式。图 5-4 所示的典型架构由接入层、存储层、索引层、查询层四部分组成。

[PRE1]
四层分工明确：
1）数据接入层：汇聚来自不同来源的数据并进行校验与预处理，涵盖文件解析、API 引入、清洗及格式校验。
2）存储层：分别存放结构化元数据与关系信息、文本的嵌入向量、原始文档内容。
3）索引层：构建倒排、向量、元数据等多类索引以加速检索。
4）查询层：提供关键词检索、语义检索、混合检索及元数据过滤能力。

#### 2. 知识库数据模型设计
模型需能组织异构数据并支持灵活的查改操作。
要点如下：
1）粒度划分：将文档切分为合适大小的 Chunk，在检索精度与上下文连贯间取得平衡，通常控制在 100~1000 token 之间，1 token 约等于 0.75 个英文词或 1~2 个汉字。
2）关系建模：简单场景可用扁平化组织，复杂场景可构建实体关系网，支持更深层次的推理。
3）元数据管理：为文档、Chunk、实体设计元数据模式，便于精细过滤与分类。
4）版本控制：内容会持续演进，需记录变更历史并保证查询结果一致。

#### 3. 知识库存储优化策略
面对海量数据与高并发，常用优化包括：

（1）分层存储
依据访问热度选择存储介质，如图 5-5。

[PRE2]
主要分为三层：
1）热层：存放访问最频繁的向量与结果，多采用 Redis 等内存缓存，实现毫秒级响应。
2）温层：存放中等活跃的向量索引与结构化数据，多采用向量库与关系库，实现百毫秒级响应。
3）冷层：存放低频历史数据与原文，多采用对象存储，成本低但延迟较高。
数据会随热度自动迁移，在性能与成本间取得平衡。

（2）分片与复制
1）水平分片：按文档 ID 或主题将数据分散到多节点。
2）垂直分片：元数据、向量、原文分别存放在不同系统。
3）多副本：对关键数据做多份复制，提升可用性与读取性能。

（3）存储格式优化
1）向量压缩：采用标量量化、乘积量化等手段压缩向量，节省空间。
2）列存：对结构化数据采用列式存储，提升属性查询效率。
3）增量存储：在频繁更新场景下仅保存变更部分，降低写入成本。

### 6.1.1 大模型服务层规划
服务层是 AI 应用的核心，需兼顾性能、成本与可维护性。

#### 1. 服务层架构模式
- 1. 单体式：将模型与组件部署于同一实例，适合小型应用与原型，简单但扩展受限。
- 2. 微服务式：把不同能力拆分为独立微服务，经 API 网关统一访问，扩展性好，便于协作与持续交付。
- 3. Serverless 式：以函数即服务部署，按需触发，资源利用率高、成本优势明显，适合流量波动场景。
