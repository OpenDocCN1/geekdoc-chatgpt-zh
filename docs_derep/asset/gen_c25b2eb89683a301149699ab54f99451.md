程序会一直跑在循环里，默默等着下一次输入到来，直到被手动终止。

到这里，MCP 规范中服务端与客户端之间使用的两种传输方式已经讲清楚了。实际开发时若借助成熟的 SDK，通常不需要手动去操纵这些传输细节。但对底层传输原理有清晰认知，会在需要精细调控时显得尤为关键。

### **2.4.1 连接与初始化**

（1）所有操作启动前，MCP 服务端先行启动。可能采用 stdio 模式，由客户端拉起；也可能采用 SSE 模式，由人工或自动启动。具体支持哪种模式由服务端决定，客户端据此挑选合适的接入方式。

### **2.4.2 交互与调用**
初始化完成后进入常态的请求响应交互。

首先客户端可调用 MCP 服务端的方法，通常是 list 方法，来获取可用的功能清单，从而知道能调用哪些工具。

随后客户端会根据具体场景执行常见操作。

（1）把可用功能呈现给用户或大模型。比如在 UI 上以列表展示供用户挑选，或把工具列表交给大模型做推理使用。
（2）发起调用请求。当大模型在输出中表示需要调用工具时，客户端即可向服务端发起对应工具调用并取回结果。
（3）借助持续交互，客户端最终能调用服务端能力完成智能体任务或普通用户请求。

某些情况下服务端也会主动向客户端发起请求，例如要求客户端进行大模型调用。对服务端发起的请求，客户端通过回调处理，可能涉及唤起用户界面进行审批确认。服务端拿到结果后继续后续处理。

若服务端支持列表变更通知，功能清单发生变化时会推送通知，客户端可重新请求更新清单。

### **2.4.3 连接关闭**
交互结束时双方可关闭协议连接。MCP 规范并未规定专门的关闭请求消息，通常靠底层传输断开来实现，比如断开 HTTP 连接或关闭 stdio 输入流，一般无需额外处理。

## **2.5 MCP 服务端三大核心能力**
MCP 规范定义了服务端向客户端提供的三大核心能力：工具、资源、提示，分别对应不同的上下文供给方式。下面逐一解析。

### **2.5.1 工具：可执行的复杂逻辑**

**1.概念与设计原则**
工具是服务端提供的可执行函数或操作，供大模型调用以完成外部系统交互、计算等任务。

什么功能适合做成工具？简单说，就是需要交给大模型自行判断是否使用的外部能力，即遵循“大模型控制”原则。当然实际应用中部分工具调用可能需要人工审核以保障安全。借助工具，大模型可在可控范围内执行数据库查询、第三方 API 调用、计算等操作，从而拓展能力边界。

工具使用也是智能体最重要的能力之一，通常也是服务端最核心的能力。常见类型有：

（1）各类数据与文件系统访问，如数据库、向量数据库、Excel 等。
（2）外部工具使用，如 GitHub 访问、Git 工具等。
（3）基于本地操作系统的界面与浏览器自动化操作。
（4）企业内部应用访问，如 ERP 模块访问与功能提供。
（5）互联网开放 API 访问，如搜索引擎、社交媒体、数据供给等。
（6）AI 接口与工具访问，如图像生成、自然语言处理、数据挖掘算法等。

### **2.5.2 资源：动态的上下文信息**

**1.概念与设计原则**
资源指服务端提供的可读数据或上下文信息，包括文件内容、数据库记录、配置数据等。通常通过 URI 标识，便于客户端和大模型引用。

资源与工具的区别在于资源不执行操作，只提供静态或可查询的数据。大模型可将其视作可读取的文件片段。资源设计强调“应用控制”，即由客户端例如智能体或 Chatbot 决定何时、如何把资源作为上下文提供给大模型，而不是由大模型自行请求读取。

常见类型：

（1）文件内容，如配置数据、日志文件。
（2）数据库中的某条记录。
（3）图片等二进制数据。

资源可以是文本或二进制，并用 URI 标识，如 "file:///user/folder/resource.md"。MCP 规范未对 URI 做严格限制，定义了若干标准方案如 https://、file://、git://，也支持自定义方案如 doc://。

服务端可利用资源模板提供参数化资源，如 "users://{user_id}/profile"。其中 {user_id} 为模板参数，由服务端根据客户端请求的 URI 自动识别。例如客户端请求 "users://user1/profile" 时，服务端会把 user1 识别为参数。
