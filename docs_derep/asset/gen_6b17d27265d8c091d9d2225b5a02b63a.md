数据洪流已经让单一架构的时代退出历史舞台。个人的网络使用每天在产生约 1GB 数据，智能汽车每天约 50GB，智能医院每天约 3TB，而智慧城市的规模则达到每天约 50PB。数据体量、类型以及处理的位置、时机和方式都在加速变化。无论计算落在边缘还是云端，无论是人工智能任务还是存储任务，都必须依靠匹配的架构和软件才能发挥应有的价值。

内存共享与冗余拷贝的消除是关键一步。早期 GPU 与 CPU 虽已集成到同一芯片，却仍各自拥有独立的内存池，定位与访问需要繁琐步骤。CPU 要把部分运算 offload 到 GPU 时，必须先把整块数据从 CPU 内存复制到 GPU 内存，运算结束后再复制回来。把两者纳入同一架构后，这种来回搬运就不再必要，处理器可以直接访问和修改统一的内存池，也省去了额外挂载在 CPU 上的 DRAM。

在 CPU 与 GPU 之外，ASIC 在异构体系中承担 AI 加速的重要角色。它通过驱动与 CSR 以及可配置表项交互来控制硬件运转。与 GPU 一样，ASIC 仍离不开 CPU 的配合：数据准备好后由 CPU 控制输入逻辑把数据从内存搬进处理器；运算完成后由 CPU 控制输出逻辑把结果搬回内存；运行过程中则由 CPU 管理 CSR、可配置表项和中断等。

从 CPU 到 ASIC，体系呈现出日益碎片化的趋势。指令作为软件与硬件的桥梁，其复杂度决定了解耦程度。典型的处理器平台包括 CPU、协处理器、GPU、FPGA、DSA 和 ASIC。随着指令复杂度上升，单个处理器能覆盖的场景越来越窄，形态也越来越多样，生态建设难度随之放大，形成了易用性与性能之间的权衡。

在 CPU+XPU 的异构计算里，XPU 的选择直接决定性能与灵活性的取舍。GPU 灵活性较好，但性能效率并非极致；DSA 性能突出，灵活性却较弱，很难应对复杂计算对灵活性的要求；FPGA 功耗与成本偏高，需要定制开发，落地案例有限；ASIC 功能完全固化，难以适应多变复杂的计算场景。

由此可见异构计算本身仍存在矛盾：系统越复杂，就越需要灵活的处理器；性能挑战越大，就越倾向于定制化加速。单一处理器无法同时满足性能与灵活性的需求。为此，超异构概念应运而生，它把多种 XPU 有机结合起来，取长补短，以兼顾性能与灵活性来应对复杂场景。

## 7.4.3 从异构到超异构
超异构为何必然到来，可以从三个维度来理解。

**需求驱动**：软件应用层层出不穷，热点大约两年一换。人工智能、大数据、元宇宙等新兴技术的快速演进，对算力提出了更高要求，传统单一架构难以支撑。现有的热点技术还在加速迭代，例如元宇宙要实现逼真的沉浸体验，算力需提升约 1000 倍。超异构通过融合不同计算单元的优势，能够显著提升性能，为元宇宙等新技术落地提供支撑。

**工艺与封装支撑**：Chiplet 封装让单芯片层次就能构建规模提升数量级的超大系统。把多个芯片封装在同一封装体内，可以大幅提高集成度与性能，也使得在单一封装内集成多种 XPU 成为可能，从而推动超异构发展。

**系统架构持续创新**：通过架构创新，单芯片层次即可实现多个数量级的性能提升。异构架构、多核架构等不断涌现，能够充分发挥不同处理器的优势。异构编程本身就很困难，超异构编程难度更高，如何驾驭它成为成败关键。

综合来看，超异构的出现顺应时代需求，是突破单一架构性能瓶颈、满足日益增长计算需求的必然选择。

结合第 2 章图 2.1.3，超异构本质上是集合三种以上引擎或架构的超架构，并非简单堆砌，而是对异构计算进行整合重构，让各类处理器之间实现充分灵活的数据交互，形成统一的超异构计算体系。计算演进的路径是从单核串行到多核并行，再到同构并行向异构并行迈进。图 7.4.7 概括了异构计算的发展脉络。

超异构具备以下基本特征：

超大规模的计算集群。超异构通常由大量计算节点组成，每个节点可包含 CPU、GPU、FPGA、DSA 等多种计算单元。节点通过高速互联网络连接，形成超大规模集群，能够提供大数据分析、人工智能、科学计算等场景所需的强大算力。

复杂计算系统，由分层分块组件构成，如图 7.4.8 所示。其复杂性体现在：不同计算单元性能特性各异，需要统一管理与调度；任务可能跨多个节点，需要分解与数据通信；还需兼顾功耗、可靠性等进行系统优化。

## 7.4.4 超异构的挑战与思考
前文阐述了超异构的概念与必要性，但实现之路也伴随诸多挑战。

### 1. 超异构的软件层
#### 1）遇到挑战
软件需要跨平台复用：跨架构、跨处理器类型、跨厂商平台、跨部署位置、跨设备类型。软件架构的复杂性因此急剧增长，成为最大挑战之一，见图 7.4.9。

#### 2）解决办法
开放接口与架构及生态：形成标准开放的接口与架构，开发者依此开发产品和服务，形成开放生态。
软件兼容：尽可能减少对已有应用的定制化开发，兼容现有软件生态，通过基础软件如编译层对接加速应用软件。
编程体系：提供门槛更低的编译体系，通过编程体系构建上层加速库以连接领域应用，即提供门槛较低的标准领域编程语言，如英伟达的 CUDA、昇腾的 Ascend C。
开放架构：进一步开放软硬件架构，避免架构过多导致市场碎片化，如 20 世纪 90 年代编译器百家争鸣最终聚焦到 2-3 个主流。

### 2. 硬件定义软件与软件定义硬件
目前存在三种可能的解法，如图 7.4.10 所示：

硬件定义软件 HDW：强调通过硬件定义软件功能与架构。软件开发与部署更依赖底层硬件特性，能够充分发挥硬件性能优势。核心是通过硬件加速器、专用指令集等为软件提供硬件层面支持，使软件运行更高效，并充分利用硬件并行计算能力。

软件定义硬件 SDH：强调通过软件定义硬件功能与性能。硬件设计实现更灵活，可快速响应软件需求变化。核心是通过软件抽象层 SAL 将软件与硬件解耦，使开发者专注功能实现，无需关注底层硬件细节。SAL 提供统一硬件接口，屏蔽平台差异，实现跨平台运行。

软硬件协同定义 Co-Design：强调软件与硬件协同设计与优化以实现最佳系统性能。软硬件团队紧密合作，共同探讨需求并提出软硬件解决方案。核心是打破传统界限，把软硬件设计视为整体，通过协同设计实现 1+1>2 的效果。

历史演进上，硬件与软件的关系经历了从“硬件定义软件”到“软件定义硬件”的转变。早期计算机系统业务逻辑主要由硬件实现，软件起辅助作用且依赖硬件接口。随着技术进步，“软件定义硬件”的理念逐渐兴起。

“软件定义硬件”也体现在硬件构建对软件接口的依赖。以 AI 算法为例，许多硬件加速器与专用芯片的设计都基于特定 AI 算法与框架，依赖软件提供的接口与规范来实现功能。这种软件驱动的硬件构建方式，使硬件能更好地适应应用需求变化，并与软件生态紧密结合。

答案与系统复杂度密切相关。对复杂度较低且迭代缓慢的系统，如 CPU，可快速设计优化的软硬件划分，先做硬件再做系统层与应用层软件，如 Windows 操作系统。此时硬件在一定程度上定义了软件开发与运行环境。

随着系统复杂度上升，如 GPU 所面临的情况，迭代速度加快，难以一次性实现完全优化。系统实现变为演进式过程。早期系统不稳定，算法与业务逻辑快速迭代，需快速验证想法。随着算法与业务逻辑逐渐稳定，后续可通过逐步优化 GPU、DSA 等硬件加速持续提升性能。

本质上这是一个系统定义过程。当复杂度过高时，难以一步到位，实现变为持续优化迭代。软件与硬件关系更加紧密动态，软件需求推动硬件优化演进，硬件进步又为软件创新提供可能。

总体而言，硬件定义软件与软件定义硬件两种关系都存在，系统复杂度的高低决定主导地位。低复杂度系统更常见硬件定义软件，高复杂度系统则更普遍软件定义硬件，且系统实现成为持续优化迭代的过程。

### 3. 计算体系与编译体系
超异构架构的处理器种类越来越多，需要构建高效、标准、开放的接口与架构体系，才能形成一致性的宏架构平台，避免场景覆盖碎片化。

当前正处于计算体系与编译体系变革期，应避免为某个应用加速而进行不必要的上层应用迁移对接到硬件 API，而应交由一致性的宏架构平台，即编译/操作系统来承担。

### 4. 超异构的未来
跨平台统一计算架构是未来计算资源中心化的关键，通过连接孤岛计算资源实现资源池化，可显著提升算力利用率。该架构能够支持应用软件跨同类处理器架构、跨不同类处理器架构、跨芯片平台以及跨云边端运行，满足复杂场景对算力的无限需求，形成开放生态。

为实现软件应用算法对硬件加速的支持，需要调整软件架构，将控制面与计算/数据面分离并实现接口标准化。同时，通过底层基础软件编译器自适应选择计算/数据，使数据输入/输出不仅可源于软件，也可源于硬件，甚至可下沉到硬件独立传输计算。

在超异构系统中，采用极致性能优化的分层可编程体系架构，绝大部分计算交由 DSA 进行极致计算，使系统整体性能效率接近 DSA。从用户角度看，应用仍运行在 CPU 上，开发者感知的是 CPU 可编程，通过操作系统与编译器区分异构。Chiplet 与超异构结合，可使系统规模数量级提升，整体性能实现数量级提升。

未来计算架构将呈现体系异构、平台化与开放生态的特点。超异构架构由 CPU、GPU、FPGA、DSA 多架构处理器组成，目标是接近 CPU 的灵活性与 ASIC 的性能效率，在不影响开发效率的前提下实现整体性能数量级提升。平台化与可编程的目标是实现软件定义一切、硬件加速一切，通过完全可软件编程的硬件加速平台满足多场景多用户需求并适应业务演进。建立标准开放生态，拥抱开源开放，支持云原生与云网边端融合，实现用户无平台依赖。

小结与思考
超异构计算融合多种计算架构如 CPU、GPU、FPGA 等，以应对摩尔定律放缓后对计算性能的持续增长需求。
超异构计算面临软件层跨平台复用、软硬件协同定义、计算与编译体系变革等挑战，需要开放接口、架构创新和统一编程模型来克服。
超异构计算的未来趋势是构建跨平台统一计算架构，实现软件应用算法对硬件加速的自适应支持，形成开放高效的计算生态系统。

# 第 8 章 传统编译器
## 8.1 引 言
随着深度学习不断发展，AI 模型结构快速演化，底层计算硬件技术层出不穷。对开发者而言，既要考虑如何在复杂多变场景下有效发挥算力，又要应对 AI 框架持续迭代。AI 编译器成为广受关注的技术方向，让用户专注上层模型开发，降低手工优化性能的人力成本，进一步挖掘硬件性能空间。

本节将探讨编译器的基础概念，以便更好地回答：什么是编译器？为什么 AI 框架需要引入编译器？AI 框架与 AI 编译器之间是什么关系？

### 8.1.1 编译器与解释器
编译器与解释器都能把编程语言和脚本语言转换为机器语言。最大区别在于：**解释器在程序运行时将代码转换成机器码，编译器在程序运行之前就完成转换。**

> 机器语言：由一系列二进制模式组成，例如 110110，表示计算机应执行的操作。机器语言程序可执行，可直接在硬件上运行。

#### 1. 编译器
编译器可把整个程序转换为目标代码，这些目标代码通常保存在文件中。目标代码也称二进制码，链接后可被机器直接执行。典型编译型语言有 C 和 C++。

编译器的主要特点如下，见图 8.1.1：
编译器读取源程序代码，输出可执行机器码，即把开发者代码转换成 CPU 等硬件能理解的格式。
将输入源程序转换为机器语言或低级语言，并在执行前报告程序错误。
编译过程复杂，会消耗较多时间分析处理源代码。
可执行结果属于某种特定于机器的二进制码。

目前主流如 LLVM 与 GCC 等经典开源编译器类型分为前端、中间层、后端。①分析阶段也称前端编译器，将程序划分为基本组成，检查词法、语义、语法，然后生成中间代码。②中间层主要是分析和优化源程序代码，分析包括词法分析、语义分析和语法分析；优化主要是优化中间代码，去掉冗余代码、子表达式消除等。③合成阶段也称后端，针对具体硬件生成目标代码，合成阶段包括代码优化器和代码生成器。

#### 2. 解释器
解释器可直接执行程序或脚本语言编写的指令，无需预先转换成目标代码或机器码。典型解释型语言有 Python、PHP 和 Matlab。

解释器的主要特点如下，见图 8.1.2：
将用高级语言编写的程序代码翻译成机器级语言。
解释器在运行时逐行把源代码转换为机器码。
解释器允许在程序执行时求值和修改程序。
分析和处理程序的时间相对较少。
与编译器相比，程序执行相对缓慢。

编译器与解释器最大差别在于编译器把程序作为整体翻译，而解释器逐条翻译。编译器生成中间代码或目标代码，而解释器不创建中间代码。执行效率上，编译器远快于解释器，因为编译器一次完成整个程序，而解释器逐行编译非常耗时。资源占用方面，由于要生成目标代码，编译器比解释器需要更多内存。

编程体验差异也很大，编译器同时显示所有错误，定位错误较困难，而解释器逐条显示语句错误，更易检测。具体而言，编译器中程序出现错误时会停止翻译，删除错误后需重新翻译整个程序。而解释器中发生错误时会阻止其翻译，删除错误后翻译才继续执行。

### 8.1.2 JIT 和 AOT 编译方式
