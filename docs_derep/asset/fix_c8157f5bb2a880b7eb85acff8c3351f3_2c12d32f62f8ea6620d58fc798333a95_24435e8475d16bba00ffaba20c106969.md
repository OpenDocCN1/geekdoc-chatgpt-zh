在规范化的分工协作里，Manager 负责把任务拆解并下达，会明确编号、目标、具体要求、优先级、交期以及交付样式。Worker 回执确认后进入执行，并实时推送进展与遇到的卡点。当 Worker 因付费文献无法访问而受阻，会向 Manager 请示，Manager 结合实际情况调整任务边界并给出明确指令。任务收束时 Worker 提交成果并汇报。整套标准交互让执行过程可控且透明。

### 2.2.4 竞争协同：多Agent方案竞选

竞争协同属于一种颇具特色的多智能体协作范式，核心思路是让若干智能体围绕同一问题各自独立产出方案，再借助评选机制遴选最优或整合各家亮点。这种做法借鉴了社会招投标与学术同行评议，有助于打破单一视角局限并提升决策质量。

评选机制的设计决定了效果。常见做法有：投票制，由多名智能体对各方案投票，按得票排序；评分制，由专职评判智能体多维度打分；辩论制，让提案方相互质询与辩护，在交锋中暴露优劣；共识制，通过多轮讨论收敛到各方可接受的方案。研究表明，推理类任务中投票可带来约13%的性能提升，而知识问答类任务中共识制优势更明显。

图2-7展示了竞争协同与方案评选的完整流程。

问题发布时，待解议题向所有参选智能体广播；独立提案阶段，三名方案智能体分别从保守、激进、平衡三种立场各自设计解法且互不交流，以保证多样性；方案评估阶段，通过投票、打分或辩论进行评判，由独立评判智能体给出中立裁决；决策输出阶段，根据评估结果择优或融合各家优点形成最终解。

### 案例2-1 多Agent方案竞选的实际应用

> 【场景】电商平台需要设计促销活动方案

【参与 Agent】

- 营销 Agent：侧重品牌曝光和用户增长
- 财务 Agent：侧重成本控制和 ROI 最大化
- 运营 Agent：侧重执行可行性和用户体验

【竞选过程】

1. 各 Agent 独立提交促销方案（满减/折扣/赠品等）
2. 评判 Agent 从效果、成本、风险三维度评分
3. 三个 Agent 对彼此方案提出质疑和改进建议
4. 经过两轮辩论，各方案优缺点充分暴露

【最终决策】

## 2.3 新兴Agent通信协议

【学习目标】

- 1) 理解MCP协议的架构设计和核心组件
- 2) 掌握A2A协议的通信机制和应用场景
- 3) 了解ACP协议的设计理念及其与A2A的融合
- 4) 能够根据实际需求选择合适的协议组合

协议标准化是支撑大规模多智能体协作的基础设施。下面介绍三大主流协议及选型思路。

### 2.3.1 MCP（模型上下文协议）：Agent与工具的标准接口

模型上下文协议（Model Context Protocol，MCP）由Anthropic于2024年11月发布，目标是解决AI系统与外部数据源、工具之间的连接问题。发布前，每个AI应用都需为不同数据源和工具编写定制集成，形成“M×N问题”。MCP通过统一接口把问题简化为“M+N”：模型只需实现一次MCP客户端，工具只需实现一次MCP服务器即可任意组合。

MCP常被比喻为“AI应用的USB-C接口”，如同USB-C统一了充电与数据传输，MCP统一了AI系统访问外部资源的方式。自发布以来，OpenAI、Google DeepMind、Microsoft等厂商相继支持，社区贡献的MCP服务器数在数月内突破1000个，覆盖GitHub、Slack、Google Drive、各类数据库等。

图2-8展示了MCP协议的整体架构设计。

[PRE2]

图2-8 MCP协议架构图

图2-8中，最上层的MCP Host为承载AI能力的应用程序，如Claude Desktop或支持MCP的IDE，内含LLM并负责管理MCP客户端连接。中间层的MCP Client为协议客户端实现，负责发现可用MCP Server并发起调用。底层的MCP Server为轻量级连接器，每个Server专门对接一种外部服务或数据源。Client与Server间通过JSON-RPC 2.0通信，支持stdio和HTTP SSE两种传输方式。右侧列出MCP的五大核心能力类型：Tools用于调用功能、Resources用于访问数据、Prompts提供预定义模板、Sampling支持向LLM请求补全、Roots定义文件系统访问范围。

表2-2 MCP核心组件与功能说明

| 组件 | 角色定位 | 主要功能 | 典型示例 |

| :--- | :--- | :--- | :--- |

### 2.3.2 A2A（Agent2Agent协议）：跨Agent通信标准

Agent2Agent协议（A2A）由Google于2025年4月在Google Cloud Next大会发布，专门解决智能体间通信与协作问题。与MCP聚焦智能体与工具/数据连接不同，A2A关注智能体如何发现彼此、交换信息、协调任务。发布时即获逾50家技术伙伴支持，包括Atlassian、Salesforce、SAP、ServiceNow等。2025年6月，A2A捐赠给Linux基金会，成为行业中立标准。

A2A核心理念是让智能体“作为智能体”而非“作为工具”通信。工具具有固定输入输出与确定性行为，而智能体具备自主推理能力。在A2A视角中，企业应用通常同时使用MCP连接工具数据与A2A连接其他智能体，二者互补。

图2-9展示了A2A协议的通信流程。

[PRE4]

在发现阶段，Client Agent通过访问Remote Agent的/.well-known/agent.json端点获取Agent Card，了解对方能力与调用方式。在任务提交阶段，Client Agent通过POST请求发送任务消息，包含任务ID与消息内容。执行阶段支持通过SSE进行流式状态更新，Client可实时获知进度。结果返回阶段，Remote Agent以Artifact形式返回执行结果，支持文本、图像、音视频等多模态。

表2-3详细解释了A2A协议的三个核心概念。

表2-3 A2A协议核心概念（Agent Card、Task、Message）

| 概念 | 定义与作用 | 核心字段 | 类比说明 |

| :--- | :--- | :--- | :--- |

| Agent Card | Agent 的身份名片<br>描述 Agent 是谁、能做什么<br>如何与它交互 | name: Agent 名称<br>description: 能力描述<br>skills[]: 技能列表<br>endpoint, auth, modalities | 类似 LinkedIn 个人主页<br>展示资质和联系方式<br>供他人了解和联系 |

| Task | 有状态的工作单元<br>封装完整的任务生命周期<br>支持长时间运行 | id: 任务唯一标识<br>status: submitted/working/<br>completed/failed/canceled<br>artifacts[]:输出结果 | 类似工单系统<br>有创建、处理、完成<br>等完整生命周期 |

| Message | Agent 间的通信载体<br>承载对话内容和数据<br>支持多模态 | role:user/agent<br>parts[]:消息内容片段<br>支持 text/file/data 等类型 | 类似聊天消息<br>可包含文本、文件、结构化数据等 |

从表2-3可见，A2A围绕Agent Card、Task、Message构建。Agent Card是身份名片，包含名称、能力描述、技能列表、服务端点、认证方式和交互模态，使其他智能体可发现并调用。Task是有状态工作单元，封装从提交到完成的生命周期，适合长时间任务。Message是信息载体，通过parts数组支持文本、文件、结构化数据等混合内容。

### 2.3.3 ACP（Agent通信协议）：IBM的开放互操作方案

ACP与MCP定位分工明确：MCP专注智能体与工具/数据连接，ACP专注智能体与智能体通信。设计上ACP采用REST风格HTTP接口，无需特定SDK即可调用，甚至可用curl或浏览器测试，降低集成门槛。

值得注意的是，2025年8月IBM宣布将ACP与Google的A2A协议合并，共同在Linux基金会旗下推进标准统一。合并反映业界对标准统一的共识，ACP核心特性已整合进A2A，BeeAI平台亦迁移至使用A2A作为通信层。

图2-10展示了ACP协议架构及其与BeeAI框架的关系。

BeeAI平台包含三个功能层：发现层负责智能体注册与能力索引，支持离线发现；编排层负责多智能体协调与任务路由；可观测层集成OTLP追踪与日志聚合，支持Arize Phoenix可视化。ACP协议层现已合并入A2A，位于平台与智能体之间提供统一通信接口。底部展示不同来源智能体的接入方式：LangChain、CrewAI等框架智能体通过适配器接入，自定义智能体可原生实现ACP，外部A2A智能体通过桥接集成。
