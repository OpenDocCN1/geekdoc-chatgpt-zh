长任务最怕边做边失焦。规划-执行的做法就是把“想明白要做什么”和“动手把它做出来”拆开，先用自上而下的拆解把大目标切成块，再借助有向无环图 DAG 来排顺序、找并行，让漫长的流程既能全局可控又能并行提速。

### 7.2.1 架构概览：规划调度执行

单体 Agent 处理长程任务时，上下文越堆越长，很容易迷失初衷。规划-执行引入分层设计，把“大脑”和“手脚”功能上解耦，中间再由一个动态调度器协同。

图7-4 中的关键角色如下。

- 规划器 Planner，相当于大脑：把模糊的目标 Goal，比如“写一个贪吃蛇游戏”，转成结构化计划 Plan。关键不只是列清单，更要明确任务间的依赖，比如任务B要等任务A产出。

- 调度器 Scheduler，相当于神经中枢：管理任务状态流转，比如待办→进行中→已完成。它读懂 DAG，任务A一结束就把任务B推入执行队列。

- 执行器 Executor，相当于手脚：通常是 ReAct 风格的 Agent，从队列取出具体任务如“编写 snake.py 核心逻辑”，专注执行到完成。

- 重规划器 Replanner，负责纠偏：当执行失败或任务A的结果让任务B不再必要时，它会介入动态调整剩余计划。

这种分层让每个 Agent 的认知负担下降，还天然支持断点续传。系统崩溃后，只要从记忆里恢复任务状态，调度器就能继续派发，不必从零重来。

### 7.2.2 规划-执行的核心机制

模式之所以有效，不在于把任务变简单，而在于把复杂度降维，靠四件事把不确定的难题变成可工程化的步骤。

**1. 任务分解与 DAG**

核心在于把大任务拆开。早期思路接近层次任务网络 HTN。

- 复合任务 Compound Task，如“编写代码”，需要继续拆分。
- 原子任务 Primitive Task，如“创建文件”，可直接交给执行器。
- 串行依赖：B 必须等 A 的输出，比如先爬数据再分析。
- 并行独立：C 与 D 互不影响，比如前端 HTML 和后端 SQL 可以同时进行。

单纯清单不够用，必须引入依赖管理与 DAG 来编排。规划器输出的计划通常包含 id、instruction 和 dependencies 三个字段。

**2. 状态隔离与上下文注入**

降低幻觉的关键是规划器和执行器用不同上下文。

- 规划器上下文只关注任务状态，例如 A 已 Done，摘要为“Data scraped”。
- 执行器上下文只聚焦当前任务细节。

调度器在启动任务 B 时，会把任务 A 的实际产出注入 B 的 Prompt，保证信息准确连贯。

**3. 动态重规划**

计划不是一成不变的。

- 执行前生成初始静态计划。
- 执行中每完成一项就更新全局状态。

若任务 A 失败，会触发重新规划：规划器可能选择重试、跳过，或生成补救任务。

**4. 状态护具**

Anthropic 在“Effective Harnesses for Long-Running Agents”里提出“状态护具 State Harness”。文章指出，Agent 做数小时长任务时，易因上下文过载或进程中断而崩溃，仅靠 LLM 上下文维持状态不可靠。工程上必须把中间状态——已完成步骤、当前变量、错误计数等序列化并持久化到数据库。即便进程挂掉或上下文溢出，也能从断点恢复。这是 Agent 从演示走向生产的关键稳定性基石。

DAG 管理依赖、上下文隔离降噪、重规划应对变化、状态护具保稳定，四者合力让 Agent 真正能扛住真实世界的复杂项目。

接下来看规划-执行模式在实践中的样子。

### 1. 全栈软件开发

- 场景：用户说“帮我写一个贪吃蛇游戏”。
- 痛点：文件间存在复杂的 Import 依赖，单体 Agent 容易写出结构混乱、逻辑不清的代码。
- 流程：
    - 规划器：生成完整文件清单及接口定义，比如 main.py 依赖 game.py，game.py 依赖 utils.py。
    - 调度器：解析依赖，发现 utils.py 无外部依赖，优先派发。
    - 执行器：领取 utils.py 开发任务，编码并通过单元测试。

借助标准作业程序把软件工程最佳实践固化进规划器的决策逻辑，能显著提升效率与代码质量。

### 2. 企业级数据分析

- 场景：“分析上季度销售数据，并把邮件发给 CEO”。
- 痛点：涉及 SQL 查询、Python 分析、邮件撰写三类异构能力，形成较长且依赖严格的处理链。
- 流程：
    - QuerySQL：从数仓拉取销售数据，耗时约 10s。
    - AnalyzePandas：基于 QuerySQL 结果清洗并生成可视化，依赖前一步。
    - DraftEmail：根据分析结果撰写邮件正文，依赖分析。
    - Review：人工介入审核准确性与合规性，依赖草稿。
    - SendEmail：审核通过后自动发送，依赖审核。

这里规划器扮演工作流引擎角色，协调多步多工具的有序执行，保证流程严谨可审计。

总体来看，规划-执行把 Agent 从聊天机器人提升到自动化工程师的层级，对兼具确定性与复杂性的场景是很好的选择。

### 7.2.4 演进与组合

该模式标志着 Agent 架构从单线程循环走向并行工程。大家逐渐意识到，光列任务清单不够，还要处理依赖、支持并发、动态调度。

### 1. 演进路径：从循环到编译

- BabyAGI，无限循环时代 2023 年初：采用“创建任务→执行→重排优先级”的循环。每完成一项就重生成整个清单，容易目标漂移 Goal Drift，甚至死循环。
- Plan-and-Solve，瀑布模型时代 2023 年中：先一次性规划，再按序串行执行。缺乏容错，中间一步出错，后面全停，也无法利用并行。
- LLM Compiler，DAG 编译时代 2024 年：将规划类比编译，通过并行把端到端延迟降到原来的 33% 到 50%。
    - 规划器生成任务 DAG，显式建模依赖。
    - 调度器分析数据依赖，动态并行调度无依赖任务，如同时搜索三个概念。

### 2. 模式组合示例

规划器作为大脑，需要与执行层的“手脚”和协作层的“组织”配合。

- 规划-执行 + ReAct = 战略定力与战术灵活统一：宏观开环保方向稳定，微观闭环做精细执行反馈。适合软件开发等长程复杂任务。
    - 规划器把控全局，生成高层计划。
    - 执行器用 ReAct Agent 处理报错、调试和工具调用，弥补 Plan-and-Solve 灵活性不足。
- 规划-执行 + 委托模式 = 组织化工程：把单体 Agent 的自我规划升级为多 Agent 系统的项目管理，适合企业级复杂项目。
    - 规划器演变为 Manager Agent。
    - 生成的不是简单函数调用，而是结构化任务工单。

### 7.2.5 设计哲学：关注点分离

模式的核心是 Separation of Concerns。

- 规划器负责“是什么”和“为什么”，需要强推理能力如 GPT-4，通常 Token 消耗不大。
- 执行器负责“怎么做”，可用响应更快模型如 GPT-3.5 或 Claude Haiku，专注细节执行。

分离不仅降成本，更提升鲁棒性。执行失败时不必推翻战略，只需调整战术，这正是容错机制。

在 7.3 节我们会深挖执行层细节：面对成百上千工具时，Agent 如何选择、如何像人一样熟练使用。

## 7.3 工具编排模式

> “工欲善其事，必先利其器。”
> ——《论语·卫灵公》

> “语言模型可以在极少人工干预的情况下，学会有效地使用外部工具。”
> ——Toolformer 论文①

如果 ReAct 像突击队的迅捷行动，规划-执行像指挥官的蓝图，工具编排就好比后方军械库管理员，确保资源被最有效调配。

当 Agent 请求支援时，管理员要解决三件事。

- 检索 Retrieval：库里上万工具，哪个最匹配当前场景？语义路由。
- 适配 Adaptation：选中工具需要哪些参数？参数填充。
- 组合 Composition：是否要多工具协同形成链路？工具链构建。

面对搜索、计算、绘图、发邮件等成百上千工具，Agent 如何像老工匠一样快速精准抓取？

工具编排解决模型与外部世界交互的“最后一公里”。通过标准化接口和智能选择机制，突破上下文窗口限制，灵活调度海量能力，从封闭大脑走向开放生态。

### 7.3.1 模式架构：能力总线

简单演示可以把所有工具 API 写进 System Prompt。企业级场景工具可达成千上万，出现 API 蔓延。此时核心要从“调用”转向“分发”，需要构建能力总线 Capability Bus。

图7-5 架构要点如下。

- 工具注册表 Tools Registry：工具的“户口本”，存储名称、嵌入向量、JSON Schema，支持动态维护。
- 语义路由器 Semantic Router：分诊台。工具超过 100 个时，利用面向工具的 RAG 从注册表检索最相关的前 5 个工具注入 Prompt。
- 协议适配器 Protocol Adapter：翻译官。模型输出标准 JSON，下游 API 可能要 gRPC、SQL 或特定 HTTP Header，适配器负责转换。

这样 Agent 不必记忆所有 API 文档，专注意图理解与参数生成。

### 7.3.2 工具编排核心机制

不只是把 API 注入模型，还需要三大机制保证准确率与鲁棒性。

#### 1. 语义路由

Prompt 装不下所有工具定义时，需要动态上下文。对所有工具描述向量化。

运行时流程：

- 用户查询触发工具选择。
- 向量检索：把查询嵌入，在工具库中找最相关项。
- Top K 筛选：按相似度排序，取前 K 个候选。
- 提示注入：把候选工具说明、Schema、调用格式动态注入 Prompt，引导模型决策。

语义路由让 Agent 拥有无限工具库的感觉，每次只带当前任务需要的工具上阵。

#### 2. 结构化强制

语言模型天生爱聊天不爱填表。为保证 API 调用成功，必须在推理阶段加语法约束。

- JSON 模式 JSON Mode：强制模型输出严格符合 JSON 语法。
