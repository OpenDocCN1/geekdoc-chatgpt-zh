(4) StructuredOutputParser：能直接输出结构化内容，不需要先定义数据结构。它和 PydanticOutputParser 用途相似，差别在于省略了模型定义这一步。

(5) PydanticOutputParser：通过预先设计 Pydantic 模型来规范输出，要求模型严格按照该结构返回信息，随后解析器会把文本解析成对应模型的对象。

### 6.2.4 索引

索引的核心在于对文档进行结构化处理，提升模型与文档的交互效率，常见于问答系统、知识库构建等场景，可直接从原始材料中抽取答案。

在索引层面，LangChain 为开发者准备了一组常用组件，用于导入与检索各类文档资料，主要包括：

+   (1) Document Loaders（文档加载器）：从多种数据源读取文档。读取之后需要把原始内容封装为 Document 对象，以供后续环节调用。

+   (2) Text Splitter（文本切分器）：负责把长文本切分成若干片段。无论是把文本作为提示发送给 OpenAI API，还是使用其嵌入功能，均受字符数限制，因此必须先把加载的文档拆分。

+   (3) Vector Store（向量存储）：把文档保存为向量形式。因为相关性搜索本质上是向量计算，不论调用 OpenAI 嵌入接口还是直接在向量数据库中查询，都需要先把文档转成向量。操作很简单，只需把数据写入对应的向量库即可，如图 6-2 所示。

### 6.2.5 内存

### 6.2.6 链

同时也可以将多条链串联，构建更复杂的流程。每条链负责特定的功能或任务，整体应用通过链的组合实现更完整的能力。

组合链后可以实现更高级的对话流程与逻辑。各链分别承担输入处理、语义解析、上下文管理等职责，这种方式让应用构建更灵活，也便于按需定制与扩展。简而言之，链接收一个提示模板，在用户提供输入后进行格式化，再把结果传递给语言模型以获取响应，如图6-3所示。

### 6.2.7 代理

代理把语言模型当作思考引擎来决定下一步操作。我们会为代理配置一系列工具，代理根据用户输入判断哪些工具能达成目标，并持续调用工具直至目标完成。

从某种角度看，代理是链的增强版：它不仅绑定提示模板和语言模型，还可以挂载外部工具。

代理是一个智能主体，其职责是在用户输入和应用场景的约束下，从可用工具池中挑选合适的工具执行操作。面对不同复杂度的任务，代理会采取不同的策略，即可根据实际情况选择最合适的工具，实现高效准确的执行。

总体而言，代理是以语言模型做推理的智能主体，可依据输入和场景选择工具，并按任务复杂度采取不同策略，从而更灵活智能地完成各类任务。

目前主要有两类代理。

(1) 动作代理（Action Agent）：每次只执行一个动作，根据执行结果再决定下一步。

(2) 计划执行代理（Plan-and-Execute Agent）：先制定一系列待执行操作，再按预定顺序逐个执行。

对于简单任务，动作代理更常见也更易实现。对于复杂或长期运行的任务，计划执行代理的初始规划有助于保持长期目标的聚焦。不过计划执行代理会增加调用次数并带来更高延迟。这两类代理并不互斥，可让动作代理执行计划执行代理所制定的计划。

代理内部涉及的核心概念如下。

+   (1) 代理：应用程序的主要逻辑单元，接收用户输入和已执行的操作列表，返回 AgentAction 或 AgentFinish。

+   (2) 工具：代理可以调用的动作，如发起 HTTP 请求、发送邮件、执行命令等。

+   (3) 工具包：为特定用途设计的一组工具集合。例如让代理与 SQL 数据库交互时，可能需要查询工具和查看表结构的工具。工具包可以看作工具的组合。

+   (4) 代理执行器：把代理和一系列工具封装在一起，负责循环运行代理直至满足停止条件。
