单体式架构：把整个业务逻辑打包成一个高度耦合的整体进行开发与发布，功能模块集中在一起，通常共享同一技术栈。

客户端-服务器架构：把系统拆成客户端与服务器两端，客户端承担界面展示与用户交互，服务器负责接收请求、执行业务逻辑并管理数据存储。

事件驱动架构：以事件与消息作为通信基础，各组件通过事件的产生、发布与订阅实现协作，达到解耦与灵活响应。

分层架构：按职责把应用切分为若干层次，各层功能明确且松耦合，便于维护，典型三层为表现层、业务逻辑层与数据访问层。

领域驱动设计架构：以业务领域为核心，把系统拆解为领域模型与领域服务，依托对业务的深入理解构建内聚性强、耦合度低的设计。

服务导向架构：把应用组织成一组可复用的服务单元，服务间通过标准化接口交互，每个服务对应特定业务功能，可独立部署与升级。

微服务架构：把应用拆分为多个小型且自治的服务，每个服务聚焦单一业务能力，支持独立开发、部署与弹性扩缩，通过轻量机制协同。

## 12.3 分层架构
分层架构是一种常用模式，把应用按职责划分为不同层次，每层承担特定功能。核心概念与原则如下。

(1) 层次划分：系统被拆分为多个层级，各层职责清晰，常见包括表现层、业务逻辑层和数据访问层。
(2) 分离关注点：每层聚焦特定任务，与其它层保持松耦合，使开发、测试与维护可独立进行。
(3) 接口定义：层间通过明确接口通信，接口清晰描述交互方式，便于层间替换与切换。
(4) 单一职责：每层只负责与其相关的任务，提升代码可读性、可维护性与可测试性。
(5) 可扩展性：可在不影响其它层的前提下对单层进行扩展，例如增加新的表现层或业务逻辑层。
(6) 可重用性：鼓励把可复用组件放在合适层级，提高复用率，减少重复开发。
(7) 安全性和可靠性：可在各层实施安全与错误处理机制，提升整体质量，例如数据访问层进行校验与访问控制。

采用分层架构，团队能够把复杂系统拆解为更小可控的模块，实现模块化、可维护与可扩展的设计，有利于组织代码与并行协作。

### 12.3.1 分层架构的核心构成
分层架构把系统功能与职责划分为多个逻辑层，各层职责明确。

( 1 ) 表现层 Presentation Layer：负责用户界面与交互，包含 UI 组件、视图模板、控制器等，接收用户输入、展示数据并处理操作。
( 2 ) 业务逻辑层 Business Logic Layer：又称服务层，负责业务规则与流程，包含业务服务、业务流程、校验逻辑等，协调业务功能并执行规则。
( 3 ) 数据访问层 Data Access Layer：负责数据交互与持久化，包含数据访问对象 DAO、对象关系映射 ORM 等，用于从数据库或其他存储读取与写入。

### 优点
+ * 可维护性：层次分离明确，修改某层不会波及其它层，降低维护成本与副作用。
+ * 可测试性：各层可独立进行单元测试与集成测试，便于验证功能与逻辑。
+ * 可扩展性：可对不同层独立扩展，松耦合设计让系统灵活应对规模与需求变化。
+ * 可重用性：接口与依赖清晰，促进组件复用，将同一层组件应用于不同系统可提升效率。

### 缺点
+ * 增加复杂性：额外层次与接口提升系统复杂度，需要较强的设计能力把控依赖。
+ * 性能开销：层间通信与数据传递会带来一定开销，高并发场景需精细优化。
+ * 过度设计：对小型或需求频繁变化的系统，复杂分层可能增加开发与维护负担。
+ * 增加通信成本：多层传递与转换提升延迟与通信成本。
+ * 不适合简单系统：对于小规模简单应用，分层可能冗余，单层架构更直观高效。

权衡上述利弊后选择合适模式，分层架构在多数场景下灵活强大，但在特定情境下需考虑其它方案。

### 分层架构的应用场景
分层架构适用于多种场景。

+ (1) Web 应用程序：可将界面层、业务逻辑层与数据访问层分离，实现良好的模块化与前后端协同。
+ (2) 企业应用程序：对复杂业务逻辑与数据流进行管理，不同层次处理不同业务功能，易于开发测试维护。
+ (3) 移动应用程序：分离界面、业务与数据访问，利于代码复用与跨平台开发，保持可维护与可扩展。
+ (4) 大型系统集成：把大型集成方案划分为多个模块与子系统，各模块负责不同功能，提升可伸缩、可维护与可测。
+ (5) 面向服务的架构 SOA：分层构建服务，通过层次划分实现松耦合与可复用，促进灵活性与扩展性。

分层并非万能，小型简单应用使用分层可能带来不必要复杂度，选择时应结合规模、需求与复杂程度。

### 领域驱动设计架构
领域驱动设计 Domain-Driven Design 是一种将业务领域与软件设计紧密结合的方法，旨在构建易理解、可维护、可扩展的系统。关键概念如下。

#### (1) 领域模型
DDD 的核心是领域模型，它是对业务领域的抽象映射，包含业务概念、规则与行为。通过建模可更好地理解需求并转化为实现。

#### (2) 聚合根
聚合根是领域模型中的核心实体，代表一组相关对象的业务一致性边界，通过聚合根访问与操作，并承载关键业务操作与规则执行。

#### (3) 领域服务
领域服务用于处理跨越领域模型边界的业务逻辑，提供高级操作并与聚合根及其它领域对象协作，常用于解决复杂业务场景。
