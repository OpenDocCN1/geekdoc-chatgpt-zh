笔者确实没有理解这个笑话，不过这不重要。重要的是同样的代码再跑一次，模型竟然原封不动地吐出同一个段子。重复感让人觉得乏味，能不能让每次生成的笑话都不一样呢？

先说默认的做法。主流大模型在生成时用的其实是贪心策略，每一步都挑当前概率最高的 token，一直选到生成结束符或者达到设定的最大长度为止。我们真正想要的，是整条序列的联合概率最高，而不是每一步单独最优，这个差别在图3-1里就能看出来。

[PRE1]

就拿图3-1来说，按贪心走最终会得到“我喜欢吃饭”。因为每一步都只看当下最大的词，但算下来“我喜欢学习”的整体联合概率反而更高。要怎么让模型去找整段概率最大的输出呢？办法就是 Beam Search。贪心每步只保留一个候选，Beam Search 则保留一组候选。

比如把 Beam 设为 2，模型会始终保留当前累计概率最高的两个序列。回到图3-1的例子，第一步会留下“我喜欢吃”和“我喜欢学”，它们的累计概率大约是 0.32 和 0.28。随后两个分支各自往下预测，再算联合概率，如图3-2所示。

[PRE2]

算下来“我喜欢吃饭”的联合概率是 0.128，“我喜欢学习”是 0.196，这两个是第二步里概率最高的序列。Beam Search 会继续为它们扩展下一个 token。若把最大生成长度设为 2，也就是到第二步就结束，最终输出的就是概率更高的“我喜欢学习”。

在代码里通过参数 num_beams 打开 Beam Search 就能复现这种效果。

[PRE3]

打开之后重新跑程序，输出确实和原来不同了。但只要 num_beams 的数值不变，多跑几次结果依然固定。因为在所有候选里，概率最高的那个序列是确定的，不会因为重复运行而改变。

想让结果每次都不同，就得给采样过程加入随机性。常见的做法是不总是取概率最高的 token，而是在概率靠前的几个里随机挑，这就是 top_k 的思路。

[PRE4]

把 do_sample 设为 True，再把 top_k 设成 10，多试几次就能发现每次的生成都不一样，多样性明显提升。

大模型内部的采样是怎么做的？先算出每个 token 的 logits，然后只保留 top_k 的 logits，其余的 logits 被置成一个很大的负数，再做 softmax。这样被剔除的 token 被选中的概率就变成 0，而保留下来的 token 概率依然是不均匀的，这个过程如图3-3所示。

[PRE5]

和 top_k 类似的还有 top_p。它的做法是按概率从大到小依次累加 token，直到累加和超过设定的 top_p 值就停止。流程上也是先 logits 转 softmax 得到概率，再筛选出满足阈值的 token 保留概率，未被选中的置零，重新 softmax。未进入列表的 token 选中概率为 0，如图3-4所示。

除了截断策略，控制随机性的另一个关键参数是温度值 Temperature。设定温度 t 后，logits 会先除以 t 再进入后续采样。温度对最终概率分布的影响如图3-5所示。

可以看出 t 取 0.5 时各 token 概率差距拉大，t 取 2 时差距被压缩。温度越低，输出越确定；温度越高，输出越不可控。可以根据需求调不同的温度来感受效果。

本章聚焦大模型在真实场景里会碰到的技术瓶颈。随着参数规模持续膨胀，训练与推理对硬件资源的消耗，特别是 GPU 显存，提出了极高的要求。为此社区涌现出一批优化手段，比如混合精度训练、模型量化以及各类新型推理框架。它们能在显著压缩显存占用的同时提升推理速度和效率。本章会梳理这些方法的原理与用法，帮助读者理解大模型的资源特性，以及在有限硬件下如何更高效地训练和推理。

## 4.1 GPU 背后的工作机制

[PRE9]

作为算法工程师，日常大多用 PyTorch 或 TensorFlow 这样的框架训练模型，底层通过 CUDA 调用 GPU，复杂的编程细节被屏蔽掉了。但在模型越来越大的今天，算力与显存成为瓶颈，深入了解 GPU 如何工作变得很重要。比如 vLLM 中的 PageAttention 以及训练里默认使用的 FlashAttention，都建立在对 GPU 机制的理解之上。

### 4.1.1 CPU 和 GPU 设计思路为何不同

先对比中央处理器 CPU 和 GPU 的设计目标。CPU 面向通用任务，追求低延迟和快速响应，擅长把单个任务迅速完成。因此 CPU 使用率通常达不到 100%，长期满载会拖慢系统响应。可以把它想象成私家车，平时停在车库，路上就能快速把人送到。

GPU 则追求高吞吐量，专为海量简单计算而生。工作时期望使用率接近 100%。它更像地铁，单次速度不及私家车，但可以满载、同时运送大量乘客去同一目的地。

起初 GPU 主要服务图形渲染，因为每个像素的计算是简单的重复操作。CPU 逐像素处理效率低，GPU 可以并行处理多像素。后来游戏渲染和深度学习都依赖大量矩阵运算，这让 NVIDIA 在这两个赛道都取得成功。

并行是 GPU 的核心优势。拿 Intel 14 代 i7 举例，它有 20 个核心、支持 28 个并行线程。而 NVIDIA A100 拥有 6912 个 FP32 CUDA 核心、3456 个 FP64 CUDA 核心、6912 个 Int32 CUDA 核心、432 个 Tensor 核心，可支持 13824 个并行线程。这种规模的并行能力让 GPU 在图形和深度学习任务上优势明显。

### 4.1.2 GPU 的架构

GPU 用的是单指令多线程 SIMT 架构，让大量线程同时执行同一条指令，从而提升效率，比如矩阵乘法里每个结果元素的计算都可以交给一个独立线程。

在实现上，每 32 个线程组成一个 Warp，作为调度和执行的最小单元，保证并行执行时的协调性。以 A100 架构图来看，如图4-1所示。

图中密集排列的部分是 CUDA 核心和 Tensor 核心，它们被划分为多个流式多处理器 SM。A100 共有 108 个 SM。

每个 SM 由 4 个处理单元组成，每个单元带一个 Warp 调度器，负责 Warp 的管理和调度，如图4-2所示。

每个处理单元里有 16 个 Int32 核心、16 个 FP32 核心、8 个 FP64 核心以及 1 个 Tensor 核心。CUDA 核心处理通用计算并针对不同数据类型优化，Tensor 核心则专攻深度学习计算。SM 下方还有 LD/ST 单元负责数据的加载与存储，SFU 负责三角函数、指数、对数、平方根等特殊数学运算。

### 4.1.3 GPU 里的存储

GPU 计算能力强，但常被数据搬运拖住。训练大模型时，计算单元常常在等数据到来。

以 A100 为例，FP64 算力约 19500 GFlops，每个 FP64 数据 8 字节，显存带宽 1555 GB/s。把一个 FP64 数据搬到核心至少需要 100 次浮点运算才能让 GPU 满载。若运算量不足，核心就会空闲。

好在深度学习里的矩阵乘法是计算密集型操作，通过调大矩阵尺寸能提升计算强度。设矩阵为 N×N，每个元素约需 2N 次计算，总计算量约 2N³，数据量约 2N²，二者比值约为 N。可通过调整 N 来匹配硬件，如图4-3 所示。

数据传输越慢，就越需要更大的矩阵来喂饱计算单元；传输越快，矩阵可以越小。反之，若矩阵本身很小且带宽不足，就难以发挥算力。

再看 GPU 内部存储。芯片内有寄存器、L1 缓存、共享内存、L2 缓存；芯片外就是显存。访问速度差异很大：L1 约 19 TB/s，L2 约 4 TB/s，主显存约 1.5 TB/s，经 PCIe 访问主机内存仅约 0.025 TB/s，NVLink 多卡互连可达 0.3 TB/s。

因此最好让计算单元尽量少访问低速存储，多从高速缓存读取，并对一次读取的数据做尽可能多的计算。这正是 Flash Attention 优化思路的出发点。

回到 A100 架构，108 个 SM 各自带 CUDA 核心、Tensor 核心和 L1 缓存，SM 外部有 L2 缓存和 HBM 显存，底部 NVLink 负责多卡通信，顶部 PCIe 负责与主机通信。

### 4.1.4 Tensor Core

得益于 Tensor Core，GPU 在硬件层面支持混合精度训练，即结合 FP32 和 FP16，在不明显损失精度的前提下加速训练并减少显存，后续章节会详细展开。

一个 Tensor Core 在一个时钟周期内可完成两个 4×4 矩阵的乘法加一个 4×4 矩阵的加法。两个被乘矩阵为 FP16，求和矩阵可以是 FP16 或 FP32，如图4-4所示。

内部实现上，两个 FP16 操作数先做全精度乘法，再用 FP32 累加，以避免精度丢失，如图4-5所示。

从 A100 算力表可见，Tensor Core 的算力远超 CUDA Core。表中出现一对指标，后者是前者的两倍，这对应稀疏计算模式，如图4-6所示。

要做稀疏推理，需要先对训练好的参数矩阵做处理：把参数每 4 个一组，挑出相对较小的两个置零，其余微调以补偿误差。处理后得到约一半参数为零的稀疏矩阵，压缩存储非零元素及其索引，用这种压缩后的矩阵推理即可获得 Tensor Core 更高的稀疏推理性能，具体流程如图4-7所示。
