## 8.2 A2A：跨厂商 Agent 对话的通用通道

技术栈、框架、数据格式各不相同，Agent 之间想协作常常被困在信息孤岛。A2A 就是为打通这道墙而设计的开放方案。

### 8.2.1 A2A协议简介

A2A 是一款面向 Agent 间联动与配合的开放规范，支持来源与技术路线迥异的代理安全交换信息、共同完成复杂工作。它的追求很直接：拆掉系统壁垒，让跨平台配合成为常态。

该规范由 Google 在 2025 年 4 月 9 日对外公布，意图让各家框架、各路厂商的 AI 代理能够互通协作，目前已有 50 多家科技公司站台，重点解决企业级 Agent 的互操作痛点。

作为开放标准，A2A 在用户侧与企业侧的通信场景里解决协作问题，主要体现在五方面：

（1）**共用消息语法**。给 Agent 制定一套统一的表达方式，能清楚说明“我要什么”“我给什么”。
（2）**自带寻址能力**。像社交平台找人一样，Agent 可以检索同类，搞清楚对方会什么，再决定是否联络。
（3）**工作拆分与委派**。遇到复杂需求时，Agent 能像 PM 一样把任务切块，指派给最擅长的那位同伴。
（4）**能力外显**。每个 Agent 都可以主动展示自己的强项，形成服务超市的展示位，类似简历投递。
（5）**准入与权限**。相当于电子门禁，只有通过校验的 Agent 才能对话，防止泄密或越权操作。

### 8.2.2 A2A协议的关键概念

**智能体卡片** 是一份公开的元数据，通常放在 /.well-known/agent.json，用来记录该代理的能力、技能、接入地址与鉴权要求。其他代理或调用方读取后就知道它能做什么，相当于代理的名片。

A2A **服务器** 指对外暴露 HTTP API 的代理，比如接收任务的接口。它收到请求后代为执行。

A2A **客户端** 是发起任务或对话的应用或代理。在代理对代理的场景里，一个代理的客户端侧会通过 A2A 规范调用另一个代理的服务端侧。

**任务** 是 A2A 里工作的最小单元。调用方通过 tasks/send 接口发消息来创建任务，每个任务都有唯一编号，状态会随着进展在 submitted、working、input-required、completed 等阶段间流转。

**消息** 是请求方与提供方交流的基本颗粒。请求方角色记为 “user”，提供方角色记为 “agent”。一次往返包含一次请求消息与一次应答消息。

**部分** 是消息内部的内容块。一条消息可由多块组成，可为文本、文件或结构化数据。例如 TextPart 承载纯文本，文件块可承载图像或二进制。

**工件** 指代理在任务执行期间产生的产出，比如生成的文件或结构化结果。

### 8.2.3 A2A协议的工作原理

一次 Agent 间通过 A2A 的交互大致分为三步：

（1）**寻址**。调用方先取回目标代理的卡片，确认名称、能力与请求入口。
（2）**发起**。调用方向服务端的 API 发起任务，通常是向 tasks/send 发 POST，请求里携带唯一任务编号与首条用户消息，即问题或指令。
（3）**执行**。服务端接收后开始处理。若支持流式，会用服务器发送事件实时推送中间进展；若不支持，则处理完毕后一次性返回结果。结果一般包含服务端的一条或多条消息，若有文件类产出则一并返回工件。纯文本问答时，最终返回的就是应答消息。

## 8.3 ANP

ANP，即 agent network protocol，是一款面向分布式 AI 代理的开源通信规范，核心是搭建开放、安全、高效的标准化协作底座，被视作未来 “代理互联网” 的基础设施。它要解决去中心化协作里的关键难题：如何在无中心环境下做到可信身份、语义一致的沟通与安全的直连协作。设计理念围绕三点：

**·** 以代理为中心的身份：借助去中心化标识符实现自主身份管理，确保每位代理都能被唯一且安全地识别。
**·** 语义化与互操作：利用 JSON-LD 等标准格式描述数据与请求含义，让架构各异的代理准确理解彼此意图。
**·** 动态协商与自适应：支持代理间按需磋商通信规则与协议，适应多样协作场景。
