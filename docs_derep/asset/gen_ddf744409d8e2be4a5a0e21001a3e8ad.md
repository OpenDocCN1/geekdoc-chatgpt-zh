# 上下文到Harness：构建可行动Agent的工程指南

## 内容摘要

本书围绕上下文工程向Harness工程的演进展开，系统拆解AI Agent如何从单纯调用工具进化为具备自主思考与协作能力的工程系统。全书共7章，以Agent工程化的落地实践为主线，完整呈现让Agent理解、规划、反思并行动的方法体系。

第1、2章奠定上下文工程的理论基础，覆盖意图识别、计划模式、反思模式、CodeAct执行与人机协作五大能力的实现；第3、4章以DeepResearch与记忆工程为抓手，给出从搜索到研究的端到端代码示例及分布式记忆部署方案；第5章聚焦Skills上下文卸载，并通过“运维巡检Skill”的开发与OpenClaw测试两个实战验证；第6、7章进入Harness工程层面，分别复现Claude Code核心特性和构建OpenClaw类产品，完成技术整合与落地。每章都配有可运行代码与真实场景案例。

适合有开发背景的工程师、架构师，以及想提升Agent实战水平的技术人员阅读参考。

## 写在前面

大语言模型的能力已大幅提升，推理与代码生成已接近甚至超越多数程序员。然而LLM本质是“思考者”而非“行动者”，它能给出修改建议，却无法直接操作工程文件。

仅靠提示词能让模型输出代码，若要让它读取已有项目、检索代码、把生成内容写入文件，就必须赋予工具调用能力。此时模型才从单一模型升级为一套设计精巧的工程系统，即AI Agent。

工具调用只是起点。写代码是循环往复的过程：读代码、思考逻辑、检索上下文、编辑文件。针对这一持续推理与工具交互的循环所做的工程化设计，就是Agent Loop。

与此同时，上下文窗口有限。读十几个文件、做几十次搜索，很快就会耗尽数十万Token。即使GLM-5这类国产顶尖编程模型，上下文也仅约200k。因此，如何挑选和组织最有价值的信息填入模型的“工作记忆”，成为关键，这就是2025年热议的Context Engineering。

进入2026年，Claude Code、OpenClaw等产品持续刷新认知。除了上下文工程，它们还引入Sub Agent、任务编排、Agent Teams等“模型之外”的工程手段。模型上下文协议MCP、上下文工程、任务管理、Agent Loop、Agent Teams、Skills等要素的集合，被归纳为Harness Engineering，中文暂译为Harness工程。第6章的核心公式为：

Agent = Model + Harness

由此，AI开发路径清晰起来：要么深挖LLM本身提升推理或降低成本；要么聚焦Harness，让模型在真实世界中完成更多有价值任务。

目前LLM能力差距在缩小，同一提示词在不同模型上的表现差异不再像2023年那样悬殊。但对同一个模型配置不同的Harness，效果却天差地别。这也解释了为何越来越多程序员放弃熟悉的IDE，转向Claude Code这类命令行工具。

本书诞生于这一变革期。写作期间上下文工程、Coding Agent、Skills、OpenClaw、Harness等概念轮番升温，每一次迭代都促使内容重排。目标是把前沿且实用的技术体系结合工程实践，毫无保留地呈现给读者。

# 第1章 从提示词迈向上下文工程

人工智能正经历范式迁移，从单纯语言理解转向系统化的语境构建。

2025年前，大语言模型凭借简单提示词即可生成流畅文本，提示词工程成为主流，人机交互边界清晰且呈单向线性。

随着场景深入，“提示-响应”模式暴露局限：
- 意图漂移：单一指令难以捕捉复杂业务的真实意图
- 长程记忆缺失：多轮对话中易丢失初始目标
- 逻辑断层：面对多步骤跨领域任务，缺乏结构化引导则输出失控

在此背景下，上下文工程应运而生。它关注的不是单次提示的优化，而是如何系统化地构建、管理并动态演化模型的输入语境。

上下文工程整合业务意图、任务需求、工具回调、历史记忆等多维信息，确保进入上下文窗口的数据精准且结构化，使模型在复杂任务中保持目标一致并高效协同。

基于提示词工程向上下文工程的演进，本章聚焦三点：
- 上下文工程的本质与核心原则
- Agent在上下文工程中的关键角色
- Agent自身的技术演进路径

## 1.1 上下文工程的核心思想

### 1.1.1 用买车决策看上下文如何搭建

在讲技术前，先看一个生活决策：购买新能源汽车。

一位有10年燃油车驾龄的朋友想换国产新能源车，对领域不熟，问通义千问“理想L6怎么样？”。模型给出了参数堆砌的通用回答，提及增程、激光雷达、智驾等术语，但因缺乏背景，难以做决策。单纯改写提问收效有限，真正需要的是补全上下文。

我建议他先完成信息补全：
- 明确约束：通勤约30公里、5口之家、预算20万~25万、持有8年
- 引入外部知识：底盘调校、电池供应商宁德时代/欣旺达等
- 实地闭环：4S店试驾并整合销售信息

基于这些，他构造了进阶提示词，描述驾龄、用车场景、预算、智驾需求、对底盘操控安全性的关注、电池续航诉求，以及试驾中获知的电池信息。模型据此给出更具针对性的评估，结论明确，维度拆解清晰，并给出Pro版建议与对比车型。

这个案例揭示上下文工程的本质：不是润色提示词，而是一套系统化的信息采集、过滤与组合范式。

首先把模糊提问“某车怎么样”转化为对具体使用场景的挖掘；
其次通过专业平台、车主反馈等渠道主动获取信息；
最后用试驾等真实工具验证认知，获取一手感知。

最终形成高度结构化且与需求对齐的上下文，既支撑更精准的提示生成，也形成可复用的记忆单元。积累多组记忆后，LLM可横向对比推理，辅助高效决策。

因此上下文工程的核心是工程化手段将用户模糊简略的原始提示，转化为富含需求、知识背景、思考的数百到上千字的高质量输入。过程包括意图识别、需求分解、多源检索、工具调用、结构化记忆构建等，最终引导模型输出更贴合真实需求的回答。

### 1.1.2 上下文工程与Agent的关系

从购车案例可给出工程化定义：上下文是输入模型的核心语义载体，工程是通过程序化和系统化手段对其动态构建与持续优化。承担这一任务的核心载体正是Agent。

熟悉ReAct范式的读者知道，其逻辑是LLM接收原始输入后拆解子任务，选择工具执行并获取反馈，如图1-4所示。

这一过程本质是动态构建与丰富对话上下文：每次决策都依赖观察结果并整合进上下文，驱动下一轮推理。尽管ReAct早在2023年提示词工程盛行时提出，其本质正是动态构建上下文。

当时单Agent多停留在Demo阶段，长程交互导致的问题如窗口溢出、推理偏离、记忆碎片化尚未充分暴露。

## 1.2 上下文工程的系统结构

理解思想后，问题是成熟系统由哪些组件构成？若提示词工程是侧重表达技巧的单兵作战，上下文工程则是多兵种协同。它是一套整合多种方法论的Agent协同系统。

### 1.2.1 上下文构建的四大模块

尽管Agent技术快速迭代，但从上下文工程视角看，核心逻辑始终围绕感知、规划、执行、反思四大模块展开。

#### 1. 感知模块，精准锚定意图
感知模块是系统入口，任务是将非结构化自然语言提问转为结构化任务描述，理解核心意图并路由到合适处理模块。工程化层面即意图识别。
