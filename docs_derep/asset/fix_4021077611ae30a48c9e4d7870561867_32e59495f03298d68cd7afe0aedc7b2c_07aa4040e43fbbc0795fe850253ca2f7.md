# 检测接口和 JNI 桥接拆解

整体分层很清晰，C++ 侧负责推理调度，JNI 侧负责把结果搬到 Android Java。先看推理入口的设计思路。

单次检测的 ApiDetect，先把错误状态设为 FRAS_SUCCESS，随后依据传入的句柄在 DetectorPool 中取出对应的 MlDetector 实例。找不到资源就把错误改成 FRAS_HANDLE_NOT_FOUND 直接返回 0。拿到实例后调用 MlDetectObjects，参数包括图像数据指针、宽高、步长 width*3、24、置信阈值 0.7f、最多返回 1 个目标。推理有命中时再把内部的 MlLandmarkResult 转成对外统一的 ObjectLandMarks，最后返回实际个数。

批量检测的 ApiDetectMany 逻辑相近，但面向多目标输出。同样先校验句柄有效性，依据 maxCount 分配一个 MlLandmarkResult 缓冲，一次请求最多 maxCount 个结果。返回后遍历索引位置，把每个内部结构映射到 detectionResult 指针数组对应的槽位，再把真实数量交回上层。

JNI 层把上述 C 接口封装成 Java 可调方法。初始化时把 jstring 转成 std::string 调用 ApiCreateDetector，得到的句柄写回 Java 对象的 handle 字段。销毁方法取出句柄调用 ApiDestroyDetector。设置参数先读出句柄并解析 Java 参数对象，再调用 ApiSetDetectorParam。单张检测 detectObject 会把 jbyteArray 通过 GetByteArrayElements 映射为 unsigned char*，调用 ApiDetect，释放数组后根据 objectCount 决定返回包装后的 Java 对象还是 nullptr。批量检测 detectManyObjects 则先分配 ObjectLandMarks 数组，调用 ApiDetectMany，释放字节数组后按返回数量构造 Java 对象数组并填充。

资源管理部分以提取器为例说明。ExtractorPool 的静态实例大小固定为 32。ApiCreateExtractor 先把错误码清零，校验 license，失败则返回 FRAS_INVALID_HANDLE。随后创建 MlExtractor，错误码透传，若创建失败同样返回无效句柄。成功后通过 ExtractorPool.Allocate 分配句柄，池满时把错误置为 FRAS_HANDLE_USE_UP。ApiDestroyExtractor 则先清零错误，通过句柄从池中取回底层资源。
