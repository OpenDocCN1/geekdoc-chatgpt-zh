delivery 是可选参数，主要用来定义任务完成后结果如何投递。
sessionTarget 属于必填项，填入 main 时任务会写入主会话，填入 isolated 时任务会在独立会话中启动 Agent。
enabled 也是可选参数，默认保持开启，关闭后任务进入暂停状态，不必删除即可恢复。

### 三种调度类型

##### at 类型——一次性定时
会在用户指定的 ISO-8601 格式 UTC 时间点执行一次，典型场景是某个时刻的单次提醒。
[PRE0]

##### every 类型——固定间隔
以毫秒为单位的固定周期重复触发，可选 anchorMs 用于时间对齐。
[PRE1]

##### cron 类型——标准 Cron 表达式
采用标准的 5 段式 Cron 写法，可通过 tz 字段声明时区，适合做精确的日历调度。
[PRE2]

### 两种执行目标 Payload

**systemEvent——注入主会话**
把一段文本作为系统事件写入主会话。只能配合 sessionTarget 为 main 使用，适合不需要独立上下文的简易提醒。
[PRE3]

**agentTurn——独立会话执行**
在全新的空白独立会话中运行 Agent，历史上下文不带入，适合对隔离性要求高的复杂任务。只能与 sessionTarget 为 isolated 搭配。
[PRE4]

### 结果交付方式
任务结束后支持三种投递策略：none 表示静默运行，仅写入日志；announce 表示发布到指定聊天频道，isolated 下的 agentTurn 默认采用此方式，可用 channel 与 to 精确指定对象；webhook 表示通过 HTTP POST 推送到指定 URL，便于接入外部系统。

使用企业微信 openclaw-wecom-bot 渠道时，必须采用 agentTurn 加 isolated 的组合，并通过 delivery.channel 与 delivery.to 明确收件人，任务内部不应直接调用 message 工具发送消息。

### 16.6 Session 会话机制：对话历史的持久化单元

#### Session 的本质
Session 是 OpenClaw 保存对话记录与运行状态的基础单元。每个 Session 绑定一个 Agent，以 JSONL 形式完整保存转录，Gateway 重启后会自动恢复上下文，用户无需重复提供背景。

Session 的标识是 session key，格式为 agent:<agentId>:<mainKey>，默认主会话为 agent:main:main。不同渠道、不同用户、不同群组会产生各自独立的 key，实现天然的上下文隔离。Telegram 上的对话与 WhatsApp 上的对话互不干扰。

#### Session 的四个生命周期阶段
- 创建：首次向某个 session key 发送消息时自动生成，无需手动初始化。元数据如创建时间、关联 Agent、渠道信息等会持久化到 ~/.openclaw/agents/<agentId>/sessions/ 目录下。
- 活跃：队列中有待处理消息或 Agent 正在运行。同一个 session key 下的执行遵循 session lane 串行原则，保证历史强一致，避免并发混乱。
- 闲置：没有新消息进入，会话保留在磁盘，新的消息到来时自动恢复，用户无感知。
- 压缩：当上下文接近 LLM 窗口上限时触发自动压缩 auto-compaction，历史会被摘要化以释放空间。压缩前会执行 Pre-Compaction Memory Flush，提示 Agent 将关键信息写入持久记忆，防止丢失。

#### 隔离 Session：为自动化任务设计
隔离 Session 专用于 Cron 任务的 agentTurn 类型。与常规 Session 有三点不同：每次运行都是全新空白，不继承历史对话；使用 minimal 提示词模式，去掉 Skills 列表与记忆召回等章节，降低 Token 消耗；运行结束后不保留在会话存储中，属于 transient 临时会话，不会污染主会话。适合每日摘要、定期数据分析等周期性场景。

#### 子 Agent Session：主 Agent 的分身
主 Agent 通过 sessions_spawn 工具创建子 Agent 时，子 Agent 在隔离 Session 中运行，继承父 Agent 的工作空间目录，但仍使用 minimal 提示词，仅注入 AGENTS.md 与 TOOLS.md 两个引导文件。可设置 cleanup: "delete" 让转录文件在结束时自动删除，减少磁盘占用。主 Agent 可用 sessions_yield 工具暂停自身轮次，等待子 Agent 完成后继续。

#### 存储格式与路径
Session 数据位于 ~/.openclaw/agents/<agentId>/sessions/ 下。以 <sessionId>.jsonl 为会话转录，每行一条 JSON 记录消息、工具调用、执行结果；sessions.json 则是元数据索引，记录所有已知 Session 的 key、创建时间、压缩状态等。

Session ID 由 OpenClaw 自行分配并保持稳定，与底层 LLM 提供商的会话 ID 无关。更换模型提供商后历史记录仍可正常读取与恢复。

### 16.7 消息渠道：OpenClaw 对外连接的桥梁

#### Channel 的架构职责
Channel 是 OpenClaw 与外部消息平台之间的适配层。一侧将平台原生格式如 WhatsApp Baileys、Telegram Bot API 等翻译成 OpenClaw 统一内部格式交给 Agent，另一侧再把 Agent 的回复翻译回平台原生格式发出。

遵循关注点分离：Agent 不感知消息来源，只处理统一格式；Channel 不关心 Agent 如何处理，只负责接入与发出。由此可在不改动 Agent 的前提下接入新平台。

#### 支持的消息渠道
官方或插件支持的渠道包括：
- WhatsApp Baileys 库，支持个人账号、群组、@提及触发
- Telegram Bot API，支持 DM、群组、频道，原生支持块流
- Discord Bot，支持服务器、频道、DM、线程，支持角色路由
- Signal signal-cli，端到端加密接入
- iMessage macOS 节点，通过 macOS companion app 接入
- Slack Bot Token，支持频道与 DM
- SMS/MMS Twilio，电话短信接入
- Google Chat Service Account，Google Workspace 集成
- Matrix Homeserver，开源 IM 协议
- IRC / XMPP Jabber，经典即时通讯接入
- 企业微信 WeCom，腾讯机器人
- Line，亚太主流 IM
- Webhook 双向，自定义 HTTP 接口对接任意外部系统

#### 渠道配置通用结构
每个渠道在 openclaw.json 中通过 plugins.entries.<channelName> 或 channels 配置，通用字段有 enabled 是否启用、accountId 账号实例标识、认证字段均支持 SecretRef、mentionPatterns 触发模式、blockStreaming 是否启用块流式回复、queueMode 消息队列模式 collect/steer/followup。

#### WhatsApp 渠道的技术要点
WhatsApp 依赖非官方 Baileys 库接入。各账号的认证文件存于 ~/.openclaw/agents/<agentId>/agent/baileys_auth_info/，丢失后需重新扫码。单实例约束严格，多个 Baileys 实例同时连接同一账号会冲突甚至有封禁风险。群组触发模式由 groupChat.trigger 决定，always 表示所有消息触发，mentioned 表示仅 @Bot 时触发。群组 ID 格式为 <id>@g.us，DM 格式为 <E.164>@s.whatsapp.net。

#### 渠道能力标记 Capabilities
不同渠道原生能力不同，OpenClaw 通过能力标记感知并利用：inlineButtons 内联按钮 Telegram、Discord 支持；reactions 表情反应 Discord、Telegram 支持；threads 线程 Discord、Slack 支持；media 媒体文件多数渠道支持但有格式与大小限制；blockStreaming Telegram 原生支持分块流式回复。不支持的能力会自动降级为文本替代，Agent 无需为不同渠道写不同逻辑。

### 16.8 心跳机制：让 Agent 主动运转

#### 心跳的设计目的
心跳把 Agent 从被动应答转为主动助手。即使没有新消息，Gateway 也会按配置间隔，默认约 30 分钟，向主 Agent 发送心跳轮询，让 Agent 主动检查邮件、日历、待办或执行后台维护。

官方称其为 “the heartbeat of your agent”，是保持活跃与主动性的生命脉搏。通过在工作空间的 HEARTBEAT.md 中定义检查清单，Agent 可在每次心跳时自动完成日常工作，无需人工触发。

#### 心跳的处理流程
流程分为五步：Gateway 按 heartbeat.intervalMs 默认 30 分钟定时检查；若距离上次用户消息超过 heartbeat.idleMs 静默阈值，向主 Session 注入心跳提示词；Agent 读取 HEARTBEAT.md 并按清单决定操作；若无待处理事项，Agent 回复 HEARTBEAT_OK，Gateway 静默丢弃，用户不可见；若发现重要事项如紧急邮件，Agent 正常回复，Gateway 将消息发送给用户。

#### HEARTBEAT.md 配置
HEARTBEAT.md 是工作空间的可选文件，列出心跳时应执行的检查清单。官方建议保持简短，因 Token 消耗与长度成正比：
[PRE6]
若文件为空或只有注释，Agent 始终回复 HEARTBEAT_OK，不产生额外 API 调用。这是一种关闭心跳任务的简便方式，无需改动配置。

#### 心跳 vs Cron 如何选择
适合用心跳的场景：多种检查可合并处理如收件箱加日历加通知；需要访问最近对话上下文；对时间精度要求不高，偏差几分钟可接受；希望合并定期检查减少 API 调用。
适合用 Cron 的场景：时间必须精确如每天 9 点整发报告；任务需与主会话历史完全隔离；希望使用不同模型或 thinking 级别；一次性定时提醒；结果需直达特定渠道而不经过主会话。

### 16.9 Canvas 与节点系统：Agent 的视界与交互面

#### Canvas：富媒体输出能力
纯文本传递信息有限，Canvas 提供轻量 Web UI 渲染，让 Agent 向配对设备展示动态 HTML/CSS/JavaScript 内容。
Canvas 默认在 canvasHost.port，默认 18793，提供 /__openclaw__/canvas/ 路由，渲染工作空间 canvas/ 目录下的 HTML 文件。配对设备内嵌 WebView 展示，Agent 通过 canvas 工具的 present、navigate、eval 等操作控制展示与交互。canvas.eval 可在 WebView 中执行 JavaScript，实现数据更新、表单提交等动态行为。

#### 节点系统：感知物理世界
Nodes 是设备配对系统，让手机、平板或 macOS 设备成为 Agent 的感官延伸。配对后节点可提供：
- Camera 拍照或短视频，实现视觉感知
- Screen 截图，用于远程监控或视觉分析
- Location 实时地理位置
- Notifications 查看与操作设备应用通知
- Photos 访问相册最新照片
- Run 在节点设备上执行命令，实现跨设备远程操控

#### 节点配对与安全考量
配对通过二维码或配对码完成，建立 Bootstrap Token 实现设备与 Gateway 信任。配对成功后节点保存 Pairing Profile，后续连接无需重复配对。Bootstrap Token 有有效期，过期需重新生成。
网络方面：局域网直连延迟低且安全；远程访问推荐使用 Tailscale serve 模式而非直接暴露 Gateway 端口；公网暴露必须配置 token 认证，防止未授权设备配对。

- security: "allowlist" 仅允许预定义白名单命令，其余需人工审批。聊天中可用 /approve allow-once 仅本次允许、/approve allow-always 加入白名单、/approve deny 拒绝处理审批请求
