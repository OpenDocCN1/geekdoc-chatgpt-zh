（1）确认待合并的分支，比如 feature-payment，上的开发工作已经全部收尾。
（2）确保所有改动都已经执行 commit 操作。
（3）本地仓库与远程仓库的状态保持一致。

按下面顺序完成合并。

（1）切到目标分支，一般为主分支。
- 在 GitHub Desktop 左侧点开当前分支；
- 从弹出菜单里挑选主分支 main 或 master。

（2）发起合并。
- 点击顶部菜单栏的 Branch；
- 选择 Merge into current branch；
- 在对话框中指定作为来源的分支，例如 feature-payment；
- 按下 Merge 确认执行。

有时两个分支各自修改了同一文件的同一段，就会产生合并冲突。好比两个人同时改同一段落，得先商量保留哪版。

处理冲突的流程如下。
- 仔细对比双方版本的代码差异；
- 决定最终保留的内容；
- 把冲突标记 <<<<<<< HEAD、=======、>>>>>>> 一并删除；
- 保存文件后提交这次解决冲突的记录。

### 3. 合并策略
不同场景下可选用不同的合并方式。

1) 普通合并 Merge commit
- 完整保留分支的历史轨迹；
- 适合需要追溯分支演进的情况；
- 会在主分支上生成一条新的合并提交。

2) 快进合并 Fast-forward
- 仅在主分支没有新增提交时可用；
- 不会额外创建合并提交；
- 历史线更干净。

3) 压缩合并 Squash and merge
- 把功能分支的多条提交压成一条；
- 让主分支历史更简洁；
- 多用于功能开发收尾时的最终合并。

### 小白必记
- 合并前准备：分支代码要通过测试再合并
- 冲突处理原则：逐行对比后谨慎取舍
- 策略选择：结合场景挑选合适方式
- 说明规范：合并信息要写清楚改了什么
- 审查要求：重要合并建议走团队审核
- 备份习惯：合并前备份关键代码
- 验证动作：合并后立即跑功能验证

## 3.4.9 撤回分支
分支创建、合并和管理之后，有时需要放弃某条开发线。就像写作时放弃一个思路，Git 也能通过撤回分支实现。撤回操作有风险，删除后恢复困难，下面给出安全做法。

先了解撤回分支的三种常见情形。

第一种是删除本地分支，相当于删掉电脑里的草稿，不影响已发布内容。步骤如下。
1. 先切换到其它分支，通常是主分支。
2. 点击顶部分支名称下拉按钮。
3. 找到目标分支，右键单击。
4. 选择 Delete 删除。
5. 若分支存在未合并改动，系统会弹出警告。

第二种是删除远程分支，类似从共享书架撤书，要更谨慎。
1. 在 GitHub Desktop 打开 Branch 菜单。
2. 选择 Delete branch。
3. 若该分支已推送到远程，会询问是否一并删除远程分支。
4. 确认无误后点确认完成删除。

第三种是放弃分支里的修改，回到初始状态。
1. 在 Changes 面板里选中要丢弃的文件。
2. 右键点击这些文件。
3. 选择 Discard changes。
4. 在确认对话框里再次确认。

操作时请注意以下事项。
(1) 删除前的自检
- 重要代码已合并或已备份；
- 当前不在要删除的分支上；
- 已与团队确认该分支不再使用。

(2) 数据安全建议
- 关键分支先复制一份备份分支再动手；
- 不确定是否删除可先改名保留；
- 删除前在本地确保代码能正常运行。

(3) 团队协作注意
- 删除共享分支前要通知相关成员；
- 确认没有人正在使用该分支；
- 在团队文档里记录删除原因和时间。

### 小白必记
- 删除原则：确认无用后再执行删除
- 备份策略：重要分支先备份再操作
- 协作准则：共享分支删除前先告知
- 安全检查：确保代码已合并或备份
- 操作顺序：先删本地再删远程
- 回退建议：保留关键节点的备份分支
- 记录要求：登记重要分支的删除原因

## 3.4.10 如何回滚代码
分支管理和合并后，难免出现合并后有问题或功能失败需要放弃的情况。这时就需要回滚。Git 就像时光机，可以把代码拉回任意历史点。下面按常见场景说明。

### 1. 场景一：撤销还没有提交的修改
开发新功能时发现思路错误，想丢弃未提交的改动回到上次提交状态，可这样做。

#### 1）放弃单个文件的修改
- 在 Changes 面板里找到目标文件；
- 对该文件右键；
- 选择 Discard changes；
- 在确认框里再次确认。

#### 2）放弃所有文件的修改
- 在 Changes 面板按 Ctrl+A 或 Command+A 全选；
- 右键选择 Discard all changes；
- 确认要丢弃这些改动。

### 2. 场景二：撤销最近的一次提交
刚提交后发现有严重 bug，可按下面方式回退。

#### 1）撤销最新的提交
- 切换到 History 标签；
- 在最新提交上右键；
- 选择 Revert changes in commit；
- GitHub Desktop 会自动生成一条新的提交来抵消上一次修改。

#### 2）修改最新提交的说明文字
- 在最新提交上右键；
- 选择 Amend commit；
- 编辑提交说明；
- 点 Amend 确认修改。

### 3. 场景三：回到特定的历史版本
想回到某个里程碑，比如功能完成前或合并前的状态。

#### 1）通过创建新分支来回滚
- 在 History 找到目标版本；
- 右键选择 Create branch from commit；
- 填入新分支名如 rollback-to-v1.0；
- 在新分支上继续开发或合并到主分支。

#### 2）直接还原到特定版本
- 定位到目标提交记录；
- 右键选择 Revert changes in commit，如图 3-1 所示；
- 这会新建一条提交把代码恢复到选中版本。

操作时特别注意。
##### 1) 数据安全
- 重要回滚前先建备份分支；
- 不确定时先在新分支试验；
- 回滚前提交所有重要修改。

##### 2) 团队协作
- 回滚公共分支前提前通知团队；
- 确认回滚不影响他人工作；
- 回滚完成后及时推送到远程。

##### 3) 代码管理
- 养成小批量提交习惯，便于精确回滚；
- 每次提交写清楚说明，方便定位回滚点；
- 定期推送到远程，防止本地丢失。

### 小白必记
- 回滚原则：重要操作前先建备份分支
- 提交习惯：小步提交，说明清晰完整
- 分支策略：不确定时用新分支试回滚
- 协作提醒：回滚公共代码先通知成员
- 安全防护：定期推送，避免数据丢失
- 版本管理：保持提交历史整洁有序
- 备份机制：关键回滚前必须先备份

## 3.4.11 如何打开项目文件夹和编辑器
管理版本和回滚之后，日常开发最常用到的就是查看和编辑代码。GitHub Desktop 除了版本控制，还提供了快速打开项目和编辑器的入口，像个智能管家。

### 1. 打开项目文件夹
开发时常要看文件结构或定位某文件，有两种做法。

(1) 右键快捷菜单访问。
- 在仓库列表里找到项目；
- 对项目名称右键；
- 选择 Show in Explorer 或 Show in Finder；
- 文件管理器会直接打开项目目录。

(2) 顶部菜单栏访问。
- 先在 GitHub Desktop 选中项目；
- 点 Repository 菜单；
- 选择 Show in Explorer/Finder；
- 系统打开对应文件夹。

### 2. 使用 Cursor 编辑项目
Cursor 是 AI 辅助编程工具，能提升编码效率。打开方式有三种。

（1）直接从 GitHub Desktop 打开。
- 选中项目；
- 点 Repository 菜单；
- 选择 Open in Cursor；
- Cursor 启动并加载项目。

（2）设为默认编辑器。
- 打开 GitHub Desktop 设置；
- 进入 Integrations 集成；
- 在 External Editor 下拉里选 Cursor；
- 设置后可用快捷键 Ctrl+Shift+A 或 Cmd+Shift+A 快速打开。

（3）未看到 Cursor 选项时的处理。
- 确认 Cursor 已正确安装；
- 重启 GitHub Desktop；
- 通过 Open in External Editor 手动指定 Cursor 程序。

## 3.4.12 如何使用开源项目
除了管好自己的代码，学会利用开源社区也很重要。开源项目就像开放的图书馆，别人贡献的代码可以直接用或在此基础上改写。主要分直接使用和二次开发两种。

### 1. 直接使用开源项目
相当于在文章里引用他人观点。

#### 1）寻找合适的项目
- 打开 GitHub，在搜索框输入关键词；
- 看 Star 数量，越多越受欢迎；
- 检查最近更新时间，越新越好；
- 阅读 README 了解功能。

#### 2）评估项目质量
- Star 数目多通常更可靠，一般 1000 以上值得考虑；
- 半年内有更新说明项目活跃；
- 看 Issues 区问题是否及时处理；
- 文档是否完整，使用说明是否清晰。

#### 3）正确引入项目
- 仔细阅读安装说明；
- 用包管理器如 npm 安装依赖；
- 按文档完成配置；
- 在自己代码里引入使用。

### 2. 二次开发 Fork
相当于把一本书改写成自己的版本。

#### 1）Fork 项目
- 打开项目主页，点右上角 Fork；
- 选择保存到自己的账号下；
- 等待 Fork 完成。

#### 2）克隆到本地
- 用 GitHub Desktop 克隆到本地；
- 新建分支进行开发；
- 按需修改代码；
- 定期从原项目同步更新。

使用时注意以下要点。
##### 1）开源协议
- MIT 最宽松，基本可自由使用；
- Apache 可商用，需保留版权信息；
- GPL 修改后代码也必须开源；
- 商业项目务必仔细核对协议要求。

##### 2）技术兼容性
- 检查支持的编程语言版本；
- 确认运行环境要求；
- 评估与现有项目是否兼容；
- 注意可能的依赖冲突。

##### 3）使用成本
- 评估学习难度；
- 考量维护成本；
- 确认团队能否维护；
- 查看社区是否活跃。

### 小白必记
- 项目选择：优先选 Star 多更新频繁的
- 协议检查：使用前必须确认协议
- 技术评估：确保与现有项目兼容
- 文档阅读：先看文档示例再上手
- 维护成本：评估团队技术储备
- 版本控制：定期同步原项目更新
- 社区支持：挑选活跃社区的项目

## 3.4.13 实用建议和最佳实践
把前面的知识点串起来，下面总结项目管理、提交、分支和协作的最佳实践。

项目文件管理上，项目像书柜，要分类摆放。好的结构要清晰易懂，便于查找和协作。

规范目录一般包括。
- src 文件夹放源码；
- docs 文件夹放文档；
- tests 文件夹放测试；
- assets 文件夹放静态资源；
- build 或 dist 文件夹放构建产物。

文件命名建议。
- 用有意义的英文名；
- 全小写，单词用连字符；
- 避免中文和特殊字符；
- 名字要能表达内容，如 user-login.js 比 page1.js 好。

代码提交最佳习惯。
（1）提交频率。
- 小功能完成就提交；
- 修复一个 bug 就提交；
- 不要攒大量改动再提交；
- 每天至少提交一次。

（2）提交说明写法。
- 标题简洁，不超过 50 字；
- 细节用要点列出；
- 说明改动原因和影响；
- 有任务编号时标注。

示例。
## 添加用户登录功能
- 新增登录页和表单校验
- 实现用户名密码加密存储
- 增加登录失败提示
- 关联任务 TASK-123

分支管理建议。
### （1）主分支 main/master 管理
- 保持主分支随时可发布；
- 不要直接在主分支开发；
- 定期部署到测试环境；
- 合并到主分支需代码审查。

### （2）功能分支管理
- 每个新功能单独建分支；
- 命名规范如 feature/login；
- 及时同步主分支更新；
- 完成后及时合并或删除。

团队协作注意。
### （1）代码审查 Pull Request
- 提交 PR 前自查一遍；
- 认真对待审查意见；
- 及时回复评论并修改；
- 保持礼貌专业的沟通。

### （2）文档维护
- 及时更新 README；
- 在代码里写必要注释；
- 记录重要配置说明；
- 保持文档与代码同步。

安全方面像保护银行账户。
### （1）账号安全
- 开启双因素认证；
- 定期更换密码；
- 不在公共场所保持登录；
- 及时清理过期访问令牌。

### （2）代码安全
- 用 .gitignore 过滤敏感信息；
- 不提交配置文件里的密码；
- 定期更新依赖包版本；
- 及时修复已知安全漏洞。

### 小白必记
- 项目结构原则：目录分明，分类有序
- 提交准则：小步提交，说明详细
- 分支策略：主分支稳定，功能分支灵活
- 协作要点：互相尊重，积极沟通
- 文档原则：及时更新，清晰易懂
- 安全要求：定期检查，及时修复
- 命名标准：简洁明了，见名知意

## 3.5 如何部署Node.js环境
### 3.5.1 Node.js是什么？
JavaScript 以前只能在浏览器里跑，像只在特定场地玩的积木。Node.js 的出现让这些积木脱离浏览器，到任何环境都能搭建。

Node.js 最大的优势是自带的包商店 NPM，里面有超过 200 万个现成积木包。每个包实现特定功能，组合起来就能搭出各种应用。

Node.js 可做的应用类型。
1. 网站应用：比如开发类似微信朋友圈的社交平台，Node.js 能处理文字图片上传、管理用户互动、保障数据安全。LinkedIn 这类求职平台就基于 Node.js 构建。
