[PRE0]

（2）检索提速方案
向量库的响应快慢直接决定使用感受，下面这些手段能明显改善。

1）调参搜索行为：以 HNSW 为例，ef 控制检索时保留的候选集规模。调高可以提升召回质量，但会拉长耗时；要与 efConstruction 区分，后者是建索引时使用的候选集规模。

2）批量调用：把多条请求合并成一次批量，减少网络往返。

3）混合检索模式：将硬条件过滤与向量相似度匹配结合，先筛后比。

4）热门结果复用：对高频查询的向量结果做缓存，下次直接返回。

（3）分布式部署思路
数据量上去后，向量库必须分布式。

1）水平分片：按 ID 区间或哈希把数据打散到多节点。

2）读写分离：检索节点与建索引节点拆开，资源更合理。

3）多副本：为关键数据准备多份，提升可用性和并发。

4）增量更新：避免全量重建，采用增量方式维护大规模索引。

选型与使用向量库是搭建大模型应用的关键，要结合业务、数据规模和性能目标综合判断。

#### 1. 知识库架构设计
一套完整系统要同时容纳结构化数据和向量数据，并支持多种查询与更新。如图 5-4，典型架构由接入层、存储层、索引层、查询层组成。

[PRE1]
四层职责清晰：
1）数据接入层：汇聚多源数据并做校验预处理，包含文件解析、API 引入、清洗、格式校验。
2）存储层：分别存放结构化元数据与关系信息、文本的嵌入向量、原始文档。
3）索引层：构建倒排、向量、元数据等多种索引加速检索。
4）查询层：提供关键词、语义、混合检索及元数据过滤能力。

#### 2. 知识库数据模型设计
模型要能组织异构数据并支持灵活的查改。
要点如下：
1）粒度划分：把文档切成合适大小的 Chunk，兼顾检索精度与上下文连贯，常控制在 100~1000 token 之间，1 token 约 0.75 个英文词或 1~2 个汉字。
2）关系建模：简单场景可用扁平结构，复杂场景可构建实体关系网，支持更深推理。
3）元数据管理：为文档、Chunk、实体设计元数据，便于精细过滤与分类。
4）版本控制：内容会演进，需记录变更历史并保证查询一致。

#### 3. 知识库存储优化策略
面对海量数据和高并发，常用优化有：

（1）分层存储
按访问热度区分存储介质，如图 5-5。

[PRE2]
主要分三层：
1）热层：放最常访问的向量与结果，多用 Redis 等内存缓存，毫秒响应。
2）温层：放中等活跃的向量索引与结构化数据，多用向量库与关系库，百毫秒响应。
3）冷层：放低频历史数据与原文，多用对象存储，成本低延迟高。
数据会随热度自动迁移，兼顾性能与成本。

（2）分片与复制
1）水平分片：按文档 ID 或主题分散到多节点。
2）垂直分片：元数据、向量、原文分别存于不同系统。
3）多副本：关键数据多份复制，提升可用与读性能。

（3）存储格式优化
1）向量压缩：用标量量化、乘积量化等压缩向量，节省空间。
2）列存：结构化数据用列式存储，提升属性查询效率。
3）增量存储：频繁更新场景只存变更部分，降低写入成本。

### 6.1.1 大模型服务层规划

#### 1. 服务层架构模式
- 1. 单体式：将模型与组件部署于同一实例，适合小型应用与原型，简单但扩展受限。
- 2. 微服务式：把不同能力拆成独立微服务，经 API 网关统一访问，扩展性好，便于协作与持续交付。
- 3. Serverless 式：以函数即服务部署，按需触发，资源利用率高、成本优势明显，适合流量波动场景。
