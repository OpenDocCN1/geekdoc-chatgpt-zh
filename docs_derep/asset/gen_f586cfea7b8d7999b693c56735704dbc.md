代码可读性：别让聪明代码变天书

先看一段很“函数式”的写法：
```js
const assignIfValueTruthy = (o, [k, v]) => (v ? { ...o, [k]: v } : o);

return resultsEntries.reduce(assignIfValueTruthy, {});
}
```
它确实把过滤和合并压进了一行，体积很小，但意图被藏起来了。看的人得先拆解 reduce 再回溯 assignIfValueTruthy，才能明白到底在干嘛。

改成更直白的版本：
```js
// 改进版本：可读性更强（直观、清晰）

function extractDataFromResponse(response) {

const [Component, props] = response;

const output = {};

if (Component) {

output.Component = Component;

}

if (props) {

output.props = props;

}

return output;

}
```
用显式的条件判断把逻辑摊开，行数多了点，但每一步都在明处，不需要额外脑力去反推。审查 AI 产出的代码时，可读性优先的写法能显著降低理解和维护成本，让 code reviewer 和后续维护者都能轻松上手。

业界的 PEP 8、Google Java Style Guide 等规范，本质都在围绕可读性和一致性。几个常被忽略的要点：

· 命名要自解释。变量、函数、类都用能看懂的名字，别用单字母或模糊缩写。customer_id 远比 x 好，名字本身就是文档。
· 缩进和布局要统一。不同语言有约定，比如 PEP8 用 4 个空格且不混用 Tab。统一的层次感能让嵌套逻辑一眼分清。
· 行长要可控。多数规范建议控制在 80～100 字符内，分行后在屏幕上能完整看到，减少横向滚动，也倒逼表达式更简洁。
· 函数要短小专注。尽量做到一个函数只做一件事，几十行内收束。过长的函数通常职责不清，不利于理解和复用。

除此之外，注释要恰到好处，风格要保持一致。规范的核心目标都是让代码更统一、好读、好维护，从而把沟通和维护成本降下来。审查 AI 生成代码，先看它是否符合这些可读性底线。

2. 可维护性

可维护性指的是代码在后续阶段是否容易被理解、修改和扩展。高可维护的代码能让后来的人快速看懂逻辑，需要改动时也能低风险地修复缺陷或加功能。现实中软件的大头成本不在开发，而在长期的维护和升级，保持活力就靠可维护性。

近期的行业反馈显示，AI 生成代码在质量和可维护性上整体在走下坡，因为模型更在乎当下问题是否被“解决”，而忽视了人类程序员长期遵循的设计原则。常见问题有三类。

· 整体式结构。AI 喜欢把功能堆到一个大块或单个文件里，模块边界模糊。像一台零件焊死的机器，动一处就可能牵连其它地方，更新时总像拆炸弹。
· 紧耦合。模块之间依赖过深，互相调用内部细节、共享全局状态。改 A 必须跟着改 B、C，否则功能会破。数据访问细节硬编码进业务逻辑就是典型，库一变，业务也要大改，还很难单独复用或测试。
· 低内聚。模块承担太多无关职责，功能杂糅。像一个叫“订单处理”的函数，里面既打日志又更新 UI，改日志策略或界面都要动它，难以预测影响范围，风险很高。

工程上的对策是模块化、低耦合、高内聚。

模块化像搭积木，每个模块形态和接口明确，可以独立拆卸、替换、升级，不用拆散整体。
低耦合像家电各自独立，冰箱坏了不影响洗衣机。代码里模块通过清晰接口通信，内部实现不外泄，修改一方不会波及另一方。
高内聚像公司的专业部门，财务只做财务，人事只做人事。一个模块只聚焦单一目标，内部元素高度相关，修改时定位精准，不易误伤。

三者合一，系统才像用标准零件组装，既分工明确又能灵活演进。若 AI 输出里看不到这种积木式设计，就要警惕。

3. 文档与注释

好的文档和注释能提升可读性、促进协作、加速维护，并在审查时帮助理解设计意图。对复杂业务，注释的关键不是说“做了什么”，而是解释“为什么这样做”，记录关键决策和背景，避免只见步骤不见缘由。

这对人类同样对模型重要。现今的大语言模型具备多模态代码理解能力，能融合代码和周边信息建模语义，文档和注释与代码的映射关系不可或缺，某些场景下注释的权重甚至高于代码本身。

问题是，AI 编程工具很少自动产出有意义的文档。常出现注释缺失，或只有机械复述，如在 if total < 50: 前写“验证总数是否小于 50”，并无增量信息。更关键的是，AI 几乎不解释设计抉择，即使用了非常规方法，也只给结果不给思考过程。

审查时可关注：
· 复杂片段是否有解释。算法或晦涩段落是否配有注释说明思路和决策，缺少就应要求补上。
· 能否看出“为什么”。注释里是否体现设计意图和取舍，而不是只有操作描述。
· 人工修改是否被记录。AI 生成后的人工修正，如修 bug 或优化性能，应在注释或提交说明中标注原因，方便追溯。

业界认可的做法：
· 为对外接口写 Docstring。包含用途概述、参数、返回值、异常、示例等，让调用方迅速理解。
· 写完善的 README。项目层面说明目的、依赖、安装、用法示例、常见问题、贡献指南等，帮助新人快速上手。
· 注释原则是解释原因。不要写“i = i + 1 // i 加 1”这类自解释注释，而要写动机，如“// 用 i 递增遍历数组索引，因为...”。
· 文档要同步更新。代码改了注释就要改，过时注释比没注释更害人。代码审查应把文档一致性作为必检项。
· 清理死代码。不要用注释保留废弃代码，版本控制能恢复历史，残留只会增加阅读负担。

总之，AI 擅长写“做什么”，人类要补足“为什么”。只有把背景和原因补全，代码才易理解、可演进。

4. 日志策略

系统运行后本质是黑盒，没日志就无法回溯。日志记录关键事件和数据，是调试、性能分析和安全审计的基础，能提供运行可见性。

AI 缺乏业务直觉，日志处理常失衡：要么泛滥，重要信息被噪声淹没；要么不足，关键步骤没记录。更危险的是可能把隐私或机密数据直接写进日志。

审查 AI 生成模块的日志时，重点看：
· 关键数据是否记录，如接口入参、中间变量、模式或特性开关等配置项。
· 业务分支是否可追踪，if/else 分支打印执行路径，如余额不足拒绝交易。
· 外部接口是否记录请求和返回，敏感字段需脱敏。
· 异常处理是否记录错误信息和堆栈，业务异常也应留下痕迹。

日志可按用途分类：
· 性能日志。监控执行时间、请求延迟、内存 CPU、缓存命中率等，如 {"latency_ms": 123, "endpoint": "/recommend"}，用于定位瓶颈。
· 用户行为日志。记录点击、搜索、转化等关键操作，含用户 ID、动作类型、目标对象，如 {"user_id": "abc123", "action": "click", "item_id": "xyz"}，用于产品优化和异常模式发现。
· 错误日志。记录错误码、信息、堆栈及降级措施，如 {"error_code": "E502", "message": "timeout", "action": "fallback_used"}，用于故障排查。

分类后可采用不同存储和分析策略，性能日志实时告警，行为日志汇总分析，错误日志支撑排障。

5. 错误处理

错误处理决定程序在异常输入或意外情况下是否崩溃、是否产出错误结果。它直接影响可靠性和用户体验。

例如：
```python
# 未进行错误处理的代码
result = 10 / int(user_input)
print("计算结果:", result)
# 如果 user_input 非数字或为 0，抛出异常并崩溃
```
加入处理后：
```python
# 加入错误处理的代码
try:
result = 10 / int(user_input)
print("计算结果:", result)
except (ValueError, ZeroDivisionError) as e:
# 捕获转换错误或除零错误
print("出现错误：", e, "。已使用默认结果 0。")
result = 0 # 使用默认值作为降级措施
```
通过捕获异常并提供降级路径，系统不会直接中断，能在边界输入下平稳运行。审查 AI 代码时，要确保异常不是被忽略，而是被有意识地处理并记录。
