# CentOS 上安装 gh 并驱动三 Agent 自动化开发

演示环境选用 CentOS，安装思路在其它发行版上同样适用。这里采用 GitHub 官方 RPM 源，兼容 CentOS 7、CentOS 8 及 CentOS Stream，流程规范且上手快。

在终端里执行添加源指令：

sudo dnf config-manager --add-repo https://cli.github.com/packages/rpm/gh-cli.repo

这一步相当于把 GitHub 官方软件仓库登记到系统，让 dnf 能准确检索到 gh 工具包。

**注意：** 若出现 `dnf: command not found` 的提示，说明当前系统未预装 dnf，可先运行 `sudo yum install dnf -y` 安装后再重复执行上面的添加源命令。

源配置成功后正式安装：

sudo dnf install gh -y

末尾的 `-y` 表示自动确认，无需手动交互。安装完成后校验版本：

gh --version

返回类似 `gh version 2.88.1 (2026-03-12)` 的信息即表示安装完成，如图 13-1 所示。

2．授权登录 GitHub 账号
安装完毕后还需完成授权，才能让 gh 操作仓库。在终端执行：

gh auth login

随后进入交互式向导，按提示逐项确认即可，整体流程如图 13-2 所示。

[PRE1]
图 13-2 gh 账号授权登录流程

向导的关键选项如下。

1．选择要登录的 GitHub 服务
默认是 GitHub.com，即全球公开站点，个人开发者通常直接回车。

2．选择 Git 通信协议
建议选用 SSH，安全性更高，后续推送代码无需重复输入凭证。gh 会自动探测本地是否已有 SSH 密钥，若无则引导生成并自动上传到 GitHub。
HTTPS 依赖用户名加个人访问令牌，配置更简便，但部分场景会频繁要求二次验证。
追求规范流程选 SSH，追求快速体验可选 HTTPS。

3．选择 CLI 验证方式
推荐使用 Login with a web browser，通过浏览器完成授权：gh 会生成一次性验证码并自动打开浏览器，用户在网页中确认授权即可，操作简便。
Paste an authentication token 属于令牌登录，需要手动填入事先在 GitHub 创建的访问令牌，适合无图形界面的服务器。日常使用优先浏览器授权。

4．完成网页授权
终端会输出一次性验证码，复制后回车，浏览器自动跳转到 GitHub 授权页，粘贴验证码并确认，随后关闭页面返回终端即可。

5．登录成功校验
终端出现以下提示即表示授权完成。

✓ Authentication complete.
- gh config set -h github.com git_protocol https
✓ Configured git protocol
! Authentication credentials saved in plain text
✓ Logged in as aacedar

## **13.3** 详细操作步骤与配置指南

下面演示如何搭建由 3 个 Agent 组成的自动化开发链路。

### **13.3.1** 飞书渠道接入配置

首先在飞书开放平台新建企业自建应用，作为与 OpenClaw 的交互入口。登录后点击“创建企业自建应用”，应用名称设为“产品经理”。进入左侧“凭证与基础信息”，记录 App ID 和 App Secret，这两个参数后续用于 OpenClaw 鉴权，如图 13-3 所示。

[PRE2]
图 13-3 飞书应用凭证信息页面

接着进入“添加应用能力”，开启“机器人”能力。然后在“权限管理”中批量导入以下权限范围：contact:contact.base:readonly、im:message、im:message.p2p_msg:readonly、im:message:send_as_bot、cardkit:card:write。
这些权限可确保机器人正常收发消息。

最后进入“事件订阅”，选择“使用长连接接收事件”方式，比传统 Webhook 更稳定且无需公网 IP，并新增 im.message.receive_v1 事件。配置完成后创建应用版本并申请发布，审核通过后即可在飞书中使用，如图 13-4 所示。

### **13.3.2** 创建多智能体工作空间与 SOUL.md

使用 openclaw agents add 为三个 Agent 分别建立独立工作空间：

openclaw agents add coder --workspace "~/.openclaw/workspace-coder"
openclaw agents add reviewer --workspace "~/.openclaw/workspace-reviewer"
openclaw agents add tester --workspace "~/.openclaw/workspace-tester"

1．Coder Agent 的 SOUL.md

Coder 承担核心执行，需要明确编码规范与协作流程，对应文件路径为 ~/.openclaw/workspace-coder/SOUL.md，内容如下：

# 角色定义

你是一名经验丰富的全栈工程师，精通 HTML5、JavaScript 和前端游戏开发，负责根据需求编写高质量、可维护代码。

## 核心职责

- 接收开发需求，使用 github 技能拉取最新代码并创建新分支，分支命名需具有描述性，如 feature/snake-game，必要时新建项目。
- 编写核心业务逻辑，兼顾系统完整性与用户体验。
- 编码完成后，必须用 agent_send 工具把文件路径和改动说明发送给 reviewer 审查。

## 协作与修复准则

- 收到 Reviewer 的修改意见后虚心接受，分析后修改并再次提交，直至通过。
- 收到 Tester 反馈的失败日志时优先处理，定位 Bug 修复后通知 Tester 重新测试。
- 未经 Reviewer 批准和 Tester 测试通过，严禁私自提交代码或创建 PR。

2．Reviewer Agent 的 SOUL.md

Reviewer 负责守门把控代码质量，对应文件路径为 ~/.openclaw/workspace-reviewer/SOUL.md，内容如下：

# 角色定义

你是一名极其严苛的资深架构师，负责对团队代码进行静态审查。对整洁度、性能和安全性要求极高。

## 审查准则

- 收到 Coder 的审查请求后仔细阅读改动代码。
- 重点检查：
  1. 变量命名是否语义化，是否滥用全局变量。
  2. 核心逻辑如贪吃蛇碰撞检测是否存在边界漏洞。
  3. 是否存在内存泄漏风险。
  4. 代码是否包含必要注释。
- 发现问题时用 agent_send 回传具体修改建议，指出错误行并给出改进方案。
- 代码达标则回复通过，并用 agent_send 通知 Tester 开始编写测试用例并执行。

3．Tester Agent 的 SOUL.md

Tester 负责编写测试并触发 Lobster 流水线，对应文件路径为 ~/.openclaw/workspace-tester/SOUL.md，内容如下：

# 角色定义

你是一名专业的自动化测试工程师，负责为业务代码编写单元测试并管理 CI 流水线。

## 工作流准则

- 收到 Reviewer 通过通知后阅读 Coder 编写的业务代码。
- 使用 Jest 或 Mocha 等框架，为核心逻辑如贪吃蛇初始状态、移动逻辑、碰撞判定编写覆盖率不低于 80% 的单元测试。
- 编写完成后必须调用 Lobster 工具运行项目根目录下的 dev-pipeline.lobster 文件。
- 若 Lobster 返回失败日志，用 agent_send 将详细错误发送给 Coder 修复。
- 若返回 needs_approval 状态，说明测试已全数通过，流水线等待人工审批。此时需向飞书用户发送消息告知测试通过并提醒在飞书中点击批准以创建 PR。

### **13.3.3** 编写 Lobster 工作流文件

在项目根目录新建 dev-pipeline.lobster，用来定义确定性的审查与测试流程。

YAML
# dev-pipeline.lobster
name: code-review-and-test
steps:
  - id: lint
    command: npm run lint --silent
  - id: test
    command: npm run test --silent
    stdin: $lint.stdout # 仅在 lint 通过时执行
  - id: approve_pr
    command: echo "All tests passed. Ready to create PR."
    approval: required # 暂停等待人类在飞书中批准
  - id: create_pr
    command: gh pr create --title "Feature: Snake Game" --body "Automated PR created by OpenClaw Pipeline"
    condition: $approve_pr.approved # 仅批准后执行

逻辑清晰：先代码检查，再执行单元测试，通过后暂停请求人工审批，批准后自动调用 GitHub CLI 创建 PR。

## **13.4** 飞书交互与效果验证

重启 Gateway 服务后，在飞书中输入“你好”，OpenClaw 会返回一次性配对码，例如 BUFLH4AH：

在 OpenClaw 服务器终端执行完整配对命令，将末尾替换为实际收到的配对码：

openclaw pairing approve feishu BUFLH4AH

执行成功后，飞书机器人与 OpenClaw 完成绑定。

随后向飞书中的 coder 机器人发送开发指令“@coder 请在当前项目中开发一个基于 HTML5 Canvas 的贪吃蛇游戏。要求包含计分系统、食物随机生成逻辑以及碰撞检测（撞墙或撞自己即游戏结束）”。发送界面如图 13-5 所示。

[PRE6]
图 13-5 向 coder 机器人下达贪吃蛇游戏开发指令

从编码、审查、测试到合并，全部环节由多智能体自主协作，具体过程如下。

1．编码阶段：Coder Agent 收到指令后自动创建 feature/snake-game 分支，编写 index.html 和 snake.js，实现 Canvas 渲染与游戏循环，完成后调用 agent_send 将文件发给 Reviewer 审查。

2．审查阶段：Reviewer Agent 检查发现 Coder 在生成食物时未检查是否与蛇身重叠，存在缺陷，随即打回并给出修改建议。Coder 修复后再次提交，Reviewer 确认通过并通知 Tester 进入测试环节。

3．测试阶段：Tester 基于碰撞检测、计分逻辑编写 Jest 测试用例，然后调用 Lobster 运行 dev-pipeline.lobster 流水线。若测试失败，错误日志自动发给 Coder 修复；若测试通过，流水线进入等待审批状态。

4．审批与合并：测试通过后，Lobster 在 approve_pr 步骤暂停，并向飞书发送交互式审批卡片，提示“贪吃蛇游戏所有测试已通过，是否批准创建 PR”。点击“批准”后，OpenClaw 使用 resumeToken 恢复流水线，执行 gh pr create 命令，自动在 GitHub 上创建 PR 并在群内同步结果。

如需查看各 Agent 完整交互日志，可执行 openclaw logs --follow 命令实时监听。
