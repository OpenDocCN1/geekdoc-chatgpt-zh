## 11. 训练图与推理图的本质差别

深度学习模型训练和推理共用同一套网络结构，但背后的计算图差异很大。

第一，推理只走前向，训练要前向还要反向。推理阶段不需要标签，训练阶段必须读取标签，用损失函数把标签与前向输出对比得到误差，再通过梯度回传逐层更新参数。即使是用同样的 API 声明，比如 TensorFlow 的 tf.nn.conv2d 来建一个卷积层，推理时权重和偏置只是常量被读取，训练时因为优化器的存在，这些数值会参与计算并被改写。

第二，部分层的行为随阶段而变。dropout 在训练时生效，推理时完全不加入或不做任何处理。批量归一化在训练时要统计当前批次的均值方差并学习额外的参数，推理时则退化为固定的线性变换。

第三，训练图会带入大量额外节点。除神经网络本身的子图外，还会挂上数据读取、预处理、损失计算、优化更新等节点。

清楚节点和运算的差异对开发、昇腾 AI 处理器使用和后续编程都至关重要。实践中建议遵守三条准则：

1) 把模型定义和业务逻辑拆开
用一个独立的函数或类来封装模型，保证输入输出格式稳定。比如 LeNet5 可单独定义，输入形状固定为 [N, 28, 28, 1]，输出为 [N, 10]，N 代表一次处理的样本数且在运行时固定。这样定义的子图可以在不同工程复用，也是各大框架提供模型库的原因。

2) 用标志区分训练与推理
像 dropout 这类层在两阶段的计算不同，有时训练还需要额外操作，定义模型时应加一个标志来判断当前环境。Caffe 在 prototxt 中用 Phase 字段标识阶段从而决定是否保留某些层。TensorFlow 则通过函数参数配合 Python 判断来决定是否加入 dropout。还可以把 dropout 的比率做成占位符，训练时调参，推理时置零实现空操作。借助这个标志，同一份定义可以快速生成对应阶段的图。

3）训练代码和测试代码分开写
虽然可以用参数切换阶段，但训练和推理的业务与计算图差异明显，通常分开实现，通过权重文件传递。具体工程一般包含：
- model.py：用框架接口定义网络结构。
- train.py：在 model.py 基础上搭建训练图，可加载预训练权重，按业务训练并保存参数。
- test.py：在 model.py 基础上搭建推理图，加载权重完成预测并保存推理图。
- 应用代码：加载推理图和参数，完成实际应用。

## 12. 模型怎么持久化

不同框架都提供保存与加载机制，用专门文件存放计算图结构和模型参数，比如 Caffe 的 prototxt、caffemodel，TensorFlow 的 meta、ckpt、pb 等。总体可分三类：

计算图结构文件：仅保存图结构，是序列化后的图，例如 TensorFlow 的 meta 文件。
模型参数文件：仅保存可训练参数，如权重偏置，以 key-value 形式存储，例如 TensorFlow 的 ckpt、PyTorch 的 pth。
模型文件：同时保存结构和参数，形式因框架而异，例如 TensorFlow 的 pb。

## 13. 跨框架模型迁移的现实问题

框架和硬件加速平台越来越多，TensorFlow、Caffe2、MXNet、PyTorch 等，以及 CPU、GPU、FPGA、ASIC 等，给模型迁移带来麻烦。例如要在亚马逊集群上开发，就得把其他框架的模型转成 MXNet 格式并重训，不同框架对同一算子的定义差异还可能导致结果偏离预期。

## 14. 推理引擎与计算图的关系

随着框架发展，对跨框架迁移的需求催生了 ONNX、MMdnn，对高效跨硬件推理的需求催生了推理引擎。

推理引擎不做训练，接收来自框架的已训练好计算图，经过优化后在不同硬件上高效运行。类似编译器栈，完成从框架模型文件到加速硬件的端到端映射。

引擎的输入是各框架定义的模型文件，即计算图的表示，ONNX 只是其中一种，因其统一性被广泛采用。对推理引擎开发者需注意：

- (1) 模型文件要同时包含图结构和参数。TensorFlow 通常用 pb 文件，PyTorch 模型参数与结构可能同扩展名，需特别确认是否齐全。
- (2) 图中应只保留推理子图。训练图包含反向、数据读取、预处理等节点，推理引擎不一定支持。最终推理图最好仅含神经网络本身，输入例如 [32,1,28,28] 的图像，输出例如 [32,10] 的概率。按需可加入像素格式转换等简单算子，前提是模型定义和引擎支持。
- (3) 优先使用统一格式。ONNX 提供统一中间表示、算子集和文件格式 onnx，同时包含结构和参数。TensorRT、TVM 等主流引擎对 ONNX 支持良好。将模型先转成 ONNX 再送入引擎，能更快发现并解决上述问题。

## 5.1.2 推理优化的原理拆解

相较训练，推理流程固定，优化空间更大。优化方向多样：算法层面如 FFT、Winograd 卷积降低复杂度；调度层面如内核融合减少调度开销；硬件层面如 TPU 的脉动阵列加速卷积。

例如某机器翻译团队通过内核融合和专用内核，让 BatchMul 内核比专业优化的 cuBLAS 快 13 倍，进一步融合前后处理再提升 1.7 倍。业界经典做法是把二维卷积、批量归一化、ReLU 融合成 Fused-Conv2d-Bn-ReLU，性能常超过 cuDNN 的手工优化内核。

总体分为两层：一是计算图优化，向上抽象，涉及内存分配、内核融合、计算调度等硬件无关优化；二是内核优化，向下抽象，涉及数据排布、循环展开等强相关的硬件优化。

### 2. 计算图优化
计算图优化不依赖具体硬件，主要从内存、调用、同步角度改进。

#### 1) 优化内存分配方式
推理需要存储参数、输入输出和中间结果。为避免每次分配，框架通常在任务开始前为每个节点和参数按形状预分配并复用。Caffe 就要求在 prototxt 中明确输入形状。

随着模型迭代，输入形状可能变化，固定分配不再适用。现代表现为动态分配，TensorFlow 的占位符可接收 [None,224,224,3]，None 在运行时确定，后续张量形状随之推导。

这种灵活性带来开销：运行时算形状、动态分配内存。TensorFlow 采用预分配大块内存加存储空间管理器，本身也有开销。

实际推理输入常固定，可像 Caffe 一样统一预分配，避免动态开销。TVM、TensorRT 等推理引擎要求指定输入形状，ONNX、TFLite 在转换前也要求固定形状，目的都是降低分配成本。

#### 2）指定合适的批量大小
批量大小对推理性能影响很大，通常随批量增大而提升并趋于峰值。小批量无法充分利用硬件计算资源。以昇腾 AI 处理器 AI Core 的矩阵计算单元为例，矩阵小于 16×16 时需补零，浪费计算。随着批量增大，浪费比例下降，性能接近峰值。

不少加速器研究拿 GPU 对比时，因批量选择不当导致 GPU 带宽和计算未满，性能远不及峰值，这种对比并不公平。
