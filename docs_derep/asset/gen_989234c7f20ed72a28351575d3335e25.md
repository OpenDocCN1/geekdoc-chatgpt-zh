#### 8.2.5 让大模型会用工具

借助 Function Calling 或 Tool Calling，大模型能够输出结构化结果，并从 function_call 字段里解析出下一步要调用的函数名与参数。

下面是一段演示如何解析 Function Calling 的示例。

工具名称: get_weather

参数: {'location': '上海', 'temperature': 25}

示例很基础，却已经是 Agent 类智能系统的起点。当模型能自主判断下一步该用哪个工具、函数，并结合检索到的知识或用户输入按接口要求给出参数格式时，就相当于给系统装上了灵活使用外部工具的手。

未来借助 MCP、RAG 与 Agent 应用，外部系统可以被串联起来实现更强能力，而精准的解析机制是让大模型与外部系统顺畅互联的前提。

### 8.3 选对模型，输出才更靠谱

接入大模型主要有三类做法：API 调用、开源模型平台部署、本地化部署。

- 通过 API 调用大模型，例如 OpenAI 的 GPT-4、Anthropic 的 Claude 等，是开发者最快的集成方式。用户直接调用云端服务，无需本地搭建，但依赖网络且成本偏高。
- Hugging Face 与魔搭社区 ModelScope 是两大开源模型平台。前者模型库丰富，工具链成熟，支持微调与部署；后者由阿里云主推，聚焦中文场景，提供本地化模型与算力，降低中文 NLP 的门槛。
- Ollama 与 vLLM 代表本地化部署工具。Ollama 体积轻、启动快，可本地跑 Llama 等开源模型，适合调试；vLLM 由加州大学伯克利分校团队开发，靠 PagedAttention 优化显存管理，大幅提升推理速度，能满足生产高并发需求。

说明一下，第一种方式多用于闭源商用模型，后两种多用于开源模型。当前常用模型有：

- GPT 系列，OpenAI 的领跑者，逻辑推理与指令遵循突出，引领创新方向。
- Claude 系列，Anthropic 的长上下文专家，支持 200K token，安全性高、幻觉率低，在数学与编程基准上表现强势。
- Gemini 系列，Google 的多模态统一架构，支持超长上下文，推理与代码能力持续强化。
- DeepSeek 系列，国产代表，采用 MoE 架构，数学与代码优化明显，支持 128K 上下文。DeepSeek-R1 开源可商用，还有小尺寸蒸馏版便于部署。
- Llama 系列，Meta 开源模型，参数 8B 到 70B，推理效率高、生态工具丰富。
- Qwen，阿里云出品，中文处理优化显著，1.8B 至 72B 规模皆有，支持多轮对话与插件。
- Mixtral，Mistral AI 的 MoE 模型，以较少激活参数实现高性能，开源可商用。

这些模型都在追求更低推理成本、更大上下文与多模态扩展，推动开源与商业化并行。

挑选模型时关注以下要点：

- **规模与性能**：模型越大理解复杂语境与生成能力越强，但算力与推理时间也会上升，需要在效果与成本间权衡。
- **任务适配性**：不同模型在代码、理解、对话等任务上各有强项，按需求选择能提升质量。
- **微调与定制化**：通过微调适配特定领域。参数高效方法如 Adapter Learning 与 LoRA 用少量可训练参数实现定制。
- **自我反馈机制**：让模型先生成初稿再自评自改，可提升准确性与一致性。流程为先生成、后审阅反馈、再优化。

### 8.4 检索结果怎样融入生成过程

小冰：咖哥，除了调提示词和换模型，还有更高级的生成技术吗？
咖哥：当然有。传统 RAG 直接把检索结果喂给生成器，检索与生成相对独立，只在输入端结合。检索质量直接决定输出效果，检索失败或噪声多就会拉低表现，但实现简单。

检索与生成的结合方式并不唯一。论文《A Survey on RAG Meeting LLMs: Towards Retrieval-Augmented Large Language Models》梳理了几种融合思路，如图8-3所示。图中检索流程与传统 RAG 相同，生成部分则列出三种集成方式。

#### 8.4.1 输入端拼接

把检索内容与用户原始查询一起拼接到生成器输入，像开卷考试带资料作答。生成器拿到问题+相关文档段落或实体后直接作答。

REALM 即检索增强语言模型，是典型代表。它在预训练阶段引入检索，实时获取外部知识，把检索段落与问题组合，提升准确率。优点是简单易实现，输出连贯；缺点是检索文档太多会超出模型最大序列长度。

#### 8.4.2 输出端加权

先让生成器生成，再把结果与检索信息结合加权，类似先写答案再对照资料校对。模型会算出两份概率分布，一份是模型本身预测的下一个词分布，一份来自检索上下文的分布，然后融合得到最终答案。

kNN-LM 是典型做法，生成后依据相似上下文调整词概率，减少错误与幻觉。优势是可在生成后介入，不改中间过程，适应复杂上下文。难点在于如何对检索结果与模型输出加权，尤其两者不一致时如何取舍。

#### 8.4.3 中间层注入

在生成器内部中间层引入检索信息，使检索在生成各阶段持续影响输出，像写作时不断查资料调整。检索片段被转成密集向量，通过注意力或集成模块注入中间层，实现动态交互。

RETRO 是代表，通过在 Transformer 中间层接入检索文本块，让模型在生成时动态访问信息。相比输入与输出层，中间层交互更频繁，适合长文本高质量任务，但改动模型内部，计算成本更高。

### 8.5 Self-RAG 让模型自己挑刺

7.3 节提到过 CRAG，本节的 Self-RAG 与其有相似之处。Self-RAG 是在 RAG 架构中加入自我反思与自我评分的策略，源自华盛顿大学论文《Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection》。核心是通过自动化决策逐步验证检索文档相关性与生成内容准确性，使模型能动态决定是否检索并评估自身输出，降低偏差与幻觉。

Self-RAG 见图8-4，有三个特点：

- 按需检索：根据问题需求动态决定是否检索，避免无用检索。
- 自我评估：生成时用特殊反思 token 评估输出，与检索知识保持一致。
- 多维控制：引入批判模型从多个细粒度维度评估与控制生成质量。

主要流程：

(1) 判断是否需要检索：输入用户提问 x，输出检索决策 Yes/No/Continue。
(2) 判断检索文档是否相关：输入 x 与检索到的文本块 d，输出 Relevant 或 Irrelevant。
(3) 确认生成内容支持度：输入 x、d 与生成内容 y，输出 Fully Supported、Partially Supported 或 No Support。
(4) 评估生成质量：输入 x 与 y，给出 1～5 分，反映完整性与有效性。

LangGraph 的 Self-RAG 代码实现示例可参考作者 GitHub 仓库。
