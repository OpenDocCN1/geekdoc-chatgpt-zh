#### 8.1.9 LangChain 迈向 LangGraph 的演进
LangChain 在 2023 年已形成相当活跃的社区来规范大模型应用。后来的三个主版本里，RAG 与 AI Agent 是体系中最关键的两块。图 8.12 展示了 LangChain 下构建智能体的底层架构。

[PRE2]

先看 LangChain 内部的智能体设计思路，被拆成智能体、Message、Toolkits 三大要素。一个智能体通常由大语言模型 + 提示词 + 输出解析器构成，形成 Chain 来处理用户输入。可接收的输入来自三处：Input 代表用户的原始问法，Model Response 是模型对子任务的中间结果，Context 则携带上下文信息。输出端会连向真实工具库，具体调用哪些工具由智能体拆分出的子任务决定。大模型调用外部函数分为识别工具与真正执行两步。Messages→AI Agent→Toolkits 这条路径负责把复杂需求拆解，在工具库里匹配对应工具并提取名称与参数，可视作一种静态执行路径。把决策落地为动作的工作则交给 AgentExecutor。

总体来看，LangChain 的智能体架构里，智能体只负责接收输入并判断该做什么，并不亲自执行，执行由 AgentExecutor 承担。只有把担任决策核心的智能体与负责运行的 AgentExecutor 搭配使用，才能构成完整智能体。AgentExecutor 调用智能体并运行其指定的工具，从而实现整体功能。

LangChain 仍是构建大模型应用的主流框架之一。最新 v0.3 基本完成从传统类向 LCEL 的迁移，让定义与执行分步操作序列变得更简洁高效。专业表述上，LangChain 本质是构建有向无环图 DAG。随着 AI 应用尤其是智能体的发展，大模型的使用正从单纯执行工具转向更复杂的推理引擎，这正是 LangGraph 诞生的动因。这一转变对循环结构和复杂条件交互提出更高要求，而基于 LCEL 的线性序列在构建更高级系统时逐渐显现局限。

#### 8.1.10 LangGraph 构建智能体的底层逻辑

##### 1. LangGraph 框架缘起
从名称看 LangGraph 与 LangChain 关系紧密。实际上它是以 LangChain 表达式语言为基础构建的开发框架，用来搭建 AI Agent。因此在模型接入与智能体构建上的优势，可自然继承自 LangChain。从技术视角看，大模型本身无法采取行动，只能输出文本，即接收输入并给出响应。

##### 2. 图的构成：节点与边的协作
在图式框架里，任何可执行逻辑都能成为对话、智能体或程序的起点。该起点可以是模型 API、基于模型搭建的 AI Agent，或通过 LangChain 等实现的线性序列，如图 8.13 中“Start”圆圈所示。无论形式如何，它首先处理用户输入并决定下一步。图 8.13 展示了一个基于 LangGraph 概念的基础智能体样例。

LangGraph 里，凡包含可执行逻辑的部件都被视为节点 Node，包括模型调用、搜索操作及条件判断。流程入口的“Start”单元接收用户输入，并按需：

- （1）调用 Action 单元进行外部信息查询，例如 Web 搜索、数据库查询或 RAG 检索。
- （2）把获取的信息传给语言模型单元，用于生成自然语言回复。
- （3）最终把回复交给 End 单元，完成链路。

如图所示，每个圆圈代表一个单元，每条连线是边 Edge，用来控制流程方向；状态通过消息沿边更新。

因此，无论智能体设计多复杂，最终都是单元与连线以特定方式组合成的图结构。工作流的核心在于：单元完成任务后，会经由连线通知下一个单元继续。简言之，LangGraph 底层消息传递算法定义了通用程序模式：单元完成操作后沿一条或多条连线向其它单元发送消息，接收方执行功能并把结果传给下一单元，如此循环往复。

##### 3. 条件边与路由决策
在更贴近实际的场景里，智能体不会沿固定路径执行，需要判断是否调用工具、调用哪个工具、是否直接给出答案等。以下是一个更复杂的示例。

我们把 AI Agent 定义为应用起点。搭建 AI Agent 通常需要配置一个或多个可用工具，否则能力有限，因为即使问题很复杂，仅靠提示词引导大模型如 OpenAI 的 o1 推理模型也能自行完成推理。当智能体配备工具后，它通过函数调用机制使用工具，而非直接执行。当用户原始问题被处理时，一般出现两种情况。

- （1）无需调用工具时，智能体直接给出自然语言回复。例如：

用户：你好，请你介绍一下你自己。

AI Agent：你好，我是一个人工智能助手，可以帮助你解决问题。

如图 8.14 所示，经过第一个单元智能体后，若认为需要调用函数，会选哪个工具、传哪些参数？在多工具可选时，Action 单元会呈现多条可能路径。如何选择？LangGraph 引入了条件边组件。条件边根据是否满足特定条件决定走向，例如智能体可能要决定使用搜索工具还是直接生成最终答案。为管理这些决策，使用了类似 if-else 的结构，称为 Router。基于 Router 的判断，智能体可能导向网络搜索单元执行搜索并返回原始文本，或直接前往 End 单元获取格式化后的自然语言回复。若选择搜索路径，获取的文本还需经另一个大语言模型处理以生成用户可读的回答；若直接回答，则可用专门工具格式化输出。

在 LangGraph 里，Router 以 if-else 形式决定路径，主要通过三种方式实现。

- 提示工程：指示大模型以特定格式回应。
- 输出解析器：用后处理从模型响应中提取结构化数据。
- 工具调用：利用大模型的内置工具调用功能生成结构化输出。

##### 4. 共享状态 State 机制
我们已知 LangGraph 通过组合单元与连线创建复杂的循环工作流，通过消息传递串联单元形成通路。维持消息及时更新并准确投递则依赖 State 概念。在 LangGraph 流程里，每次执行都会启动一个状态，单元在处理时会传递和修改该状态。这个状态不是静态数据，而是由各单元输出动态更新，进而影响循环里的后续操作，如图 8.15 所示。

共享状态指图执行过程中单元之间传递的数据或信息。LangGraph 允许单元在执行时通过共享和更新公共状态进行交互。这种机制使单元能基于共同维护的数据通信、交换信息并相互影响行为。借助共享状态，LangGraph 能实现单元操作的协调与同步，支持动态交互和复杂工作流构建，使单元可依据已有共享信息协同工作并做出决策。

##### 5. 官方定义与核心优势
从官方定义看，LangGraph 是一个用于用大模型构建有状态、多参与者应用的库，可创建智能体和多智能体工作流。官方总结的优势如下。

- 循环和分支：在应用里实现循环和条件。
- 持久性：图每步执行后自动保存状态。可随时暂停和恢复执行，以支持错误恢复、人机交互工作流、时间旅行等。
- 人机交互：中断图形执行以批准或编辑智能体计划的下一步操作。
- 流支持：每个单元生成的输出流，包括令牌流。
- 与 LangChain 集成：与 LangChain 和 LangSmith 无缝集成。
