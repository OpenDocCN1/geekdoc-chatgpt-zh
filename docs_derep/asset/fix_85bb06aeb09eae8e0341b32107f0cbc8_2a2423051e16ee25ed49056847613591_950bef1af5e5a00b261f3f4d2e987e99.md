多代理协作：精准匹配与安全边界

让一组专项助手协同工作，关键在于如何自动找对人、给对权限、选对模型。

指令如何自动找到对口助手
用户抛出需求，例如“帮我审查一下这个 PR”，总控不会写死路由表。先把当前已注册的专项助手自我介绍全部取出来，再把用户话术与这些介绍做语义层面的相似度比对，判断当前工作是否落在某个助手的职责范围内。一旦匹配度很高，比如代码审阅助手的说明覆盖代码审查、安全审计等方向，总控就会把任务材料完整打包，转交给该助手，全程无需用户手动点名。

安全层面的第一道闸是工具清单
tools 配置体现的是从底层落实最小授权的思路。以代码审阅助手为例，可用的能力只有三项只读操作：Read、Grep、Glob。清单外的写类或执行类能力，例如 Edit、Write、Bash，对该助手而言完全不可见、也不可调用，从根上避免越权。

模型选择是成本与质量的平衡杆
model 字段常被忽略，实际是隐形的成本杠杆。格式校验、日志过滤这类偏模式化的轻量工作，选用 Haiku 这类快速响应的轻量模型即可；架构设计、安全审计这类需要深度理解与复杂推理的场景，则更适合 Sonnet、Opus 这类高性能版本。搭配得当既能压住开销，也能保证交付水准。

权限模式提供第二层兜底
permissionMode 用来调节授权边界。设为 plan 时，助手进入系统级只读保障状态，这种全局性的保险比单纯的工具清单更严格；默认值 default 则沿用常规的权限流。

执行型助手会有不同取舍
测试运行器就是一个偏执行的例子。它必须调用 Bash 来跑命令，所以可调用工具比审阅类更宽，但对返回格式的约束更严。

你是一名测试执行专家。你的核心价值是从海量测试输出中提炼关键信息，为主对话提供精准的测试摘要

## 执行流程

1. 确认项目的测试命令（查阅 package.json 或 CLAUDE.md）

2. 运行测试套件

3. 分析输出结果，区分通过和失败的测试用例

4. 针对失败的测试，定位具体失败原因

## 输出格式（严格遵守）

### 测试摘要

- 总计：x个测试

- 通过：x个

- 失败：x 个

- 跳过：x 个
