##### 多 agent 的好处

好处一：记忆隔离

工作 agent 的 MEMORY.md 和生活 agent 的 MEMORY.md 各自独立。工作侧不知道你晚上做了什么，生活侧也不了解你白天的项目进展。

好处二：权限隔离

工作 agent 可以访问公司邮箱和内部系统，生活 agent 无权访问；反过来也一样。权限分开更安全。

好处三：成本分摊

工作 agent 可以配更贵的模型比如 Claude Sonnet，生活 agent 用 DeepSeek 这种便宜的，按用途分配预算。

#### 6.3.2 方案二：子 agent 临时协作

适合场景：主 agent 收到一个复杂任务，需要多线并行推进。

##### 什么是子 agent

子 agent 是主 agent 临时派出的执行单元，完成特定任务后就把结果交回并自行销毁。

典型例子：

你告诉主 agent“帮我准备明天的会议材料。”

主 agent 拆成三件事：

1. 从邮件里提取会议议程
2. 从上次纪要里提取未完成事项
3. 从项目文档里提取最新进展

串行会很慢，主 agent 就同时派出三个子 agent 各自处理。

##### 子 agent 怎么工作

OpenClaw 内部用 sessions_spawn 命令创建子 agent，你不需要手动触发，主 agent 会自行判断是否需要并行。

子 agent 的特点：

- 拥有独立的上下文和 token 消耗
- 不继承主 session 的工具权限，更安全
- 可以单独指定模型，主 agent 用贵的，子 agent 用便宜的
- 任务结束自动销毁

#### 6.3.3 省钱技巧：主 agent 和子 agent 便宜

官方文档明确说明子 agent 可以独立设置模型。

实际思路：

- 主 agent 用 Claude、GPT 这类强模型做推理与调度
- 子 agent 用 DeepSeek、通义千问这类模型做搜索、整理、重复劳动

既保证整体质量，又压住成本。

##### 多 agent VS 子 agent：怎么选

表 6-1 梳理了两种模式的差异。

表 6-1 多 agent 与子 agent 对比

| 维度 | 多 agent | 子 agent |
| :--- | :--- | :--- |
| 用途 | 长期分工 | 临时并行 |
| 生命周期 | 持久存在 | 任务完成即销毁 |
| 记忆隔离 | 完全独立 | 临时隔离 |
| 配置复杂度 | 需要配置文件 | 自动创建 |
| 适合场景 | 工作/生活分离、团队协作 | 复杂任务并行处理 |

选择建议：

- 需要长期角色分工比如工作助手、生活助手、学习助手，用多 agent
- 只是偶尔要并行处理复杂任务，交给子 agent 自动处理即可

#### 6.3.4 实用建议

##### 建议一：别一开始就使用多 agent

刚上手 OpenClaw 时，一只“龙虾”就够了。等真的出现工作生活串台或项目混淆的问题，再考虑多 agent。

##### 建议二：多 agent 要明确分工

职责必须清晰，不要模糊。“工作 agent 管所有工作事务，生活 agent 管所有生活事务”这种划分最简单有效。

##### 建议三：子 agent 让 OpenClaw 自己决定

不要手动干预子 agent 的创建，把复杂任务交给主 agent，由它自行判断是否派“小弟”。

##### 建议四：为不同 agent 设不同模型

重要任务配贵模型，琐碎任务配便宜模型，整体成本自然下降。

多“龙虾”协作的核心就两点：长期分工用多 agent，临时并行用子 agent。理解了这一点，就能让几只“龙虾”有序干活，而不是乱成一团。

### 6.4 担心它乱动重要文件，如何给它设安全围栏？

OpenClaw 能读写文件、执行命令、操作浏览器，能力强也意味着风险高。

## 第六章 “龙虾”用熟了之后如何玩得更好

- exec – 执行系统命令
- bash – 运行 bash 脚本
- apply_patch – 应用代码补丁

这三项最容易造成破坏。禁止它们后，OpenClaw 仍能读写文件、搜索、调用 API，却无法直接操作系统。

#### 6.4.2 第二道围栏：Sandbox 沙箱

工具黑名单只管能不能调用，调用后能访问哪些文件、能否跳出工作区，就靠 Sandbox 控制。

##### 什么是 Sandbox

Sandbox 是一个隔离环境，限制 OpenClaw 只能在指定目录活动。

启用 Sandbox：

[PRE4]

scope 设为 “workspace” 表示只能访问工作区目录，无法触及工作区外文件。

##### Sandbox 的局限

官方明确提醒：workspace 并非硬沙箱。它只是默认工作目录，不是安全边界。

即便开启 Sandbox，若工具权限放开且使用绝对路径，仍可能访问到工作区外。

真正隔离需要组合使用：

- 工具白名单/黑名单
- Sandbox scope 限制
- 不同 agent 拆到不同系统用户，甚至不同主机

#### 6.4.3 第三道围栏：拆分信任边界

当场景涉及不同部门、不同人、不同风险等级共用 OpenClaw 时，应该拆分 Gateway。

官方说明：OpenClaw 不适合让多个互不信任的人共享同一个高权限 Agent/Gateway。

正确做法：

- 个人用途：一个 Gateway，高权限，自行管理
- 团队用途：每个部门或风险等级一个 Gateway
- 公共服务：低权限、只读、沙箱、独立主机

举例：个人 agent 完整权限，部门 agent 可读写本部门文件但不能执行命令，公开 Bot 仅读和搜索。这样即使公开 Bot 被攻破，也影响不到个人数据。

#### 6.4.6 实用建议

**建议一：默认 deny 高危工具**

除非必须，否则把 exec、bash、apply_patch 加入 deny 列表。大多数日常任务不需要它们。

**建议二：测试环境用严格权限**

测试 agent 先只给 read 权限，功能验证后再放开 write。宁可麻烦，也别把生产数据改坏。

**建议三：每月跑一次 audit**

配置会随使用慢慢变化，定期审计能早发现风险点。

**建议四：重要数据提前备份**

再严的围栏也不保证 100% 安全，重要数据定期备份到 OpenClaw 访问不到的位置，是最后保险。

**建议五：别共享高权限 agent**

多人使用时，每人一个 agent 各自管理。不要图方便共用一个高权限 agent，风险太大。

安全围栏不是一次性工作，而是持续维护。初期权限严一点，用熟后再按需逐步放开。谨慎比事后补救更划算。
