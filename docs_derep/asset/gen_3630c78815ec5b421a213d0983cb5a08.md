外观类为了把多个子系统的调用集中起来，很容易变得臃肿，职责被过度堆叠，违背单一职责。

子系统一旦有新增或调整，往往需要回头改动外观类里的转发代码，这与开闭原则的精神相悖。

外观层也可能让客户端间接感知到底层子系统的存在，耦合度提升，系统灵活度受损。

总体来看，外观模式在简化复杂调用、隔离底层变动、提供统一高层入口的场景下很适用。但在实际使用时，需要对照利弊，结合具体业务权衡后再决定是否引入。

# 5.13 享元模式

享元模式是一种结构型设计模式，核心思路是通过对象复用来支撑海量细粒度实例。

# 5.13.1 应用场景

享元模式可以被应用于以下场景。

+   (1) 系统中出现大量相似实例，且实例化成本较高时，可借由享元共享实例来压缩内存占用。
+   (2) 需要对对象进行缓存并反复使用时，享元机制能够提升整体运行效率。
+   (3) 对象的状态可拆分为可共享的内部状态和每次调用不同的外部状态时，可通过享元共享内部状态来减少实例总量。

# 5.13.2 结构

享元模式的结构包含以下角色。

+   • Flyweight（享元）：给出享元对象的规范，包含设置外部状态的方法。
+   • ConcreteFlyweight（具体享元）：实现享元规范，为内部与外部状态提供存储。
+   • FlyweightFactory（享元工厂）：负责享元对象的创建与管理，并提供获取入口。
+   • Client（客户端）：使用享元的调用方，通过工厂获取或使用享元对象。

图5-11 展示了享元模式的结构，其中，“Flyweight”是享元接口，“ConcreteFlyweight”是具体享元类，“Flyweight Factory”是享元工厂类，“Client”是客户端类。

+   • “Client”经由“FlyweightFactory”来获取“Flyweight”对象。
+   • “FlyweightFactory”承担创建与管理“Flyweight”对象的职责。
+   • “Flyweight”接口定义了享元对象可操作的方法。
+   • “ConcreteFlyweight”是具体的享元实现类，实现“Flyweight”接口。

借助享元模式，相似对象的内部状态可以被复用，从而减少实例创建和内存开销。

# 5.13.3 优缺点

享元模式的优点包括以下几个方面。

+   (1) 资源复用：相同或相似对象可以被共享，降低创建次数和内存消耗。(2) 内存占用下降：共享内部状态后对象数量减少，内存压力随之降低。(3) 性能提升：减少频繁创建与销毁带来的开销，系统响应更快。

享元模式的缺点包括以下几个方面。

+   (1) 管理复杂度上升：需要引入共享对象的管理机制，设计会更复杂。(2) 状态可共享的限制：享元内部状态必须是可以被安全共享的，这会对对象设计和扩展带来约束。(3) 并发安全隐患：多线程同时访问享元对象时需要同步，会增加实现负担。

是否采用享元模式，需要结合具体场景评估利弊，确保它确实带来性能与资源的优化。

# 5.14 代理模式

代理模式是一种结构型设计模式，通过代理对象对真实对象的访问进行控制。代理充当真实对象的替身，能够在转发请求前后加入额外逻辑。

# 5.14.1 应用场景

代理模式的应用场景包括以下几种。

+   (1) 远程代理：处理对远程对象的调用。
(2) 虚拟代理：对象创建成本高时延迟实例化，待真正需要时才生成。
(3) 安全代理：限制对真实对象的使用权限。
(4) 智能代理：在访问真实对象时加入日志、缓存等增强行为。

# 5.14.2 结构

代理模式的结构包括以下角色。

+   - 抽象主题( Subject )：为真实对象与代理对象提供统一接口，可为接口或抽象类。
- 真实主题( Real Subject )：真实业务逻辑的具体实现，被代理对象所指向。
- 代理( Proxy )：持有对真实主题的引用并实现同一接口，可在调用前后执行权限校验、缓存等额外处理。

# 5.14.3 优缺点

代理模式的优点包括以下几个方面。

+   (1) 代理模式可以实现客户端和真实对象的解耦，客户端只需与代理进行交互，无须直接与真实对象进行通信。
(2) 代理模式提供对真实对象的控制和管理，可以在代理中添加额外的逻辑，例如，权限验证、缓存等。
(3) 代理模式可以增强真实对象的功能，通过代理对象可以在不修改真实对象的情况下，对其进行扩展或增强。

代理模式的缺点包括以下几个方面。

+   (1) 引入代理对象会增加系统的复杂性，需要额外的代码来处理代理和真实对象之间的交互。
(2) 在一些情况下，引入代理对象会增加请求的处理时间和资源消耗。

代理模式能在解耦、控制与功能增强上提供价值，但也需权衡带来的复杂度与性能成本。

# 5.15 策略模式

策略模式是一种行为型设计模式，允许在运行期灵活挑选算法。把算法封装到独立的策略类中，客户端无需了解具体实现。

# 5.15.1 应用场景

策略模式适用于以下场景。

+   (1) 系统中存在多个相似算法，且实现可能随时间演进时。
+   (2) 需要在运行时动态切换算法时。
+   (3) 需要把一组相关算法打包成整体，在使用时进行切换时。

# 5.15.2 结构

策略模式由三个核心组件组成。

+   * 策略接口( Strategy Interface ): 规定算法的统一契约，具体策略需实现该接口。
+   * 具体策略类( Concrete Strategies ): 实现策略接口，封装各自算法。
+   * 环境类( Context ): 持有策略接口引用，负责在需要时调用对应策略。

图5-13展示了策略模式的结构，其中，“Strategy”是策略接口，定义了策略类需要实现的方法。“ConcreteStrategyA”“ConcreteStrategyB”和“ConcreteStrategyC”是具体的策略类，分别实现了不同的策略。“Context”是环境类，持有策略接口的引用，并提供设置策略和执行策略的方法。

# 5.15.3 优缺点

策略模式的优点包括以下几个方面。

+   (1)可以在运行时动态地改变对象的行为，即使在程序运行时也可以根据需要选择不同的策略。
+   (2)可以通过定义不同的策略类避免使用大量的条件语句，使代码更加清晰、简洁。
+   (3)提供一种松耦合的设计，策略类之间相互独立，易于单独修改、扩展和维护。

策略模式的缺点包括以下几个方面。

+   (1)会增加系统中的类和对象数量，每个具体策略类都需要一个对应的类。
+   (2)客户端必须知道所有的策略类，并自行选择合适的策略，这会增加客户端的复杂性。

总体而言，策略模式适合在不同情境下选用不同算法的场景，能提升灵活性与可扩展性，但使用时需权衡类数量膨胀与客户端选择复杂度。
