MCP 架构与协作全景解读

MCP 的整体框架围绕两类角色展开：运行在宿主程序内部的客户端，以及独立对外提供能力的服务端。客户端本质上是一个适配器，负责将上层指令封装成标准消息发出，并把返回结果送回应用；服务端则是自包含的服务单元，供给上下文、触发工具等能力，并对客户端请求做出响应。

##### 1. 客户端的核心职能
在整体协作中，客户端主要承担以下工作。

- (1) 通道建立：与服务端完成握手，建立稳定且安全的通信链路。
- (2) 消息组装：依据宿主程序的业务需求，将调用信息编码为符合 MCP 规范的消息体发送给服务端。
- (3) 结果回传：接收服务端返回的消息，解析后交由宿主程序进行后续处理或展示。

##### 2. 服务端的核心职能
服务端侧的职责集中在以下方面。

- (1) 请求处理：解析客户端发来的消息，按需供给上下文信息或调用外部工具。
- (2) 资源与工具管理：统一注册并暴露可供调用的资源与工具，支撑复杂任务的执行。
- (3) 会话维护：在多轮交互场景下，保持会话状态，保证交互的连贯与一致。

##### 4. 传输层落地方式
MCP 支持多种传输手段，以适配不同场景：

- (1) 标准输入输出 stdio：适用于本地集成与命令行工具，通过 stdin/stdout 收发消息。
- (2) 服务端发送事件 SSE：基于 HTTP 实现服务端向客户端的单向事件流，适合实时更新场景。

此外，开发者可按需实现自定义传输，保持协议的灵活与可扩展。

##### 5. 协作流程全景
实际应用中的交互通常遵循以下步骤：

- (1) 建立连接：客户端初始化并与服务端建立通信通道。
- (2) 功能协商：双方交换能力清单，明确可用操作范围。
- (3) 请求处理：客户端发出具体请求，服务端接收并执行。
- (4) 响应返回：服务端将结果封装为响应消息回传。
- (5) 会话管理：服务端按需维护会话状态，支持多轮对话。

通过上述机制，MCP 实现了高效协作，支撑复杂的上下文管理与工具集成，满足大模型应用的多样需求。

#### 2.3.2 通信协议与数据格式全景
MCP 中，协议与数据格式是客户端与服务端交互的基础。消息传输采用 JSON-RPC 2.0，定义请求、响应、通知三种类型，保证传递规范与一致。传输层负责将 MCP 消息转为 JSON-RPC 格式发送，并把接收到的 JSON-RPC 消息解析回 MCP 消息。

内置传输方式包括 stdio 与 SSE。stdio 通过标准输入输出流通信，适用于本地集成与命令行。SSE 通过 HTTP POST 实现服务端到客户端的流式推送，并支持客户端到服务端的通信，适用于需要流式输出的场景。

协议允许开发者按需实现自定义传输，只要遵循传输接口规范即可。实现时需关注错误处理、资源释放、超时控制等最佳实践，并确保传输安全，包括鉴权、加密与网络安全。规范的协议与格式为复杂 AI 应用提供了可靠交互基础。

##### 1. 通信层设计定位
MCP 采用面向消息的异步通信架构，协议基于 JSON-RPC 2.0 构建，用于规范客户端与服务端之间的请求-响应及事件通知行为。该层核心目标是为上下文构建、工具调用、资源获取等操作建立统一且可扩展的远程过程调用语义，保证多组件协作时行为一致与语义稳定。

##### 2. 消息格式规范
MCP 所有消息在传输时均遵循 JSON-RPC 2.0 标准格式，每条消息可以是：
请求 Request：发起操作并等待结果；
响应 Response：对应请求的返回结果；
通知 Notification：无需响应的单向消息，用于状态变更或事件广播。

##### 3. 上下文 Slot 构成
上下文通过 Slot 注入实现，每个 Slot 包含以下关键字段。

- (1) role：语义角色，如 user、system、tool、memory 等；
- (2) name：可选标识名，用于引用、模板调用或版本控制；
- (3) content：实际注入的文本或结构化数据；
- (4) options：可选控制项，如是否参与推理、是否只读、是否持久化等。

Slot 定义了模型输入的精细语义结构，是 MCP 通信中最核心的上下文载体。所有 Slot 按序排列，最终构成模型调用时的 Prompt 流，保证语境一致与语义清晰。

##### 4. 传输方式与实现接口
MCP 支持多种传输实现，通过统一的传输接口 Transport Interface 定义标准的 read、write、close 等方法，开发者可自定义传输逻辑。官方提供两种内置方式。

- (1) 标准输入输出 stdio：适用于本地部署、CLI 交互或嵌入式调用；使用标准输入输出流收发消息；延迟低、部署简便。
- (2) 服务端发送事件 SSE：通过 HTTP POST 与客户端建立单向推送通道；适用于需要推理结果流式输出的 Web 场景；支持增量响应与连接保持。

所有传输方式均可自动检测与动态注册，使用 MCP SDK 时只需指定传输类型，系统会自动完成协议握手与数据通道初始化。

##### 5. 错误处理与完整性保障
为保证通信安全与鲁棒性，MCP 内置错误处理机制，包括：

- 标准化错误码体系，如 -32600 表示非法请求、-32000 表示服务端内部错误；
- 超时控制与自动重试机制；
- 消息体完整性校验与格式验证，防止非法 Payload 破坏流程；
- 对上下文 Slot 与参数字段进行 Schema 校验，确保数据规范性。

#### 2.3.3 能力协商与版本管理
随着 LLM 生态演进，不同 MCP 服务端、客户端及模型服务在实现细节、支持能力与版本策略上存在差异。若缺乏标准化能力协商与版本管理机制，将制约 MCP 在多模型多平台环境下的可扩展性与互操作性。为此，MCP 在通信初始化阶段引入能力声明与版本对齐机制，确保协同运行前达成协议层共识。

##### 1. 能力协商机制
能力协商是通信初始化的关键步骤。客户端建立连接后向服务端发起能力声明请求，表明自身支持的功能范围、传输格式、工具结构、上下文特性等。服务端作为响应方返回自身支持的功能子集，并在必要时指明功能版本范围或约束条件。协商不仅涉及基础功能如工具调用、资源管理、消息格式，也涵盖传输层支持、Slot 类型扩展、语言支持能力、流式响应能力等增强特性。

协议中规定的能力字段包括但不限于：

- supports_tools：是否支持 Tool 调用；
- supports_streaming：是否支持流式输出；
- supports_dynamic_slots：是否支持动态 Slot 生成与更新；
- supports_templates：是否支持 Slot 模板化注入；
- transport_modes：支持的传输方式列表；
