#### 2.2.1 指令解析型模板：让 Agent 听懂复杂需求

指令解析型模板的核心，是把用户表达模糊、依赖隐含上下文的自然语言，转化为智能体能精准理解并执行的结构化任务蓝图。这不只是翻译语言，更是需求分析与工程化设计的过程。一个高效的模板通常建立在分层指令体系上。在大语言模型里，指令一般分为系统提示、开发者提示和用户提示三层。系统提示用来定义模型的长期角色和安全边界，相当于为智能体设定世界观和行为准则。

在 OpenClaw 的架构中，这对应工作区里的引导文件，例如 SOUL.md 规定人设、边界和语气，AGENTS.md 存放操作指令和记忆规则。我们也可以通过提示词约束任务范围和可用工具，相当于立下游戏规则。用户提示则承载具体需求和上下文，是每次交互的输入变量。层次清晰后，复杂工作流在多轮对话中更稳定，能从根源减少指令冲突，提升一致性和复用性。

成熟的指令解析模板通常包含四个要素：角色定义、任务目标、约束条件、输出格式。角色定义给智能体赋予专业身份和沟通姿态，比如“资深 Java 后端架构师”或“严谨的数据分析师”，从而引导其采用对应视角和知识库。在 OpenClaw 中，IDENTITY.md 定义智能体名称与风格，USER.md 记录用户偏好，可实现更精准互动。

任务目标要明确最终结果和成功标准，把“做什么”拆成模型可执行的动作序列或可验证的产出。例如把“分析数据”细化为“读取 sales_q3.csv，计算各产品线月度增长率，找出增长最快和最慢的三类，并以 Markdown 表格输出结论”。这需要产品经理或系统分析师级别的需求拆解能力。

约束条件划定安全、效能和合规边界，告诉智能体不能做什么、必须在什么范围内做。包括数据源边界如仅处理指定路径文件、操作限制如禁止调用未授权系统命令、内容红线如输出需匿名化不含个人身份信息。在具备直接操作能力的 OpenClaw 中，约束通过工作区和技能权限配置、沙箱隔离等机制保障授权内安全运行。

输出格式规定交付物的结构，确保结果可读、可处理、可接入下游自动化。指令应明确要求 JSON、特定字段的 Markdown 表格或带章节标题的完整报告。结构化输出是产出能否被程序化消费的关键。OpenClaw 生态里，智能体生成的代码、图表或报告可通过 Canvas 组件可视化展示，这本身就要求输出格式统一（见图2-20）。

除四大要素外，高质量模板常加入示例与反例，帮助模型对齐预期。复杂场景下，还需列出工具清单与调用规则，明确调用顺序和参数格式，确保函数调用与数据操作的安全正确。

## 从模糊需求到结构化蓝图：智能体指令解析模板构建

从工程实践看，CRISPE 框架强调上下文、角色、意图、风格、人设和示例的一致性，适合内容生成与复杂问答；STAR 框架突出情境、任务、行动、结果的度量，适合流程型和项目型任务分解。两者都能转成可填表单，在编排系统里做版本管理，便于复用。

在 OpenClaw 实战中，指令解析与运行时流程紧密耦合。用户通过 Telegram 等通道发送指令后，网关会转发给智能体。运行时的首要步骤是上下文组装，动态拼接系统提示、会话历史以及工作区引导文件如 AGENTS.md、SOUL.md、TOOLS.md，形成完整 Prompt。设计良好的解析模板正是此时激活，指导模型解读原始输入、结合历史上下文、调用合适 Skills 并规划执行路径。

以下以 Windows 环境文件整理为例：

> 角色定义：你是一名文件系统操作专家，擅长把自然语言指令转为可执行的命令行序列。
>
> 任务目标：在 `~\Desktop\text` 目录下找到所有 docx 文件，按修改时间倒序排列，打包成 archive.zip 并放在原路径。
>
> 约束条件：
> - 数据源仅限指定文件夹，不得读取其他位置
> - 安全限制：不得修改原始文件，不得使用 rm、del 等删除命令，分析在内存中进行

智能体接收到指令后，先用 PowerShell 定位到 Desktop 目录，却出现了路径解析错误，报错包含 “InvalidArgument” 和 “DirArgumentError”（见图2-21）。意识到问题后，它改用命令验证桌面路径是否存在并获取正确路径。随后用 Test-Path 检查 “text” 目录是否存在，返回 True 确认目录有效（见图2-22）。接着执行 Get-ChildItem 搜索所有 docx 文件并按修改时间排序，成功列出两个文件及详细信息（见图2-23）。最后用 Compress-Archive 将文件打包为 archive.zip，命令无输出表示执行成功，任务全部完成（见图2-24 和图2-25）。

#### 2.2.2 工具调用型模板：引导 Agent 选择正确技能

工具调用型模板让大模型从被动回答转向主动调用工具。它自身不执行操作，而是解析需求、挑选工具并生成结构化调用指令，具体执行由后台完成。OpenClaw 通过提示词引导模型匹配技能与参数，实现想法落地。

设计遵循“工具定义→意图识别→参数生成→结果整合”四段结构，核心是赋予 AI 自主决策能力。

- ① 工具定义标准化。每个工具需包含函数名、功能描述和参数规范。功能描述是用自然语言说明作用与适用场景，是模型选择依据。在 OpenClaw 中，工具定义会动态注入系统提示，涵盖 read、write、exec、web_search 等核心能力。
- ② 意图识别精准化。面对提问，模型需判断是否需要工具及调用哪一个，依赖工具描述与需求匹配。OpenClaw 通过 <available_skills> 标签动态注入可用技能列表，模型在回复前扫描选择最合适的技能。
- ③ 参数生成结构化。模型输出的是结构化调用指令，通常为 JSON，明确工具名和参数，便于程序解析执行。
- ④ 结果整合智能化。执行完成后，模型需把结果整合成易懂的自然语言，完成从执行到沟通的闭环。

实操中需注意四点：工具描述准确，参数名用英文、数据类型标注清楚、说明用中文；强制结构化输出，要求严格返回 JSON；调用前校验参数，如日期格式、数值范围；设计兜底逻辑，模型识别错误或函数失败时有备选方案，避免崩溃。

工具调用与 ReAct 提示工程思路不同。ReAct 通过“思考-行动-观察”循环引导模型动态规划，适合多步复杂任务；工具调用则预定义函数接口，模型只输出调用指令，适合接口固定、步骤明确或链式调用场景。形象地说，ReAct 是给模型一本问题解决手册让它自己琢磨，工具调用是给它一套标准操作指南让它直接使用。

在 OpenClaw 架构中，工具调用与技能系统深度融合。每个技能以独立目录存在，内含带 YAML 前置的 SKILL.md。系统会加载内置捆绑技能和用户可选的本地覆盖技能，并按运行环境和配置筛选。技能来源有三：安装包自带的捆绑技能、用户主目录的托管或本地技能、工作区技能。冲突时优先级为工作区 > 托管/本地 > 捆绑。

以下以内置天气查询技能为例（见图2-26）：

> 角色定义：天气查询专家，负责准确高效调用天气查询技能提供可靠信息。
>
> 任务目标：调用 openclaw-bundled 查询北京天气
>
> 约束条件：
> - 数据源使用技能提供数据
> - 安全限制不得执行危害系统操作
> - 输出避免过度专业术语
> - 错误处理需给出明确信息和解决建议

#### 2.2.3 流程控制型模板：管理多步骤任务状态

流程控制型模板让智能体独立完成复杂多步任务，把宏观模糊的需求转成结构清晰、可控、可暂停恢复的自动化流程。与单次指令不同，它需管理任务全生命周期：拆解大任务、跟踪每步状态、处理异常、整合结果。

模板采用“状态定义→步骤分解→依赖管理→异常处理→结果整合”五段结构。

首先是状态定义标准化。复杂任务中，单步失败不应导致整体崩溃。每个任务需携带明确状态标识，如待执行、执行中、已完成、失败、暂停。OpenClaw 内置状态持久化机制，自动记录每个 Agent 各时刻的输入输出和执行上下文，中断后可从精确断点恢复。

第二步是分解结构化。复杂任务拆解为边界清晰的子步骤，每步含明确输入条件、处理逻辑和预期输出。例如订单履约可分解为原料入库→预处理→加工/装配→质量检验→包装→成品入库的线性序列。
