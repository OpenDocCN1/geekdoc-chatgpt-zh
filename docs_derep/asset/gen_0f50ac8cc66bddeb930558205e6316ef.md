### 3. 节点分工怎么定
节点设计的本质就是给每个模块划清职责边界。

拿计划模块来说，核心任务就是让大模型基于预设提示词产出内容大纲，这件事一个 LLM 执行节点就能搞定。

执行模块就复杂得多：它要根据目录名动态去拉取相关资料，这就绕不开外部工具调用。所以除了 LLM 执行节点，还得配一个工具运行节点来真正执行操作；再加一个循环控制节点来调度多轮对话与工具调用之间的来回，管理迭代和状态流转。

## 2.2.2 复杂计划模式实现通用计划执行
本节介绍进阶版的计划模式。进阶点主要在执行模块对任务的跟踪能力上，因此不再单独让 LLM 生成计划，而是直接把计划和用户提示词一起喂给执行模块。

示例也换掉了 2.2.1 节的潮汕旅游，而是搭建一个更通用的计划执行工作流。架构思路变了，代码实现仍基于 LangGraph，保持技术栈一致。接下来从提示词设计开始逐步搭建。

#### 1. 提示词的设计
本节的提示词在 2.2.1 节执行模块提示词基础上做了关键增强，目标是实现对执行过程的精细跟踪与控制，避免步骤跳过、重复或遗漏。完整内容如下。

你是一个任务执行助手，根据给定的任务按步骤执行，不要添加任何多余的步骤

最后一步的结果应该是最终答案。确保每个步骤都有所需的所有信息，不要跳过步骤

你的计划是:

{plan}

当前已经完成的步骤：

[PRE9]

### 请遵循以下规则

1. 请输出JSON字符串。

2. 相应地更新你的计划。如果不需要再执行更多步骤，就直接回复用户。否则，请填写计划。

3. 只在计划中添加仍然需要完成的步骤，不要将之前完成的步骤作为计划的一部分返回。

### 输出格式说明：

- 如果所有步骤都完成了，输出：{{"actions": {{"response": "最终回答内容"}}}}

- 如果还有步骤需要执行，输出：{{"actions": {{"steps": ["步骤1", "步骤2", ...]}}}}

注意：actions字段是必需的，不要使用其他字段名。

相比 2.2.1 节的执行提示词，本设计做了两处关键改进。

- 引入了 `{past_steps}` 结构化占位符，运行时会注入上一步的运行记录，包括执行了哪一步、结果是什么，让 LLM 在每轮推理开始时就能准确知道自己处在哪个位置。

- 用严格的 JSON 输出规范取代原有的 Final Answer 文本标记。通过强制使用 `{"actions": {"response": ...}}` 或 `{"actions": {"steps": [...]}}` 两种结构，系统能清晰区分“任务已完成”和“仍需继续”两种状态。

另外 `{"actions": {"steps": [...]}}` 只返回剩余待办。随着任务推进待办列表不断缩短，模型处理的上下文干扰减少，后续步骤的聚焦度和准确性自然提升。
