## 2. 工作流节点设计

基于反思模式的思路，本节搭建一个由 3 个核心节点组成的工作流。

- 生成节点：依据用户需求以及可能的反思反馈，生成或再优化 Linux 运维命令。
- 反思节点：对生成节点的结果做多维度校验，输出优化建议或确认已达标。
- 条件分支节点：根据反思结论决定是否继续迭代回生成节点，还是终止流程认为已是最优解。

三个节点构成“执行-反思-决策”的闭环，可在多轮自我优化中，直到命令同时满足安全、效率和功能要求。接下来逐步实现各节点代码。

## 2.4 行动：代码即工具的 CodeAct 模式

本节探讨上下文工程中的行动环节，即 Agent 通过与外部环境交互调用工具来获取信息或执行操作，从而动态更新上下文。

目前基于 Function Calling 或 ReAct 的工具调用已成为主流。笔者在《AI Agent 开发实战：MCP + A2A + LangGraph 驱动的智能体全流程开发》中已有系统阐述。本节不重复基础模式，而是聚焦更具灵活性与创新性的 CodeAct 方案。

### 2.4.1 CodeAct 模式的架构

CodeAct 的核心是把代码本身作为行动载体。如图2-14 所示，与传统依赖预注册工具函数不同，CodeAct 允许 LLM 在推理时直接生成可执行代码片段，如 Python 脚本，由运行时执行器动态运行，完成信息获取、数据处理或系统操作。

[PRE8]

其思想是把“工具”从静态黑盒函数解放出来，把整门编程语言视作通用开放的工具空间。只要模型具备足够代码能力，就能在任意时刻临时构造满足需求的“工具”，实现高度灵活求解。

例如用户要求“计算过去 7 天某只股票的平均收盘价”，传统方式需提前注册 `get_stock_price(symbol, days)`；CodeAct 下模型可直接生成调用金融 API 并计算均值的 Python 代码，由执行引擎运行返回结果。

该模式显著提升通用性与适应性，尤其适合工具集合不明、任务多变或需多步组合的复杂场景。
