消息存储表 Messages 的设计如下：

- message_id 作为消息记录的主键
- user_id 关联到具体的用户
- content 保存对话正文
- role 区分发言方是用户还是模型
- timestamp 标记消息产生的时间点

会话表 Sessions 的设计如下：

- session_id 作为会话的主键
- user_id 关联到用户
- start_time 记下会话开始时刻
- end_time 记下会话结束时刻，允许为空

写入消息时，用户提问和模型回应分别落库到 Messages。拉取历史对话时，可通过 user_id 配合 session_id 从 Messages 中读取完整上下文。会话的起止则在 Sessions 中维护。

#### 5. 部署与扩展规划

##### 5.1 部署方式

容器化：借助 Docker 与 Docker Compose 打包并编排服务。

反向代理：使用 Nginx 处理静态资源并做流量分发。

WSGI 运行：用 Gunicorn 启动 Django 应用。

##### 5.2 扩展思路

分布式：把后端拆分为多个独立服务，服务间通过消息队列通信。

微服务：将对话编排、账户管理、模型调用拆分为各自服务。

数据层扩容：采用 PostgreSQL 集群或 DynamoDB 的自动水平扩展能力。

按照上述方案可以快速搭建以 DeepSeek 为核心的多轮对话系统，兼顾扩展性与可维护性。
