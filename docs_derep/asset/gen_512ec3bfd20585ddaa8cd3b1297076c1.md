非关键状态的更新，指的是和关键状态更新相对的那一类操作。若不做区分，所有的状态变更在 React 眼里权重相同。正如 4.3.4 节所述，React 18 会在各类事件处理函数或回调里对多个状态更新做自动合并，在一次渲染里把新值一次性应用。这种批量处理整体提升了渲染效率，但也暗藏风险：一旦其中某个状态更新的渲染开销过大，就会拖慢其它更新，典型的表现就是在输入文字时出现卡顿。对此，可以把成本较高的那部分状态变更标记为非关键的 transition，让调度器把它排在关键更新之后执行。transition 运行期间，调度器大约每 5ms 就把主线程控制权归还，检查是否有更紧急的工作单元，有的话就暂停 transition，从而避免长时间阻塞界面。

## 11.3 React 应用的整体性能优化

除了在组件代码层面，React 应用的性能优化还有其它思路。

### 11.3.1 为生产环境构建

React 源码中存在大量仅在开发模式下生效的代码分支，用来做运行时校验、提醒开发者 API 用法不当或给出更优写法。11.1.3 节提到的 React 浏览器扩展性能分析工具，也在源码里埋入了大量数据采集点。

这些对开发调试有帮助的代码，在生产环境里几乎用不到，反而会拖慢框架运行。例如调试常用的 `console.log` 在某些环境下会同步执行，大量使用可能阻塞业务流程。并且框架本身的代码量越大，浏览器需要下载的 JavaScript 越大，模块加载消耗的资源也越多。

因此在为生产环境构建 React 项目时，需要明确指定生产模式，让编译构建工具从最终产物中剔除开发模式的代码，减轻浏览器运行时的负担。在 Vite 项目里，执行 `vite build` 即 `npm run build` 生成的就是生产产物，随后运行 `npm run preview` 即可在浏览器中预览生产模式下的执行效果。

这种优化成本低、收益明确，适合作为首选方案。

### 11.3.2 代码分割

如果生产产物，比如单个 JavaScript 文件，体积达到数兆字节，就可借助构建工具的代码分割功能，把产物拆成多个 chunk，每个文件控制在数百 KB 左右。这样能分散整体体积，充分利用浏览器的并行下载和缓存机制，提升加载速度。

除了与业务无关的通用分割，开发者还可以按功能模块或路由显式分割应用，并用懒加载按需在浏览器中加载部分功能。相关 API 和实践会在 13.3 节介绍。

我们希望 Copilot 能结合上传的性能数据文件和 oh-my-chat 的源代码做综合分析。提示语开头的 “@workspace” 是 Copilot 插件内置的聊天对象之一，其作用是把整个工作区加入提示上下文，这就包含了 oh-my-chat 的源码。

这里存在一个限制：LLM 的上下文窗口。上下文窗口指模型一次能处理的 token 上限，即输入 token 与输出 token 之和。超出后模型会“遗忘”靠前内容，导致相关性和准确度下降。不同模型上限不同，如 GPT-4o 为 128K，Claude 3.5 Sonnet 可达 200K。目前 src 目录约 32KB 文本，profiling-data.*.json 约 95KB，再加上工作区其它文件、Copilot 内部上下文和指令，输入总量可能超过 GPT-4o。上文大小需转成 token，大约是字节数除以 4。约 30K token 尚可接受，剩余 token 足以输出。

实际操作中，工作区文件会持续增长，特别是 Profiler 记录步骤增多时 JSON 体积也会膨胀，很容易填满模型上下文，导致分析不完整或出错。应对措施有两种：精打细算地减小输入体积，或更换上下文更大的模型，例如 GPT-4.1，其上下文窗口为 1M 足够使用。

提示语开头 “你是一位 React 开发的资深专家” 属于提示工程中的角色提示技巧。角色提示让 LLM 扮演特定角色，使输出更符合该角色风格。实践中确实有帮助，并非必须。

在 AI 辅助分析 React 性能时，除了 AI IDE，还可借助 ChatGPT。但 ChatGPT 缺乏项目源码上下文，分析效果会受影响。

## 11.6 小结

本章探讨了前端应用性能优化策略，强调避免过早优化。应用开发的核心仍是开发本身，只有“慢”或“卡”的问题真实出现时，才需用工具定位根源，判断是否与 React 相关。一旦确认，组件层面可用纯组件、useMemo、useCallback、startTransition 或 useTransition 等特性；应用层面可采用生产环境构建或代码分割等方案。最后借助 AI 技术辅助分析了 React 的性能问题和报错信息。

## 12.1 React 代码的分解和抽象

面对日益复杂的组件逻辑，我注意到许多单个组件的代码行数已达数百行，甚至上千行。其中有一些结构清晰易维护，但更多是存在以下问题的反面案例。

- 职责过多。
- 业务逻辑与交互逻辑混杂。
- 从其它组件复制粘贴代码。

具体表现包括但不限于：

- 传递的 props 数量过多。
- useState 使用次数过多。
- 单个 useEffect 的依赖项数组成员过多。
- JSX 中嵌套了循环渲染或条件渲染。
