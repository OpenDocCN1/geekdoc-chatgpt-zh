### 5.2.2 Agent间对话协议的设计与优化

多Agent协同下，通信的效率与准确度决定整体表现。好的协议要兼顾结构化便于程序解析，和自然语言便于LLM发挥。A2A、ACP 等主流方案均以 JSON 为底座，关键字段保留自然语言。

设计遵循三点：结构统一，所有节点共用同一消息骨架，包含发出方、接收方、类型、载荷与元数据；语义明确，类型采用 REQUEST、RESPONSE、HANDOFF、ERROR 等枚举，避免歧义；上下文完备，转交时带足背景，确保接手方可无缝继续。

图5-5 说明了标准结构与四类消息。左侧给出完整 JSON 字段：消息ID、时间戳、路由、类型、业务内容与上下文。右侧解释四类用途与必含字段：REQUEST 发起请求，RESPONSE 返回结果，HANDOFF 执行交接，ERROR 上报异常。底部要点是 JSON 保证机器可读，content 发挥 LLM 理解力。

## 消息类型定义

- **REQUEST-请求消息**
  - 用途：发起任务请求或询问
  - 必含：task（任务描述）、input（输入数据）
- **RESPONSE-响应消息**
  - 用途：返回处理结果
  - 必含：status（状态）、result（结果）、reply_to
- **HANDOFF-转交消息**
  - 用途：将任务转交给其他Agent
  - 必含：reason（转交原因）、context（完整上下文）
- **ERROR-错误消息**
  - 用途：报告处理异常
  - 必含：error_code、error_msg、recoverable

设计原则：结构化JSON+自然语言content，兼顾程序解析与LLM理解。

### 5.2.3 动态Prompt调整与个性化定制

固定 System Prompt 难以应对复杂多变的业务。动态调整技术可依据运行期上下文、用户画像与交互历史，对基础 Prompt 做实时扩充，实现更精准的个性化。

核心是 Prompt 注入：在基座 System Prompt 上按条件叠加指令或上下文。来源包括画像信息、会话态、业务规则与实时数据。注入时需设定优先级，避免冲突。

### 5.2.4 多语言与跨文化Agent的适配策略

全球化 Agent 不仅要翻译，还需兼顾文化习惯与本地规范。主要难点为语言能力不均、语义差异与格式本地化。

常见方案三类：原生多语，直接使用多语 LLM 并在 Prompt 中指定目标语言，简洁低延但小语种与文化适配弱；翻译桥接，先译为英语处理再译回，发挥英语模型优势但会累积误差并损失语境；本地化分支，为各语区维护独立 Prompt，适配最深但维护成本高。
