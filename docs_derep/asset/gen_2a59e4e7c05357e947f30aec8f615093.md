赫伯特·西蒙提出的有限理性告诉我们，人在决策时从不追求理论上完美的全局最优，而是寻找一个足够好、可以接受的满意解。把这个逻辑放到 Agent 上，就意味着不存在万能的完美行动，我们真正能做到的，是在充满不确定性的环境里，持续地、安全地、有效地创造价值。

从这个认知出发，最经典的行动范式就是 ReAct。下面就从它开始展开行动的思路。

## 7.1 ReAct模式

“推理轨迹让模型能够生成并跟进中间决策，而行动则让模型可以探查环境并拿到外部信息。”

—— ReAct 论文 ①

如果只做推理，就像坐在扶手椅上的学院派，靠已有知识做严密推演，前提一错，整个结论就崩塌。

如果只做行动，就像没头的苍蝇乱点按钮，靠运气撞对一个。

ReAct，即 Reason+Act，让 Agent 变成边思考边实践的探险者。

- 先做预判。看着地图说：“前面可能有沼泽，得先找根棍子探路。”
- 再执行动作。把棍子伸出去，戳一下地面。
- 接着看反馈。棍子陷下去了，于是说：“果然是沼泽。”
- 最后调整方案。收回棍子说：“绕路走吧。”

这种方式打破了先想完再动手的传统线性逻辑，形成了“思考—行动—观察”的微循环。Agent 能在与环境的互动中不断修正策略，解决靠内部知识 alone 难以处理的复杂问题。

图 7-2 里涉及的核心部件如下。

- Agent：汇总全部历史轨迹，包括过往的思考、行动和观察，来做现状判断。它既要推理，也要决定下一步是继续调用工具，还是信息已够直接回答。
- 执行器：把 Agent 用文本写出来的指令，比如 Search[Apple]，转成具体的函数调用，并处理网络波动等执行异常。
- 感知器：工具返回的数据通常很杂乱，比如冗长的 HTML 或复杂的 JSON，感知器负责清洗、截断，防止 Token 爆炸，只把精华写回草稿纸。
- 草稿纸：整个任务的记忆板。每完成一次循环，就往里追加新内容，实时刷新 Agent 的状态与环境认知。

ReAct 把一次推理改造成了基于历史轨迹的状态机维护过程。Agent 就在这张越写越长的纸上，通过一次次试探和反馈，把内部逻辑与外部现实拴在一起，完成了从纸上谈兵到实地探险的转变。

### 7.1.2 ReAct核心机制

ReAct 比单纯的思维链或单纯的工具调用更有效，关键在于推理与行动产生的协同效应，这种效应能催生出 1+1 大于 2 的智能表现。

#### 1. 交织推理

ReAct 的核心创新是让推理与行动互相牵引。

- 推理引领行动。推理能缩小行动的搜索范围，Agent 会先判断“现在缺什么信息”，再精准调用对应工具，而不是胡乱尝试。
- 行动反哺推理。外部反馈能立刻纠正内部的幻觉。比如 Agent 认为“A 是 B 的子公司”，工具返回却显示两者无关，这个结果会迫使推理立刻修正。
- 推理轨迹帮助模型引导、追踪并动态更新行动计划。
- 行动让模型能与外部资源如知识库或环境交互，获取增量信息。

这种协同解决了两个痛点。

- 幻觉问题。推理被外部观察“接地”，避免了空想。
- 错误传播问题。行动有推理指路，一旦某步走偏，反馈会立刻提示“此路不通”，帮助模型及时调整后续思路。

#### 2. 动态接地

模型的致命伤是幻觉，即自信地输出看似合理却不实的内容。ReAct 强制每一步推理都必须建立在真实观察之上，从而缓解幻觉。

通常我们在 System Prompt 里会明确写：“你的每一步思考都必须基于前面的观察，不许凭空捏造。”

这样就把模型原本飘忽的生成能力锚定在真实世界的反馈上，可靠性和事实一致性明显提升。

与 7.2 节的规划—执行模式“先搭完整计划再执行”不同，ReAct 是“走一步看一步”。在不确定环境里，这种动态规划很重要：当搜索结果与预期差异很大时，ReAct 能立刻根据新信息调整下一步的推理和行动，保持任务推进。

#### 3. 错误作为反馈信息

在传统编程里报错意味着失败，在 ReAct 里报错是高价值的信号。

- 检索关键词后返回“未找到结果”，等于告诉 Agent：关键词不对，得换一个。
- Python 或 SQL 返回 SyntaxError，等于明确提示语法有问题，依据错误信息修正后，下一次成功率往往大幅提升。

### 7.1.3 ReAct工程实践

理论很美好，落地时 ReAct 却常在细节上翻车。架构师需要重点解决两类工程难题。

#### 1. 停止词与解析地狱

LLM 是文本补全模型，它不仅会生成行动，还常“自作聪明”地把本该由环境提供的观察结果也编出来，形成自问自答的幻觉闭环。工程上要这样遏制。

- 强制截断生成。调用 API 时显式设置停止词，比如 stop=["Observation:"]，一旦模型生成到该标记就立刻截断，把控制权交回运行时，避免虚构观察。
- 结构化输出约束。模型输出格式容易漂移，用正则提取行动极不稳定。推荐做法是放弃纯文本解析，改用 Pydantic 校验或 Function Calling，强制模型输出符合预定义 Schema 的标准 JSON，从根源杜绝解析错误。

#### 2. 死循环陷阱

工具效果差或报错时，Agent 容易陷入“搜索—失败—再搜索”的西西弗斯循环，浪费算力并快速耗尽 Token 预算。

需要双重防护。

- 硬性步数上限。为推理—行动过程设定合理上限，通常 10 步左右，到达后强制终止，防止无限循环。
- 动态动作去重。运行时维护一个已执行动作集合，发现重复执行且无有效结果时，在 Prompt 中明确提醒：“你已执行过此动作且未获有效结果，请换策略。”这样能逼 Agent 跳出局部无效循环，探索新路径。请看以下示例。

## 3. 显式思考动作

Anthropic 在 2025 年关于新工具 “The ‘think’ tool” 的文章里指出，对复杂任务而言，隐式思维链有时不够，必须引入强制思考步骤。具体做法是在“思考→行动”循环里加入一个特殊的内部工具——Think。当 Agent 感到困惑或任务极复杂时，它不会急着调外部 API，而是先调用 Think，进入“深思模式”，暂停行动专注纯推理。这是在行动循环里手动嵌入 System 2 慢思考的工程手段，能有效防止手比脑快导致的误操作。

ReAct 不适合需要宏观规划的长程任务，那是规划—执行模式的强项；也不适合对精度要求极高的专业任务，那是工具编排模式的专长。但在不确定性和开放域探索场景里，它是最得力的工具。

### 7.1.4 ReAct模式的演化与组合

ReAct 从单步贪婪决策，发展到具备反思能力的闭环，最终走向基于搜索的全局优化。它往往不是单独存在，而是更复杂 Agent 的核心原子单元。

### 1. 演化路径：从贪婪到搜索

- 原始 ReAct（贪婪策略）：2022 年的原始版本采用“思考→行动→观察”线性循环，每步都挑当前概率最高的动作。一旦走偏，很难回溯。
- ReAct 与 Reflexion（反思增强策略）：Reflexion 于 2023 年引入反思记忆模式（见 8.2 节）。任务失败时，Agent 会停下来基于执行轨迹做自我批判，把总结的教训存入记忆，后续重试时把教训注入 Prompt，避免重蹈覆辙，让 ReAct 具备“吃一堑长一智”的能力。
- LATS（树搜索增强策略）：LATS，即 Language Agent Tree Search，2024 年提出。执行不可逆动作前，Agent 会在思维空间里做蒙特卡洛树搜索，推演不同路径的后果并评分，再选期望价值最高的动作执行。这把 ReAct 从莽撞的探险家升级为深思熟虑的棋手。

### 2. 模式组合示例

ReAct 通常作为执行层的“手脚”，需要与认知层的其他模式配合才能发挥最大效能。

- ReAct 与 RAG 模式（见 5.2 节）的组合 = 知识接地：ReAct 提供动态决策与流程控制，RAG 保证事实准确性。适用于需要专业知识的问答或操作。具体流程：ReAct 负责整体流程控制，检测到知识缺口时生成如 Lookup("Transformer architecture") 的动作，RAG 介入检索并把结果作为观察返回给 ReAct。
- ReAct 与自我修正模式（见 8.1 节）的组合 = 鲁棒执行：为 ReAct 的行动循环引入实时纠错机制，防止在无效路径上无限重试。适用于工具调用易出错的场景。具体流程：ReAct 生成初步动作，自我修正模块中的 Critic 组件在执行前拦截检查参数格式，或在执行失败后介入分析错误并生成修正动作。

ReAct 的演化史，就是 Agent 从脚本化走向智能化的缩影。通过与记忆和反思模式深度融合，它已成为现代 Agent 架构中不可或缺的通用执行引擎。

### 7.1.5 设计哲学：认知的具身化

ReAct 标志着模型从“缸中之脑”迈向“具身智能”，即使只是数字世界的具身化。之前模型只是旁观者，之后模型成为参与者。ReAct 的核心观点是：智能不仅在于对静态数据的模式识别，更在于与环境动态交互时展现的适应能力。

ReAct 是所有 Agent 的基本功能，它把“错误处理”内化为认知过程的一部分。一个能用 ls 看目录、用 grep 找错误、用 vim 改代码并根据报错不断重试的 Agent，比只能背诵所有 Linux 命令却无法操作终端的 Agent，展现出更高维度的智能。

## 7.2 规划—执行模式

> “凡事预则立，不预则废。”

——《礼记·中庸》

Agent 不仅要会执行，还要会战略布局。当任务复杂到无法靠“走一步看一步”完成时，就需要运筹帷幄的能力。

在 ReAct 模式下，Agent 像一名装修工：看到墙上有洞就立刻补，看到漆剥落就马上刷，采用的是反应式策略。

在规划—执行模式下，Agent 更像一支建筑工程队，分工协作。

- 总工程师（规划器）：根据蓝图把“盖大楼”拆成“打地基”“浇筑”“封顶”等阶段，不下场施工，只负责制定计划。
- 工头（调度器）：安排施工顺序，比如浇筑必须在打地基之后，管理任务间的依赖关系。
- 工人（执行器）：只按指令干活，不追问原因，专注执行。
