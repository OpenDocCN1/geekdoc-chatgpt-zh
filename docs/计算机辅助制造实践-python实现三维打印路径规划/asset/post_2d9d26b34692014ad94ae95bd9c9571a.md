## 第 6 章 截交线段拼接计算优化

## 引言

针对三维打印路径规划中涉及的算法优化问题，我们在上一章已经做了非常不错的尝试，成功设计并实现了两种原理截然不同的截交优化算法，得到了令人鼓舞的结果。这一章，我们将在上一章工作的基础上，对得到的无序离散截交线段进行拼接，生成一系列封闭的轮廓线。事实上，关于截交线段拼接的问题我们在第 4 章已经有所阐述，并在那时提出了一种暴力拼接法，显然，暴力法不是我们想要的。在这一章，我们将对离散线段的拼接问题展开进一步探索和研究，设计两种优化拼接算法，希望能够大幅提高线段拼接效率。

## 6.1 暴力拼接存在的问题

我们先来回忆一下截交线段的拼接问题。当我们用一张平面和一个 STL 模型做相交计算时，由于三角面片在 STL 模型中存储的无序性，最终落在该平面上的截交线段序列也必然是散乱无序的。我们不能直接拿线段序列中的第 1 号线段和第 2 号线段进行拼接，因为这两条线段在平面上可能不相邻，甚至不在同一个轮廓中(参见图 4.6)。

截交线段的拼接问题可以抽象为:对同一平面上 N 条散乱无序的线段序列,将其首尾相连成 M 条多段线。显然这里 M ≤ N,如果 M = 1,则所有 N 条线段都将拼接到同一条多段线上;如果 M = N,则 N 条线段中不存在首尾重合的两条线段。对三维打印这一具体应用来说,最终拼接得到的多段线应该还需满足首尾相接的要求,即它们应该是闭合的。

对以上拼接问题,最为简单而且容易实现的方法当然是暴力拼接法。我们已在第 4 章对该方法有过介绍,它的基本原理是:对于当前拼接过程中的多段线,遍历线段序列,搜索能和当前多段线端点(起点或终点)重合的那条线段,如果能够找到线段,我们只需将该线段拼接到多段线上;如果找不到线段,则对当前多段线来说,拼接过程结束。

暴力拼接法之所以暴力,是因为它在最优的情况下,仍需要经历 n(n+1)/2 次搜索和坐标比对,其中 n 为线段序列中的线段数量,即暴力截交法的时间复杂度为 O(n²)。在我们实际测试例中,对如图 5.8 所示的 monk 模型(面片数为 336974),当切片层厚为 0.2 毫米、切片层数为 877 层时,使用扫描平面法所需的截交时间约为 21 秒钟(参见表 5.1),得到的各层截交线段总数为 866540 条,平均每层线段数约 988 条。对这些层上的截交线段,使用暴力法进行线段拼接的总时间约为 975 秒钟,超过 16 分钟,平均每层拼接时间超 1.1 秒钟。暴力拼接所需的时间和截交所需的时间极不对等,对同一模型,如果层厚更加细密,层数更多,那么拼接时间将更长。

一个真正优秀的线段拼接算法首先应该能够得到正确的拼接结果，且算法本身具有较强的鲁棒性，能够适应各类复杂输入；其次，这个拼接算法还应该具备较高的执行效率，能够在较短的时间内完成拼接，至少能和之前介绍的优化截交算法在运行时间上持平。在认识到暴力拼接法存在的问题后，我们在本章将介绍两种针对线段拼接问题的优化算法，一种是基于点坐标字典序排序的拼接算法，另一种是基于字典查询法的拼接算法。虽然这两种算法表面上都和“字典”有关，但它们在原理上大不相同。尽管如此，这两种算法都用到了一种用于存储点（或线段）的数据结构。

## 6.2 链接点数据结构

在 STL 模型截交阶段，在某一截平面上，我们已经得到了一系列截交线段。初始情况下，这些截交线段直接以我们最初建立的 Segment 数据结构（参考代码 2-8）保存两端点坐标。但 Segment 结构太过简单、基础，仅仅依靠 Segment 结构，我们发现很难对线段拼接算法做出进一步优化。

线段拼接问题的本质就是寻找目标点附近和目标点重合的线段端点，因此解决线段优化拼接问题的方向应该是构建各线段端点之间的临近关系。而线段端点临近关系的构建依赖于设计精巧的数据结构。为此，我们在这里介绍一种介于点和线段之间的新型数据结构，我们既可以用这种结构保存一个点，也可以用这种结构保存一条线段。我们把这种数据结构命名为 LinkPoint（链接点），顾名思义，它本质上还是表示一个点。LinkPoint 的具体定义如下（写在 LinkPoint.py 文件中）：

```python
from GeomBase import Point3D
class LinkPoint():
    def __init__(self, pnt3d, digits = 7):
        self.x = round(pnt3d.x, digits)
        self.y = round(pnt3d.y, digits)
        self.z = round(pnt3d.z, digits)
        self.other = None
        self.used = False
        self.index = 0
    def __str__(self):
        return 'LinkPoint: used: %s\nself (%s, %s, %s)\nother (%s, %s, %s)\nlinked to: %s\'' % (self.used, self.x, self.y, self.z, self.other.x, self.other.y, self.other.z, self.other.index)
    def toPoint3D(self):
        return Point3D(self.x, self.y, self.z)
```

由以上类的定义可知，LinkPoint 仍然表示一个点，拥有 X、Y、Z 坐标。在 LinkPoint 的初始化函数中，我们使用一个 Point3D 的对象来给 x、y、z 坐标赋值，并通过 digits 变量和 Python 的 round 函数来控制连接点坐标的小数位数。这里我们设置的 digits 为 7，即通过初始化函数得到连接点坐标的小数位数为 7。设立 digits 变量的原因其实还是和计算机在浮点运算中的截断误差有关，截断误差可能导致本应重合的两个端点不重合，比如理论结果应该是 1.0，然而实际计算可能得到类似 0.99999999 或 1.00000001 这样的结果。在之前介绍的暴力拼接算法中，我们利用两点距离和 0 的微小偏差来规避截断误差产生的影响。

LinkPoint 的一个至关重要的属性就是 other，该属性为一指针，指向另一个 LinkPoint 类型的对象。如图 6.1 所示，对一条线段的 A、B 两个端点，如果 LinkPoint 本身的 X、Y、Z 坐标储存了 A 这个端点坐标，那么 other 将表示 B 这个端点。我们可以按照以下代码完成对 LinkPoint 对象的初始化：

| | Segment 和 LinkPoint 数据相互转化 | 6-2 |
|---|---|---|
| 1 | lp1 = LinkPoint(A) | # A、B 为线段 Segment 的两端点 |
| 2 | lp2 = LinkPoint(B) | # A、B 为 Point3D 类型对象 |
| 3 | lp1.other = lp2 | # 链接到 lp2, 而非 B |
| 4 | lp2.other = lp1 | # 链接到 lp1, 而非 A |

![](img/c3ab49ac4eb80e7a0a66462a29869ca2_113_0.png)

图 6.1 链接点具备的点和线段双重特性

我们发现，LinkPoint 其实已经具备了线段两端点信息，因此，它也可以用来表示一条线段。这也就是 LinkPoint 既是一个点，又是一条线段的原因。由图 6.1 及以上代码可知，当我们将一条普通线段转化成链接点保存时，将得到两个不同的链接点和两条完全重合的线段。

在 LinkPoint 类中，我们还定义了 used 和 index 两个属性。其中 used 属性为布尔型变量，默认值为 False，表示当前链接点在线段拼接过程中是否已经被使用过，显然，如果一个点已经被使用过，它就不应该被使用第二次，否则得到的拼接轮廓将产生拓扑错误。如果我们已经将众多链接点放到了一个列表中，那么 index 属性就可以用来表示当前点在列表中的序号。一般情况下，在用列表存储数组元素时，我们可以通过列表和已知元素序号很快查询到对应元素。但是当我们只有元素本身时，却很难定位它在列表中的序号（只能通过遍历比对）。借助元素中保存的 index 属性，我们便能很快定位元素，并找出和它具有相邻序号的其他元素。

现在，我们已经有了一个 LinkPoint 数据结构，它不太对称，既表示点，又表示线段。它的这些特性，包括 used 和 index 属性，对于我们将要解决的线段优化拼接问题都是至关重要的。下面我们将使用 LinkPoint 构建一个基于字典序排序的线段优化拼接算法。

## 6.3 字典序排序法拼接优化

在现实生活中，我们可能经常需要处理那些包含大量同类型元素的优化问题，针对这些问题，暴力遍历所有元素可能消耗大量的运算时间，不太可取。先对这些元素进行排序可能会是一个不错的选择，这也许会激发我们进一步解决问题的灵感。我们在前面章节处理 STL 模型截交问题时已经做过这样的尝试，通过对三角面片最低点进行排序，实现了扫描平面快速截交算法，取得了非常不错的效果。在处理同一平面上大量截交线段的拼接问题时，我们也可以先对这些线段进行排序。更进一步，当我们把线段转化为 LinkPoint 对象后，我们可以考虑先对这些链接点进行排序。但是点不能像实数一样进行大小比较，那么该如何对它们进行排序呢？

### 6.3.1 点的字典序

我们从小就学会了查字典，这的确是一项非常有用的技能。尽管有了电脑之后我们可能很少使用字典，但这项技能也不会丢失。以前，当我们碰到一个不熟悉的英语单词时，我们会去找一本厚厚的英文字典，并根据这个单词中的字母排列情况定位这个单词，最终得到释义。那么，为什么查字典能够这么方便和高效？事实上，这和单词在字典中的排列顺序有关。

在字典中，所有的单词都是按一种被称为“字典序”的顺序排列的。如果单词中只有一个字母，那么这些单词将按照 a~z 的顺序排列，比如 a 在 b 的前面（记为 a < b），b 在 c 的前面（记为 b < c）等。如果单词由一个或两个字母组成，那么这些单词先按照第一个字母排序，如果第一个字母相同，则继续按照第二个字母排序，比如 ab < b，ab < ba，ab < ac 等。同理，如果单词由一个、两个或三个字母组成，那么这些单词先按照第一个字母排序，如果第一个字母相同，则按照第二个字母排序，如果第二个字母也相等，则按照第三个字母排序，比如 abc < bc，a < bcd，abc < acd 等。以此类推，我们可以按照这种规则对字典中所有的单词进行排序，每个单词也总能在字典中找到一个合适的位置。

那么，我们可否按照字典序对三维空间中的点集进行排序呢？我们可以把点的坐标数值转化为字符串，然后对字符串进行排序。比如对点 P1 (1.1, 2.2, 3.4) 和 P2 (1.1, 3.4, 4.5)，我们可以将两个点的坐标分别格式化为 “112234” 和 “113445” 字符串，然后对两个字符串按 ASCII 码顺序的字典序排序，最终可以得到 P1 < P2。但这样做没有任何几何意义。而且，如果按照这种方法排序，点坐标值的波动对排序结果影响极大。比如 P2 坐标变为 (1.10, 3.4, 4.5)，这样的变化根本不会改变 P2 的几何意义，但此时排序的结果将变为 P2 < P1，这是不应该发生的。

事实上，我们不必照搬针对字符串的字典序排序方法，但我们可以做一些小小的改动，将一个点在一个方向上的坐标值看成是一个字符。对任意两个点 P1(x1, y1, z1) 和 P2(x2, y2, z2)，我们可以首先比较两个点的 X 坐标：如果 x1 < x2，那么 P1 < P2。但是如果 x1 = x2，我们再比较两个点的 Y 坐标：如果 y1 < y2，那么 P1 < P2。但是如果 y1 = y2，我们再比较两个点的 Z 坐标：如果 z1 < z2，那么 P1 < P2。通过这种比较方式，即便 P1、P2 坐标发生微小扰动，也不会影响比较结果。而且，这种排序的几何意义非常明确，如图 6.2 所示，在二维情况下，左下方的点总是小于右上方的点。

以上我们使用了一种经过简单修改的字典序，实现了任意两个三维空间点的“小于”比较。事实上，针对排序问题，任何排序算法的基础其实就是定义一种比较操作符或函数，能够返回比较结果。以上我们定义的就是针对空间点的“小于号”操作符，有了这个操作符，我们就能对序列中的所有点进行排序。

![](img/c3ab49ac4eb80e7a0a66462a29869ca2_115_0.png)

图 6.2 空间点的字典排序


其中 lpnts 为用于存放链接点的列表，cmp_to_key 可将我们定义的比较函数转化为 sort 函数中的 key 参数，但使用 cmp_to_key 需要手动导入 functools 库。

### 6.3.2 字典序拼接原理

对平面上的 M 条散乱截交线段，当我们通过类似代码 6-2 中的方法对每条线段进行处理后，将得到 2M 个 LinkPoint 对象，我们可以把这 2M 个链接点暂时存放在一个 lpnts 列表中，并使用 cmp_pntSmaller 比较函数对 lpnts 中的元素进行排序。下面我们先来看一下这些经过字典序排序的链接点在平面上的分布情况，如图 6.3 所示。

![](img/c3ab49ac4eb80e7a0a66462a29869ca2_116_0.png)

图 6.3 已排序链接点在平面上的分布情况

如果我们在调试模式下查看 lpnts 中各个元素的值，我们将会发现一个非常重要的规律：lpnts 中间隔相邻的点是重合的。就像如图 6.3 中所示的点序列，0 号点和 1 号点重合，2 号点和 3 号点重合，4 号点和 5 号点重合，以此类推。这种情况完全是合情合理的：首先，每对重合点就是原来相邻两条线段的公共端点，它们本应重合；其次，经过字典序排序之后，坐标相同的点在列表 lpnts 中必然会被排到相邻的位置上，即它们的序号必然相邻。

有了这个规律，我们会发现，线段拼接问题瞬间变得如此简单。我们还是以图 6.3 为例讲解拼接原理。首先，我们从 24 个点中选出任意一个点作为起点。为了不失一般性，我们选择 3 号点作为起始点。因为这里的点都是 LinkPoint 类型的点，而 3 号、6 号点本来就在同一条线段上，因此，从 3 号点的 other 属性便能立马定位 6 号点。然后我们再从 6 号点出发，根据相同的规律，和 6 号点重合的点在 lpnts 中的序号必然和 6 相邻，即 5 号点和 6 号点相邻，或者 7 号点和 6 号点相邻。此时我们可以对 5 号、7 号点做进一步检测，看哪个点到 6 号点的距离最逼近 0，哪个点就是 6 号点的重合点。在图 6.3 中，显然，7 号点为 6 号点的重合点。接下来我们再循着 7 号点继续往下走，定位 7 号点的 other 点，即 4 号点，然后再从相邻序号中找出 4 号点的重合点 5 号点……以此类推，我们会依次找到 16、17、18、19、…… 1、0、2 号点。当我们绕了一圈重新回到 2 号点时，会发现走过的轮廓已经闭合，这时我们就可以结束当前的寻找步骤。

接下来，我们从图 6.3 所示的点中再找出一个从来没有被用过的点，比如 8 号点，然后从 8 号点出发，按照以上步骤依次找出第二个封闭轮廓。以此类推，直到平面上所有的点都被用过。这样，我们就可以将所有截交线段拼接成若干封闭轮廓。

但是，在以上的介绍中，我们忽略了一个比较关键的细节，在此我们做出进一步解释。在图 6.3 中，当我们从 3 号点通过 other 定位到 6 号点后，我们在 lpnts 中寻找 6 号点的邻点 5 号点和 7 号点。但是，通过 3 号点的 other 定位的是点对象，而不是点的序号。一般情况下，我们是没有办法直接从对象获取它在列表中的序号的，除非我们遍历整个列表，比较对象地址或值从而找出它的序号，但这样做可能会浪费不少运算时间。幸运的是，在定义 LinkPoint 数据结构时，我们已经考虑到了这个情况。我们可以使用 LinkPoint 类中 index 属性标记当前点在列表中的序号。初始情况下，每个链接点的 index 属性值为 0，index 的赋值方法如下：

```python
for i in range(len(lpnts)):
    lpnts[i].index = i
```

有了 index 属性，我们就可以从 3 号点的 other 属性获取 other 的 index 值，即它在 lpnts 列表中的序号( 即 6 )，然后通过这个序号找到和它相邻的序号( 5 和 7 )。

在封闭轮廓逐渐形成的过程中，我们会将用过点的 used 属性标记为 True，在链接点初始化时，used 属性值为 False，即尚未被用过。当我们得到一个封闭轮廓，再去寻找下一个轮廓的起点时，我们正是通过判断 lpnts 中点的 used 属性是否为 False 来实现的。

以上我们介绍了基于字典序排序的截交线段拼接原理，显然，这种方法的基础是我们定义的 LinkPoint 数据结构和对截交点的字典序排序。通过这种方法，我们不必再去做费时的遍历搜索，而是可以使用指针或邻近序号直接定位下一个点，速度非常快。如果我们考虑这种拼接方法的时间复杂度，它的主要运算时间花费在对点的排序过程中，其余过程均可在常数时间内完成，因此它的时间复杂度为排序的复杂度，即 O(nlog( n ))，其中 n 为需要拼接的截交线段条数。
